# 最小模型交付法

本文规定功能实现、缺陷修复和代码审查的共同顺序。核心原则是：**如无必要，勿增实体；功能由模型设计出来，
测试只验证模型；不能靠不断增加条件分支和测试样例拼出行为。** “实体”包括 wire 类型、状态、字段、日志、
store、manager、receipt、proof、gate、后台循环和测试专用概念，不只指数据库记录。

## 五步闭环

### 理解原始需求

开始编码前只写四项：期望结果、参与者与输入输出、明确不变量、明确排除项。把静态授权、
运行时观测和完成证据分开。issue、旧文档、代码和测试可以暴露事实或矛盾，但不能替代产品需求。

如果现有实现已经得到所需结果，只核对正常入口和结果，不重复创建材料、迁移状态或实现第二套路径。

### 设计最小模型

选择能够覆盖全部已知场景的最少实体、状态和转换。优先使用集合、状态机和统一选择规则表达一类问题，
不为某个节点、某次超时或某个 fixture 增加特判。每份权威事实只能有一个来源；其他缓存、索引、UI 数据和
制品均为可重算投影。引入新的持久字段、schema、日志、门禁或后台循环前，必须指出现有模型为什么无法表达需求，
并删除被替代的表达。

模型审查使用三个问题：

1. 删除这个实体或状态后，哪条明确需求无法实现？
2. 新场景能否只增加数据，而不增加代码分支？
3. 同一事实是否在两个组件中分别决定结果？

答不出第一个问题的逻辑应删除；第二个问题若答案是否，先重做模型；第三个问题若答案是，先收敛事实来源。

### 枚举最小必要测试集

测试从不变量和等价类推导，而不是从文件、节点和历史 bug 数量推导。最小集合包括：

- 一条正常业务路径；
- 每个不同语义的边界或失败类各一条；
- 只有存在持久状态时，增加一条重启/恢复路径；
- 只有存在信任边界时，增加一条越权或篡改拒绝路径。

同一规则覆盖的节点、路径、协议或平台不做笛卡尔积。单元测试证明模型对等价类成立；部署验收选择有代表性的
真实路径证明正式调用链接通。扩展矩阵不能替代这两者，也不能在最小闭环前成为门禁。

### 编码、部署并完成最小验收

沿一条纵向业务链完成：正式入口、鉴权、处理、持久化、运行时消费、结果回读。先让正常结果在真实入口成立，
再验证第 3 步的边界。只存在于包、fixture、手工调用或测试服务器中的能力不算实现。

调试时如果需要为新样例增加专用条件，停止编码并回到第 2 步；不要先补分支再用更多测试解释它。

### 尝试扩展测试

最小闭环通过后才进行探索性测试。发现问题时先分类：

- 违反既有不变量：统一修正模型或实现，并替换相应最小测试；
- 新需求：回到第 1 步确认，再扩展模型；
- 环境或某个候选不可用：记录为运行时事实，不改写静态授权，也不为该对象增加代码特判。

扩展测试不是默认发布门禁。除非任务明确要求，不遍历所有节点、出口、协议、故障方式和平台组合。

## 现有代码的恢复审查

对已经膨胀或反复修改的实现，不先补测试。先独立写出需求和最小模型，再从正式入口反查调用链，把代码分为：

- **保留：** 最小模型和正式闭环必需；
- **删除：** 不可达、重复表达、仅服务旧测试或与需求冲突；
- **重做：** 功能必要但模型错误，不能继续在原分支上补条件；
- **未接通：** 组件存在但正式入口、持久化、运行时消费或回读缺失。

删除错误测试与删除错误实现同等重要。测试数量、代码行数、schema 数量和门禁数量都不是完成度指标。

## 选路示例

需求是“在已授权候选中，根据当前网络事实选择可用且更优的路径”。最小模型只需要：

- 候选：标识、最终出口和有序链；
- 授权：当前设备允许使用的候选集合；
- 观测：候选在当前网络上下文中的 `available / unavailable / unknown` 及可比较指标；
- 选择：先过滤授权与不可用，再按用户模式、最终出口和目标函数排序。

`public_data_ingress` 或 certified EndpointSet 只声明直连候选存在，不声明它此刻可用。直连失败时可以选择
同一最终出口的境内入口→WG 候选，即使链更长；未知不能伪装成成功或失败。某个公网 UDP 入口暂时被阻断又恢复，
只改变观测，不改变拓扑或授权。

最小模型测试是：代表性直连可用、直连不可用时使用同出口中继、未知保持未知、未授权或不同固定出口不被选择。
真实验收只选择一条可用直连和一条同出口 fallback，不遍历所有出口与 transport。
