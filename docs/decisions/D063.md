**日期** 2026-08-24 · **状态** 生效

`loom rollback` 要一个快照 id,而 id 是十二位十六进制 —— **没地方查**:

| 以为能查到 | 实际 |
|---|---|
| 分发点列目录 | `autoindex off`(demo-b 的 nginx),列不出来 |
| 事件历史的 `snapshot` | 记的是"**某台节点装的版本变了**"。一个发出去但还没被任何节点取到的快照,那里一条记录都没有 |

所以中控自己记:`deploy/ssot-history/published.jsonl`,与源头存档同一个目录
(它们本来就是一件事 —— 中控的发布历史),因此也一起进 `loom backup`。

**只记变化,不记状态**(同 events 包)。发布器每 30 秒收敛一轮,同一个快照
被反复确认;逐轮记一行的话一天 2880 行"还是那个快照",真正的版本变化会被
淹掉。只有 id 与上一条不同才追加。

> 去重是**跟上一条比**,不是"见过的 id 就跳过"。回滚回旧版是一次真实的
> 版本变化,按"见过就跳过"的话,**回滚这件事本身会从历史里消失。**
> 有测试钉住(`TestPublishedKeepsReturnToOldSnapshot`)。

### 那一列才是重点

`loom snapshots` 的判据是"**源头存档真的在、且内容对得上哈希**",不是
"历史里有这一行" —— 存档被清理过或被改过时,历史行照样在。而回滚失败最糟的
时机就是需要它的那一刻。

```
  快照          发布时间          源头          能回滚吗
  7ca7aa7755a0  08-24 08:21       6d909ee84b7a  ❌ 源头存档没了
  45f1b5fe4f77  08-24 08:21       b0949a92998d  ❌ 存档对不上哈希
→ 39470e023ff3  08-24 08:21       5da74d247aff  ✅
```

两个显示口径上的坑,都属于"会说谎的面板比没有面板更糟"([D55](D055.md#d55--不是所有变化都是问题))
那一类:

- **同一个快照出现两次时,`→` 只标最后那次。** 都标会看成有两个当前版本
- **统计对全量算,不对 `-n` 截出来的那几行算。** 否则 `-n 1` 会显示
  "1 / 2 个版本",读起来像"有一个退不了",而那纯粹是显示条数造成的
