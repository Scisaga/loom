**日期** 2026-08-26 · **状态** 生效 · **相关** [D77](D077.md#d77--改代码要显式-loom-release改-ssot-才自动发布)、§14.2.3、§15.4

发布器过去只保证“一轮内部按顺序执行”，却没保证两轮的先后：旧轮先读取 SSOT
后阻塞，新轮先发布，旧轮再醒来就会把分发点倒回去。**所有发布入口共用发布锁，
并在取得锁后重新读取 SSOT、pin 与 release；锁前读到的内容不能参与提交。**

二进制仍必须由 `loom release` 显式批准。放行记录绑定 commit、字节哈希、大小、
自检结果、原因和时间；pin 的签名 manifest 必须与请求的 snapshot id、放行记录
声明的 snapshot 完全一致。手工 `publish` 与守护发布器使用同一套 pin/release
目录和判据，不能因入口不同悄悄丢掉已批准二进制。
写 pin/release 和 rollback 也使用同一把锁；rollback 先写新 pin 再写 SSOT，
后者失败时两者不匹配会继续拦住发布，不能失败开放地发出半份回滚。
撤销 pin/release 在删除后同步父目录，掉电不得让已撤销授权复活。

“发布成功”不再只表示本地文件写过：推送前先完成不可变归档，归档或历史记录
失败都让本轮失败；推送后从 HTTP 分发视角逐项读取 current、manifest、签名、
节点包和二进制 blob，边读边核对大小与 SHA-256。目标路径必须是规范化的非根
绝对目录，拒绝 `/`、`//` 与 `..` 等价写法；SSH 只修改本轮明确创建的条目，绝不
对整个目标树递归 `chmod`。相同 runtime tree 的语义 no-op 可以保留既有签名
快照，但目标缺文件时仍要原子修复，不能把“ID 没变”当成“分发点没坏”。

语义 no-op 只在旧 snapshot 对应的 SSOT 不可变存档仍存在时才能复用，
否则必须生成一份可回滚的新 snapshot。JSONL 历史若留下掉电造成的末尾
半行，先截至上一条完整记录再追加并读回确认。本地与 SSH 目标都拒绝
symlink 路径逃逸，采用不可预测临时名 + rename；小文件读取有大小上限，
SSH 命令还有按操作类型设定的总时限，恶意远端不能永久占住发布锁。
