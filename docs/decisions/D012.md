**日期** 2026-08-21 · **状态** 生效 · **这是全项目最重要的一次模型修正** · 已重写 design.md 第一部分

**修正前的模型(错的):**

```
节点能力 = {access, relay, target}
target 分三种形态:落地型 / 端点型(自有) / 端点型(第三方)
路径 = access → relays → target_node
```

**修正后:**

```
Loom 管的:接入节点、服务器节点          ← 只有这两类
Loom 不管的:目标地址                    ← 它不是节点
路径 = 接入节点 → [服务器…] → 目标地址
```

**三条具体的认识:**

| # | 修正 |
|---|---|
| 1 | **目标只是地址。** 自建推理服务和买来的第三方 API,对 Loom 完全同等 —— 都是发请求过去的地址。哪怕那台机器你有 root,Loom 也不管它的网络配置 |
| 2 | **出口不是节点类型,是位置。** 链上最后一台服务器就是这次的出口。同一台北京云机这次是出口,下次可能只是中间一跳 |
| 3 | **服务器之间没有本质区别。** 国内云机和境外 VPS 是同一类东西,区别只有两点:在哪(出口 IP),怎么接入(能被连 / 必须它连出来) |

**推论:**

- 中继当然可以直接访问 API —— 它就是一台有 IP 的服务器。用不用境外 VPS 是
  **选路的结果**,不是架构里预先分好的类;
- `capabilities` 里的 `target` 删除,只剩 `{access, server}`;
- `target_kind`、`managed` 从节点模型移除 —— 前者不存在,后者恒为 true
  (Loom 管的机器都是你的);
- §4 的"模式 A / 模式 B"改成两个独立的轴:**地址轴**(由请求决定 / 从等价类选)
  与**出口轴**(钉死 / 任选)。四种组合都真实存在,原来的两模式只覆盖了两种;
- 中继与落地的配置渲染**合并成一套** —— 服务器就是服务器。

**为什么之前会错:** 把"应用语义"(流量到了那儿干什么)和"管理语义"(这台机器
我能不能动)混成了一维。它们是两件无关的事,而其中一件根本不适用于目标 ——
因为目标压根不在 Loom 的管理范围内。
