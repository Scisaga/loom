回滚原来有两道防线,中间空着一档:

| 情况 | 现有措施 |
|---|---|
| 配置改坏了 | 五步安装回滚 ✅ |
| 新二进制**起不来** | `.prev` 自动换回去 ✅ |
| 新二进制**起得来但是错的** | ❌ 什么都没有 |

第三档才是最常见的 —— 今天就撞到一个(报告者跑着被替换掉的 inode,数据少
字段,任何检查里都看不出来)。当时唯一的退路是 `git checkout` + 重新编译 +
重新发布,**要求手上有源码树**。

而历史二进制在分发点上本来就都在:内容寻址 `bin/<sha256>`,26 个快照 /
21 个二进制 / 261 MB 全躺着。所以不需要新的存储,只需要让发布器改用其中
一个。

`loom pin <快照 id>` 取回来、验签、核对哈希、**真跑一遍 selfcheck** ——
钉一个跑不起来的二进制上去等于把退路也堵死。

三个设计上的取舍:

1. **钉住是状态,不是一次性命令。** 发布器是每 30 秒收敛的守护进程,
   一次性发布下一轮就被它用本机二进制覆盖回去了。
2. **必须显眼。** `-reason` 是必填的;发布器在**本机二进制变了而钉住仍
   生效**的那一刻专门说一句 —— 那正是"我重新编译了但没发出去"的时刻。
   粘性覆盖不显眼就是陷阱(同 D58)。
3. **记录在、二进制不在要报错**,不能默默回落到当前二进制 —— 那正好是
   钉住要防的事。

> 一个副作用值得知道:SSOT 没变时钉回快照 X,渲染是纯函数(§12),
> 于是重新算出来的就是 X 本身,字节相同。**钉住 + 不动 SSOT = 完整回滚。**
> SSOT 变过就不是了 —— 那会得到"旧二进制 + 新配置",正是 §15.4 要防的
> 组合。这一点目前只写在文档里,还没有让工具拦。

> 而且 `loom rollback` 让"两半一起回去"成为默认路径。
