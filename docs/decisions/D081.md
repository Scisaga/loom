D71/D73 的结论是"版本核不了转述来的节点",理由是**身份不该听别人转述**:
"C 跑的是 commit X"如果只由 B 说,排障时恰恰不能假设 B 可信 —— 出问题的
往往就是链路上某一环。

代价是 `loom status` 长期只能报 `3/5 台核对过`,demo-b / demo-c 永远空白。
而它们够不到中控是**拓扑事实**,不会自己好转。

**决定:节点给自己的身份陈述签名,转述照旧走原路。**

签了名之后转述的是密文不是信任:改一个字验不过,伪造要那台机器的私钥。
于是"够不够得到"和"能不能核对"解耦了。

## 用现成的 PKI,不引入新密钥

每台机器早就有 `/etc/loom/tls/node.key` 和 `node.crt`(CN 是
`<节点>.node.internal`,内部 CA 签发)。新密钥意味着新的分发路径和新的
轮换路径,而那是这个系统里最贵的东西 —— D74 刚因为备份漏了一把钥匙
差点变成灾难。

## 三道检查,少一道就是摆设

1. 证书链得到 CA —— 否则谁都能自签
2. **证书的名字要和 Claim.Node 对上** —— 否则 demo-a 可以拿自己的合法
   私钥签一条"demo-b 跑的是 commit X",而那正是转述,正是要根治的东西
3. 签名覆盖固定字节

第 2 条是整个机制的关键,单独钉了测试。签名覆盖的字节**不走 JSON**:
字段顺序、空白、转义都可能因库版本而变,而签名是针对字节的 ——
换个 Go 版本就验不过的签名不如没有。

## 验过了才算,验不过和没签名同等对待

`Attest` 为空**不等于可信**(中控只有 ca.crt,签不了)。验不过则是**故障**
要报出来 —— 要么转述内容被改过,要么证书过期了。但两种情况调用方要做的
事一样(去 ssh 那台机器),所以在版本表里同归"没核对过",不再细分。

## 用真钥匙验过

不只跑了合成 CA 的单测:拿 demo-b 的**真私钥**用 openssl 签,在中控用**真
ca.crt** 验,通过;把同一份签名改说成 demo-c 的,被真证书拦下:

```
证书是 "demo-b.node.internal" 的,却在替 "demo-c" 发言
```
