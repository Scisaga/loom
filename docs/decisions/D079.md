`loom release` 的 `-binary` 原本默认 `/usr/local/bin/loom`。那是个陷阱,
而且**实测输过一次**。

**中控同时也是一个被管理的节点。** 它自己的 `loom-pull` 每 10 分钟把
`/usr/local/bin/loom` 收敛到**已发布快照里的那份**。于是"手工装 → release"
这个流程有竞态,窗口就是一个 pull 周期:

```
11:01:22  pull:二进制要换 9b45f30b88f3 → e90d0efe56c9   ← 把手工装的退回去了
11:03     loom release                                  ← 记下的是被退回的旧版
```

慢了两分钟,放行记录就指向了上一个版本,而命令本身**报告成功**。

**决定:`-binary` 默认改成构建产物 `deploy/staging/loom`。** 那个路径不归
pull 管,不会被收敛掉。显式指向 `/usr/local/bin/loom` 时打印警告说明原因。

## 顺带简化掉一步

想通这件事之后,发布流程比原先短了:

```bash
go build -o deploy/staging/loom ./cmd/loom
loom release -reason "..."
```

**不用手工装到 `/usr/local/bin`,也不用重启发布器。** 中控自己的 pull 会
把新二进制装上去,并重启跑着旧 inode 的服务 —— 它本来就在做这件事。

原先那两步是我把中控当成"不受管的机器"想出来的,而它不是。
