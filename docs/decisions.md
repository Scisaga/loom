## 一 · 实现期间的推导决定

### D1 · 每条隧道一个 WireGuard 接口,不是一个接口挂多个 peer

**日期** 2026-08-20 · **状态** 生效 · **相关** §17.2、§20.1

标准做法是一个 `wg0` 挂 N 个 peer。这里反过来:节点上每条隧道一个接口,
文件名 `wg-<对端id>.conf`。

**理由(2026-08-21 修订,原理由不成立):**

原来写的理由是"AmneziaWG 的混淆参数是接口级的"。**这条站不住** —— §17.3 明说
参数可以按隧道**或按批次**生成,一个网卡挂多个 peer 用同一批参数完全合法。

**真正的理由是路由选择原理:多台出口服务器都要承载 `AllowedIPs = 0.0.0.0/0`。**
出口流量的目的地是任意公网地址,所以每个出口 peer 都得吃下全部地址空间;而
WireGuard 按目的地址匹配 peer,**同一个网卡上不能有两个 peer 都是 0.0.0.0/0**。
必须分网卡。

**代价:** 接受方每条隧道占一个端口;接口数随隧道数线性增长。在数十节点规模
可接受。

> ⚠️ **不要为了"更简洁"合并成单接口** —— 多个出口会互相覆盖 AllowedIPs,
> 结果是只有一个出口生效,而且不报错。

### D2 · 私钥用 `wg-quick` 的 `PostUp` 引用本地文件

**日期** 2026-08-20 · **状态** 生效 · **相关** §12.1、§13.1 · **部分回答 C16**

渲染层不写 `PrivateKey`,改为:

```
PostUp = wg set %i private-key /etc/loom/secrets/%i.key
```

用 `%i` 让 wg-quick 自己展开接口名,避免文件名与接口名在两处各写一遍。

**理由:** §12 要求配置是 SSOT 的纯函数渲染,§13.1 要求私钥永不离开节点。
平台既然没有私钥,就渲染不出完整文件。这条引用是两者的调和点 —— 渲染层进
快照哈希,秘密层不进。

**仍未定(C16 的其余部分):** `secret_generation` 的记法、轮换流程、
节点首次加入时生成密钥对的具体时机。

### D3 · 无法完整表达的输入一律硬报错,不静默降级

**日期** 2026-08-20 · **状态** 生效 · **相关** §17.2

隧道设了 `obfuscation` 但渲染器尚未实现 §17 参数输出时,`Render` 返回错误
而不是输出一份不带参数的配置。

**理由:** §17.2 说参数全部置零等于标准 WireGuard 行为。静默输出无参数配置,
结果是使用者以为开了混淆而实际没开 —— 这是安全性质上的谎报,比不实现更糟。

**推广:** 未实现的协议进 `render.Result.Skipped` 并由 CLI 显式打印。
渲染少生成了东西,调用方必须看得见。

### D4 · 推导字段不进结构体,靠严格解码拒绝

**日期** 2026-08-20 · **状态** 生效 · **相关** §2.2、§19

`Node` 没有 `mesh_eligible` 字段,`Tunnel` 没有 `initiator` 字段。SSOT 用
`KnownFields(true)` 解码,写这些键直接报错。

**理由:** §19 要求"校验器应拒绝矛盾值"。比起"允许写入再校验一致性",
不给字段更彻底 —— 不存在"写了但被忽略"这个中间状态。

### D5 · 接口名为 `wg-<对端id>`,长度由校验器提前拦截

**日期** 2026-08-20 · **状态** 生效 · **相关** §20.1

Linux `IFNAMSIZ` 是 16(含结尾 NUL),可用 15 字符。校验器检查
`len("wg-"+peerID) <= 15`,超长报错并指名要缩短哪个节点 id。

**理由:** 备选方案是超长时回退到哈希名(如 `wg-a1b2c3d4`)。否决,因为
命名不统一是排障时的额外负担;把约束推给 SSOT 作者更好,而这正是校验器
该做的事。

### D6 · 校验返回全部发现,并按 (节点, 条款) 稳定排序

**日期** 2026-08-20 · **状态** 生效

**理由:** §20.1 的场景是一次维护 24 个互相对应的文件。停在第一个错误会
逼出"改一次跑一次"的循环。排序是为了 CI 输出不抖动。

### D7 · 配置包哈希只覆盖渲染层

**日期** 2026-08-20 · **状态** 生效 · **相关** §12.1、§15.3、§19

`Bundle.Hash()` 不含秘密层,也**不含 SSOT 全局哈希**。

**理由:** 把 SSOT 哈希写进每个文件,会让任何一处改动导致全部文件的 diff
变化,§12.1 要的"看到会改哪些文件的哪些行"就没了。全局哈希属于
`Snapshot.ssot_hash`,不属于文件内容。

### D8 · 技术栈

**日期** 2026-08-20 · **状态** 生效 · **相关** 附录 B

Go 1.27,唯一第三方依赖 `gopkg.in/yaml.v3`。附录 B 选 Go 的理由是渲染器与
校验器要和 Agent 共用同一份实现 —— 跨语言实现同一套规则是长期漂移来源。

### D9 · 凭据在渲染层是占位符,不是明文

**日期** 2026-08-21 · **状态** 生效 · **相关** §12.1、§18 · 扩展自 [D2](#d2--私钥用-wg-quick-的-postup-引用本地文件)

sing-box 配置里的凭据渲染成 `${secret:<secret_ref>}`,由 Agent 在写盘前用本地
秘密层替换。

**理由:** 明文写进渲染层有三个后果 —— `loom diff` 把凭据打到终端、快照哈希
覆盖了它、配置包在整条分发链路上处处是明文。D2 已经为 WireGuard 私钥确立了
"渲染层只写引用"的模式,凭据是同一个问题。

**附带的好处:** 替换失败时 sing-box 会因密码非法而拒绝启动。这正是想要的 ——
总好过拿着字面量 `${secret:...}` 去连然后认证失败。

> ⚠️ **两端必须引用同一个 `secret_ref`。** 中继侧的 user 密码与接入侧的 hop
> 密码指向不同条目时,认证会静默失败。`TestSingBoxPathCorrespondence` 断言这一点
> —— 实现时正是先写错、再被这个测试拦住的。

### D10 · ~~目标选择编码为"目标在隧道中的地址"~~ 已被 D12 推翻

**日期** 2026-08-21 · **状态** ❌ **已推翻**,当天即被 [D12](#d12--目标不是节点出口是路径上的位置) 取代

原方案:落地目标在每条隧道的本端地址上开一个 socks inbound,接入节点的下一跳
链是 `hysteria2(中继公网地址) → socks(目标隧道地址)`。

**为什么推翻:** 它建立在一个错误前提上 —— 把"目标"当成了一类节点。一旦认清
目标只是一个地址(D12),问题本身就消失了:链的最后一跳是**服务器**,它直接
向目标地址发起普通的对外连接。不需要在目标那边装任何东西。

**保留这条记录的价值:** 当模型的层次分错时,会催生出一整套看起来自洽、实际
多余的机制。D10 就是一个例子 —— 它解决的是一个不该存在的问题。

### D11 · 用 selector 而不是 urltest

**日期** 2026-08-21 · **状态** 生效 · **相关** §5.5、§5.6

接入节点每条声明生成一个 `selector` 出站,成员是它的全部 RouteCandidate。
当前选择由 Agent 设置,不用 sing-box 的 `urltest`。

**理由:** §5.6 要求选路的决策者只有一个。`urltest` 会按自己的节奏和判据独立
选路,与 Agent 的 §5.5 阻尼规则形成两个互不知情的决策者 —— 这正是 §5.6 拒绝
"让中继自主选下一跳"的同一条理由。

**附带发现的阻抗不匹配:** `switch_threshold` 在设计里是比率(如 20%),而
sing-box 的 `urltest.tolerance` 是毫秒。即使想用 urltest 也表达不了 §5.5 的
阻尼语义。

**当前状态(2026-08-23 更新):** Agent 已实现(§5.5.1),按 objective 排序并带
阻尼切 selector。Agent 没跑起来时 selector 停在 `default` 上,而 default 刻意
不取直连([D22](#d22--selector-的默认值不许是直连))。以下是原始记录:§20.2 说的
"路径静态指定"。

### D12 · 目标不是节点,出口是路径上的位置

**日期** 2026-08-21 · **状态** 生效 · **这是全项目最重要的一次模型修正** · 已重写 design.md 第一部分

**修正前的模型(错的):**

```
节点能力 = {access, relay, target}
target 分三种形态:落地型 / 端点型(自有) / 端点型(第三方)
路径 = access → relays → target_node
```

**修正后:**

```
Loom 管的:接入节点、服务器节点          ← 只有这两类
Loom 不管的:目标地址                    ← 它不是节点
路径 = 接入节点 → [服务器…] → 目标地址
```

**三条具体的认识:**

| # | 修正 |
|---|---|
| 1 | **目标只是地址。** 自建推理服务和买来的第三方 API,对 Loom 完全同等 —— 都是发请求过去的地址。哪怕那台机器你有 root,Loom 也不管它的网络配置 |
| 2 | **出口不是节点类型,是位置。** 链上最后一台服务器就是这次的出口。同一台北京云机这次是出口,下次可能只是中间一跳 |
| 3 | **服务器之间没有本质区别。** 国内云机和境外 VPS 是同一类东西,区别只有两点:在哪(出口 IP),怎么接入(能被连 / 必须它连出来) |

**推论:**

- 中继当然可以直接访问 API —— 它就是一台有 IP 的服务器。用不用境外 VPS 是
  **选路的结果**,不是架构里预先分好的类;
- `capabilities` 里的 `target` 删除,只剩 `{access, server}`;
- `target_kind`、`managed` 从节点模型移除 —— 前者不存在,后者恒为 true
  (Loom 管的机器都是你的);
- §4 的"模式 A / 模式 B"改成两个独立的轴:**地址轴**(由请求决定 / 从等价类选)
  与**出口轴**(钉死 / 任选)。四种组合都真实存在,原来的两模式只覆盖了两种;
- 中继与落地的配置渲染**合并成一套** —— 服务器就是服务器。

**为什么之前会错:** 把"应用语义"(流量到了那儿干什么)和"管理语义"(这台机器
我能不能动)混成了一维。它们是两件无关的事,而其中一件根本不适用于目标 ——
因为目标压根不在 Loom 的管理范围内。

### D13 · 隧道矩阵只覆盖 `reverse_only` 服务器

**日期** 2026-08-21 · **状态** 结论生效，理由已由 [D29](#d29--63-的建议是对的给的理由过时了) 修正 · **相关** §6.3、§8.3

两个可被公网主动拨号的服务器不需要常驻 WireGuard，当前直接走公网
Hysteria2；只有链路一端是 `reverse_only` 时才产生隧道矩阵条目。Headscale
仍是未部署的独立目标，不能拿它解释当前连通性。

**原理由已过时:** 当时假设 Headscale 负责密钥/peer 自动分发；生产并未部署
Headscale。D29 用真实数据路径说明，当前替代机制是公网 Hysteria2 直拨。

**校验器规则:** 两端都能被主动拨号时，显式 `Tunnel` 报错并提示直接公网拨号；
不要再提示一个尚未部署的 Headscale 会接管。

### D14 · 快照 id 是内容哈希,时间从外部注入

**日期** 2026-08-21 · **状态** 生效 · **相关** §12、§19

快照 id = 除 `created_at` 与 `author` 外全部内容的 SHA-256 前 12 位。
时间与作者由**调用方传入**,`snapshot.Build` 自己不读时钟。

**两个理由:**

1. **打包必须和渲染一样是确定的。** §12 要求渲染是纯函数;如果打包过程
   读时钟,那"同样输入产生同样字节"就断在最后一步,而签名恰恰针对那串字节。
2. **id 相同就意味着产物没变。** 同一份 SSOT 隔天再打一次,id 一样 ——
   "这次改动有没有实际影响产物"于是变成一眼能看出的事,不必逐文件比对。

`created_at` 照常如实记录,只是不进 id。

### D15 · 签名放在旁文件,不放进 manifest

**日期** 2026-08-21 · **状态** 生效 · **相关** §14.3

产物是 `snapshot.json` + `snapshot.sig` 两个文件,而不是把签名字段塞进
manifest。

**理由:** 签名针对的必须是**确切的那串字节**。签名如果在 manifest 内部,
校验时就要先把它挖掉、再重新序列化一遍 —— 而"重新序列化出来的字节"与
"当初签的字节"是否逐字节相同,取决于序列化实现的稳定性。这是一类不必要的
风险,分成两个文件就不存在。

> §19 的 `Snapshot` 里列了 `signature` 字段,那是概念模型;落到磁盘上它是
> 旁文件。二者不冲突。

### D16 · 一台机器一把 WireGuard 私钥,放在 `/etc/wireguard/node.key`

**日期** 2026-08-22 · **状态** 生效 · **相关** §13.1、§12.1 · **上真机时才暴露的两个 bug**

原来渲染的是 `/etc/loom/secrets/%i.key` —— 按接口名展开,即**一条隧道一把私钥**。
两处都错:

**错误一:私钥应当按机器而非按隧道。** SSOT 里每个节点只有一个
`wg_public_key`。若各接口用不同私钥,对端拿到的公钥就对不上。同一把私钥用在
多个接口上是合法的 —— 对端靠公钥认身份,而身份本来就该一致。

**错误二:路径必须在 `/etc/wireguard/` 下。** Ubuntu 24.04+ 给 `wg` 上了
AppArmor profile,只允许:

```
file rw @{etc_rw}/wireguard/{,**},
```

放在别处会被拒:

```
apparmor="DENIED" profile="wg" name="/etc/loom/secrets/node.key" denied_mask="r"
```

**表现极具迷惑性:** `wg-quick up` 打印一行 `fopen: Permission denied`,
删掉刚建好的接口,**然后退出码仍是 0**。看起来像成功了。

给每台机器加 AppArmor 例外(profile 里有 `include if exists <local/wg>`)也能解,
但那是在削弱一个本该存在的防护;换个路径不花任何代价,而且 `/etc/wireguard/`
本来就是 WireGuard 密钥的惯例位置。

> **"秘密层"是个概念,不是一个目录。** 不同类型的秘密可以放在各自消费者
> 期望的位置 —— 这不违反 [D2](#d2--私钥用-wg-quick-的-postup-引用本地文件),
> 渲染层依然只写引用。

### D17 · `ClientProfile` 并入 `Node`,端口范围改 61617-61799

**端口范围** 从 61610-61699 改为 **61617-61799**(与实际放行的一致)。

### D19 · 角色字段分块,`capabilities` 由块推导

**日期** 2026-08-23 · **状态** 生效 · **相关** §1.1、§1.3 · 取代 [D18](#d18--惰性字段按能力拒绝-已被-d19-取代)

```yaml
- id: cn-a
  city: 广州
  server:                    # 这个块存在 = 持有 server 能力
    direction: bidirectional
    inbound_port: 61698

- id: access-a
  city: 北京
  access:                    # 这个块存在 = 持有 access 能力
    platform: linux-server
    credentials: [...]

```

**两个块都有也合法** —— 一台服务器自己也要走代理出去,是真实需求。渲染器
把两边合并进同一份 sing-box 配置(一台机器一个进程)。

> **曾经短暂地禁止过双角色,理由是"两类节点走两个控制面、会互相覆盖"。
> 那个论证是错的:配置源只有一个**(SSOT → 渲染器)。§18 的加入输入只是
> 把中控已创建的 Device 与本机身份绑定并引导首次签名配置，适用于服务器等
> 所有新 Device；之后由相应宿主继续 signed pull/Agent 投递。把"投递阶段或
> 宿主不同"当成了"配置源不同"。

**`capabilities` 字段删除。** 它与角色块是同一个事实的两次编码 —— 写了
`capabilities: [server]` 却不给 `server` 块(或反过来)就是自相矛盾,而那
正是 [D4](#d4--推导字段不进结构体靠严格解码拒绝) 要消灭的东西。

**收益:惰性字段变成不可表达,而不是被拒绝。** 把 `direction` 写进 `access`
块,严格解码在**加载阶段**就失败,根本到不了校验器:

```
field direction not found in type model.AccessRole
```

D18 那 30 行 `checkRoleFields` 随之删除。对应的测试也从"校验器拒绝"下移到
"解码器拒绝"(`model.TestLoadRejectsDerivedFields`)。

> **判据:需要运行时校验来保证字段共现,就说明类型分错了。** 校验器该管的是
> 跨实体的一致性(隧道两端对不对得上、引用存不存在),不是同一个实体内部
> 哪些字段该一起出现 —— 后者是类型的职责。

### D20 · selector 必须配一个能切它的端点

**日期** 2026-08-23 · **状态** 生效 · **相关** §5.6、§7.3.1 · 承接 [D11](#d11--用-selector-而不是-urltest)

D11 选了 `selector` 而非 `urltest`,理由是选路的决策者必须只有一个。但当时
漏了一件事:**selector 是手动开关,得有东西去切它。** 渲染出的配置没有任何
控制端点,于是候选集永远停在 `default` 上 —— 调度层做完了也落不了地。

接入节点的配置现在带 `experimental.clash_api`,监听 `127.0.0.1:61800`,
口令走秘密层。Agent 通过它切换当前候选。

**这个洞是"检查一遍"时才发现的**,而它足以让整个 L3 白做:候选枚举、排序、
下发都对,唯独最后一步没有落点。

> **教训:一条链路上任何一环缺失,前面所有环都白做。** 而缺的那一环往往不
> 报错 —— selector 停在 default 上,配置合法、服务正常、流量也通,只是永远
> 走同一条路。

### D21 · 加字段之前先验证下游真的会用它

**日期** 2026-08-23 · **状态** 生效

一个会话里造出了三个"能写、不生效"的东西:

| # | 东西 | 怎么发现的 |
|---|---|---|
| 1 | `direction` 写在纯接入节点上 | 审查时想到 |
| 2 | selector 没有控制端点,永远停在 default | 用户追问"这句话什么意思" |
| 3 | `probe_url` —— delay 接口忽略 `url` 参数 | 读 debug 日志,发现它连的是 `www.gstatic.com` |

第三个最糟:我不但加了字段、加了必填校验、写进了文档,还**据此下过一个错误
结论** —— 对比两个探测目标发现"排序几乎一样",于是判定这个功能没必要。
而那批对比数据本身是假的:两次测的都是同一个目标。

> **判据:一个配置项从写下到生效,中间每一环都要有人验证过。**
> 尤其是最后一环 —— 下游组件真的读了它吗?
>
> 验证成本极低(传一个独特的域名,看日志解析了什么,十秒钟),而不验证的
> 代价是:基于假数据做决策,然后把错误结论写进文档。

**排查这类问题的通用手法:给参数传一个绝不会重合的值,再看下游实际用了什么。**
`neverbefore.example.org` 不出现在日志里,就说明参数被丢了。

### D22 · selector 的默认值不许是直连

**日期** 2026-08-22 · **状态** 生效

原来 selector 的 `default` 取 `tags[0]`,也就是枚举出的第一条候选。枚举零跳
优先,所以**默认永远是直连**。这不是一个决定,是枚举顺序的副产物。

代价是具体的:实测 `best-egress` 的直连候选对目标超时 10 秒,而 sing-box
每次重启都回到 default。于是每次重启后,流量都打在一条已知不通的路上,
直到有人发现。

现在默认取第一条**经过服务器**的候选;只有直连是唯一选项时才用它。一条声明
存在的意义就是绕道,直连是最不该盲选的那个。

这仍然是个静态猜测 —— 真正的选择由 Agent 按实测数据接管(§5.5.1),这里只
保证 Agent 没跑起来的那段时间里不至于停在最差的一个上。

### D23 · 停在死候选上不受阻尼保护

**日期** 2026-08-22 · **状态** 生效

`switch_threshold` 和 `min_samples` 是为了防止在两个**都能用**的候选之间反复
横跳。把它们无差别地套在所有切换上,会得到一个荒谬的结果:当前候选 100%
失败、旁边有候选 100% 可用,而 Agent 因为"样本数不够 6 个"继续等 30 分钟。

所以 Agent 的第一条规则是:**当前候选窗口内全部失败 → 立刻切,不看阈值也不
看样本数。** §5.8 说样本不足的候选"不参与排序也不被淘汰",管的是**选谁**,
不是**要不要离开一具尸体**。

同一个道理的另一半:排序键是 **(实际失败率, 目标指标)**,失败率优先。把失败
折算成"很慢"混进分位数,会让一条 50% 失败但很快的候选赢过 100% 成功但慢
一点的 —— 而用起来一半的请求是错误。失败与快慢不是同一个量纲。

实现修正：取消旧 10% 分档，使用 `failures/samples`，避免小幅失败率差异被延迟
掩盖；现任样本不足未参与挑战者排序时，切换前仍须拒绝失败率更高的候选。

### D24 · 调参字段之间的算术要校验

**日期** 2026-08-22 · **状态** 生效

主动探测一个 `tuning_period` 才出一个样本,所以 `window` 里最多装
`window / tuning_period` 个样本。小于 `min_samples` 时排序永远不会启动。

写这条规则的时候,参考矩阵和真实部署里**每一条声明**都违反它 —— 全都把
`window` 和 `tuning_period` 写成了同一个值,然后要求 20 个样本。

这是 [D21](#d21--加字段之前先验证下游真的会用它) 的延伸:没有消费者的字段
不只是"不生效",它们还会**互相矛盾而没人发现**。字段之间有算术关系时,
校验器要把关系本身钉住,不能只检查每个字段自己合法。

### D25 · "Agent"是两个角色,拆开

**日期** 2026-08-22 · **状态** 生效

被问到"是不是每个拓扑节点都该跑 agent",我原来的回答是"服务器上没有
selector 可切"。这句话是对的,但它回答的是**服务器该不该做决策**(不该,
那是 D11),而不是**服务器该不该跑 agent**。

拆开:

| 角色 | 做什么 | 装在哪 |
|---|---|---|
| **决策者** `internal/agent` | 排序、切 selector | 每个接入节点恰好一个 |
| **上报者** `internal/report` | 观测、自检、如实说 | **每个节点**,服务器也要 |

服务器上不装决策者,不等于服务器上不需要跑任何东西。DDNS 重解析、隧道断连、
有人手工改配置 —— 这些只有节点自己知道,而在此之前全程静默。

上报者上线后**第一次跑就在 5 台机器里的 3 台上找到了真实漂移**:装着的
`sing-box.service` 是 access-a 加入拓扑之前渲染的,缺 `After=wg-quick@wg-access-a`。
后果是重启时 sing-box 可能先于隧道起来。这个问题存在了多久没人知道,因为
在此之前**没有任何东西会去看**。

### D26 · 上报接口只绑隧道内地址,且这是硬错误

**日期** 2026-08-22 · **状态** 生效

上报接口没有自己的认证:能连上隧道内地址,就已经持有 WireGuard 密钥了。
再加一层口令只是多一个要分发和轮换的秘密,换不到实际的隔离。

代价是绑错地址的后果严重(拓扑和隧道健康成为公开信息)**且完全无症状** ——
接口照常工作,没有任何迹象表明它同时对着公网。所以这不是文档里的一句提醒,
而是**加载配置时的硬错误**:主机部分不是私有 IP 或回环就拒绝启动。

没有隧道的纯接入节点绑回环 —— 远端拉不到,但本机 `loom report` 的配置自检
仍然可用。**自检不该因为"拉不到"而整个消失**,那是两件事。

### D27 · 按段量,不按整条路线量

**日期** 2026-08-22 · **状态** 生效

原来的测法是:接入节点把每条完整候选链跑一遍。候选数是 `1 + N + N(N-1)`,
串行探测,而且**每个接入节点各来一遍**。

真正的问题不是慢,是**同一个事实被反复发现**。实测 `best-egress` 的 15 条
候选里有 9 条出口在境内,而境内机器根本到不了目标 —— 这是关于 cn-a 和 cn-b
两台机器的一个事实,却在 9 条不同的链上各被发现一次。

改成:**每台机器只量自己能量的那几段**(到隧道邻居的 RTT、直接访问每个目标
的结果),然后互相交换。cn-a 自己量一次,全网复用。

第一步的收益是剪枝:15 条探测降到 6 条,一轮从 13 秒降到 4 秒。更大的收益
在后面 —— 新接入的设备不必从零攒样本,拉一份现成的表就能排序。

**代价要说清楚:合成估计不等于实测。** 延迟大致能相加,但每多一跳多一次握手,
还有排队和分片。所以用估计排序,再对前几名做一次真实验证。

### D28 · 推论与亲测必须分开标记

**日期** 2026-08-22 · **状态** 生效

按别人的观测剪掉一条候选之后,要不要往度量文件里记一笔?

**要记** —— 不记的话有个洞:当前选中的候选如果正好被剪掉,它在窗口里的**旧
数据**会让排序以为它还健康,流量继续停在一条已知不通的路上,正是
[D23](#d23--停在死候选上不受阻尼保护) 要解决的那个问题。

**但必须标成 `observation_kind: derived`**,与 `active`(亲自探到的)分开。
本机并没有真的发过这个请求;混在一起,回放历史时(§16.5)分不清哪些数字
是真测的。

同一个道理的另一面:剪枝只认**已知不能到**。已知能到、已知不能到、不知道 ——
三个状态,把"不知道"当成"不能到",一台刚加进来还没被观测过的服务器会永远
不被尝试。

### D29 · §6.3 的建议是对的,给的理由过时了

**日期** 2026-08-22 · **状态** 生效(2026-08-22 修正)

§6.3 拒绝为两个 `bidirectional` 节点手工建隧道,理由写的是"该交给 Headscale
自动分发"。而 Headscale 没有部署,所以这条消息读起来像是"这里有个洞"。

**实测下来没有洞。** 两台都能被公网拨到的机器之间,链路本来就走得通:

```
access-a → cn-a>cn-b → baidu   200  272ms
配置:hysteria2 → cn-a 公网,detour 之后 hysteria2 → cn-b 公网
```

隧道只有 `reverse_only` 的服务器才需要 —— 它们拨不进去,只能自己拨出来
(§2.2)。两台 `bidirectional` 之间加隧道确实是白做工,规则的**建议是对的**。

错的是它给的**理由**:今天的替代方案不是"Headscale 会处理",而是
"这两台互相能直接拨,不需要隧道"。留着旧理由的后果是,读到这条消息的人
会去找一个不存在的组件。

> **我当初想加那条隧道的唯一动机,是让 access-a 够到 cn-a 的上报端口** ——
> 那是监控需求,不是数据平面需求,已经由转述解决(§16.1.2)。
> 判断一条规则有没有洞之前,先问清楚"到底是什么东西需要它"。

Headscale 因此仍然是**独立可选项**,不在主线上。

### D30 · apply 的五步顺序,每一条都对应一个踩过的坑

**日期** 2026-08-22 · **状态** 生效

`loom apply` 之前,部署是我一条条手打 scp 和 ssh。三个常驻进程 × 五台机器,
每次都可能漏掉一步 —— 而且**只有我能部署**。

固化下来的顺序是:暂存 → 预检 → 存 previous → 就位重启 → 验证,失败回滚
(§14.2.1)。不是想出来的,是每一条都对应一次真实的失败:

| 步骤 | 对应的坑 |
|---|---|
| 预检在覆盖之前 | 直接覆盖再重启,配置非法 → sing-box 崩溃重启循环,而我只测了新功能 |
| 只重启文件变了的服务 | 一律全重启的话,改一行 sing-box 配置也会断三条隧道 |
| unit 文件变化重启对应常驻 service | `ExecStart` / Capability / sandbox 只有新进程才生效；只 `daemon-reload` 会被旧进程的 active 假绿骗过 |
| 验证前先等几秒 | 崩溃循环的第一次崩溃在启动后一两秒,立刻查会看到 active |
| 回滚只碰动过的东西 | 实测:预检失败(什么都没装),回滚却重启了三条隧道 |

另外 **wg-quick 不能用 `systemctl restart`**:down 与 up 之间有竞态,报
`` `wg-xxx' already exists ``,而后果是 **unit 停在 failed、接口其实还在、
隧道看起来是好的** —— 最难查的那种状态。必须显式停、`ip link del`、再起。

### D31 · 备份加不加密必须显式选

**日期** 2026-08-22 · **状态** 生效

`loom backup` 不接受"默认行为"。给 `-passphrase-file` 就加密,给
`-plaintext` 就明文,两者必选其一,都不给直接报错。

两个默认值都会坏事,而且坏在不同的方向:

- **默认明文** —— 人会在不知情的情况下把全网凭据放进网盘。
- **默认加密** —— 人会在没记住口令的情况下以为自己有备份。口令丢了的
  备份和没有备份是一样的,而这件事只有在真的需要它的那天才会发现。

这是 [D3](#d3--无法完整表达的输入一律硬报错不静默降级) 的同一条道理:
两个选项各有严重后果时,不许替人选。

备份只覆盖**不可再生**的东西:秘密层与内部 CA。渲染产物不备份 ——
它们能从 SSOT 再生成,字节完全一样(§12)。

### D32 · 控制面是一棵签了名的静态树,不需要被信任

**日期** 2026-08-22 · **状态** 内容签名已生效；D88 freshness 阶段一已实现、待部署

附录 C #14"控制平面放在哪"一直未定,于是我先做了 ssh 推。被问到"我为什么
要自己部署"才想清楚:**这个问题之所以难,是因为默认假设了控制面必须可信。**

去掉那个假设,问题就没了。渲染产物里全是 `${secret:REF}` 占位符,manifest
有 Ed25519 签名,节点用**本地钉住的公钥**验。于是分发点既看不到凭据,也改
不了内容 —— 它是什么、放在哪、经过谁,都不影响安全性。**一个静态目录足矣。**

现在分发点就是 cn-a 的 nginx 上一个目录,而 cn-a 本身也是被管的节点之一。
这在"控制面必须可信"的假设下是荒唐的,在签名模型下完全正常。

三种篡改都实测过并被拒:改配置包(哈希对不上)、改 manifest(验签失败)、
`current.json` 指向别的快照(id 对不上)。

2026-08-27 复审修正：旧实现的最后一项只覆盖“指针与所取 manifest ID 不一致”，没有
覆盖“指针改指另一份合法旧快照”。签名证明内容来源，不证明当前授权；旧快照
又必须保留，故分发点仍可重放。D88 阶段一用签名 deployment envelope 与节点
单调 floor 闭合首次可信接受后的反重放；首次 bootstrap 和自动 canary 仍是明确
边界。无 floor 首见高代现可用中控 authority + `-expected-current` 带外锚定，
但控制端/分发点协调回滚仍需节点 floor 或外部 witness 发现；不能把本决策概括成
“任何状态下、所有维度都不需要信任”。

**签名私钥只在 `loom publish` 用到,不上任何服务器。**

顺带解决了一个此前没意识到的问题:ssh 推传的是**已 hydrate** 的配置,含明文
凭据;改成节点自己填之后,凭据从不离开它该在的机器。`loom secrets split`
按各节点的实际引用拆总表 —— cn-a 拿 3 项,edge-b 拿 2 项,只有 access-a 有控制
端点口令。

### D33 · 期望状态不只是文件内容

**日期** 2026-08-22 · **状态** 生效

`loom pull` 最初拿快照 id 做早退:和本机记录一样就什么都不做。

这是错的。**id 只说明配置来自哪一版,不说明机器现在是不是那个样子。**
实测 cn-b 的 `loom-pull.timer` 一度 `active` 但没 `enable`(重启就没了),
而 pull 每次都报"已是最新,无事可做"。

同一天发现的更严重的一例:**四台机器的全部 `wg-quick` 单元都是 `failed`,
而接口都在、隧道都通。** 任何一台重启,隧道都不会自己回来。这个状态存在了
多久没人知道 —— 因为在此之前,检查的是"接口在不在",而不是"单元该不该在"。

两条改动:

- pull 不再按 id 早退。安装脚本本身幂等(逐文件比哈希),跑一遍很便宜,
  顺带把 enable、服务状态这些**不在文件里**的期望状态拉回来。
- 上报者的隧道检查加上 `wg-quick@<iface>` 的单元状态,与"接口在不在"分开报。

### D34 · 装配置的东西自己也是被装的东西

**日期** 2026-08-22 · **状态** 生效

`loom pull` 的最后一步是重启服务,而它自己就是一个服务。三次踩到同一类坑:

| 触发路径 | 后果 |
|---|---|
| 重启 `loom-pull.service`(oneshot,ExecStart 就是 pull) | 内层那次把外层的回滚清单清空,外层失败时"回滚"成了空操作,机器停在装了一半的状态 |
| timer 带 `Persistent=true` + `OnBootSec` | `enable --now` 立刻触发一次 —— 而 enable 往往就发生在安装阶段里 |
| 定时器那次与手工那次重叠 | 同上 |

前两个按类堵掉:oneshot 单元永不重启、也不进"必须 active"的验证名单
(它跑完就是 inactive);timer 用 `OnActiveSec` 且不 `Persistent`。

第三个用文件锁兜住整类问题 —— **具体路径能一个个堵,但"两个 pull 同时跑"
这件事本身要有一道总闸。**

顺带修了一个相邻的错误:`NRestarts` 是 Service 的属性,Timer 没有。对 timer
查它拿到空串,而 `[ "" = 0 ]` 恒假,于是每次部署都"失败并回滚"。

### D35 · 中控只在"改变系统"时需要,不在"运行系统"时需要

**日期** 2026-08-23 · **状态** 生效

签名私钥只能在一个地方 —— 否则任何一台被拿下就能给全网签配置,签名白做。
发布器必须在私钥旁边,SSOT 必须在发布器看得见的地方。**三样东西塌到同一台
机器上,没得选。** 那台就是中控。

但它比通常说的"控制面"窄得多:

| | 中控有 | 中控**没有** |
|---|---|---|
| SSOT、私钥、发布器 | ✅ | |
| 全网视图 | 有,但每台机器也都有(靠转述,§16.1.2) | |
| 节点运行时依赖 | | ❌ 它挂了,节点照常跑、照常调参、照常上报 |
| 观测依赖 | | ❌ 随便打开哪台都能看全网 |

**它挂了不影响系统运行,只影响改变系统。** 这比典型的控制面好 —— 那种一挂,
你既瞎了也动不了。

中控节点**支持转移**:把 SSOT 和签名私钥搬到另一台,改一下标记。

### D36 · 发布自动化之后,界面就没有"命令台"

**日期** 2026-08-23 · **状态** 设计已定,发布器待实现

如果 SSOT 一改就自动发布,那**界面上每一个写操作都只是"改 SSOT"**。加节点是
改 SSOT,换测试地址是改 SSOT,挪窝也是改 SSOT。

于是不存在"对 cn-a 执行某某"这种通道 —— 而这正是 §12 想要的:节点上的所有
配置都是 SSOT 的渲染输出。开一条"临时改这台"的旁路,等于在系统里造一个
官方认可的漂移来源。

界面能触发的只有**收敛**(立刻拉一次、重新应用一遍),不能制造**分歧**。
真要临时动手,用 ssh —— 那条路本来就在,而且看得出是人为干预。

推论:界面按能力分两层。**读**在每个节点上都有(数据本来就在同一个端口上
无认证提供,换成 HTML 不增加任何面);**写**只在中控一台上。原本"一个运维
五道门"的顾虑,因为写操作收敛到一台而消失了。

### D37 · 节点有四个状态,加和删要对称

**日期** 2026-08-23 · **状态** 生效

原来只有"在 SSOT 里"和"不在 SSOT 里"两个状态,而这不够:

**删掉之后它自己什么都不知道。** 别人不再配到它的隧道,但它的 sing-box 继续
监听、继续用旧凭据接客 —— 而那些凭据是**跨节点共享**的。删掉 edge-a 时,
`cred/access-a-sg` 和 `cred/access-a-eg` 还明文躺在它硬盘上。一台没人管的出口。

改成四个状态(§14.4):正常 → **排空** → **下线** → 移除。

- **排空** `drain`:配置和隧道照旧,但不进候选。迁移期间新旧并存,拿实测
  数据决定何时切。隧道保留是有意的 —— 排空期间还要能观测它。
- **下线** `decommission`:进签名过的 manifest 的 `decommissioned` 名单,
  节点读到自己在里面就停服务、禁自启。

**为什么不用"不在 manifest 里"当停机信号:那是歧义的。** 可能是被删了,也
可能是渲染时漏了一个节点。对歧义信号采取不可逆动作是危险的 —— 缺席只报错并
维持现状,停机要明说。

**秘密不自动销毁。** 销毁不可逆,误签一次就全没了。它要停,不要自毁。

移除之后还有两件机器管不了的事,写进文档是因为**忘掉它们不会有任何症状**:
轮换它持有过的凭据、从内部 CA 吊销它的证书。

### D38 · 离线根密钥当前有意不做

**日期** 2026-08-23 · **状态** 生效(有意降级)

§13.3 要求离线根 CA、中间 CA 加密存储、启动时人工解锁、审计日志。

**5 台机器、一个运维的规模上,这套流程的成本远大于收益。** 当前 CA 私钥与
平台签名私钥都放在中控上,0600,靠 `loom backup` 保存(加密,口令另存)。

记在这里是为了让它是一个**明知的取舍,而不是一处遗漏** —— 两者在代码里
长得一模一样,区别只在有没有人写下来。

什么时候该改回去:出现第二个运维,或者节点数到了"某台机器被拿下的概率不再
可忽略"的量级。

### D39 · 发布器也要收敛,不能只反应文件变化

**日期** 2026-08-23 · **状态** 生效

发布器最自然的写法是"SSOT 变了就发布"。不够。

分发点会以别的方式和真相分叉:被清空、推到一半断线、有人手工动过。只盯文件
变化的发布器对这些无能为力 —— 而它们的表现是"全网停在一个旧快照上,而中控
认为一切正常"。

所以每一轮都比对**分发点当前指向的快照**与**本地算出来的**,不一致就重推。
这和 [D33](#d33--期望状态不只是文件内容)(pull 不按快照 id 早退)是同一条
道理:**期望状态要主动核对,不能等事件通知。**

同一轮里还多做一件事:推完从**节点视角**再取一次。推成功不等于取得到 ——
nginx 路径写错时推送侧完全正常。加上这条检查的第一次运行就抓到了中控自己的
DNS 问题(那台机器上有个无关的 WireGuard 接口把所有域名劫走)。

### D40 · 装文件的那一步必须产出自检清单

**日期** 2026-08-23 · **状态** 生效

配置漂移自检靠一份"绝对路径 → 内容哈希"的清单。清单原本只有
`loom hydrate` 会写 —— 而节点自取根本不经过它。

后果:**每次 pull 之后,机器上的文件更新了而清单没有,自检永远误报"被改过"。**
实测五台机器同时报 `report/config.json` 漂移,而它们装的恰恰是刚发下来的
正确版本。

判据:**产出清单的必须是"最后决定文件内容"的那一步**,不能是旁边某个恰好
也知道内容的命令。现在 `loom pull` 自己算,`loom hydrate` 也算,两条路径
各自保证自己装的东西和清单一致。

这是 [D21](#d21--加字段之前先验证下游真的会用它) 的另一面:那条说"加字段前
先确认下游会读",这条说**加一条新路径时,先确认原路径上的每个副产物都还有人产出**。

### D41 · 界面上的校验按钮不是守卫

**日期** 2026-08-23 · **状态** 生效

中控界面能改 SSOT。页面上有"只校验"和"校验并保存"两个按钮 —— 而**保存路径
必须在服务端自己再校验一次**,不能信任前一个按钮点过。

理由不只是"表单可以被直接 POST"。真正的问题是**失败模式很隐蔽**:一份坏
SSOT 存进去不会有任何提示,发布器随后拒绝发布,线上停在旧快照。症状是
"我改了但没生效",而人第一反应会去查发布器、查网络、查节点,最后才想到
是自己存进去的东西根本没通过校验。

**在能挡住的地方挡住,而不是在能报错的地方报错。**

顺带两条同类的:

- 写盘用同目录临时文件加改名。发布器可能正好在读,半截 YAML 会让它报一个
  跟真实原因毫不相干的解析错误。
- 中控取不到运维口令时,写操作**全部关闭**,而不是退化成"不需要认证"。

### D42 · `<什么>/<节点 id>` 形式的引用归那个节点

**日期** 2026-08-23 · **状态** 生效

`loom secrets split` 原本只按"渲染产物里引用到了什么"来拆总表。中控界面的
运维口令 `ui/access-a` 不出现在任何渲染文件里(它由本机 bootstrap 配置读取),
于是每次重新拆分都会把它丢掉 —— 症状是"界面突然登不进去了"。

规则改成:渲染产物里引用到的,**加上**任何形如 `<什么>/<本节点 id>` 的引用。

这条规则也顺带解释了 `api/<节点>` 和 `probe/<节点>` 为什么长这样 —— 它们
本来就是节点私有的秘密,只是恰好也被渲染产物引用了。命名规范因此变成一条
可执行的约定,而不只是习惯。

### D43 · §5.6 曾经假设"地址不影响该选哪条链",这是错的

**日期** 2026-08-23 · **状态** 生效(修正 §5.6)

§5.6 原来写着:地址轴为"由请求决定"时,**"候选集里地址是常量,只在服务器
链上选"**。我照着实现了很久 —— 一条声明一个 selector,一个候选,所有目标
共用。

那句话把两件事混为一谈:**"地址不由我们选"**(对)和**"地址不影响该选哪条
链"**(错)。地址不是我们的*选择*,但它是决定该走哪条链的*输入*。

实测:

| 目标 | 经 edge-b | 经 cn-a | 直连 |
|---|---|---|---|
| `www.baidu.com` | 1.464s | 0.145s | **0.058s** |
| `www.aliyun.com` | 1.175s | 0.182s | **0.056s** |
| `api.ipify.org` | **0.401s** | 失败 | 失败 |

**没有任何一条候选对三个目标都好。** 而 `best-egress` 给整条声明选了 edge-b,
于是访问 baidu 慢了 25 倍 —— 一个我自己每天在用、而从来没测过的场景。

这条记在这里,是因为它和别的 bug 不是一类:**代码忠实地实现了文档,而文档
是错的。** 测试全绿、校验全过、部署全通,都发现不了。发现它的是"拿真实
目标测一遍"这个动作本身。

### D44 · 接入端只能选服务,不能指定地址

**日期** 2026-08-23 · **状态** 生效(2026-08-23 实现并真机验证)

修正 [D43](#d43--56-曾经假设地址不影响该选哪条链这是错的) 有两条路:让目标
集合开放、按目标学习;或者**让中控声明服务清单,接入端只能从中选**。

选后者。它一次消掉三个难题:

| | 开放目标集 | 服务清单 |
|---|---|---|
| 冷启动 | 第一个请求必然是猜 | **不存在** —— 服务上线前就能测完 |
| 分组 | 靠域名后缀 / ASN 推断,会错 | **已知**,声明的 |
| 被动观测 | **必须**(没有别的数据来源) | 回到"优先但可选" |

还有两个额外的好处:

**安全边界。** 接入端能指定任意 URL,意味着一份泄露的凭据能把服务器变成开放
代理。§8.2 的准入校验只管"允许走哪",服务清单把它扩展到"允许去哪"。

**请求带上了语义。** "我要服务 X"而不是"我要这个 URL",于是按服务的配额、
objective、归因才成立。

推论:如果服务按地址集合声明,数据平面可以**从请求的 host 反查服务** ——
接入端连"我要哪个服务"都不用说,这才是完整的"接入端不知道任何事情"。

代价是任意 URL 用不了。而这应当是一个**显式声明的服务**("我不知道里面有
什么" + 明确的兜底策略),不是默认假设 —— 区别在于显式声明时你知道自己在
放弃什么。

### D45 · 事件只记变化,而且记在中控一处

**日期** 2026-08-23 · **状态** 生效

被问到"为什么不推给中控端和其他节点"。查完发现我把一整层跳过去了:

**"推给其他节点"已经在做了** —— 转述每分钟传一轮,全网一分钟内都知道。
传输不是问题。

**真正缺的是:只有"现在",没有"曾经"。** 转述表每个观测者只留最新一份,
旧的被覆盖;度量文件里只有探测结果,没有隧道健康。所以"隧道昨晚断了 20
分钟"这件事无法回答,之前四台机器的 `wg-quick` 坏了多久也查不到。

三条判据:

**只记变化。** 两次观测不同才产生记录。一次 69 秒的断连是两条,不是 70 条。

**`From` 和 `To` 都要记。** 只记 `To` 的话,"从坏变好"和"一直是好的"
在日志里长得一样。

**记在中控一处,不是每个节点。** 每个节点视图相同,记 N 份只会让人不知道
看哪份。代价:中控停了就不记 —— 写下来,不装作没有。

分层因此是四段,而我上一次只说了第一和第四段:

```
每个节点发现问题     ✅ 自检
其他节点都知道       ✅ 转述,1 分钟传遍
中控记下来           ✅ 本条
把人拉过来           ❌ 需要外部通道
```

**第四段不能用前三段代替。** §16.3 早就写着"告警通道不能依赖被管网络",
而事件日志恰恰在被管网络里面。它是事后查的,不是叫人的。

做第四段之前值得先看一段时间事件日志 —— 那时才知道**多久发生一次值得被
吵醒的事**,而这个问题在有历史之前只能猜。

### D46 · 先装二进制,后装配置

**日期** 2026-08-23 · **状态** 生效

配对失败的方向不对称:**新版通常读得懂旧配置,旧版读不懂新配置。**

不是推测。发布器崩过一次:它跑着旧二进制,而 SSOT 里多了 `services` 字段,
于是直接拒绝发布,而症状是"改了 SSOT 但全网没动"。

所以 `loom pull` 换完二进制**就结束这一轮**,配置留给下一次(几分钟后)。
继续用当前进程里的旧代码去装新配置,正是要避免的那种配对。

二进制的 SHA256 进签名过的 manifest,而 manifest 的内容哈希就是快照 id ——
**换二进制就换快照 id**。§15.4 要的"配置与二进制绑定回滚"因此是结构性的,
不靠任何约定。

分发树里它内容寻址(`bin/<sha256>`,顶层共享):同一个二进制不重复推送,
回滚到旧快照时旧二进制还在。

### D47 · 跑不起来的二进制装上去,这台机器就再也拉不到修复了

**日期** 2026-08-23 · **状态** 生效

自升级最糟的失败模式不是"升级失败",是"升级成功但新版跑不起来" ——
那之后节点连拉取修复的能力都没了,只能 ssh 上去救。

三道防线,顺序从便宜到贵:

| 防线 | 挡住什么 |
|---|---|
| 哈希比对 | 传输截断、分发点被改 |
| **冒烟测试**(`loom selfcheck`,在临时位置跑) | 架构不对、文件损坏、**读不懂本机现有配置** |
| 保留旧版 + 服务起不来就换回去 | 冒烟测试没覆盖到的运行期问题 |

第二道里"读不懂本机现有配置"是关键:它直接检验 [D46](#d46--先装二进制后装配置)
关心的那个配对,而不只是"这个文件能不能执行"。

实测:发一个不能执行的文件过去,哈希对得上,冒烟测试 `exit status 3`,
**不安装 —— 机器上的二进制和服务全都没动**。

> **第一次升级躲不掉手工。** 节点上的旧 `loom pull` 不知道要升级二进制,
> 所以这个能力本身要先手工推一次。和信任根、本机秘密层一样属于 bootstrap。

### D48 · 发布器在跑的时候,手工 publish 曾经是个陷阱

**日期** 2026-08-23 · **状态** 历史(入口分叉已由 D85 消除)

[D39](#d39--发布器也要收敛不能只反应文件变化) 让发布器每轮核对分发点、
不一致就重推。正确 —— 但它有一个反直觉的后果:

**手工 `loom publish` 会在 30 秒内被守护进程覆盖回去。**

实测踩到:我手工发了一个带二进制的快照,守护进程下一轮发现"分发点指向的
不是我算出来的",把不带二进制的版本推了回去。日志里写得清清楚楚,而我
花了几分钟才反应过来。

这不是 bug,是收敛的定义。结论是:**发布器跑着的时候,它是唯一的发布者。**
手工 publish 只在守护进程停着时才有意义(首次发布、排障),而且用完要
把该给守护进程的参数也补上 —— 否则下一轮它就把你的东西冲掉了。

**当前结论（D85）：上述覆盖行为不再成立。** 手工入口与守护发布器现在共用
逐次发布锁、release/pin 目录和同一套构建/校验逻辑；`-binary` 旁路被拒绝。
锁被占用时手工命令 fail closed，相同输入也不会再产生一份独立目标态供下一轮
“纠正”。手工命令仍只用于首次发布和排障，但无需为了避免旧式入口分叉而永久
停掉 daemon。

### D49 · 只测首字节会挑出连得快、传得慢的路

**日期** 2026-08-23 · **状态** 生效

被问到"只考虑握手时间吗?不考连接创建后的数据传输吗"。查了一下:是的,
探测只量到首字节,吞吐完全没测。而这会**选错路**。

同一批候选,同时量:

| 候选 | 首字节 | 下载速度 | 拉 2MB | 跳数 |
|---|---|---|---|---|
| `edge-b` | 454ms | **2018 KB/s** | 0.97s | 1 |
| `edge-a` | 956ms | **860 KB/s** | 2.27s | 1 |
| `cn-a>edge-a` | 779ms | 251 KB/s | 7.78s | 2 |
| `cn-a>edge-b` | 885ms | 251 KB/s | 7.76s | 2 |
| `cn-b>edge-b` | 4545ms | 273 KB/s | 7.15s | 2 |
| `cn-b>edge-a` | 1128ms | 244 KB/s | 7.99s | 2 |

**一跳 860–2018 KB/s,两跳 244–273 KB/s。** 四条两跳的链挤在一个很窄的区间,
系统性、不是巧合。

`edge-a` 首字节排第 4、真实耗时排第 2,比排它前面那条快 3.4 倍。

改成一次探测同时量两个数,按 objective 分别用。`objective: throughput`
因此从"拒绝执行"变成可用。

**两条附带的结论:**

§3 只说了跳数上限"实践中 ≤2",没说第二跳的代价。现在有数了:**第二跳换来
可达性,代价是四分之三的吞吐。** 两跳链该是"没别的办法时才用"。

而这也部分解释了为什么"按段量、加起来"的合成估计失败(见下):丢包和吞吐
不是可加的,一条链丢包多一点,TLS 握手就要重传,首字节被非线性放大 ——
这没法从单跳时间推出来。

### D50 · 合成估计:试过,不成立

**日期** 2026-08-23 · **状态** 已否决(留记录,别再试同一条路)

用户提出用寻路算法代替枚举。方向是对的 —— 边比路少得多
(`N² + M×N` vs `M×N²`),而且边可以由 N 台机器并行量。

为此做了一个新原语:**让链条上最后那台机器去连它自己的地址**,量到的就是
纯粹那一段,不依赖任何外部目标的可达性。它有效,而且是白赚的诊断能力
(见下)。

**但"单段相加 = 整条"不成立。** 同时量单段和端到端,7 次取中位数:

| 候选 | 单段 | 端到端 | 比值 |
|---|---|---|---|
| `edge-b` | 228 | 519 | 2.28 |
| `cn-b>edge-b` | 262 | 867 | 3.31 |
| `cn-a>edge-a` | 272 | 831 | 3.06 |
| `cn-a>edge-b` | 289 | 1144 | **3.96** |

**比值 2.28–3.96,不是常数。** 加上"末跳→目标"之后排序有两处颠倒。

原因:一次 HTTPS 请求是**好几个来回**(握手、请求、响应),而**每个来回都
要走完整条链**。来回几次取决于对方网站 —— TLS 版本、会话复用、内容大小 ——
不是从"走一趟多久"能推出来的。最清楚的反例是同一个第一跳的
`cn-a>edge-b`(×3.96)和 `cn-a>edge-a`(×3.06)。

**保留:** 测量当时网络状况偏差(端到端比历史 p50 差三四成)。要真正证否需要
更长时间的秩相关分析。但那是很大的投入换不确定的收益,而"探测太贵"这个
问题有便宜得多的解法([D51](#d51--探测有界当前那条必探其余轮换))。

**白赚的:** 单段测量留下来做**诊断**。它回答了一个此前完全答不出的问题 ——
一条链慢,是慢在哪一段。不拿它做选路决定。

### D51 · 探测有界:当前那条必探,其余轮换

**日期** 2026-08-23 · **状态** 生效

候选数是 `1 + N + N(N-1)`,再乘上目标数,再乘上"要读正文才算得出吞吐" ——
全探会让探测本身变成网络上最大的一股流量(15 条 × 2 目标 × 256KB ÷ 5 分钟
≈ 90 MB/小时)。

有界之后:当前选中的**每轮必探**(它变坏了要立刻知道,D23 依赖这个信号),
其余按游标轮换。实测 792 次/小时 → 132 次/小时,而且现在测的是**对的东西**
(含吞吐)。

**少探了多少要说出来。** 静默截断会让"这一轮没试到"看起来像"试过了但不行"。

**预算引入了一条新的算术约束:**

```
每条候选的样本数 ≈ (window / tuning_period) × (budget-1) / (候选数-1)
```

小于 `min_samples` 就永远排不了序 —— 和 [D24](#d24--调参字段之间的算术要校验)
是同一类错误,原因从"窗口太短"换成"预算太小",症状一模一样。校验器现在
算这一条。`stale_after` 也要比轮换周期宽,否则候选在轮到之前就先"过期"。

### D52 · 延迟与吞吐是两个测度,用帕累托前沿而不是合成一个数

**日期** 2026-08-23 · **状态** 方向已定,待实现

我一度提出把两者合成一个"完成时间"公式,并据此说 objective 应该消失。
那是错的([见 D49 的讨论](#d49--只测首字节会挑出连得快传得慢的路)):
objective 是**在乎什么**(策略),不是**是什么**(可测量的属性),两者不能
互相推导。

正确的做法是把它们当成**两个维度**:

- 一条候选如果在延迟和吞吐上都不比另一条好,它就被支配,可以直接淘汰
- 剩下的是**帕累托前沿** —— 前沿上的候选各有所长,谁都不是无条件更优
- `objective` 决定在前沿上取哪一点

好处是把"客观淘汰"和"主观取舍"分开了:前者由数据决定,后者由声明决定。
现在的单指标排序把两件事糅在一起,于是"按延迟排"会淘汰掉吞吐好得多的候选
(实测 `edge-a` 首字节排第 4、真实耗时排第 2)。

**抖动归入吞吐这一维**,不单列第三维:波动的实际后果是有效吞吐下降
(TCP 窗口收缩、重传),而不是另一种独立的"差"。

### D53 · 共同命运:记录路由,先给人看,暂不进选路

**日期** 2026-08-23 · **状态** 方向已定,待实现

实测 mtr 证明了一件端到端测量永远看不见的事:

```
cn-a → edge-b:  192.0.2.30 → 192.0.2.31 → 198.51.100.30 → 203.0.113.30
cn-b → edge-b:  192.0.2.32 → 192.0.2.33  → 198.51.100.30 → 203.0.113.30
                                                └────── 完全相同 ──────┘
```

**cn-a 和 cn-b 到柏林,从第三跳起是同一条路。** 这解释了为什么两条候选的
实测值几乎一样(646ms / 600ms),也意味着**在它们之间切换是徒劳的** ——
共用段拥塞时两条一起坏。

还有一件事只有逐跳才看得见:代价全在出境那一跳(4ms → 203ms)。所以
**对境外目标,选哪台国内中继几乎无所谓**。

**先只做记录与展示**,不接进选路:

- 每个节点的上报者定期 mtr **自己那几段**(只有起点看得见那条路)
- 跳表转述出去,中控台可查
- IP → ASN 用**离线**数据表。不接在线服务 —— 那会把拓扑告诉第三方,
  也给系统加一个外部依赖

频率:一次 mtr 约 45 个包、30 秒,且 ICMP 常被限速。**几小时一次**,
不是几分钟一次。

### D54 · `ttft` 与 `cost` 是扩展点,不是缺口

**日期** 2026-08-23 · **状态** 生效(重新归类)

这两个 objective 一直挂在"被附录 C #8 / #13 阻塞"下面,给人一种"再写点代码
就能用"的错觉。**不是。它们要的是部署方自己的数据源,而不是平台的功能。**

平台该做的部分已经做完了:

| | 声明的位置 | 没配时会怎样 |
|---|---|---|
| `ttft` | 等价类的 `observation_point` | 校验器拒绝:"tokens/s 不是 L4 能被动观测的量;首字节只是近似,不能当它用" |
| `cost` | 等价类的 `price_source` | 校验器拒绝:"价格是声明值,不会从度量里长出来" |

外加 Agent 在渲染期第二次拒绝并说明理由。**两层守卫,而且都不静默降级。**

数据源为什么必须由部署方给:

- **`ttft`** 要 L7 观测点。四个选项(自有端点埋点 / L7 网关 / 调用方 SDK /
  主动契约请求)各有真实代价,而**哪个可行取决于你在访问谁的服务** ——
  别人的 API 埋不进去,自己的可以。这不是平台能替你选的。
  L7 网关那条尤其要谨慎:它会破坏"L4 不碰字节"这条不变量。
- **`cost`** 更进一步:**它对当前拓扑根本不适用。** 现在的候选是"同一个
  目标地址,经不同的路",走哪条路付给对方的钱一分不差。成本排序只在
  **不同供应商的等价端点**之间才有意义 —— 也就是模式 B,而模式 B 被
  附录 C #3(访问契约)卡着。

**处理方式:从缺口表移到"扩展点",排在最后。** 需要时由部署方配上数据源,
平台侧不需要再写代码。

### D55 · 不是所有变化都是问题

**日期** 2026-08-23 · **状态** 生效

事件的级别原本靠"取值在不在白名单里"判断。于是每个快照哈希都不在白名单里,
**每次发布都被记成一次故障**。

后果实测到了:界面上"还在持续的问题"列了 7 条,**7 条全是快照号和选路
结果** —— 而这个面板正是为了防止真问题被淹没才建的。它自己变成了噪声源。

改成按**类别**分级:`snapshot` / `route` 永远是 `info`,`rotation` 是
`pending`(过渡态),其余按类别各自的"正常值"判断。

顺带修了同一处的第二个 bug:**"没有后续"不等于"还在持续"。** 上报者重启时
静默播种,所以日志的最后一条可能早就不是现状 —— 一条 2.4 小时前的快照事件
被显示成"还在持续",而那台机器早换了两个版本。判断要和当前状态核对。

> 这两个 bug 合起来,让"待处理"面板既报了 7 条假的、又会漏报真的。
> **一个会说谎的告警面板比没有面板更糟**:它训练人忽略它。

顺带:没有未解决项时明确打出"✅ 没有未解决的问题"。一片空白分不出
"一切正常"和"这功能没在跑"。

### D56 · 隧道地址和端口由分配器算,不靠手填

**日期** 2026-08-23 · **状态** 生效

加一台机器要手工算的东西:每条隧道两个 `/32`、一个监听端口,而且不能跟
已有的撞。5 台机器 9 条隧道时还能对付,再加一台就是 12 条 —— 手填必错,
而**填错的表现不是报错,是那条隧道悄悄不通**。

`model.AllocateTunnel` 从现有部署里读出两条规则,继续按它们分配:

1. **每个 `reverse_only` 节点占一个 `/24`**(edge-a 是 `10.99.0.x`,
   edge-b 是 `10.99.1.x`),段内成对顺排 `.1/.2`、`.3/.4`。归属给
   reverse_only 那一端,是因为它是被拨的那头 —— 一台被拨的机器的所有
   隧道天然聚在一起。
2. **端口刻意不连号。** 端口取 `sha256(节点对)` 起步线性探测。连号本身
   是个特征 —— 61619、61620、61621 摆在一起,扫到一个就知道还有一串。

用 sha256 而不是随机数,是为了满足 §12 的纯函数要求:同样的输入永远得到
同样的分配,与调用顺序无关。

当前 Device 接入规划仍复用该分配器；Device 身份由客户端本地生成，私钥不离开
客户端。旧的 `loom addnode` SSH 接入命令已经删除。

### D57 · "该轮换哪几张凭据"按候选链算,不按 allowed_servers 算

**日期** 2026-08-23 · **状态** 生效

§14.4 要求删掉一台机器之后轮换它持有过的凭据 —— 那些 `cred/...` 是跨节点
共享的,它硬盘上还留着明文。**忘了轮换没有任何症状**,直到有人拿捡到的
凭据连进来。

所以 `loom status` 直接把清单列出来。第一版按声明的 `allowed_servers` 算,
**多列了两倍**:`allowed_servers` 是"允许用到",而渲染器只在**候选链真的
经过这台机器**时才给它配上 user。允许 ≠ 配了。

判据因此和渲染器对齐,并且有测试逐台交叉核对渲染出来的 sing-box 配置里
实际有哪些 user —— 这个清单少一张,那张就永远不会被轮换。

还有一个反直觉的地方:**要按"假如它还在服役"来枚举**。排空和下线的机器
已经不进候选了,而恰恰是这两个状态才需要问"该轮换什么"。问的是它硬盘上
曾经有什么,不是它现在还路由什么。

### D58 · 转述来的节点也要进快照分布表

**日期** 2026-08-23 · **状态** 生效

`loom status` 的"全网快照分布"只统计了**直接拉到**的那几台。够不到的节点
靠转述进来(§16.1.2),它们的 `applied` 就在观测里,却从没被算进去。

实测:5 台机器的表上只列了 3 台。access-a 跟 cn-a、cn-b 没有隧道,于是这两台

危险的不是少两行,是**少得静默**:落后的那台如果恰好直接够不到,你看到的

Web 界面没有这个 bug —— 它遍历的是含转述节点的 `View.Nodes`。**同一件事
算了两遍,只有一遍是对的**,和 D51 那次 `pinnedDecls` 重复推导同一个毛病。


### D59 · 大块下载同时检测停顿与按签名大小计算的总时限

**日期** 2026-08-23 · **状态** 生效

二进制原来跟 manifest 共用一个 HTTP 客户端 —— 一个 **60 秒的总时长**上限。
12.3 MB 配 60 秒等于要求全程持续 205 KB/s,而本次实测二跳吞吐只有
244–273 KB/s。**贴着线跑。**

实测到了两次:edge-a 一次 60 秒超时失败,下一轮 38 秒成功。同一台机器、同一个
文件 —— 每次二进制更新都是一次掷硬币。

固定 60 秒的超时形状不对:它把"慢"和"卡住"当成一回事,而这两件事的正确
反应相反。主判据改为停顿检测:连续 45 秒没有新字节就放弃，并在错误里说清
下到多少卡住的。

但**只有停顿检测也会 fail-open**:不可信分发点每 44 秒滴一个字节，就能永久
占住 `loom-pull.service`，使后续配置乃至签名过的 decommission 永远没有机会
被读取。最终语义是两道同时成立:

- 45 秒无进展立即失败；
- 按 manifest 签名覆盖的 `size`、32 KiB/s 保守最低吞吐加一个停顿余量计算
  硬总时限，并夹在 2–20 分钟之间。

因此慢链路不再被一刀切的 60 秒误杀，持续滴流也不能无限续命。二进制网络
预取在 `deploy.lock` 外完成；硬总时限到达前也不会堵住人工 `loom apply`。

读取上限仍然保留，并绑定签名覆盖的 `size`（只给 1 MiB 余量）—— 那道防线
防的是无限流吃内存，跟两种超时是三件不同的事。

> 这个 bug 的隐蔽处在于**它平时是好的**。60 秒够 12 MB 用了很久,直到
> 二进制长大、或者链路差一点。而失败的后果不是"这次没升上":两段式升级
> (先二进制、后配置)意味着失败的机器停在半路。


### D60 · 二进制回滚靠"钉住",不靠重新编译

**日期** 2026-08-23 · **状态** 生效

回滚原来有两道防线,中间空着一档:

| 情况 | 现有措施 |
|---|---|
| 配置改坏了 | 五步安装回滚 ✅ |
| 新二进制**起不来** | `.prev` 自动换回去 ✅ |
| 新二进制**起得来但是错的** | ❌ 什么都没有 |

第三档才是最常见的 —— 今天就撞到一个(报告者跑着被替换掉的 inode,数据少
字段,任何检查里都看不出来)。当时唯一的退路是 `git checkout` + 重新编译 +
重新发布,**要求手上有源码树**。

而历史二进制在分发点上本来就都在:内容寻址 `bin/<sha256>`,26 个快照 /
21 个二进制 / 261 MB 全躺着。所以不需要新的存储,只需要让发布器改用其中
一个。

`loom pin <快照 id>` 取回来、验签、核对哈希、**真跑一遍 selfcheck** ——
钉一个跑不起来的二进制上去等于把退路也堵死。

三个设计上的取舍:

1. **钉住是状态,不是一次性命令。** 发布器是每 30 秒收敛的守护进程,
   一次性发布下一轮就被它用本机二进制覆盖回去了。
2. **必须显眼。** `-reason` 是必填的;发布器在**本机二进制变了而钉住仍
   生效**的那一刻专门说一句 —— 那正是"我重新编译了但没发出去"的时刻。
   粘性覆盖不显眼就是陷阱(同 D58)。
3. **记录在、二进制不在要报错**,不能默默回落到当前二进制 —— 那正好是
   钉住要防的事。

> 一个副作用值得知道:SSOT 没变时钉回快照 X,渲染是纯函数(§12),
> 于是重新算出来的就是 X 本身,字节相同。**钉住 + 不动 SSOT = 完整回滚。**
> SSOT 变过就不是了 —— 那会得到"旧二进制 + 新配置",正是 §15.4 要防的
> 组合。这一点目前只写在文档里,还没有让工具拦。
>
> 已由 [D62](#d62--整份回滚源头跟着成品一起回去) 补上:工具现在拦了,
> 而且 `loom rollback` 让"两半一起回去"成为默认路径。


### D61 · 源头存档在中控本地,不进分发树

**日期** 2026-08-23 · **状态** 生效

做整份回滚时发现的:**SSOT 没有任何版本历史。**

| 以为它在哪 | 实际 |
|---|---|
| git | `.gitignore` 里 `/deploy/` 被整个排除 |
| `loom backup` | 默认只收 `deploy/secrets.env` 与 `deploy/pki` |

### 第一版做错了,记在这里

最初的做法是把源头当成一个 blob 塞进分发树(`ssot/<sha256>`,与二进制
同样内容寻址)。论证是"分发点早就持有每个节点的完整渲染产物,源头里的
信息是它的子集,不增加泄露面"。

**那个论证漏了一整类东西。** 实测:

| SSOT 里的东西 | 已在渲染产物里? |
|---|---|
| 4 个真实公网 IP | ✅ 全部已在 |
| DDNS 域名 | ✅ 已在 4 个文件里 |
| **`ssh_port`(非默认值)** | ❌ **0 个文件** |

`ssh_port` 是模型里的真字段,而 SSOT 自己的注释就写着这类字段
"记在这里是为了 bootstrap 与排障,**不是为了被连**"。分发点在设计上是
当作已被攻陷来对待的([D32](#d32--控制面是一棵签了名的静态树不需要被信任)),
而签名拦不住"主动把管理平面的信息送过去"这一类风险。

> **错的是类别,不是这一个值。** 非默认 SSH 端口只是弱混淆,真正拦人的
> 是密钥。但一旦确立"源头整份上分发点",以后每加一个这类不下发的运维
> 字段都会默认外发 —— 而加字段的人不会想到这件事。

### 定下来的做法

源头存档**只在中控本地**(`deploy/ssot-history/<sha256>.yaml`),每次成功
发布写一份,内容寻址。

换个角度看这本来就是它该在的地方:**这份存档只有中控用得着** ——
只有它做渲染,节点从来不读 SSOT。它不是分发树的一部分,是中控自己的备份,
所以归 `loom backup` 管(默认清单已加上,顺带补掉"SSOT 不在备份里"这个洞)。

**完整性一点没削弱。** manifest 里的 `ssot_hash` 仍然是权威,而 manifest
是签了名的:回滚照样按它核对取回来的字节。改的只是字节从哪来 ——
本地读而不是下载。变的是耐久性,不是可信度。

耐久性的代价说清楚:中控硬盘挂了就没有源头历史。但中控挂了本来就是
"从备份恢复"事件 —— 签名私钥、秘密层、PKI 全在那台机器上,早就不可再生。
源头历史进的是同一个篮子,而那正是它该在的篮子。

> 没做的:给 SSOT 加注释扫描器。明文秘密只可能出现在注释里,而按注释形状
> 做粗筛正是本项目一贯拒绝的"会误报的检查"(见 `looksLikeSecret` 的注释)。
> 模型里根本没有能装明文秘密的字段(只有 `secret_ref` 与 `wg_public_key`),
> 加上严格解码,这个结构性保证比粗筛强 —— 由测试钉住。


### D62 · 整份回滚:源头跟着成品一起回去

**日期** 2026-08-23 · **状态** 生效

`loom pin`(D60)回滚二进制,`loom apply` 回滚"上一次"的配置。中间一直缺
"整份退回快照 X"。

**关键在于源头必须一起回去。** 只把成品退回去是无效的:发布器每 30 秒从
SSOT 重新渲染一次,收敛机制(D33、D39)会立刻把线上带回新版本。

所以 `loom rollback <id>` 动的是两样东西 —— 源头和二进制 —— 然后**什么都
不做**,让发布器自己收敛过去。

**刻意不引入"冻住分发点"这种粘性覆盖。** 那会是一个新的、必须有人记得
解除的状态,而每个这样的状态都是一个"我改了但没生效"的来源(D48 踩过)。
源头一退回去,现有的收敛机制就够了。实测:回滚后发布器下一轮自己发出了
目标快照,没敲任何发布命令。

### 自证是这条命令的核心

源头与二进制取回本地后**重算一遍快照 id,必须还是 X**。渲染是纯函数
(§12),这条等式才成立 —— 它也是纯函数性质第一次被拿来当运行期检查用。

不成立就说明这个快照里有东西不由这两样决定,而回滚会留下一个**看起来
成功、实际没回去**的系统。当场报错,不发。

### 顺带堵掉 D60 留下的洞

D60 末尾写着"钉住 + SSOT 变过 = 旧二进制 + 新配置,目前只写在文档里,
还没有让工具拦"。现在两处都拦:

- **发布器**每次发布都比对,对不上就说出那个组合,并给出两条出路
- **`loom rollback` 不带参数**报告当前状态,把源头现在算出来的 id 和钉住的
  id 摆在一起

### 实测过的失败路径

| 情况 | 结果 |
|---|---|
| 本地存档被改过 | 认出"内容与哈希对不上 —— 被改过了" |
| 存档里没有这一版 | 报出可能的两个原因,并指向 `loom backup` |
| 用错的公钥 | 验签就拒了,没取任何内容 |

两种取不到源头的情况**刻意分开说**:"被改过"和"没有这一版"该做的事不一样,
合成一条会把人带偏。

三次失败之后 SSOT 逐字节未被改动 —— 覆盖发生在全部检查通过之后。

> **回滚前那一版存在 `deploy/pinned/ssot.prev.yaml`。** 因为 D61 才刚让
> 源头有历史,而回滚本身要覆盖它:这是本次操作唯一不可再生的东西。


### D63 · 发布历史记在中控,只记变化

**日期** 2026-08-24 · **状态** 生效

`loom rollback` 要一个快照 id,而 id 是十二位十六进制 —— **没地方查**:

| 以为能查到 | 实际 |
|---|---|
| 分发点列目录 | `autoindex off`(demo-b 的 nginx),列不出来 |
| 事件历史的 `snapshot` | 记的是"**某台节点装的版本变了**"。一个发出去但还没被任何节点取到的快照,那里一条记录都没有 |

所以中控自己记:`deploy/ssot-history/published.jsonl`,与源头存档同一个目录
(它们本来就是一件事 —— 中控的发布历史),因此也一起进 `loom backup`。

**只记变化,不记状态**(同 events 包)。发布器每 30 秒收敛一轮,同一个快照
被反复确认;逐轮记一行的话一天 2880 行"还是那个快照",真正的版本变化会被
淹掉。只有 id 与上一条不同才追加。

> 去重是**跟上一条比**,不是"见过的 id 就跳过"。回滚回旧版是一次真实的
> 版本变化,按"见过就跳过"的话,**回滚这件事本身会从历史里消失。**
> 有测试钉住(`TestPublishedKeepsReturnToOldSnapshot`)。

### 那一列才是重点

`loom snapshots` 的判据是"**源头存档真的在、且内容对得上哈希**",不是
"历史里有这一行" —— 存档被清理过或被改过时,历史行照样在。而回滚失败最糟的
时机就是需要它的那一刻。

```
  快照          发布时间          源头          能回滚吗
  7ca7aa7755a0  08-24 08:21       6d909ee84b7a  ❌ 源头存档没了
  45f1b5fe4f77  08-24 08:21       b0949a92998d  ❌ 存档对不上哈希
→ 39470e023ff3  08-24 08:21       5da74d247aff  ✅
```

两个显示口径上的坑,都属于"会说谎的面板比没有面板更糟"([D55](#d55--不是所有变化都是问题))
那一类:

- **同一个快照出现两次时,`→` 只标最后那次。** 都标会看成有两个当前版本
- **统计对全量算,不对 `-n` 截出来的那几行算。** 否则 `-n 1` 会显示
  "1 / 2 个版本",读起来像"有一个退不了",而那纯粹是显示条数造成的


### D64 · 备份区分"必须有"与"可以还没有"

**日期** 2026-08-24 · **状态** 生效

把源头存档加进 `loom backup` 默认清单之后,**备份当场整个不干活了** ——
`deploy/ssot-history` 要发布器成功发过一次才建,而在那之前它不存在,
于是原有的"少打包了什么就硬失败"把整次备份拒了。

原来那条硬失败是**对的**,不能放松:一个"成功"但内容不全的备份,只有在
需要它的那天才会被发现。所以改成分两类:

| | 缺了怎么办 | 为什么 |
|---|---|---|
| `secrets.env`、`pki` | **硬失败** | 它们不存在意味着这台机器有别的问题 |
| `ssot-history` | 说一声,继续 | 它可以合法地还没出生 |
| 命令行显式点名的 | **硬失败** | 人写出来就是指望它在 |

**"可选"说的是它可能还没出生,不是它不重要。** 所以缺了仍然要打印出来 ——
静默省略就是在制造"你以为你备份了",与那条硬失败是同一个理由,只是不该
拦住整次备份。

> 分错边的代价不对称,这是关键:必需项当可选 → 备份看起来成功但少东西;
> 可选项当必需 → **一台刚起来的中控连备份都做不了**,而"做危险变更之前先
> 备份"恰恰是最需要它能跑的时候。


### D65 · 链路通断要变成事件

**日期** 2026-08-24 · **状态** 生效

实测发现 demo-a ↔ demo-c 的隧道断了 7 小时,而**事件历史里一条记录都没有**,
未解决面板上也没有。

原因不是代码跳过了转述来的节点。是 `detect.go` 产出的六类事件里
(`reach` / `snapshot` / `tunnel` / `drift` / `rotation` / `target`)
**没有 `edge`**:

| 数据 | 转述带得过来吗 | 变成事件了吗 |
|---|---|---|
| 隧道握手年龄 | ❌ 只有直接问才有(view.go 的 `st == nil` 分支) | 只有中控自己的 |
| **节点间 RTT(`Edges`)** | ✅ 一直都在 | ❌ **从来没有** |

所以两台都不是中控的机器之间断了,除了 `loom status` 上一个 ❌,
没有任何地方会发现,"断了多久"更是答不出 —— 而那是做事件历史的全部理由。

**只记通与不通,不记 RTT。** RTT 每轮都在变,记进状态就是每轮一条事件。

**一条链路两端都报,于是产生两条事件 —— 这是刻意的。** 单向故障真实存在:
这次实测就是 demo-a → demo-c 的包到得了、demo-c → demo-a 的回程被丢。
合并成一条就看不出这种不对称。


### D66 · 面板问当前状态,时长才问历史

**日期** 2026-08-24 · **状态** 生效

D65 做完之后那条链路**仍然上不了面板**。

因为 detector 第一轮是**静默播种**的(否则每次重启都像全网同时变化一次 ——
这个设计是对的),而播种那一刻它已经是坏的,没有"变化",没有事件。
旧面板从事件历史筛"未解决",于是:

> **上报者启动那一刻已经坏掉的任何东西,在它恢复之前面板永远看不见。**

这跟当初"四台机器 wg-quick 全 failed、存在多久没人知道"是同一个形状的
盲区,只是换了一层。

修法是把两个问题分开问:

| 问题 | 该问谁 |
|---|---|
| **现在有什么问题** | 当前状态(`state.json`,每轮覆盖) |
| **多久了** | 起点(状态自己记)+ 事件历史 |

`events.jsonl` 只追加、只记变化;`state.json` 每轮覆盖、只记现状。
**两个文件,两个问题,不要合并。**

### 时长必须跨重启存活

第一版改完之后真机上出了个新毛病:那条断了 10 小时的链路显示成
**"至少 28 秒"** —— 因为上报者刚重启,起点归零了。技术上没说错,实际效果
是让人以为它刚坏,**比不显示更糟**。

时长是这个面板唯一真正新增的信息("链路断了"看节点表也知道,"断了两天了"
才让人动手),而上报者重启是常事 —— 就为了发这两个版本,今天重启了两次。

所以状态文件在启动时被读回来:**值没变的,起点接着用**。实测重启前后
`since` 都是 `13:26:38`,时长连续。

**停机期间变掉的不接。** 变化发生在什么时候无从得知,那就从新起点算并标成
下界 —— 把停机那段算进去等于假装知道。

### 下界必须标成下界

`已 9 小时` 和 `至少 9 小时(上报者启动时已如此)` 是不同的两句话。
把后者写成前者就是在假装知道起点 —— 而那正是面板说谎的方式(同 [D55](#d55--不是所有变化都是问题))。


### D67 · 同一个测量,两种含义:target 是数据,uplink 才是告警

**日期** 2026-08-24 · **状态** 生效

`api.ipify.org` 由 SSOT 显式选择，不是程序默认值或硬编码依赖。这里选择它不是
为了泛化的 HTTP 健康检查，而是为了区分大陆直连与境外出口可达性；这个语义不能
被一个普通的自有健康页替代。仓库夹具保留同一目标，锁住这条分类契约。

面板上"demo-b 到不了 api.ipify.org"挂了 14 小时。被问到"国内机器的 target
换一换,为啥非要卡在这里"。

**换不得。** 查下来这个测量有两个消费者,而我一开始只看到一个:

| 谁 | 用它干什么 | "demo-b 到不了 ipify"是 |
|---|---|---|
| **Agent 剪枝**(`agent/run.go`) | 砍掉出口够不到目标的候选 | ✅ 正是要的数据 —— 15 条砍到 6 条,一轮 13 秒降到 4 秒 |
| **未解决面板** | 当成待处理问题 | ❌ 误报 |

`report/config.go` 的注释早就写着"这是链路状态测量里最值钱的一项"。
换成 baidu,Agent 就不知道 demo-b 出不去,会退回挨个探 15 条。

### 错的是面板拿观测当告警

但"一刀切降级成 info"也不对:**境外机器够不到 ipify 是真故障**。

而且缺的那一半更要命:**国内机器现在没有任何一个"本该够得到"的目标**。
demo-b 的直连整个坏掉,面板上不会有任何变化 —— 因为它本来就是 ❌。
两件事恰好反着:该响的不响,不该响的一直响。

### 所以是"加"不是"换"

节点上加 `probe_targets`:**这台机器本该够得到的地址**。照 `Node.DNS`
那个先例 —— 它的注释讲的是同一个道理("大陆机器用 8.8.8.8 会被污染,
境外机器用 223.5.5.5 又绕远"),目标同样要按机器所在地选。

| 来源 | 回答什么 | 事件类别 | 失败时 |
|---|---|---|---|
| 声明的 `probe_url` | 这台机器够不够得到那个目标 | `target` | **info** —— 喂剪枝的数据 |
| 节点的 `probe_targets` | 这台机器的直连还好吗 | `uplink` | **problem** —— 上面板 |

**一个测量,一条线上的记录,只多一个标记。** `Reach.Uplink` 决定失败算数据
还是算问题;转述的线格式只多一个 bool,而剪枝按 URL 匹配,完全不受影响。

境外节点的两个列表可以是同一个地址(demo-e 就是),那时它既是剪枝数据又是
健康检查 —— 对一台出口来说"够不到目标"确实两者都成立。

### 实测选的目标

| 节点 | 目标 | 实测 |
|---|---|---|
| demo-b / demo-c | `www.baidu.com` | 200,40ms / 103ms |
| demo-d | `www.baidu.com` | 200,59ms(系统解析器是坏的,但 loom 自带 DNS) |
| demo-e / demo-a | `api.ipify.org` | ✅ 339ms / 110ms |

> `www.aliyun.com` 试过,返回 403(挡 curl 的 UA),不适合当自检目标 ——
> **自检目标要选一个稳定返回 2xx 的**,否则每轮都在报假故障。

### 上线当场踩到:自检本身用了系统解析器

配好之后 demo-d 的 baidu 检查报 unreachable —— 而实测它 200/59ms。

`reachTarget` 用的是裸 `http.Client`,**没走 `internal/netx`**,于是用系统
解析器。而 demo-d 的 systemd-resolved 上游是 8.8.8.8,大陆被污染。

讽刺的地方在于 `internal/netx` 存在的全部理由就是"不依赖机器全局设置、
自带 DNS",而**量可达性的这个函数偏偏没用它**。

症状极具误导性:它长得像"这台机器出网坏了",而真实流量一直好着 ——
sing-box 自己配了 DNS(§7.4),根本不经过系统解析器。这与
[设计文档里的 DNS 坑](design.md#732-dns-必须显式配而且要给它留一条出路)是同一个形状,
只是换了一个消费者。

修法:上报者配置带上本节点的 `dns`(来自 SSOT,渲染时填),`reachTarget`
走 `netx.Client`。国内三台拿到 `223.5.5.5`,境外两台拿到 `1.1.1.1` ——
正是 `Node.DNS` 那条注释要的"按机器所在地选"。

> **教训与 `probe_url` 那次是同一条:加东西之前先验证下游真的会用它。**
> 我实测过 demo-d 用 223.5.5.5 解析后能到 baidu,然后**假设**上报者也会这么
> 解析。那个假设没验证,于是配了一个它够不到的目标 —— 亲手造了一条新的
> 永久误报,正是这次要修的东西。

### 没做的

**"能出口却没配 `probe_targets`"没有做成校验错误。** 校验发现没有分级,
每条都会拦住发布,而现有部署里四台 `egress_capable` 的机器本来都没配 ——
做成硬错误会把正常配置拦下来。代价是:漏配的节点,它的直连健康无人监控,
而且这件事本身不会被说出来。


### D68 · 换端口要记住换掉了什么:退役名单既是记忆也是盐

**日期** 2026-08-24 · **状态** 生效

`AllocateTunnel` 按 `sha256(节点对)` 分端口([D56](#d56--隧道地址和端口由分配器算不靠手填)),
确定性、刻意不连号。但它**没有"换一个"的概念** —— 重跑给出同一个端口。
demo-c ↔ demo-a 那次换端口是手工挑的。

补这个能力时有两个坑,而它们互相纠缠:

### 一 · 不记住就会转回去

轮换两次会回到第一个端口 —— 而那个端口是**已知不通**的。症状是
"换了端口还是不通",人会去查网络,查不到原因。

所以要有记忆。放在哪?第一反应是加个 `port_generation`,但那正是
[CLAUDE.md 第 2 条](../CLAUDE.md)警告的形状:**它和 `listen_port` 可以
互相矛盾**,而"可写即可与推导结果矛盾"。

换成 `retired_ports []int`:**它是纯历史,不与任何字段矛盾** ——
`listen_port` 是当前事实,退役名单是曾经。而且人一眼看得懂为什么不能回去。

### 二 · 只跳过不够,还要换起点

跳过退役端口之后,线性探测会挑中它的**紧邻位**(61654 → 61655)。
如果丢弃是按范围或邻近特征做的,那等于没换。

所以退役个数进哈希输入:`sha256(pair|N)`。每退役一个就得到一个全新的、
分布均匀的起点。实测 61691 的下一轮是 61684,不是 61692。

> **`N == 0` 时哈希输入与从前完全一致**,所以既有分配不会因为这个改动而
> 变；同一份 SSOT 的基础分配由回归测试钉住。

### 工具只算不写

`loom rotate-tunnel <ssot> <A> <B> -reason <理由>` 打印出替换后的那一行,
由人粘回 SSOT。这避开两件麻烦:

- **自动改写会毁掉 SSOT 里的注释**(那是 YAML 往返的老问题)
- **"系统自己改 SSOT"会给它添第二个写入者**,而单一写入者是 dry-run diff、
  漂移检测、回滚三个产物的地基。Agent 至今只改运行时 selector,从不碰 SSOT

`-reason` 必填,打印的那一行带日期。因为**换端口既是修复也是诊断**:
"这条流被标记了"和"某处状态坏了"两个假设对换端口的反应完全一样,
判据是能撑多久 —— 下次翻到这一行的人需要知道这个实验在等什么答案。

### 校验器钉住的关系

`listen_port` 不能出现在 `retired_ports` 里,退役端口要在保留段内。
第一条尤其重要:两者矛盾时没有任何别的东西会发现它。

### 顺带修掉一个会误导人的注释

`deploy/ssot.yaml` 写着"从保留范围 61610-61699 里挑",而
`model.TunnelPortMin/Max` 是 **61617-61799**,防火墙放行的也是这一段 ——
demo-d 那两条隧道(61711、61763)本来就在注释说的范围之外。手工挑端口的人
会被它带偏。

> 退役端口**不进渲染产物**:它是运维历史,不是配置。有验证。

### D69 · 版本坐标:commit 靠 Go 的 VCS 戳,不靠构建脚本

**日期** 2026-08-24 · **状态** 生效 · **相关** §15.4、[D62](#d62--整份回滚源头跟着成品一起回去)

现场同时存在四个互不相干的标识,排障时反复绕晕:

| | 是什么 | 从哪儿看 |
|---|---|---|
| `commit` | 源码是哪一版 | `loom version` |
| `binary` | 分发的是哪一份(sha256,§15.4) | `loom version` |
| `snapshot` | 配置是哪一版 | `loom report` |
| `ssot` | 源头是哪一版 | `loom snapshots` |

以前 `selfcheck` 只印一个写死的 `buildTag = "dev"`,于是"远端跑的是哪个
commit"根本答不上来,只能报一串二进制哈希 —— 而哈希对不回 git。
**文档里把二进制 sha 写成 "HEAD",毛病就是这么来的。**

**决定:commit 由 `debug.ReadBuildInfo()` 的 VCS 戳读取,不用 `-ldflags`。**

理由是**别让正确性依赖人记得做某件事**。ldflags 方案要求每次构建都带上
一串参数,而 CLAUDE.md 里写的构建命令是 `go build ./...` —— 两者一旦不一致,
漏掉的那次构建就成了认不出自己的二进制,而且**没有任何信号**。Go 从 1.18
起对 `go build` 自动戳入 `vcs.revision`,普通构建就有。`version.Tag` 仍留着,
但它是标签不是身份。

**顺带白拿一个更要紧的东西:`vcs.modified`。** 脏工作区构建出来的二进制
对不上任何 commit,出了问题没法用 git 复现。现在 `loom version`、
`loom selfcheck`、`loom status` 都会把它报出来(D3 的"不许静默降级"在版本上的落点)。

`Binary` 是**磁盘上那个文件**的哈希,不一定等于正在跑的镜像 —— 升级会
原地换掉它,这个坑踩过(见 history/)。所以两个都要:commit 回答"现在在跑
什么",binary 回答"下次重启会变成什么"。

**为什么 `loom status` 要单独报 commit 一致性。** 快照一致不等于版本一致,
而**旧二进制配新配置**正是发布器崩掉的那类故障 —— `services` 字段一次,
`retired_ports` 字段一次(D68 加的那个)。SSOT 用 `KnownFields(true)` 严格
解码,对"控制面比数据面旧"零容忍。只看快照的表对这类故障完全是盲的。

> **推论,写在这里免得再踩第三次:改 SSOT schema 要先升级发布器,再改 SSOT。**
> 顺序反了,发布器会拒绝解析,而它的进程仍然是 `active` —— 看起来活着,
> 实际已经发不出去。

### D70 · 当前状态与历史分开:一页快照 + 一堆归档

**日期** 2026-08-24 · **状态** 生效

`docs/status.md` 长到 1361 行、88 个小节,因为它同时承担两件事:**当前是
什么样**,和**发生过什么**。后者只增不减,于是前者被埋掉了。

后果不是"文档有点长",而是**每次都要从三天的流水账里现推当前状态,
推出来还互相矛盾**。同一份文档里能同时读到 4 台机器和 5 台机器。

**决定:拆成 `docs/status/current.md`(唯一的"现在",改它不追加)
+ `docs/status/history/`(一件事一个文件,写完不再改)。**

`current.md` **必须短到能整个读完** —— 读不完的当前状态等于没有当前状态。

这个目录含真实地址,继续不进版本库。但**规矩进** —— 写法写在 CLAUDE.md 里。
只忽略内容,不忽略规矩:否则下一个会话又会把两者混回一份追加文档。

> 与本文档的区别:decisions.md 是**只追加不删改**的,因为被推翻的决定和
> 它当时的理由同样有价值。`current.md` 恰恰相反 —— 它是快照,过期内容
> 没有价值,只有干扰。两种文档,两种规矩。

### D71 · 两种"没版本"性质不同,不能都报成告警

**日期** 2026-08-24 · **状态** 生效 · **相关** [D69](#d69--版本坐标commit-靠-go-的-vcs-戳不靠构建脚本)、[D67](#d67--同一个测量两种含义target-是数据uplink-才是告警)

`loom status` 的版本表第一版只拿到"够得到的"节点名单,于是靠转述听到的
demo-b / demo-c 从来没进过表 —— 既没核对,也没被列进没问到的。5 台里只覆盖
3 台,显示出来却是"都一致"。

`snapshotSpread` 踩过同一个坑并已修好,写新表时没沿用教训。

**为什么版本表不能照抄快照表的修法。** 快照表的修法是把转述来的观测折进去,
因为**快照 id 在观测里带着,转述过来仍是事实**。版本坐标不在,而且更根本的是
**身份不该听别人转述** —— B 说"C 跑的是某个 commit",这句话的可信度取决于 B,
而排障时恰恰不能假设 B 可信。所以够不到的节点,版本就是核不了。

**决定:核不了要印出来,但分成两类,只有一类算告警。**

| 情况 | 含义 | 处理 |
|---|---|---|
| 够得到却没报版本 | 它跑的是不带版本坐标的旧二进制 | ⚠️ 计入 bad |
| 够不到、只能靠转述 | 拓扑事实 | 印出来,**不计入 bad** |

第二类刻意不报警。demo-b / demo-c 在这张拓扑里**永远**够不到,报成告警就是
每次都响的常驻误报 —— 正是 [D55](#d55--不是所有变化都是问题)–D67 花力气清掉的那类噪音。
但空白也不能不说:一台跑着老二进制、又恰好够不到的机器,会被表的沉默
算成同意。

**顺带:分母要印。** "问到的 3/5 一致"和"问到的 5/5 一致"看起来必须不一样。
只写"都一致"时,n=1 和 n=5 的说服力天差地别,而显示完全相同。

### D72 · 发布器要自报死活,判据是"上次成功之后又失败"

**日期** 2026-08-25 · **状态** 生效 · **相关** [D69](#d69--版本坐标commit-靠-go-的-vcs-戳不靠构建脚本)、[D67](#d67--同一个测量两种含义target-是数据uplink-才是告警)

2026-08-24 发布器连续 **2 小时 17 分**发不出任何东西,而 `systemctl status`
全程 `active (running)`。**进程活着不等于功能活着**,而当时没有任何地方
能区分这两件事 —— 要发现它得去翻 journal,而没人会去翻一个显示正常的
服务的日志。

版本坐标也覆盖不到它:`loom report` 报的是**跑 report 那个二进制**的 commit,
发布器是另一个进程,可能还持着被换掉的旧 inode。

**决定:发布器每轮把自己写进 `/var/lib/loom/publisher.json`,`loom status` 读它。**

**判据是 `LastErrorAt > LastSuccess`,不是"距上次成功多久"。**

这条最关键。发布器只在 SSOT 变了(或分发点分叉)时才发布 —— 一周不改 SSOT
就一周不发,那完全正常。拿时长当告警会天天误报,而误报的面板等于没有面板
(D64–D67 刚清掉的就是这个)。昨天那次故障的真正形状是**19:43 成功过一次,
之后每一次都失败**,而这个形状在 SSOT 不变时不会响。

两条配套约束:

1. **LastError 成功后不清空。** 清了的话一次成功就把"刚才卡了两小时"抹掉,
   而那正是要留住的信息。恢复之后改成"曾经失败过……之后已恢复",不报警。
2. **心跳(UpdatedAt)与 LastSuccess 分开。** 昨天心跳一直正常,停住的是
   LastSuccess —— 合并成一个字段就什么都看不出来了。

状态文件写不出去不拦发布(发布是主职),但要说一次 —— 否则"状态一直是旧的"
就成了新的静默故障。

### D73 · 版本表要用"真的答上来了",不是"拓扑上够得到"(修正 [D71](#d71--两种没版本性质不同不能都报成告警))

**日期** 2026-08-25 · **状态** 生效

D71 把节点分成"够得到"和"够不到"两类,但**"够得到"取自 SSOT 拓扑,
不是取自成功拉取**。于是一台超时的机器会先被报"❌ 拉不到",再被版本表
指认成"跑的是旧二进制",而且 `bad` 加两次 —— 同一件事报两遍,还报成两回事。

**修正:分三类,判据取自真实答复集。**

| 情况 | 含义 | 处理 |
|---|---|---|
| 答上来了但没版本 | 确实是旧二进制 | ⚠️ 计入 bad |
| 根本没答上来 | 超时/断线,上面已报过 | **这里不再提** |
| 够不到、只能转述 | 拓扑事实 | 印出来,不计 bad |

**分母改取 SSOT 的节点数。** 一台彻底失联的机器(没隧道又没人转述)如果不
进分母就会从统计里整个消失,而消失的样子和一切正常一模一样。

判断逻辑拆成纯函数 `versionFindings` 并钉了 7 个测试 —— 这类坑只有喂进
"拉不到的节点"才看得出来,靠肉眼看代码看不出来(第一版就是这么漏的)。

### D75 · 追溯不回 git 的二进制,默认不许发到全网

**日期** 2026-08-25 · **状态** 生效 · **相关** [D69](#d69--版本坐标commit-靠-go-的-vcs-戳不靠构建脚本)、[D31](#d31--备份加不加密必须显式选)

D69 让脏构建**能被看见**,但只是打印警告 —— `selfcheck` 印完警告仍然返回
成功,发布器也照发不误。于是"看得见"和"拦得住"之间还差一步:一个对不上
任何 commit 的二进制仍然可以一次性铺满 5 台机器,而出了问题没法用 git 复现。

**决定:发布器在分发前读那个二进制文件的构建信息,认不出 commit 或构建自
脏工作区就拒发,除非显式 `-allow-dirty`。**

三个要点:

1. **读的是文件,不是本进程。** `version.OfFile` 用 `debug/buildinfo.ReadFile`,
   不执行它。钉住时发的是历史二进制,它的 commit 只有那个文件自己知道 ——
   拿发布器自己的 `Self()` 去判会判错对象。
2. **拒发也要记进 Health(D72)。** 只打日志的话,这本身就变成一个新的
   "systemd 说 active 但发不出去"的静默故障 —— 正是 D72 要根治的形状。
3. **留出口,不硬堵死。** 救火时确实可能要发一个还没提交的修复。但要
   **显式选** —— 与 [D31](#d31--备份加不加密必须显式选)"加不加密必须显式选"
   同一个规矩:风险选项不能默认帮人做主,也不能默认拦死。

`OfFile` 读不出构建信息时**报错,不返回空坐标** —— 空坐标会让闸门把不可
追溯的二进制当成合格的放过去,那比没有闸门更糟。

### D77 · 改代码要显式 `loom release`,改 SSOT 才自动发布

**日期** 2026-08-25 · **状态** 生效 · **相关** [D75](#d75--追溯不回-git-的二进制默认不许发到全网)、[D60](#d60--二进制回滚靠钉住不靠重新编译)

发布器每轮重新读 `-binary` 指的那个文件,sha 一变就发。于是**任何一次
`go build` 都武装了一次全网升级** —— 改一行状态页面的措辞,5 台机器各下载
12.5 MB 并重启服务。而人在调试时会编译很多次:2026-08-24 一小时编了四次,
把分发点撑到 261 MB,D59 那个超时 bug 就是这么撞出来的。

**决定:两种改动走两条路。**

| 改了什么 | 怎么生效 | 为什么 |
|---|---|---|
| SSOT | 发布器自动发 | 它本来就是声明,改了就该生效 |
| 代码 | 必须 `loom release` | **编译只是编译,不是决定** |

优先级是 **钉住 > 放行 > 什么都不发**。钉住是救火状态,不该被一次 release
悄悄解开;而都没有时**不回落到本机二进制** —— 那正是要根治的东西。

三道检查全在**人按下回车的这一刻**做完,不留给发布器半夜静默失败:
追溯得回 git 吗(D75)、这台机器上 selfcheck 过得了吗(§15.4)、理由填了吗。

**二进制随记录一起存下来,按内容寻址放在 `bin/<sha256>`。** 只记 sha 不够 ——
记完之后 `/usr/local/bin/loom` 还会变,那样发布器拿到的就不是被批准的
那一份了。

> 副作用是本机攒下了历史二进制,而**回滚因此不用回网络取**。这正是
> "快速回滚"缺的那块,顺手就有了。

`loom release -clear` 停发二进制但配置照发,**且不删本地副本** —— 那些是
回滚缓存。

## 迁移:装上之后要手工放行一次

新发布器默认 `-release-dir deploy/released`,而那里还没有记录,所以它会
**只发配置,不发二进制**,并且每次启动说一句。

这是安全的:快照不带 `binaries` 字段时,节点的 `upgradeBinary` 走
"快照没带这个平台的二进制,不是错误"那条路,保持现有版本不动。

装上之后跑一次 `loom release -reason <理由>` 即可恢复分发。

### D78 · rollout 是显式状态机,但先只观察不接管

**日期** 2026-08-25 · **状态** 生效(观察阶段) · **相关** [D77](#d77--改代码要显式-loom-release改-ssot-才自动发布)、[D72](#d72--发布器要自报死活判据是上次成功之后又失败)

阶段本来就存在:验签 → 换二进制 → 装配置 → 验证。但它们只是 `pull` 里的
一串注释 —— **没有名字、不落盘、崩了就丢**。两个后果:

1. **崩在半路等于失忆。** 装到一半断电,下一轮从头开始,而"上一次死在
   哪一步"没人知道。
2. **"等下一个定时器"被当成了续跑机制。** 换完二进制主动 `return`,靠
   10 分钟后的下一次 pull 接着装配置。安全原则(旧程序绝不处理新 schema)
   是对的,但拿定时器当 continuation —— 于是二进制+配置一起变要 20 分钟。

新增 `internal/rollout`:`staging / activating / verifying / verified / decommissioned / failed`,
落在 `/var/lib/loom/rollout.json`,进 `report.Status`,`loom status` 汇总。

**和 `applied` 是一对**:applied 说现在装着哪个(结果),rollout 说正在往
哪走、走到哪步(过程)。一台卡在 activating 的机器 applied 仍是旧值 ——
只看快照表会以为它"还没轮到",实际上它可能已经半装着躺了半小时。

两条判据上的讲究:

- **只有 Verified 推进 LastGood。** 装上了不算,`applied` 写下来了才算 ——
  否则回退目标会指向一份装得上但跑不起来的快照。
- **Decommissioned 是成功终态但不推进 LastGood。** 它证明签名停机指令已
  完整收敛，不代表那份配置可以拿来回退。
- **卡住看的是"进入当前阶段多久",不是整次 rollout 多久。** 一次正常的
  二进制升级本来就要走好几步,总时长长不说明问题。

## 为什么先不接管

**这是全系统最关键的路径,而上一次动它的人刚把它停了 2 小时 17 分。**

所以这一版只写记录,不改任何控制流。先跑几轮真实发布,确认记下来的阶段
和现实吻合,再让它接管。**这样切换那一刻不是"新代码第一次上真机"。**

这段观察期最初把 `stuckLimit` 设为 30 分钟 —— 因为两段式升级本来就要等
下一个定时器,一台机器当时会合法地在 activating 待十几分钟。D80 换掉
"等定时器"并取得真机数据后,阈值已经降为 **10 分钟**。这里保留原始判据的
来由,不再把历史值写成当前值。

## 当时的接下来（现状见 D80）

1. 换完二进制**起子进程续跑**同一个 release,而不是 `return` 等定时器。
   子进程而不是 `exec`:exec 把唯一还知道怎么撤销的进程销毁了,而
   `loom release` 已经在本地攒下历史二进制(D77),回退不用回网络取。
2. 轮询降到 30–60 秒,同时加 **canary**:一台先行验证通过,其余的才动。
   只提速不加灰度等于优化"全网坏掉的速度"。

截至 D85，短轮询和二进制 continuation 已实现，**真实 canary 仍未实现**：
5 台节点各自轮询同一个全局 `current.json`，没有“一台验证成功后才推进其余节点”
的批次闸门。人工先看一台只能算上线观察，不能算灰度发布能力。

### D79 · 放行构建产物,不放行"正在跑的那份"

**日期** 2026-08-25 · **状态** 生效 · **相关** [D77](#d77--改代码要显式-loom-release改-ssot-才自动发布)

`loom release` 的 `-binary` 原本默认 `/usr/local/bin/loom`。那是个陷阱,
而且**实测输过一次**。

**中控同时也是一个被管理的节点。** 它自己的 `loom-pull` 每 10 分钟把
`/usr/local/bin/loom` 收敛到**已发布快照里的那份**。于是"手工装 → release"
这个流程有竞态,窗口就是一个 pull 周期:

```
11:01:22  pull:二进制要换 9b45f30b88f3 → e90d0efe56c9   ← 把手工装的退回去了
11:03     loom release                                  ← 记下的是被退回的旧版
```

慢了两分钟,放行记录就指向了上一个版本,而命令本身**报告成功**。

**决定:`-binary` 默认改成构建产物 `deploy/staging/loom`。** 那个路径不归
pull 管,不会被收敛掉。显式指向 `/usr/local/bin/loom` 时打印警告说明原因。

## 顺带简化掉一步

想通这件事之后,发布流程比原先短了:

```bash
go build -o deploy/staging/loom ./cmd/loom
loom release -reason "..."
```

**不用手工装到 `/usr/local/bin`,也不用重启发布器。** 中控自己的 pull 会
把新二进制装上去,并重启跑着旧 inode 的服务 —— 它本来就在做这件事。

原先那两步是我把中控当成"不受管的机器"想出来的,而它不是。

### D80 · 换完二进制起子进程续跑,不等下一个定时器

**日期** 2026-08-25 · **状态** 生效 · **相关** [D78](#d78--rollout-是显式状态机但先只观察不接管)、[D46](#d46--先装二进制后装配置)

D78 的观察阶段拿到了要的数字:**demo-d 卡在 `activating` 10 分 11 秒**,
而那 10 分钟里它是"新二进制 + 旧配置"。

原因是 `pull` 换完二进制主动 `return`,把装配置留给 10 分钟后的下一次
定时器。安全原则没错 —— 继续用**当前进程里的旧代码**去装新配置,正是
要避免的那种配对(D46)。错的是实现:**拿定时器当 continuation**。

**决定:换完二进制立刻起一个子进程,用刚装好的那个二进制跑完这一轮。**

## 为什么是子进程,不是 exec

exec 把当前进程替换掉,而当前进程是唯一还知道"旧二进制在 `.prev`、
出事了能退回去"的东西。子进程留住了这个能力,代价只是一个进程。

## fork 炸弹那道闸

子进程看到二进制哈希已经对上,不会再换,所以深度天然是 1。
**但"天然"是个假设**,而这个假设错了的代价是 fork 炸弹。所以用环境变量
`LOOM_PULL_CONTINUATION` 显式挡一道,并钉了测试 —— 包括"标记确实传给了
子进程",因为传不下去的话那道闸形同虚设。

## 顺带:轮询 10min → 45s

原来的理由是"配置变更是人发起的,太频繁只是刷日志"。那个理由**把成本
估高了、把代价估低了**:

| | |
|---|---|
| 成本 | 一次无变化的 pull 实测约 1 秒,几个小 JSON。二进制哈希对上就不下载,没有 12.5 MB 那回事。5 台 × 45 秒 ≈ 7 次/分钟 |
| 代价 | 全网收敛要等一个周期 —— 实测 10 分 11 秒 |

45 秒 + 15 秒抖动(**抖动必须小于周期**,否则它不是错峰而是让周期失去
意义)。加上发布器的 30 秒:

- 纯配置变更:端到端 90 秒以内
- 二进制 + 配置:同样一个周期,因为续跑不再等第二次定时器

后续观察已经把 `stuckLimit` 从 30 分钟降到 **10 分钟**。正常 continuation
应在同一轮完成；10 分钟仍远高于正常路径,但足以把真正停住与瞬时抖动分开。

### D81 · 身份签名之后,转述来的节点也能核对版本(收窄 [D73](#d73--版本表要用真的答上来了不是拓扑上够得到修正-d71))

**日期** 2026-08-25 · **状态** 生效 · **相关** [D71](#d71--两种没版本性质不同不能都报成告警)、§13.3

D71/D73 的结论是"版本核不了转述来的节点",理由是**身份不该听别人转述**:
"C 跑的是 commit X"如果只由 B 说,排障时恰恰不能假设 B 可信 —— 出问题的
往往就是链路上某一环。

代价是 `loom status` 长期只能报 `3/5 台核对过`,demo-b / demo-c 永远空白。
而它们够不到中控是**拓扑事实**,不会自己好转。

**决定:节点给自己的身份陈述签名,转述照旧走原路。**

签了名之后转述的是密文不是信任:改一个字验不过,伪造要那台机器的私钥。
于是"够不够得到"和"能不能核对"解耦了。

## 用现成的 PKI,不引入新密钥

每台机器早就有 `/etc/loom/tls/node.key` 和 `node.crt`(CN 是
`<节点>.node.internal`,内部 CA 签发)。新密钥意味着新的分发路径和新的
轮换路径,而那是这个系统里最贵的东西 —— D74 刚因为备份漏了一把钥匙
差点变成灾难。

## 三道检查,少一道就是摆设

1. 证书链得到 CA —— 否则谁都能自签
2. **证书的名字要和 Claim.Node 对上** —— 否则 demo-a 可以拿自己的合法
   私钥签一条"demo-b 跑的是 commit X",而那正是转述,正是要根治的东西
3. 签名覆盖固定字节

第 2 条是整个机制的关键,单独钉了测试。签名覆盖的字节**不走 JSON**:
字段顺序、空白、转义都可能因库版本而变,而签名是针对字节的 ——
换个 Go 版本就验不过的签名不如没有。

## 验过了才算,验不过和没签名同等对待

`Attest` 为空**不等于可信**(中控只有 ca.crt,签不了)。验不过则是**故障**
要报出来 —— 要么转述内容被改过,要么证书过期了。但两种情况调用方要做的
事一样(去 ssh 那台机器),所以在版本表里同归"没核对过",不再细分。

## 用真钥匙验过

不只跑了合成 CA 的单测:拿 demo-b 的**真私钥**用 openssl 签,在中控用**真
ca.crt** 验,通过;把同一份签名改说成 demo-c 的,被真证书拦下:

```
证书是 "demo-b.node.internal" 的,却在替 "demo-c" 发言
```

### D82 · 删除收敛照 dpkg 的文件清单模型,不自己发明

**日期** 2026-08-26 · **状态** 生效 · **相关** [D33](#d33--期望状态不只是文件内容)、§14.2

`BuildPlan` 只遍历这次渲染出来的文件,**没有任何删除逻辑**。于是 SSOT 里
删掉一条隧道之后:渲染输出里没有 `wg-demo-a.conf` 了,但节点上的文件和
`wg-quick@wg-demo-a` 服务**都还在跑**。

以为删了、实际还连着 —— 这是安全问题,不只是洁癖。

## 这是个有名字的老问题,不该当新设计做

| 现成的 | 怎么做的 |
|---|---|
| **dpkg** | 包的文件清单存在机器上(`<pkg>.list`),卸载时按清单删 |
| **Puppet** | `resources { purge => true }`:声明之外的一律清掉 |
| **Nix** | 由构造保证:新 generation 里没有的就是没有 |

节点上早就有一份自检清单(`/etc/loom/report/manifest.json`,记着 Loom
装过哪些绝对路径)。**差集就是答案**:旧清单 ∖ 新计划 = 该删的。

照 dpkg 的模型抄,而不是发明一套,好处是边界语义有地方可查 ——
以后遇到"被人手改过的文件删不删"这类问题,知道去看 conffile 是怎么定的。

## 三条边界,都是 dpkg 已经想清楚的

1. **只删自己装过的。** 清单里没有的文件一律不碰。
2. **清单确实不存在 = 什么都不删。** 这是第一次安装的合法状态；但清单
   已存在却损坏、不可读或校验失败必须 fail closed。把“无法证明不存在”也
   当成 absent，会在权限漂移或半写文件时悄悄放弃删除边界。
3. **先停服务再删文件。** 反过来的话 `wg-quick stop` 找不到配置,接口会
   留在内核里 —— 那正是"以为删了其实还连着"的形状,只是换了个地方发生。

## 删除也是一种变更

两个推论,漏掉任何一个这个功能就是半成品:

- 只有删除、没有文件改动时,**不能走"无变化"早退** —— 否则该删的永远删不掉
- 删掉的文件要存进 `$PREV`,**回滚时放回去** —— 否则一次失败的部署会
  永久毁掉一条还在用的隧道配置

## 反推服务,不查表

要删的文件**已经不在这次的渲染输出里**,`BuildPlan` 那套
bundlePath → 服务的映射对它无能为力。所以 `UnitFor` 从绝对路径反推:
`/etc/wireguard/<x>.conf` → `wg-quick@<x>`,`/etc/systemd/system/<x>.service`
→ `<x>.service`。认不出来的返回空串,那只是普通配置文件,删掉即可。

### D83 · 拓扑分四层，候选存在与实时健康不能互相冒充

**日期** 2026-08-26 · **状态** 生效 · **相关** §16.4、[D81](#d81--身份签名之后转述来的节点也能核对版本收窄-d73)

`demo-d`、`demo-b`、`demo-c` 都是拓扑节点。生产没有三者之间的常驻 WireGuard
三角形，但 SSOT 枚举出的业务候选明确包含 `demo-d → demo-b`、`demo-d → demo-c`、
`demo-d → demo-b → demo-c` 与 `demo-d → demo-c → demo-b`。**没有常驻 WG 直边不等于
没有路径。**

界面因此分开显示四层：SSOT 承载边、完整 `RouteCandidate`、实时观测、Agent
从 selector 实读的当前选择。承载边不能由一条陌生 Observation 发明；候选边
只能标“未核验”，不能因为存在于 SSOT 就涂绿。

反过来也一样：一条边变绿是运行时事实，必须有真实样本，而且转述来的
`Edges/Targets` 必须由观测节点自己签名绑定。D81 的 v2 只签版本、Applied、
rollout 与 selector，relay 仍能改外层测量；v3 在 Claim 中加入测量 payload 的
SHA-256，采样完成后再签。legacy/unsigned 测量仍可作为未知信息存在，但既不能
把 WG 边抬成健康，也不能进入 Agent 的不可达剪枝改变 selector。

### D84 · 部署是可恢复事务，不是按顺序跑完一串命令

**日期** 2026-08-26 · **状态** 生效 · **相关** [D80](#d80--换完二进制起子进程续跑不等下一个定时器)、[D82](#d82--删除收敛照-dpkg-的文件清单模型不自己发明)、§14.2

同一台节点上的 timer、人工 `pull/apply` 与二进制 continuation 可能同时到达。
分别给某个命令加锁仍会留下交叉写：一个进程正在替换配置，另一个正写
`applied` 或 `.prev`。**所有激活路径共用 `/var/lib/loom/deploy.lock`；网络
预取在锁外，实际文件、服务、rollout 与 applied 状态只在锁内改变。**

锁只解决并发，不解决进程被杀。激活前写入持久事务状态，记录已动文件和服务
原态；成功提交后才清除。下一轮若看到未提交事务，先完整回滚，回滚不完整则
以专用错误退出，不能在半旧半新状态上继续覆盖。状态文件和 `applied` 都采用
临时文件、`fsync`、rename 与父目录同步，不能把半截 JSON 当成“没有状态”。

验证也按事实而不是机械口令：`NRestarts` 看稳定窗口内的增量，不要求一生累计
为零；unit 变化要重启对应常驻服务；配置无变化仍修复应为 active 的服务；下载
同时有停滞超时和按字节数计算的总时限，慢速滴流不能永久占住 pull。下线时先
停并核验所有其他 Loom 单元，最后才停 pull timer；任何一步失败都保留重试入口，
不提前写“已下线”。

服务存在性是 systemd 已加载单元与 unit-file 清单的并集，不能用
“unit 文件没了”推导“旧 inode 进程没了”。下线发现也取已安装清单、
WireGuard 文件与 systemd 已加载/已安装单元的并集。任一查询不确定都
fail closed；`LoadState=not-found` 也要独立核对 active/enabled，不能跳过暗连收敛。

### D85 · 发布的原子单位包含输入时刻、放行记录与可取回字节

**日期** 2026-08-26 · **状态** 生效 · **相关** [D77](#d77--改代码要显式-loom-release改-ssot-才自动发布)、§14.2.3、§15.4

发布器过去只保证“一轮内部按顺序执行”，却没保证两轮的先后：旧轮先读取 SSOT
后阻塞，新轮先发布，旧轮再醒来就会把分发点倒回去。**所有发布入口共用发布锁，
并在取得锁后重新读取 SSOT、pin 与 release；锁前读到的内容不能参与提交。**

二进制仍必须由 `loom release` 显式批准。放行记录绑定 commit、字节哈希、大小、
自检结果、原因和时间；pin 的签名 manifest 必须与请求的 snapshot id、放行记录
声明的 snapshot 完全一致。手工 `publish` 与守护发布器使用同一套 pin/release
目录和判据，不能因入口不同悄悄丢掉已批准二进制。
写 pin/release 和 rollback 也使用同一把锁；rollback 先写新 pin 再写 SSOT，
后者失败时两者不匹配会继续拦住发布，不能失败开放地发出半份回滚。
撤销 pin/release 在删除后同步父目录，掉电不得让已撤销授权复活。

“发布成功”不再只表示本地文件写过：推送前先完成不可变归档，归档或历史记录
失败都让本轮失败；推送后从 HTTP 分发视角逐项读取 current、manifest、签名、
节点包和二进制 blob，边读边核对大小与 SHA-256。目标路径必须是规范化的非根
绝对目录，拒绝 `/`、`//` 与 `..` 等价写法；SSH 只修改本轮明确创建的条目，绝不
对整个目标树递归 `chmod`。相同 runtime tree 的语义 no-op 可以保留既有签名
快照，但目标缺文件时仍要原子修复，不能把“ID 没变”当成“分发点没坏”。

语义 no-op 只在旧 snapshot 对应的 SSOT 不可变存档仍存在时才能复用，
否则必须生成一份可回滚的新 snapshot。JSONL 历史若留下掉电造成的末尾
半行，先截至上一条完整记录再追加并读回确认。本地与 SSH 目标都拒绝
symlink 路径逃逸，采用不可预测临时名 + rename；小文件读取有大小上限，
SSH 命令还有按操作类型设定的总时限，恶意远端不能永久占住发布锁。

### D86 · 组件版本先闭合观测，再增加自动升级

**日期** 2026-08-27 · **状态** 生效 · **相关** §15.4、[D81](#d81--身份签名之后转述来的节点也能核对版本收窄-d73)

SSOT 里有 `components` 只证明“希望运行哪个版本”，不能证明节点已经安装，
更不能证明 Loom 会替外部包升级。此前模型注释和目标设计把三件事揉成一句
“进入同一收敛回路”，实现却只管理 Loom 自身二进制；这是典型的假生效。

当前先闭合最小可信链：renderer 只给实际运行该 workload 的节点下发期望版本；
report 对 sing-box 同时核 systemd MainPID 对应的运行 inode 与 unit `ExecStart`
明确指定的 `/usr/local/bin/sing-box` 磁盘文件（不能从 PATH 误认另一份），
对 WireGuard 的既有签名线名保持 `wireguard`（滚动兼容不能在 canonical v5 内
改名），语义明确是 `wireguard-tools` 包；固定执行 `/usr/bin/wg`，同时核对
`dpkg-query` 安装状态/包版本、关键配套文件归属和 `dpkg --verify`，数据面另由
握手证明。探测并行、限时、限制输出，并用短缓存 singleflight；缺失、读失败和不一致都使节点健康失败。
结果与 Agent 候选健康一样由节点签名，relay 只能转述，不能
把 mismatch 改绿。Agent 的 `component_version` 明确定义为状态线协议版本，
运行中二进制身份仍由 commit、binary SHA-256 与快照坐标证明。

外部组件的下载、校验、A/B 或包级回滚尚未实现，所以这一阶段只检测、不擅自
修复。没有 workload 启用真值的 Tailscale 版本直接拒绝；声明但尚未实现的
constraints、非 fail-closed fallback、凭据 expires_at 和多代秘密层也同样
fail closed。后续实现自动升级时，必须与真实 canary 和配置回滚一起进入事务，
不能先加一个“下载安装”按钮再补安全边界。

新节点声明 bootstrap 有一个刻意收窄的例外：SSH host key 已由操作者带外确认、
受信 preflight 已证明内核支持和 root/免密 sudo、且 `/usr/bin/wg` 缺失时，固定
脚本可通过受支持的系统包管理器安装 `wireguard-tools` 并立即复检。它不升级已安装
版本、不作用于现有 fleet，也不声称具备 canary 或包级回滚；失败时 SSOT 不变。

### D87 · Attestation 扩展必须两阶段启用，兼容不是永久降级口

**日期** 2026-08-27 · **状态** 生效 · **相关** [D81](#d81--身份签名之后转述来的节点也能核对版本收窄-d73)、[D86](#d86--组件版本先闭合观测再增加自动升级)

新 writer 直接把 v3 换成 v5 会让旧 reader 验签失败；在 gossip 拓扑里这不是
短暂少一个字段，而是旧节点拒收新节点、`/status` 503 和转述分区。因此阶段 A
由 writer 同时发旧 reader 能验的 v3 与完整 v5，新 reader 两份都验；旧 reader
忽略 `attest_extended`，滚动窗口仍保持连通。

双签不能永久作为结束态：relay 可以剥掉扩展签名和新外层字段，只留下仍合法的
v3，把组件漂移或候选全失败降级成“没有数据”。所以 SSOT 增加
`defaults.attestation_min_version`。阶段 A 保持 0；确认所有节点 reader 已升级后，
阶段 B 单独改成 5。此后 report、CLI、UI、gossip 与 Agent 剪枝共同拒绝没有 v5
的观测，剥离变成明确故障。不能在阶段 A 首次发新二进制时就设 5，也不能升级
完成后永远忘记收口。

当前生产已经完成 phase B，`attestation_min_version=5`。新 producer 直接把 canonical
v5 放入主 `attest`，不再复制迁移期的 legacy + `attest_extended` 双签写法。

“确认”必须是可执行闸门，不靠逐页目测：每台 report 节点（包括没有入站角色的
接入节点）都必须有自己的节点证书；CLI 从本机 `127.0.0.1:61802/status` 读取与
远端同源的后台 Observation。只有
`loom status --require-attestation=5 <ssot>` 显示全部适用节点 ready 且退出码为 0，才允许切换。

### D88 · 用签名 deployment envelope 同时闭合反重放与真实 canary

**日期** 2026-08-27 · **状态** 阶段一已实现、待部署；自动 canary controller 待实现 · **相关** [D85](#d85--发布的原子单位包含输入时刻放行记录与可取回字节)、§14.2.2、§15.4

签名 manifest 只能证明“这份快照由平台签过”，不能证明“平台现在仍授权部署
这份快照”。修复前的 `current.json` 未签名、旧快照永久保留且节点没有单调代次，因此被
攻陷的分发点可以把所有节点重放到任意真实旧快照；当前全网共用一个指针，也无法
做到一台验证后才推进其余节点。

两件事使用同一个最小控制对象解决，而不是分别增加裸 per-node 指针。阶段一的
`current.json` 保留旧 reader 已认识的顶层 `snapshot` / `published_at`，并增加：

- `schema`、单调 `generation` 与 Ed25519 域分隔签名；
- 可选的 `assignments: node → snapshot`。空映射表示全局目标；映射一旦非空，
  新 reader 找不到自己的节点就失败关闭，不静默回落到全局值；
- 节点本地 `/var/lib/loom/release-floor.json`，记录最高已接受 generation、签名
  payload 哈希与本节点实际选择的 snapshot。同代异内容、低代重放，以及 floor
  激活后的 unsigned current 全部拒绝；合法回滚必须签发更高 generation 指回旧快照。

发布端把精确签名 envelope 耐久保存在
`deploy/ssot-history/release-authority.json`，并用 `release-authority.enabled` 防止文件
丢失后悄悄从 generation 1 重开。同一逻辑目标的失败重试复用完全相同的代次、时间
和签名；目标变化才递增。authority 在 Push 前落稳；分发点出现有效高代或同代异
payload 时拒绝覆盖，低代、legacy 或无效签名才按本地 authority 修复。节点在取得并
验签 envelope 后、下载 manifest/blob 前短暂持有 deploy.lock 落稳 floor，因此分发点
不能靠“先给高代但扣住正文，再给可下载的低代”绕过记忆。

二进制回退也进入同一边界：`release`、`pin`、`rollback` 和节点激活候选都要求
`selfcheck -require signed-current-v1`，floor 启用后不能再装回会忘记它的旧 Agent。
首次分配 generation 1 前，publisher 还会从稳定候选重新执行同一能力检查，并要求
该 Agent 就在 generation 1 快照中；旧/空 release 不会先写 authority。旧 Agent 会
忽略 envelope 的新增字段，便于滚动获得新 reader；新 Agent 只对 schema=0 的旧配置
临时禁用缺少 CA 的观测剪枝，新 renderer 明确写 schema=1，漏 CA 必须失败关闭。

continuation 也有单独的提交屏障：子进程若看见已验签高代，会先把结构化状态推进到
不可恢复旧 reader 的阶段，再持继承 deploy.lock 落稳 floor，最后才核对父进程目标
快照。这样即使发布恰好在续跑中换代，也不会留下“高 floor + 已恢复旧 Agent”。

阶段一只闭合“首次可信接受之后”的重放，不能凭空给一台全新/丢失 floor 的机器
证明全网当前最高代次。generation 1 是一次性自动迁移锚点；无 floor 首见更高代
必须用受信通道带来的 authority 文件和 `pull -expected-current` 精确核对，不能把
一般 first-seen 说成 freshness。控制端 authority 与分发点若被协调恢复到同一份
自洽旧备份，本机文件仍无法发现；恢复前必须与节点 floor 对账，外部单调 witness
仍是后续加固项。阶段二仍未实现：publisher 目前签发空 assignments 的全局目标；
节点视角 verifier 已会核完 assignment 指向的所有不可变表面，但 controller 仍须
在收到节点签名的配置/服务稳定、承载与代表路径验证后签发更高代扩大批次。因此
“上线观察”仍不是真实 canary，四级业务数据面确认也仍是发布门的缺口。

### D90 · 流量历史只由可信相邻 counter 样本推导

**日期** 2026-08-28 · **状态** 仓库已实现、待部署 · **相关** [D87](#d87--attestation-扩展必须两阶段启用兼容不是永久降级口)、[D89](#d89--控制中心是-ssot-的事务视图不是第二套网络模型)、§16.2、§16.4

WireGuard 只给接口/peer 从创建以来的累计 RX/TX。单个累计值既不是速率，也不是
某个时间窗口的流量；把页面刷新时看到的 counter 当成 24 小时数据，会把接口年龄
误当成流量。因此决定只在中控保存可信样本，并从相邻样本的单调差值生成时间桶。

流量变化频率远高于部署、组件和健康陈述。把 counter 直接加入
`loom-attest-v5` 会改变 v5 canonical bytes，使旧 reader 在滚动升级期间无法验证
新 writer。counter 因此使用独立的 `loom-traffic-v1` 签名域，作为 Observation 的
可选附件转述。旧 JSON reader 可以忽略整个附件；新 reader 使用现有节点证书，
独立验证 CA、节点名、签名和新鲜度，并要求内外层 node/TS 完全一致。流量附件失败
不能被外层健康签名“带过”。只采集 Loom 配置里的 `wg-<peer>` 接口；一条受管接口
出现多个 peer 时拒绝整份样本。稳定聚合键来自 node/peer/link identity，peer 公钥
只作诊断，轮换密钥不能平白创建一条新逻辑链路。

每条 counter 都带 reset epoch，由本机 boot ID、接口 ifindex 与 peer public-key
指纹构成；peer-key 变化也单独判定为 reset。中控只接受
node/interface/peer/epoch 相同、时间递增且间隔不超过上限的相邻样本；epoch 改变、
同 epoch counter 回退或长 gap 都记录为质量边界，但不贡献任何 byte。缺失桶和一个
被真实采样的零流量桶必须分开表示，不能跨 reset/gap 插值。中控以每轮一个完整
fleet frame 的 JSONL 文件追加，权限收紧为 0600，原子压缩并保留 30 天；普通节点
不复制这份历史，自己的网页与 `/traffic.json` 只暴露本机直接观测的当前累计
counter；`/status` 可能同时携带 learned 签名附件。中控的 `/traffic.json` 在相同
current 字段之外附带历史时间桶，并明确区分 available、unavailable 与普通节点的
not_supported。所有 byte 字段使用十进制字符串，避免 JSON consumer 丢失 int64
精度；HTTP 路径复用 gossip-cycle cache，不因 scraper 刷新重复 Collect 和扫描历史。

生成配置固定 60 秒采样，中控固定 3 分钟最大 gap，不把它们做成控制台调参项。
每个 frame 持久化当时的 gap 判据，重启或未来默认值变化不能重写旧历史语义。
history 文件由单个 report 进程持有 no-follow 锁，追加和压缩不允许多 writer 竞态。
采样循环以固定 ticker 为基准，不在一轮结束后再机械睡满 60 秒；邻居 RTT、目标
可达性和邻居拉取分别做有上限的并发，避免 N 个超时把一分钟节奏线性拖长。同一轮
carrier 状态与 traffic 陈述复用一次 `wg show all dump`，不能为两个消费者连续读出
两份可能跨越接口重建边界的快照。

三个页面的聚合语义不同且必须写在界面上：

- **Overview** 把所有节点的受管 WG 接口 RX+TX delta 相加，显示时间桶柱状图。
  同一 payload 可能在两端、也可能跨多个 hop 出现，所以这是 hop-weighted
  infrastructure load，不是去重后的应用流量。
- **Node detail** 只聚合所选节点，RX 与 TX 分开画柱；上方当前累计值仍保留，
  但不能与 24h delta 混算。
- **Topology** 按无向 link 归并两个端点，但每个端点只贡献自己的 TX delta。
  这样 sender TX 不会再以 receiver RX 重复一次；单端样本仍可用，双端均有可信
  delta 时显示两个 reporting endpoints。现有陈述没有签名的预期接口 roster，
  因此界面只说“有样本的桶”，不冒充完整 coverage。

这个决定只覆盖 Loom WireGuard carrier。`direct` 没有 WG hop，Service/sing-box
与 Hysteria2 也没有进入这个 counter 契约；在各自的数据平面/L7 collector 落地前，
不得把这些流量塞进当前图表，也不得把 WG hop-weighted 总量命名为 service traffic。

assignment 与本地 release floor，然后选择最高合法 generation。URL 顺序只决定同一
release 的正文优先级，不能让靠前的旧镜像压住新代；同 generation 的不同签名 payload
视为签发端分叉并失败关闭。manifest、节点 bundle 和 content-addressed binary 都可从
任一镜像回退取得，但必须分别通过原有签名、ID、hash 与 size 检查。

publisher 接受多个 target 和 verify URL。同一轮会尝试推送全部镜像；任何一个失败，
即使其他镜像已安全更新，本轮也不写绿色健康状态，下一轮继续收敛。这里不声称跨主机
原子提交：镜像可以短暂处于不同 generation，节点的最高合法代选择与本地 floor 正是
这个异步复制模型的安全边界。`current.json` 不缓存；不可变 snapshot 与 binary 使用
长效 immutable 缓存。

这一步只消除传输可用性单点，不冒充真实 canary。批次推进仍须由 D88 的 assignments、
节点签名回执和尚未实现的 controller 完成；外部 monotonic witness 也仍是更强灾难恢复
模型的后续加固项。

### D92 · 拓扑分环表达建连职责，链路标签只使用可信滚动观测

**日期** 2026-08-29 · **状态** 已实现、待部署 · **相关** [D89](#d89--控制中心是-ssot-的事务视图不是第二套网络模型)、[D90](#d90--流量历史只由可信相邻-counter-样本推导)、§16.4

左右两列虽然能画出当前六节点的九条持久边，却把布局偶然性冒充成网络分层，并在
节点增加后迅速形成密集交叉。拓扑改为两个同心椭圆环：能接受反向建连的节点等距放在
内圈，`reverse_only` 节点等距放在外圈；两环使用半步角度错位。这里的内外只表达
WireGuard 建连职责，不代表内网/公网、安全级别、地理距离或控制层级。没有 direction
元数据的旧节点视图继续使用确定性分组，而不是从 IP 或城市猜角色。

持久 WireGuard 边显示三个不同语义的观测值：最新一分钟观测中的 RTT、近五分钟可信
TX counter 差值换算的实际传输速率，以及近十五分钟连续 RTT 摘要的 P95−P50。第二项
是窗口内实际经过链路的 throughput，不是容量测试得到的 bandwidth；第三项是多个
一分钟五样本中位数之间的滚动变化，不是 packet-level jitter。界面必须明确写出窗口，
缺少相邻 counter 或至少两个 RTT 摘要时显示缺失，不得补成零。

为避免修改已经部署的 `loom-attest-v5` canonical bytes，控制节点在本地 traffic JSONL
frame 里保留通过现有身份/测量门禁的 `report.neighbors` 摘要，读取时按节点、邻居和
观测时间去重，再按无向链路计算滚动分位数。重复收集同一份 gossip 陈述不能增加样本，
同键异值必须失败关闭。流量仍完全复用 D90 的 independently signed `loom-traffic-v1`
相邻差值。候选虚线没有连续探测和 counter，因而不显示这些指标；它们仍只代表 SSOT
允许的按需路径。

内圈节点之间没有常驻 WireGuard 边时，不能拿 Agent 的完整候选路径观测拆成单跳
指标：例如 `demo-d → demo-b → demo-e → 目标站点` 的耗时同时包含多个网络段以及目标响应，
把总数贴到 `demo-d ↔ demo-b` 会失真。每个可公网直拨的内圈无向对因此只派生一个真实
可拨方向，使用隔离凭据经 Hysteria2 请求对端 loopback 上的固定响应，并签发独立的
`loom-linkmetric-v1` 陈述。标签显示该方向的单跳响应延迟、十五分钟 P95−P50 与固定
响应的 achieved probe throughput；最后一项只是主动探测速率，不是业务流量或链路
容量。方向必须在 tooltip 中披露，缺样本显示 warming up，不能用候选路径数字补齐。

### D93 · 交互式代码发布默认用管理 SSH 并行直发

**日期** 2026-08-29 · **状态** 运维约定生效 · **相关** [D77](#d77--改代码要显式-loom-release改-ssot-才自动发布)、[D85](#d85--发布的原子单位包含输入时刻放行记录与可取回字节)、[D91](#d91--保留-signed-pull用多镜像消除分发可用性单点)、§14.2

生产节点的管理 SSH 均可从中控直达。`reverse_only` 只约束 WireGuard 隧道的发起
方向，过去据此把 SSH push 限定为 bootstrap 是把数据面约束误套到了管理面。

操作者触发的代码发布因此默认先用 `loom release` 记录精确 commit 和制品，并立即
用一次性 `loom publish` 固化对应 signed current；随后通过 SSH + SCP 把同一二进制
并行直发所有当前节点：远端临时落盘、核对 SHA-256、原子
替换并重启实际运行的 Loom 服务。命令完成以各节点 SSH/SCP/激活返回为准；默认不
再等待 publisher 的 30 秒周期、pull 的 45 秒加抖动或 6/6 状态轮询。失败必须指出
具体节点，不能把部分成功写成全部成功。

这只改变交互式代码制品的快速传输路径，不取消 D91：`loom release`、签名快照、
多镜像和 signed pull 继续负责发布记录、配置与秘密边界、离线节点补齐和长期漂移
纠正。直发不得原地覆盖正在运行的二进制，也不得绕过放行记录或签名配置。

### D94 · v1 客户端收敛为一个中控托管入口，端口覆盖退出主模型

**日期** 2026-08-30 · **状态** 设计生效、生产 Linux 首轮迁移完成，Windows/Android 待实现 · **相关** D17、D44、§4.5、§7、[客户端接入设计](client-access.md)

“一个端口对应一个访问声明”已经证明了显式选择与并发能力，但把端口继续暴露为
Service 页面和桌面/移动客户端的主模型，会让接入协议细节取代业务身份，也会要求
用户在 URL、端口、声明和出口之间手工保持一致。v1 因此只提供一个逻辑上的日常
入口：中控按 matcher 识别请求，将其映射到 Service，再映射到既有
`AccessDeclaration`；候选、授权、fallback 和 fail-closed 仍沿用声明模型。

各平台只按操作系统能力呈现这一套规则。Linux server 提供一个默认仅回环监听的
日常 mixed；Linux desktop 可用 TUN 加一个同规则 mixed；Windows 使用 TUN 主接管，
另提供一个同规则 mixed 给显式代理的开发工具；Android 只使用 `VpnService` TUN。
Windows 与 Android 客户端只读展示命中的规则、Service、声明和当前路径，连接、
断开、重连与诊断不构成策略修改。规则只在中控维护，Loom 客户端 UI 不提供
“选 URL / 声明 / 固定出口 / fallback”控件；应用仍然正常发起请求，由请求 host
命中中控规则。

Service 页面管理 matcher → Service → `AccessDeclaration` 及其验证结果，不显示
“每个策略一个端口”，也不把 TUN/mixed 当作业务对象。旧端口绑定声明仍可在 Linux
作为兼容/高级覆盖保留，用于迁移既有脚本或临时 CLI 强制出口；它必须命名明确、
默认仅回环监听，并继续受目标授权、候选集与 fail-closed 约束，不能借覆盖扩权。
Windows/Android 不渲染或编辑这类覆盖。生产环境确认没有遗留调用方，因此 Linux
使用惯用的 1080 作为唯一入口并停止监听 1081–1083；固定 SG/DE 改由 Service 在
中控引用对应声明，不再让客户端选端口。若存在遗留调用方，则仍必须保留原义或
显式迁移，不能静默复用端口。

同一域名的不同账号需要不同固定出口时，L4/TUN 不能可靠看到账号身份。显式
profile、SDK 或 L7 代理可以解决，但会新增身份、凭据和选择边界，因此不进入 v1；
也不得用重复同域名规则、规则顺序或代理用户名暗中模拟。以后若引入 profile，必须
另作数据模型、安全审查与决策记录。

### D95 · 设备默认出口是唯一客户端偏好并复用现有入口

**日期** 2026-08-30 · **状态** catch-all 底层与中控运维 API 已实现；客户端偏好语义已由 D97 取代 · **相关** D94、D97、§4.5、§7.3、§8.2、[客户端接入设计](client-access.md)

D94 的一个中控托管入口保持不变，但“客户端完全不能选择出口”过于严格。实际场景
同时需要两层意图：明确 URL/domain/package 命中 Service 时由中控规则决定；没有
命中 Service 时，设备可能希望全部走自动、新加坡或德国。为此 v1 只增加一个受控
偏好 `access.default_declaration`，并以本决策取代 D94 中禁止客户端选择默认出口的
部分。

优先级固定为：Linux 显式兼容覆盖 > 命中的 Service > 设备默认声明 > block。
Windows 的 TUN 与 `127.0.0.1:1080` mixed、Linux Server 的
`socks5h://127.0.0.1:1080`、Android 的 `VpnService` TUN 都复用这条规则。选择
“默认德国”不创建德国端口，1081–1083 也不恢复；它只改变同一入口上未命中
Service 的 catch-all 出站。

客户端不能提交任意节点、IP 或国家名，只能从中控已经授权给该设备的
`AccessDeclaration` 中选择。固定声明可以钉到内圈或外圈节点，但目标节点必须是
`egress_capable`，且声明、候选与设备凭据必须通过完整校验。选择必须携带设备身份
和当前 revision 交给中控，持久化到 SSOT 后再由常规发布器签名下发；禁止先修改
本地配置再异步补记。没有默认声明时，未匹配流量继续 fail closed。

matcher、Service、声明定义、fallback 与候选集仍只由中控管理，客户端只读展示。
同域名多账号 profile 仍不在 v1。v1 客户端范围是 Windows、Linux Server 与
Android；Linux Desktop 暂不设计或交付。

服务端先实现 `/api/control/default-exit`：只接受中控运维会话，返回最小授权选项，
并用 SSOT 内容 revision、进程锁、跨进程文件锁、完整校验和原子替换完成写入。它
刻意不是客户端认证端点；Windows/Android 不得保存运维口令。现有内部加入协议已提供
设备公钥绑定和 claim 重放约束，但面向客户端的偏好写入认证端点仍未实现；它落地时必须
复用同一 Device 身份与事务边界。默认声明还必须使用
`address_axis: from_request`，否则会把任意未匹配请求错误改写到等价类地址。

### D96 · 新增出口与全量自动策略池在同一 SSOT 事务中收敛

**日期** 2026-08-31 · **状态** 已实现 · **相关** D89、D94、D95、§4、§5.1

节点加入后只生成节点、隧道和固定出口声明，会让 `egress_axis:any` 的自动策略仍停留
在旧 `allowed_servers` 集合；拓扑已经看到新节点，但 Agent 永远不会把它枚举为候选，
形成“节点可作出口、规则却不认识它”的双重事实。Add Node 因此必须把规则对账纳入同
一份预览、完整校验、revision guard 和原子保存事务，UI 同时展示即将扩展的策略池，
不能在提交后靠另一个后台任务补写。

系统不按 `best-egress` 这类历史名字判断，也不把所有 `egress_axis:any` 都当成无限池。
只有在新增前已经包含每个在役 `egress_capable` 节点的显式池，才被识别为“全量自动
池”并加入新出口；漏掉任一现有出口的地域池、灰度池或人工 allowlist 保持原样。没有
既有出口时无法从集合推断意图，也不擅自扩展。新增非出口节点同样不会触发规则扩展。

自动池复用原声明及既有凭据，不产生新的秘密分发需求。为新节点补出的固定出口声明
仍属于新的授权对象；在控制面尚未拥有各接入节点的可信管理地址、主机身份和最小秘密
分发事务之前，UI 必须继续标记 `credentials pending`，不得复用密码或把未授权声明

### D97 · 客户端路由偏好收敛为 Direct、Auto、指定出口三模式

**日期** 2026-08-31 · **状态** 设计生效，客户端 selector 与 UI 待实现 · **相关** D94、D95、D96、§4.6、§7、[客户端接入设计](client-access.md)

D95 把设备默认声明定义成“仅在 Service 未命中时生效的 catch-all”，这不能表达实际
需要的三个互斥顶层模式。本决策取代 D94、D95 中关于客户端可写路由偏好的部分；
已经实现的 `access.default_declaration` 与 `/api/control/default-exit` 不删除，但
只保留为 Auto 模式下的中控 catch-all，不能包装成三模式已经交付。

客户端只提供一个三态控件：Direct 让全部接管的业务流量从设备本地直连；Auto 完整
执行中控签名下发的 `Host → Service → Policy`，完整路径由 Agent 自动选择；指定出口
从全部在役 `egress_capable` 节点中选择最终出网节点，全部接管的业务流量固定该末跳，
到达它之前的中继仍由 Agent 自动择优。当前部署的全部节点均具备出口能力，因此都会
出现在指定出口列表；若以后某节点明确关闭 `egress_capable`，它不再是有效出口。

三种模式复用同一个 TUN/mixed 接管面，不增加端口。客户端不得选择接入节点、首跳、
中继或完整路径；Current Paths 始终是只读运行时观测，也不得出现 `Apply`。三态偏好
由客户端本地原子保存和切换，控制面离线时仍依据最后一份已验证配置工作；它可以作为
状态观测上报，但不写入 SSOT，也不为每次切换触发发布。中控只签名下发 Auto 规则、
可用出口集合与既有授权材料；客户端不得编辑 Policy、候选集或生成的 sing-box 配置。
若所选出口在新配置中被撤权，客户端明确标为不可用并 fail closed，不静默改成其他
模式。正式交付只需补齐本地 selector、受保护偏好存储和 UI，不能复用 catch-all 字段
暗中改变其旧语义。

### D98 · NAT Device 只新增 Observation 传输适配器，不新增状态协议

**日期** 2026-09-05 · **状态** 服务端与 Windows 最小 producer 已实现，生产客户端验收待完成 · **相关** D81、D87、§13.5、§14.2、§16.1

既有 Linux 上报闭环由节点采集、`loom-attest-v5` 与 `loom-selfcheck-v1` 签名、
邻居 GET `/status`、接收验签和 gossip 转述组成。没有受管 WireGuard 入站、可能位于
NAT 后的 Windows Device 即使在回环能提供 `/status`，中控也无法发现或访问该地址；
把公网反代直接指向 `/status` 又会暴露完整诊断与 learned 转述，并依赖原本由
WireGuard 承担的网络隔离。

因此服务端只增加一个客户端主动访问的窄传输适配器：公网精确路径
`/loom-client/report` 接收 `application/json` POST，请求体直接是现有
`report.Observation`，不包新的 envelope，不接收 `Status` 或 `learned`，也不定义
self-check v2。`/status` 保持原语义；它即使接受 POST 方法也不读取请求体，不能作为
上传接口。合法陈述写入同一 gossip table，后续转述、健康和配置版本判定完全复用现有
代码。

公网传输不能只依赖“证书链到内部 CA”。接收器强制 canonical v5、签名
measurements 和 self-check v1，并独立验证可选 traffic/link-metric；全部附件的证书
必须使用同一个 ECDSA P-256 SPKI。该 SPKI 还必须精确匹配控制节点 registry 中
`ready`、`identity_source=enrollment` 的当前记录，node 同时必须是 SSOT 中未退役的
`windows-desktop` Device。这样旧证书即使仍在有效期内，也会在设备替换或吊销后被
拒绝。输入限 1 MiB，反代只开放精确 POST 路径并限速；格式、认证、过大和本地状态
故障使用不同 HTTP 状态，但认证失败不泄露 registry 是否存在。

客户端无需在加入响应或 SSOT 新增 endpoint 字段。本次生产部署把已经通过邀请平台指纹、
HTTPS、ready bootstrap 和首轮 signed pull 验证的 enrollment URL 固定为
`/loom-client/enroll`，客户端据此做同源精确路径替换到 `/loom-client/report`；这是一项
当前部署约定，不是任意 enrollment URL 的通用语义。不匹配时 fail closed，不跟随跨源
重定向，也不从 HTTP Host 或未签名输入猜地址。Windows producer 使用正常二维码加入
时由客户端自动生成并保存的身份，已接入 active snapshot、现有 canonical 字节签名和
周期提交；用户无需提供私钥或恢复旧加入身份。服务端入口上线本身不能冒充设备已经
在线，完整扫码与上报验收见 [接入说明](windows-client-reporting.md)。

### D99 · WireGuard 发起方向与客户端公网数据入口分离

**日期** 2026-09-10 · **状态** 已实现 · **相关** §2.2、§2.3、§6.1、D97

`direction` 继续只决定 WireGuard 隧道由谁发起；新增可选

### D100 · `control` 是节点能力，控制集合不固定为三台

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D19、D35、§1.3、§11、
[分布式控制平面](distributed-control-plane.md)

D35 选择单中控是上一阶段的实现取舍，不再是目标架构。`control` 改为与 `access/server`
正交的 Device 角色块；committed SSOT 中所有合格 `control` Device 的规范化投影构成
`ControlSet(epoch)`。集合至少一个，最多可以是全部合格 Device，协议不得固定为三台，也
不得出现永久 `primary_controller`。

首版采用 crash/partition fault model，法定人数为
`q=floor(|ControlSet|/2)+1`，永远按已提交成员数而非在线数计算。N=1 合法但无 HA；N=2
需要 2/2；N=3 的 2/3 是能容忍一个节点离线的最小推荐部署；N=5 可容忍两个。3/5 是部署
建议，不进入 schema 或验证协议。

任何 control Device 都能提供读、接收 admin proposal 和转发给临时 leader。leader 只解决
活性和排序，不是额外 authority。失去 quorum 时所有安全关键写停止，观测/草稿仍可复制，
数据面继续 last-known-good。普通多数不宣称 Byzantine 安全；若要容忍 `f` 个恶意 voter，
必须另用经审计的 BFT profile，满足 `N>=3f+1`、提交至少 `2f+1` 并实现完整轮次/锁定协议。

成员和 control key 变化必须走 learner 全量同步以及 old/new joint quorum。普通
drain/decommission/remove 不能隐式删 control；旧 quorum 永久丢失时只能用离线 recovery
root 签更高 recovery epoch。此决定取代 D35 的单中控结论，并把 D19 的角色分块从两个扩展
为两种数据平面角色加一个正交 control 角色。

### D101 · CRDT 复制材料，quorum commit 定义唯一生效 SSOT

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D32、D36、D39、D41、
D45、D61～D63、D72、D77、D85、D88～D93、§12、§14、§16

多副本不等于多份事实来源。管理员请求、完整 candidate SSOT、不可变制品、观测、草稿和
副作用回执都变成签名、内容寻址对象，通过 Merkle/CRDT anti-entropy 乱序、重复、分区后
合并。CRDT 原始并集永不直接改变权限或渲染输入；唯一生效 SSOT 是
`Reduce(quorum-certified committed head)`。

ControlSet、admin ACL、Device membership/grants、邀请消费、吊销、唯一资源分配、release
current、DNS/端口代次和 tombstone checkpoint 必须串行提交。每个候选 head 绑定
`cluster_id/control_epoch/revision/parent_hash/operation_root/effective_ssot_hash`，每个 voter
对同一坐标只耐久签一个 hash；达到 quorum 才形成 QC。字段级 LWW 不能把两份分别合法的
草稿自动合成一份从未审核的配置；UI 用 MV-register 显示冲突，再提交一个精确 blob hash。

现有严格 YAML、完整校验、diff、纯函数渲染、秘密占位符、内容寻址静态树和原子 apply
继续保留。Git/YAML 从在线单写 authority 降为导入、导出、评审和归档格式；单机文件锁、
本地 authority 与单 publisher 只是 v1 迁移实现。任一 control 副本可以 materialize/publish，
但只有 QC 能推动 mutable current。事件与观测用 CRDT 去重复制，配置和运行态仍分域。

本决定取代 D36 的“写只在中控”、D45/D61～D63 的“历史只在中控”、D91 对有状态共识的
否定及相关单机 authority 结论；D32/D91 关于不可信静态镜像、内容寻址和传输不等于真实性
的部分继续有效。

### D102 · 控制成员、管理员、Device、CA 与公开 TLS 使用独立信任域

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D38、D74、D87、D88、
§13、§13.5

现有一把在线 Ed25519 平台 key 不能继续既代表集群又独自发布。每个 voter 使用独立且按
用途分开的 membership/config/enrollment key；QC 首版携带按 signer ID 排序的普通多签，
客户端拒绝重复、未知、已移除或错误用途 signer。阈值聚合签名可后置，不改变签名对象。

至少分开 recovery root、control peer、control vote、human admin、Device identity、internal
CA、public WebPKI/ACME 和 APK/MSI code-signing。证书使用不同 EKU/profile；证书只证明身份，
授权还要核对 committed ControlSet/ACL/registry。control cert 不自动授予 admin，普通 Device
cert 不投票，公开 TLS 证书不签 SSOT。

当前平台 key 在迁移期只签一次 bootstrap transition，绑定初始单成员 ControlSet 和新离线
recovery anchor；它不是永久 recovery root。客户端保存
`control epoch/set hash + control revision/head hash + device generation/view hash` 三层 floor，
只有连续 joint transition 或 recovery proof 能改变信任集。v1 严格 schema 不能原位增加
未知字段，必须并行发布 versioned v2 QR/current/view，先升级 reader，再撤旧 signer。

邀请 token 只以 hash 进入 committed log；跨 seed claim 用 quorum CAS 绑定唯一 SPKI。在线
intermediate 只能在 enrollment approval QC 后签证，验证方仍核对 committed binding，防止
单个 CA executor 独自创造有效成员。本决定取代 D38/D74 把在线单机密钥和备份当完整恢复
模型的部分；当前生产边界仍须在 status 中如实保留直到迁移完成。

### D103 · 托管 DNS/ACME 与多代 listener 使用同一提交和协调边界

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D56、D68、D99、§2.3、
§14.2～§14.4、[分布式控制平面 §12～§15](distributed-control-plane.md#12-域名与公开证书管理)

受管节点的公开控制、分发和数据入口使用稳定 logical endpoint 与托管 hostname。Loom 只
自动管理显式委派的 zone/subzone；域名购买、迁移和续费扣款默认仍需管理员批准。DNS
provider 使用可替换 adapter，Gandi、Dynadot 或 RFC 2136 都不是协议 authority。provider
token、ACME account key 和 TLS private key 只在秘密层。

FQDN、RRset、CertificateIntent、端口和 listener generation 先 quorum commit，再由持资源
租约的 executor 幂等调用 DNS/ACME/防火墙/NAT API并读回验证。租约只协调副作用，不授予
desired-state authority；外部 API 不支持 CAS/fencing 时只承诺检测漂移后的最终收敛，不
冒充 exactly-once。DNS 只负责发现，不能改变 ControlSet 或让 signed EndpointSet 外的地址
获得信任。公开证书优先 ACME DNS-01，TLS key 在终止节点本地生成，新证书验证后才替换旧证书。

单 `public_endpoint + inbound_port` 只作为 v1 generation 0 兼容。目标 EndpointSet 为同一
logical ID 保存多个 listener generation，正常轮换固定为
`allocate → prepare → advertise → prefer → drain → retire`：先开启新 listener、证书、
防火墙和 NAT，外部验证后下发新旧两代；新连接优先新代并可回退，旧会话自然排空；满足
客户端 applied/兼容窗口/quiet period 后才关旧端口并写 retired tombstone。准备失败时旧端口
始终 active。

该机制适用于所有显式公网 Hysteria2 入口及需要轮换的 WireGuard/Trojan listener，不按境内/
境外分叉。端口变化不新增客户端选择轴，Direct/Auto/指定出口仍绑定逻辑节点。既有连接不
承诺跨端口迁移；“无中断”只保证计划内没有新旧同时不可用。D56 的唯一分配和 D68 的退役
记忆原则保留，但其单端口人工替换不再是目标轮换流程；D99 的显式公网数据入口边界继续有效。

### D104 · Raft 耐久日志决定提交，signed replication QC 只证明已提交状态

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D100～D103、
[分布式控制平面 §7～§10](distributed-control-plane.md)

首个可交付的一致性 profile 固定为 crash-fault-tolerant Raft。管理员签名 proposal、CRDT
对象和完整 candidate blob 都只是日志输入；只有按 Raft term/index 排序、写入法定多数的
耐久日志并推进 `commitIndex` 的 entry 才能改变状态机。voter 必须在确认 AppendEntries
前持久化 `currentTerm/votedFor/log`，并执行 Raft 的 log-matching、leader-completeness 和
提交规则；未提交的冲突 suffix 可以被新 leader 覆盖。因此，D101 所称“每个 voter 对同一
epoch/revision 永久只签一个候选 hash、凑齐签名即提交”不再是提交算法，明确由本决定取代。

每个安全关键 entry 的规范坐标至少包括
`cluster_id/recovery_epoch/control_epoch/control_set_hash/raft_term/raft_index/`
`parent_head_hash/entry_hash`；
对外的 `control_revision` 从已提交 Raft log position 确定，不允许 leader 另行分配。状态机
应用 entry 后计算 `operation_root/effective_ssot_hash/device_views_root` 和新 `head_hash`。
Control voter 只有在确认该 entry 已提交、按序 apply 且本地计算结果逐字节相同后，才以独立
config key 签署 domain-separated `ReplicationAttestationV1`；签名输入覆盖上述坐标、三个
计算 root 和新 `head_hash`。满足当前 quorum 的有序多签
组成 signed replication QC。QC 是供客户端、镜像和审计者离线验证的“已提交且已复算”证明，
不是 Raft 的投票消息，也不能反过来提交日志。已在 Raft 内提交但尚未收齐 QC 的 head 标记为
`committed_not_certified`，不得发布为 mutable current；客户端继续 last-known-good。

ControlSet 的变化不允许由普通 SSOT 字段先行自我授权。规范成员事实是复制状态机中的
`FinalControlSet` 记录，committed SSOT 的 `control` block 只是它的投影。每次变化只允许一个
进行中的 transition，并严格执行：

1. 新成员先作为无投票权 learner 验证 key possession、实现版本和 eligibility，再同步已认证
   checkpoint 及其后的完整日志；
2. 在旧配置下提出 `JointControlSet(old,new)`；该 entry 的提交和 replication QC 都必须同时
   满足 `majority(old)` 与 `majority(new)`；
3. joint 状态 certified 后提出 `FinalControlSet(new)`；其提交和 QC 仍必须同时满足 old/new
   两个 majority；状态机 apply 该 entry 时递增 `control_epoch`，取得 joint QC 后新的
   `control` 投影才成为 effective；
4. 此后 entry 才能只按 `majority(new)` 提交。被移除 key、旧成员的迟到签名和较低 epoch
   的 QC 一律不计数。

control key 轮换按“加入新 key identity、joint commit、移除旧 identity”处理，不允许原地换
key。任一 signer ID 在一个 QC 中只计一次；签名集合必须携带 ControlSet hash，joint QC 必须
标明 old/new membership 并分别验 quorum。普通 SSOT、邀请、DNS/ACME 或 listener proposal
不能绕过该流程改变 voter。以上 `FinalControlSet` authority 取代 D100 中“committed SSOT
的 control block 构成 ControlSet”的措辞；D100 的动态数量与 joint quorum 其余结论保留。
D103 中的
“先 quorum commit”自此精确定义为 Raft durable commit，只有取得 replication QC 的 certified
intent 才可公开或驱动外部副作用。该 profile 仍只承诺 CFT，不因增加签名而宣称 BFT。

### D105 · 每台 Device 的最小视图用 Merkle inclusion proof 绑定到 quorum head

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D88、D101～D104、
[分布式控制平面 §10～§11](distributed-control-plane.md)

客户端不得把“由某个 control 返回”当成配置真实性。每个 certified head 必须包含
`device_views_root`；它承诺该 revision 中每台 Device 的完整授权结果，而不只承诺一个 generation
整数。目标 wire schema 中含义较弱的 `device_generations_root` 由此字段取代；若迁移实现暂时
保留旧字段名，它也必须承诺本决定定义的完整 leaf，不能只哈希 generation。

`DeviceViewLeafV2` 使用版本化 canonical encoding，至少包含
`cluster_id/view_schema_version/device_id/device_generation/state/payload_hash/`
`previous_view_hash/endpoint_set_hash/min_reader_version`。
`state` 必须显式表示 `active/revoked/decommissioned`；吊销和删除以 tombstone leaf 表达，缺少
leaf 既不授权也不等于吊销。leaf 不包含 control revision、当前 `head_hash` 或 root，避免
无关提交迫使所有 Device 改 generation，也避免自引用；inclusion proof 所指 root 等于
certified head 中的 root 才完成绑定。leaf 的任一字段发生变化都必须提高该 Device generation。
Device payload、EndpointSet 和 route/grant 的实际字节分别由相应 hash 承诺，DNS、证书或新旧
listener 地址不能在证明外追加。

树形固定采用 RFC 6962 的二进制 Merkle 形状：按规范化 Device ID 的原始字节升序排列且拒绝
重复 ID，`LeafHash=SHA-256(0x00 || canonical_leaf)`，
`NodeHash=SHA-256(0x01 || left || right)`，空树 root 为 `SHA-256("")`。响应携带 canonical
leaf、payload、leaf index/tree size 和 inclusion audit path；所有实现必须通过同一组跨语言
golden vectors，包括 0/1/奇数 leaves、Unicode/大小写非法 ID、重复 ID 和错误 proof。不得用
“复制末叶”等未写入 profile 的本地约定补树。

客户端验证顺序固定为：先验证 v2 bootstrap/recovery lineage 与当前 ControlSet，再验证 head
的 replication QC 和单调坐标，随后重算 inclusion proof，最后核对 `device_id/state/`
`payload_hash/endpoint_set_hash` 及各项 floor，全部通过后才原子安装。任一 control、静态镜像
或 CDN 可以单独传输 view 和 proof，但不能创造或扩大授权。相同 Device generation 对应不同
leaf/payload，proof 指向错误 tree size，或高 revision 携带回退 generation，均作为 fork/replay
fail closed；合法回滚必须发布更高 generation 且明确引用被恢复的 payload。

客户端至少耐久保存
`recovery_epoch/recovery_statement_hash/recovery_policy_hash + control_epoch/control_set_hash + `
`control_revision/head_hash + device_generation/leaf_hash/view_hash`，并在激活依赖内容前原子提高
floor。D101 的 committed head 因而有了可验证的 per-Device 投影；D102 的三层 floor 由这里扩展
为可实现字段。D103 的 EndpointSet、DNS 与 listener rotation 只能经 leaf hash 进入某台 Device
视图，取代“已签 head 之外的 endpoint 也可被客户端信任”的任何解读。

### D106 · Recovery lineage 与 v2 latch 独立单调，bootstrap 绑定旧 floor 和初始信任

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D88、D100、D102、D104、
D105、[分布式控制平面 §9、§10、§19](distributed-control-plane.md)

`recovery_epoch` 是独立于 `control_epoch` 和 Raft term/index 的最高级 lineage。正常 joint
consensus 永远不改变它；旧 ControlSet 永久失去 quorum 时，只有已钉住的 offline recovery
policy 达到其阈值，才能签署 domain-separated `RecoveryTransitionV1`。规范对象至少绑定
`cluster_id/previous_recovery_epoch/new_recovery_epoch/previous_trusted_head_hash/`
`previous_recovery_statement_hash/previous_recovery_policy_hash/new_recovery_policy_hash/`
`new_control_set_and_key_hashes/new_lineage_genesis_entry_hash/initial_admin_acl_hash/`
`internal_ca_profile_and_anchor_hash/reason/issued_at`。`new_recovery_epoch` 必须严格增加，同一
previous epoch 出现两个不同 transition 是 security fork；证明链和其引用对象必须能从不可变
镜像、control 或受信 bootstrap 包完整取得。transition 只授权新 lineage bootstrap；新
ControlSet 仍须将所绑定 genesis 以 `q(new)` durable install/commit、apply/recompute 并形成首个
replication QC。recovery threshold signature 不能替代该 QC。

客户端先以已经钉住的 recovery anchor 验 transition，再验证所绑定 genesis 的 `q(new)`
replication QC；两者都通过后，才把新 epoch、statement/policy hash、新 ControlSet 与首个 head
原子写入 durable floor 并安装 view。缺少新 QC 时继续旧 LKG。一旦写入，所有较低
recovery epoch 永久拒绝，即使它带更大的 control epoch、revision 或旧 quorum QC。客户端尚未
接触新 recovery proof 时仍可能在隔离分区继续旧 last-known-good，这是 CFT 和离线模型的固有
限制，不能用 DNS freshness 或墙上时钟冒充解决；重新联网或新 enrollment 必须拿到并比较最新
recovery checkpoint。遗失 durable floor 视同重新入网，不能 TOFU 接受任一在线 control。

v1 到 v2 只允许经过 canonical `BootstrapTransitionV1ToV2`。它由当前 v1 platform key 用独立
domain 签名，并精确绑定
`cluster_id/v1_platform_key_id/v1_device_floor_merkle_root/initial_recovery_epoch_and_policy_hash/`
`initial_control_set_and_key_hashes/initial_admin_acl_hash/internal_ca_profile_and_anchor_hash/`
`initial_v2_head_hash/initial_v2_raft_index/schema_version/min_reader_version`。迁移 Merkle leaf 按
Device ID 排序并绑定每台既有 Device 的精确
`device_id/v1_generation/v1_signed_current_hash/v1_payload_hash`；客户端必须收到自己的 inclusion
proof，generation 不得低于本地 v1 floor，两个 hash 都必须与已验证的 v1 current/payload 一致。
初始 v2 head 还必须带初始 ControlSet 的有效 replication QC；platform signature 不替代 v2 quorum。

旧 platform key 能签名不代表它能自行选择新网络根。transition hash 还必须匹配客户端经部署
专属升级包、企业策略、现场 QR 或人工核验预置的独立 migration-anchor digest；普通应用代码
签名、DNS 和旧 current 下载源都不能代替这个 pin。旧 key 签出的另一 transition 即使签名有效，
只要不匹配该 digest 就作为 bootstrap fork 拒绝，不能按时间、generation 或下载速度择一。

验证成功后，客户端必须在安装首个 v2 view 前原子持久化 transition hash、初始 recovery/control
floor 和不可逆 `protocol_latch=v2`。此后可以在控制面不可用时继续运行已有 last-known-good，
但永远不得再用 v1 current、v1 QR 或 v1 view 推高状态；应用更新器也必须禁止降级到不认识该
latch 或低于 `min_reader_version` 的 reader。卸载、Keystore 丢失或状态损坏后只能凭新的受信
邀请/bootstrap checkpoint 重新入网，不能静默清除 latch。

任何 v2 邀请/QR 都必须钉住 `cluster_id/bootstrap_transition_hash/min_recovery_epoch/`
`recovery_statement_hash/recovery_policy_hash/control_set_hash/min_head_hash` 和预期公开入口身份；二维码中的 URL
仅用于发现，不能替换这些信任对象。没有携带这些字段的旧 QR 只可进入显式 v1 迁移流程，
不能直接建立 v2 信任。离线客户端在没有受信新 QR、recovery witness 或在线 quorum 的情况下
无法证明自己看见的是全局最新 lineage，产品和状态页必须如实显示这个 freshness 边界。

初始 admin ACL、ControlSet、recovery anchor 和内部 CA 都由同一个 bootstrap transition 绑定，
解决“先信谁来授权第一位管理员”的循环；之后的任何变化一律走 v2 quorum/joint/recovery
规则。迁移完成后撤销旧在线 signer 只是缩小攻击面，安全性不得依赖它确实只签一次。D100
对 recovery epoch 的简述和 D102 的一次 bootstrap/三层 floor 由本决定补全并在冲突处取代；
D103 的 DNS、ACME、端口或证书状态不能改变 recovery lineage，也不能充当 bootstrap freshness
证明。

### D107 · 公网暴露必须显式授权，EndpointSet 同时承诺地址与传输身份

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D56、D68、D99、D103、
D105、[分布式控制平面 §12～§14](distributed-control-plane.md)

存在公网 IP、`control`/`server` 能力、受管域名或可申请证书都不等于允许公网暴露。只有经
Raft commit 和 replication QC 的 `PublicEndpointIntent(exposure=public)` 才能授权创建公网
DNS、证书、listener、防火墙或 NAT 映射。intent 至少绑定稳定 endpoint ID、owner Device、
role、protocol、暴露范围、地址/域名 intent、listener policy 和 generation；扩大地域、端口池、
provider scope 或入口角色是新的安全关键提交，不能由 executor、实时测量或节点自报隐式产生。
control peer RPC 地址只属于 ControlSet，面向客户端的
`control_api/enroll/device_config/device_report/distribution/data_ingress` 地址只属于
EndpointSet；二者不能互相推导成员资格或公网可达性。

客户端可用的 `EndpointSetV2` 是 certified head 经 D105 Device leaf 授权的完整 transport trust
bundle。每个 LogicalEndpoint 至少携带稳定 ID、owner、role、protocol，以及与 protocol 匹配的
`transport_identity` tagged union：HTTPS/Hysteria2/Trojan 固定 server name、WebPKI profile 和
带 generation/重叠界限的 TLS SPKI pins；WireGuard 固定 peer key ID 与精确 public key/digest。
TLS 与 WireGuard identity 不能同时出现。首个 v2 profile 要求
`control_api/enroll/device_config/device_report/distribution/data_ingress` 各自使用独立
logical endpoint、hostname、CertificateIntent 与认证策略；control peer RPC 仍只属于
ControlSet。role×protocol 合法矩阵以分布式控制平面 §13 为准，未知组合失败关闭。listener
projection 为：

```text
ListenerGenerationV2
  generation, dial_target(dns_name|ip_literal), public_port, local_port?
  address_families[], credential_generation, certificate_intent_hash?
  introduced_revision, published_state, rotation_operation_hash, retire_not_before?
```

`published_state` 只能是 `advertised/preferred/draining`，每个可用 LogicalEndpoint 恰有一个
preferred；`preparing` 只在运维 view，`retired/blocked/quarantined` 只以历史 tombstone 和
分配约束存在。客户端按 listener generation 连接和上报，不能从端口大小、最新 revision 或
数组顺序猜 preferred。HTTPS、Hysteria2 和 Trojan 验证 server name/WebPKI 后还必须匹配授权
TLS SPKI；WireGuard 必须匹配授权 peer public key。DNS、WebPKI 或连接成功都不能替代这些 pin。

Enrollment 发生在 Device view 之前，因此 v2 QR 必须自身携带有界 seed 列表、精确 HTTPS URL、
预期 hostname、当前与 staged-next TLS SPKI pin，以及 recovery/ControlSet/head checkpoint/QC；
发送 bearer token 前 WebPKI 和 pin 必须同时通过，且禁止跨 origin redirect。pin 换代必须先把
old+new 写进 certified QR/EndpointSet，再展示新 key，最后至少等待所有仍有效旧邀请消费或
过期、客户端兼容窗口和观测 quiet period 才移除旧 pin。只续证且 SPKI 不变不需要伪造一次
pin 换代。

域名、地址、证书和 listener 分别有代次，但一个 rollout 必须以 operation hash 明确关联。地址
变化严格执行 `prepare → overlap → drain → retire`：先验证新地址上的正确 transport identity，
再让权威 DNS 同时返回 old+new；移除旧 RR 后，旧地址、listener、防火墙和 NAT 仍继续服务，
直至移除前实际权威 TTL、传播安全余量、客户端 DNS cache grace、EndpointSet 离线兼容窗口和
最后新握手/活动会话门槛全部满足。ACME DNS-01 的并行 order 只可添加和删除自己拥有的 TXT
value；不得用整 RRset replace 清掉别的 order。TLS key 更换同样先发布 old+new SPKI overlap，
新证书安装并从外部验证后才 prefer，旧证书/key 最后退役。任一阶段失败都保留上一个可用代；
DNS 仅负责发现，不能把 EndpointSet 外的地址或身份变成 authority。

首版“计划内无中断”只适用于运行时能真正并行承载 generation-scoped listener 的 Hysteria2
和 Trojan：新连接 prefer 新代并立即回退仍 advertised 的旧代，已建立 QUIC/TCP 会话留在旧
listener 自然排空，不承诺跨端口迁移。reload 会杀死旧会话、NAT 无法并存或旧 listener 在
overlap 前必须关闭时，必须标记为 disruptive maintenance，不能使用“无中断”状态。

WireGuard 只有在 renderer 和目标主机支持两套同时工作的 interface/peer generation，且具备
独立 key、隧道地址、listen port、fwmark/policy route、NAT/firewall 规则、健康检查和确定性
回滚，并完成跨 Linux/Android/Windows 的重复路由与泄漏验收后，才能获得同一产品承诺。只改
单 interface 的 `ListenPort` 或复用冲突路由不合格；在达到门槛前，WireGuard 轮换是独立的
显式维护流程。端口代次与 credential 代次正交，紧急换端口也不能冒充已撤销泄露凭据。

本决定保留 D103 的稳定 logical endpoint、先开后关和“既有会话不迁移”原则，但取代其可能
被理解为“节点角色会自动公网暴露”“DNS/WebPKI 足以授权地址”或“所有 transport 天然共享
同一种无中断轮换”的部分；D107 是公网 endpoint 与 transport identity 的规范边界。

### D108 · 权威 secret 先固化再提交，外部副作用按可逆性选择自动化等级

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D74、D87、D102～D107、
[分布式控制平面 §12、§15](distributed-control-plane.md)

任何会决定邀请、Device、listener、CA、provider 或传输身份的 secret 都必须在引用它的 proposal
提交前生成，并固定为不可覆盖的 sealed artifact、硬件/Keystore key version 或精确 KMS version。
提交对象至少绑定 `secret_id/purpose/owner/generation/public_identity_or_spki/immutable_ref`，并按
后端绑定 `ciphertext_digest + sealing_policy/recipient_set`，或精确
`kms_or_hardware_key_id + version + policy`；禁止引用 `latest`、可变 alias、可覆盖文件路径或
“executor 首次运行时随机生成”。非导出私钥以 key handle/version、公开 key 和
proof-of-possession 表达；TLS 终止节点先本地生成 key/CSR，再提交 SPKI 和 CSR hash。需要多方
读取的随机凭据先按获授权 recipient 分别封装，提交只含 artifact hash/ref，不含 plaintext。

voter 在 commit 前验证对象不可变性、hash、用途、recipient/policy 和所需 possession/availability
ack；它们无需也不应普遍解密 secret。未获提交的预生成 artifact 没有 authority，按显式 orphan
retention policy 隔离，不能被后续 proposal 凭可变名字捡用。提交后 executor 只能把 certified
intent 指定的同一 version 重放到目标系统；unwrap、安装或 API 调用失败时状态保持 pending 并
重试该 version。任何“重试时换 secret”、重新生成 key 或改变 recipient 都必须创建更高
generation 的新 proposal、artifact 和 QC。ACME nonce/order response 等非 authority 临时值可以
由 executor 取得，但证书只在其 CSR/SPKI、intent 与外部握手读回完全匹配后进入 EndpointSet。

外部系统通常不能与 Raft 原子提交，因此统一采用 certified intent、quorum-issued lease、稳定
idempotency key、读回验证和签名 receipt 的 at-least-once reconcile，不声称 exactly-once。
`ResourceLeaseV2` 至少绑定
`resource_id/holder/recovery_epoch/control_epoch/raft_term/acquired_index/desired_hash/`
`fencing_token/expires_at`；租约只减少并发，不创造 desired state。executor 在调用前后都复核
最新 certified intent，并使用
`cluster_id/resource_id/action/generation/desired_hash` 作为幂等/fencing 上下文。失去租约必须
停止发起新动作，但网络中已经发出的迟到请求仍由 provider CAS、generation fencing 和读回
reconcile 防护。

副作用按最坏迟到重放结果分三类，不能按 API 名称笼统授权：

1. **immutable/additive**：上传内容寻址对象、增加 generation-scoped listener、增加本 order
   的 ACME TXT 或明确集合元素。只要名字含 generation/hash、重放幂等且不覆盖其他 owner，
   可以无人值守执行；“replace 整个集合”不属于 additive。
2. **monotonic pointer/upsert**：发布 `current`、设置 preferred、写 DNS binding 或 provider
   metadata。优先强制 provider version/CAS；确无 CAS 时，只能在旧写不会获得密码学 authority、
   能读回检测并由新 lease 收敛的资源上自动执行，且必须暴露 stale/degraded。包含隐式删除的
   upsert 降级为 destructive。
3. **destructive/irreversible**：删除 RR/TXT、关闭 listener、撤防火墙/NAT、删除 secret/key、
   撤销或释放唯一资源。必须同时具备新鲜 certified tombstone、精确 owner/generation、单调
   fencing token 与 provider/local Agent 的条件删除。外部 API 若不能证明 CAS/fencing，禁止
   无人值守执行；系统宁可暂留资源并告警，只有管理员在读回精确对象、影响预览和二次确认后
   才能走受审计的 supervised cleanup。

receipt 和 CRDT observation 只报告调用及读回事实，不能反向修改 desired state。secret 删除、
端口释放和 DNS 清理都必须满足各自 retention/overlap 后再另行提交 tombstone；过期 executor
的成功回执不能复活旧 generation。此决定细化 D103 的租约/幂等原则，并取代其中任何允许
executor 在 commit 后临时生成权威 secret、把 lease 当授权、或在无 fencing provider 上自动
关闭/删除资源的解读。

### D109 · Recovery policy 的连续轮换必须由旧阈值授权并进入更高 recovery epoch

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D102、D106、D108、
[分布式控制平面 §9、§10、§18～§19](distributed-control-plane.md)

recovery policy 是客户端已经钉住的根，而不是普通 SSOT/CA/provider secret。policy 的 canonical
对象至少包含 `policy_id/generation/algorithm/key_ids_and_public_keys/threshold/ceremony_profile`；
新 key/share 必须先在离线环境生成不可变 version，并为每个 key 或 DKG transcript 产生
domain-separated proof-of-possession。阈值必须满足 `1 <= threshold <= key_count`，校验器还应
展示故障域和在 share 丢失、泄露后的实际容错，不能把普通 ControlSet 多数当 recovery threshold。

有当前 ControlSet quorum 的计划轮换固定为四步：

1. control 以 Raft/QC 提交 `RecoveryPolicyIntent`，绑定当前 recovery statement/head、等于
   `previous_recovery_epoch + 1` 的 `new_recovery_epoch`、新 policy hash、
   proof-of-possession root、ceremony ID 和理由；
2. **旧 recovery policy 的有效 threshold** 对引用该 intent QC 的
   `RecoveryPolicyTransitionV1` 签名；transition 同时绑定 previous/new epoch、previous statement
   hash、old/new policy hash、最后 certified head 和保持不变的 ControlSet hash；
3. 当前 ControlSet 验旧阈值签名后，把 `RecoveryActivation` 作为更高 recovery epoch 的首个
   certified head 提交，绑定 transition hash。因而计划轮换必须同时有旧 recovery threshold
   的信任连续性和当前 control QC 的在线审计/排序，任一方都不能单独完成；
4. 发布完整 intent QC、threshold signatures、transition、activation head/QC 和后续 view proof。
   客户端先原子提高 `recovery_epoch + statement/policy hash` floor，再接受新 epoch 内容。

同一时刻只允许一个 recovery transition；从 intent 到 activation 禁止并行启动 ControlSet joint
transition 或另一 recovery 操作。普通配置若在其间继续提交，activation 必须证明其 parent 是
intent head 的连续后代且中间没有改变 ControlSet/recovery policy；否则原 intent 作废并重新举行
仪式，不能把旧 threshold signature 拼接到另一条 head 上。

每个新 epoch 只接受一个 previous-statement-linked transition；同一 previous statement 指向两个
新 policy/epoch 是 recovery fork，fail closed。旧 public policy、所有历史 transition 和 proof
永久按恢复链保留，使跨过多次离线轮换的客户端可以从自己钉住的 policy 逐跳验证；客户端兼容
不需要旧 private share。新 policy 完成独立恢复演练、activation finality 且 transition 已有足够
离线副本后，旧 private share 按 ceremony 销毁；继续保留它们只会增加签出竞争分叉的风险。

当前 ControlSet quorum 不可用时，不存在“计划轮换”。若旧 recovery threshold 仍可用，只能
走 D106 的显式 emergency recovery：声明缺少 control QC 的原因，选择完整新 ControlSet/genesis
head，并进入更高 recovery epoch；UI、审计和客户端不得把它显示成普通 policy maintenance。
反过来，若**旧 recovery threshold 已丢失**，即使全部 control、管理员证书和内部 CA 都可用，
也无权给自己签发连续的新 recovery root。集群可继续普通 quorum 操作，但必须在灾难前安排
全体客户端带外 rebootstrap；真正失去旧阈值后只能创建新 cluster/trust root 并逐台重新锚定，
不能保留旧 `cluster_id` 冒充连续升级。

新 recovery policy 的 sealed shares/KMS versions 遵守 D108，但 KMS、DNS、ACME、control QC、
管理员证书或云账户都不能代替旧 threshold signature。此决定补全 D106 的
`previous_recovery_policy_hash/new_recovery_policy_hash` 语义，并取代 D103 中把所有秘密都视为
普通秘密层可由在线协调者轮换的任何泛化；recovery trust continuity 始终是独立仪式。

### D110 · Recovery statement hash 固定为建立该 epoch 的 canonical statement body

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D106、D109、
[分布式控制平面 §9.3](distributed-control-plane.md#93-丢失-quorum)

客户端保存的 `recovery_epoch/recovery_statement_hash/recovery_policy_hash` 三元组不能只有字段名
而没有跨平台相同的取值规则。每个 recovery epoch 只接受一个带显式 `statement_type` 的
`RecoveryStatementBodyV1`：epoch 0 是 bootstrap body，失去 control quorum 时是 emergency
`RecoveryTransitionV1` 的无签名 body，有 quorum 的 policy 轮换时是
`RecoveryPolicyTransitionV1` 的无签名 body。body 不序列化签名数组、statement hash 本身或其他
由自身导出的 hash；首版按 §7.1 的 I-JSON/JCS/UTF-8 规则 canonicalize，并计算：

```text
SHA-256(uint32_be(len("loom-recovery-statement-v1")) ||
        UTF8("loom-recovery-statement-v1") || JCS(statement_body))
```

该值同时就是建立新 epoch 的 `transition_hash`/`new_recovery_statement_hash`。紧急 transition
不得绑定含该 statement hash 的完整 Genesis entry；它改为绑定不含 statement hash、entry hash、
Raft envelope 或 QC 的 `RecoveryGenesisPayloadV1` hash。payload 精确承诺 cluster、新 recovery
epoch/policy、新 ControlSet、`new_control_epoch=0`、previous trusted head、初始 admin/CA、操作与
effective SSOT/Device roots、render contract 和 minimum reader；实际 Raft term/index 由新集合在
提交完整 Genesis entry 时赋值并由其 QC 认证。每条新 recovery lineage 的 control epoch 在首版
wire profile 都重置为 0，包括保持同一 ControlSet 的计划 policy 轮换。

初始
`BootstrapTransitionV1ToV2` 内嵌 bootstrap body 并承诺其导出值，不能对包含自身 hash 的外层
对象循环取 hash；紧急 RecoveryGenesis、计划 RecoveryActivation、首个 ControlHead、QR/checkpoint
和客户端 floor 都必须绑定同一个值。threshold signatures 使用各对象独立的签名 domain 覆盖同一
canonical body，不因签名顺序或收集数量改变 statement identity。

同 epoch 的 statement hash 或 policy hash 任一不同即为 recovery fork，不能按更大 revision、
时间、下载源或签名更多的一侧自动选择。实现必须用 bootstrap/emergency/policy-rotation 三类正常
向量以及错 type、自引用、签名数组参与 hash、非 JCS 输入等负向量做 Go/Kotlin/Windows 互操作
测试。本决定以 `new_lineage_genesis_payload_hash` 取代 D106 中会形成自引用的
`new_lineage_genesis_entry_hash`，并消除 D106/D109 中 `transition_hash` 与
`recovery_statement_hash` 可能被实现成两套序列化的歧义；其他恢复授权和阈值规则保持不变。

### D111 · 首次 v2 bootstrap 按 payload → transition → head/QC 单向构造

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D104、D106、D110、
[分布式控制平面 §10.3](distributed-control-plane.md#103-v1--v2-不可逆-latch)

D106 让 `BootstrapTransitionV1ToV2` 绑定完整 `initial_v2_head_hash`，而初始 head 又必须绑定该
bootstrap transition proof；两者互相引用，无法得到 canonical bytes。首版改为三层单向 DAG：

1. 先生成 `InitialV2HeadPayloadV1`，固定 recovery 三元组、`control_epoch=0`、初始 ControlSet、
   `control_revision=1`、snapshot/operation/effective SSOT/Device/admin/CA roots、render contract
   与最低 reader；payload 不含 transition proof/hash、head hash 或 QC。
2. `BootstrapTransitionV1ToV2` 绑定该 payload hash、完整 recovery bootstrap statement、v1
   per-Device floor root、初始 ControlSet/admin/CA、`initial_v2_raft_index=1` 和最低 reader，由
   v1 key 签名并计算 bootstrap transition hash。它不再绑定完整 initial head hash。
3. 最后生成初始 `ControlHeadV2`：加入实际 Raft term、固定 index 1、空 previous-log hash，令
   `transition_proof_hash=bootstrap_transition_hash`，计算完整 head hash，再由初始 ControlSet
   durable commit、apply/recompute 并形成 post-commit QC。

三种摘要分别使用 `loom-initial-v2-head-payload-v1`、
`loom-bootstrap-transition-v1-to-v2` 和 `loom-control-head-v2` domain，并采用 DCP §7.1 的长度前缀
framing + JCS。transition body 排除自身 hash/signature；head body 排除自身 hash/QC，但必须包含
transition proof。这样旧 v1 authority 精确承诺初始逻辑内容与新 authority，新 ControlSet 的 QC
精确承诺 Raft 排序和完整 head，不存在任何 hash 豁免或循环。

本决定以 `initial_v2_head_payload_hash` 取代 D106 的 `initial_v2_head_hash` 字段，并与 D110
一同固定所有新 recovery lineage 的初始 `control_epoch=0`。实现必须提供三层正常向量，以及把
transition proof 漏出 head hash、把 QC 纳入 head hash、把完整 head hash 塞回 transition 等负向量。

### D112 · ControlSet 采用 exact set bytes，Joint commit 立即改变内部提交规则

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D100、D102、D107、
[分布式控制平面 §9.1](distributed-control-plane.md#91-加入)

首版以 `ControlMemberV1` 和 `ControlSetV1` 作为跨实现唯一成员对象。member 精确承诺 Device ID、
三把用途隔离的 Ed25519 public key/key ID、peer identity SPKI、排序 peer endpoints、fault domain 与
最低 control protocol；set 非空并按 member ID 的 UTF-8 bytes 排序，所有 member、key、SPKI 与
endpoint 标识按 schema 去重。`control_set_hash` 使用
`loom-control-set-v1` 长度前缀 domain + JCS；epoch 不进入 set bytes，使 recovery epoch 重置
control epoch、但成员不变时仍能引用同一集合 hash。

成员变化按单向 DAG 构造：old/new set → old/new membership-key 双多数
`ControlMembershipApprovalProofV1` → `JointControlSetEntryBodyV1` → old/new 双多数
`JointConfigReplicationQCV1` → `JointControlSetProofV1` → signature-free
`FinalControlSetHeadPayloadV1` → `ControlSetTransitionProofV1` → Final head → Final old/new 双多数 QC。
各层的 exact 字段、hash domain 和排序规则由 DCP §9.1 固定；proof hash 不包含尚未生成的 Final
head/QC，外层 bundle hash 也不写回内层，禁止循环引用。

Raft 内部 membership 由最新 durable committed config entry 决定：Joint 一旦 committed，选举、
普通 entry 和 Final 都立即要求 old/new 双多数；Final 一旦 committed，从其后使用新稳定集合。
对外 authority 更保守：只有 Final apply/recompute 且取得 old/new post-commit QC 后，才发布新
ControlSet、`control` projection 和客户端 transition。此决定取代任何“内部始终只看最后一个
FinalControlSet”或“SSOT control 块可以改变 voter”的表述。

### D113 · 计划 recovery policy 轮换必须验证 Intent → threshold proof → Activation

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D109、D110、D112、
[分布式控制平面 §9.4](distributed-control-plane.md#94-recovery-policy-的计划轮换)

### D130 · Enrollment 采用 reservation→issuance→approval→completion 原子流程

**日期** 2026-09-10 · **状态** 目标设计生效、尚未实现 · **相关** D102、D123、D126、D129、
[分布式控制平面 §11](distributed-control-plane.md#11-enrollment邀请与报告)

claim head 只把 invite 从 `available` 变为 `claim_reserved`，并建立有界 retry transaction；它不激活
Membership、Device view 或 secret。CA 对该 certified reservation 产生内容寻址 issuance 结果，随后
历史 claim head 的 stable enrollment quorum 签 approval；最后一个普通 completion head/QC 原子完成
`claim_reserved→consumed`、激活 Membership/view，并授权释放已绑定 artifact。失败、超时、authority
变化或 profile 失效走 certified abort，写入 tombstone 后才能用新 invite/request 重试，不留下半激活
Device。本段取代 D102 的“approval 后才允许 CA 签证”顺序，以及 D126 的二态 invite reducer。

幂等 identity 是 token 加 exact `EnrollmentClaimRequestBodyV1`，其中包含 CSR/identity、facts 与完整
wrapping-key descriptor；同 body 的 detached ECDSA/PoP 签名可以重签，任一 body 字段变化都是冲突。
Android API 31+ 使用不可导出 P-256 ECDH wrapping key，API 26–30 使用 intent 明确允许的独立
RSA-2048 OAEP fallback；identity key 不能兼任 wrapping key。公开 invite 只含 token commitment 与
private-binding hash，完整 secret ref、recipient 和 availability receipt 留在 control-private binding。
本段取代 D123 的旧 retry tuple、D126 的“除 invite ID 外完全相同”限制，以及 D129 把 detached token
proof 写成 claim operation 内嵌字段的表述；完整 exact wire 以目标文档当前 §6.2/§11 为准。
