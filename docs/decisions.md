## 一 · 实现期间的推导决定

### D1 · 每条隧道一个 WireGuard 接口,不是一个接口挂多个 peer

**日期** 2026-08-20 · **状态** 生效 · **相关** §17.2、§20.1

标准做法是一个 `wg0` 挂 N 个 peer。这里反过来:节点上每条隧道一个接口,
文件名 `wg-<对端id>.conf`。

**理由(2026-08-21 修订,原理由不成立):**

原来写的理由是"AmneziaWG 的混淆参数是接口级的"。**这条站不住** —— §17.3 明说
参数可以按隧道**或按批次**生成,一个网卡挂多个 peer 用同一批参数完全合法。

**真正的理由是路由选择原理:多台出口服务器都要承载 `AllowedIPs = 0.0.0.0/0`。**
出口流量的目的地是任意公网地址,所以每个出口 peer 都得吃下全部地址空间;而
WireGuard 按目的地址匹配 peer,**同一个网卡上不能有两个 peer 都是 0.0.0.0/0**。
必须分网卡。

**代价:** 接受方每条隧道占一个端口;接口数随隧道数线性增长。在数十节点规模
可接受。

> ⚠️ **不要为了"更简洁"合并成单接口** —— 多个出口会互相覆盖 AllowedIPs,
> 结果是只有一个出口生效,而且不报错。

### D2 · 私钥用 `wg-quick` 的 `PostUp` 引用本地文件

**日期** 2026-08-20 · **状态** 生效 · **相关** §12.1、§13.1 · **部分回答 C16**

渲染层不写 `PrivateKey`,改为:

```
PostUp = wg set %i private-key /etc/loom/secrets/%i.key
```

用 `%i` 让 wg-quick 自己展开接口名,避免文件名与接口名在两处各写一遍。

**理由:** §12 要求配置是 SSOT 的纯函数渲染,§13.1 要求私钥永不离开节点。
平台既然没有私钥,就渲染不出完整文件。这条引用是两者的调和点 —— 渲染层进
快照哈希,秘密层不进。

**仍未定(C16 的其余部分):** `secret_generation` 的记法、轮换流程、
节点首次注册时生成密钥对的具体时机。

### D3 · 无法完整表达的输入一律硬报错,不静默降级

**日期** 2026-08-20 · **状态** 生效 · **相关** §17.2

隧道设了 `obfuscation` 但渲染器尚未实现 §17 参数输出时,`Render` 返回错误
而不是输出一份不带参数的配置。

**理由:** §17.2 说参数全部置零等于标准 WireGuard 行为。静默输出无参数配置,
结果是使用者以为开了混淆而实际没开 —— 这是安全性质上的谎报,比不实现更糟。

**推广:** 未实现的协议进 `render.Result.Skipped` 并由 CLI 显式打印。
渲染少生成了东西,调用方必须看得见。

### D4 · 推导字段不进结构体,靠严格解码拒绝

**日期** 2026-08-20 · **状态** 生效 · **相关** §2.2、§19

`Node` 没有 `mesh_eligible` 字段,`Tunnel` 没有 `initiator` 字段。SSOT 用
`KnownFields(true)` 解码,写这些键直接报错。

**理由:** §19 要求"校验器应拒绝矛盾值"。比起"允许写入再校验一致性",
不给字段更彻底 —— 不存在"写了但被忽略"这个中间状态。

### D5 · 接口名为 `wg-<对端id>`,长度由校验器提前拦截

**日期** 2026-08-20 · **状态** 生效 · **相关** §20.1

Linux `IFNAMSIZ` 是 16(含结尾 NUL),可用 15 字符。校验器检查
`len("wg-"+peerID) <= 15`,超长报错并指名要缩短哪个节点 id。

**理由:** 备选方案是超长时回退到哈希名(如 `wg-a1b2c3d4`)。否决,因为
命名不统一是排障时的额外负担;把约束推给 SSOT 作者更好,而这正是校验器
该做的事。

### D6 · 校验返回全部发现,并按 (节点, 条款) 稳定排序

**日期** 2026-08-20 · **状态** 生效

**理由:** §20.1 的场景是一次维护 24 个互相对应的文件。停在第一个错误会
逼出"改一次跑一次"的循环。排序是为了 CI 输出不抖动。

### D7 · 配置包哈希只覆盖渲染层

**日期** 2026-08-20 · **状态** 生效 · **相关** §12.1、§15.3、§19

`Bundle.Hash()` 不含秘密层,也**不含 SSOT 全局哈希**。

**理由:** 把 SSOT 哈希写进每个文件,会让任何一处改动导致全部文件的 diff
变化,§12.1 要的"看到会改哪些文件的哪些行"就没了。全局哈希属于
`Snapshot.ssot_hash`,不属于文件内容。

### D8 · 技术栈

**日期** 2026-08-20 · **状态** 生效 · **相关** 附录 B

Go 1.27,唯一第三方依赖 `gopkg.in/yaml.v3`。附录 B 选 Go 的理由是渲染器与
校验器要和 Agent 共用同一份实现 —— 跨语言实现同一套规则是长期漂移来源。

### D9 · 凭据在渲染层是占位符,不是明文

**日期** 2026-08-21 · **状态** 生效 · **相关** §12.1、§18 · 扩展自 [D2](#d2--私钥用-wg-quick-的-postup-引用本地文件)

sing-box 配置里的凭据渲染成 `${secret:<secret_ref>}`,由 Agent 在写盘前用本地
秘密层替换。

**理由:** 明文写进渲染层有三个后果 —— `loom diff` 把凭据打到终端、快照哈希
覆盖了它、配置包在整条分发链路上处处是明文。D2 已经为 WireGuard 私钥确立了
"渲染层只写引用"的模式,凭据是同一个问题。

**附带的好处:** 替换失败时 sing-box 会因密码非法而拒绝启动。这正是想要的 ——
总好过拿着字面量 `${secret:...}` 去连然后认证失败。

> ⚠️ **两端必须引用同一个 `secret_ref`。** 中继侧的 user 密码与接入侧的 hop
> 密码指向不同条目时,认证会静默失败。`TestSingBoxPathCorrespondence` 断言这一点
> —— 实现时正是先写错、再被这个测试拦住的。

### D10 · ~~目标选择编码为"目标在隧道中的地址"~~ 已被 D12 推翻

**日期** 2026-08-21 · **状态** ❌ **已推翻**,当天即被 [D12](#d12--目标不是节点出口是路径上的位置) 取代

原方案:落地目标在每条隧道的本端地址上开一个 socks inbound,接入节点的下一跳
链是 `hysteria2(中继公网地址) → socks(目标隧道地址)`。

**为什么推翻:** 它建立在一个错误前提上 —— 把"目标"当成了一类节点。一旦认清
目标只是一个地址(D12),问题本身就消失了:链的最后一跳是**服务器**,它直接
向目标地址发起普通的对外连接。不需要在目标那边装任何东西。

**保留这条记录的价值:** 当模型的层次分错时,会催生出一整套看起来自洽、实际
多余的机制。D10 就是一个例子 —— 它解决的是一个不该存在的问题。

### D11 · 用 selector 而不是 urltest

**日期** 2026-08-21 · **状态** 生效 · **相关** §5.5、§5.6

接入节点每条声明生成一个 `selector` 出站,成员是它的全部 RouteCandidate。
当前选择由 Agent 设置,不用 sing-box 的 `urltest`。

**理由:** §5.6 要求选路的决策者只有一个。`urltest` 会按自己的节奏和判据独立
选路,与 Agent 的 §5.5 阻尼规则形成两个互不知情的决策者 —— 这正是 §5.6 拒绝
"让中继自主选下一跳"的同一条理由。

**附带发现的阻抗不匹配:** `switch_threshold` 在设计里是比率(如 20%),而
sing-box 的 `urltest.tolerance` 是毫秒。即使想用 urltest 也表达不了 §5.5 的
阻尼语义。

**当前状态(2026-08-23 更新):** Agent 已实现(§5.5.1),按 objective 排序并带
阻尼切 selector。Agent 没跑起来时 selector 停在 `default` 上,而 default 刻意
不取直连([D22](#d22--selector-的默认值不许是直连))。以下是原始记录:§20.2 说的
"路径静态指定"。

### D12 · 目标不是节点,出口是路径上的位置

**日期** 2026-08-21 · **状态** 生效 · **这是全项目最重要的一次模型修正** · 已重写 design.md 第一部分

**修正前的模型(错的):**

```
节点能力 = {access, relay, target}
target 分三种形态:落地型 / 端点型(自有) / 端点型(第三方)
路径 = access → relays → target_node
```

**修正后:**

```
Loom 管的:接入节点、服务器节点          ← 只有这两类
Loom 不管的:目标地址                    ← 它不是节点
路径 = 接入节点 → [服务器…] → 目标地址
```

**三条具体的认识:**

| # | 修正 |
|---|---|
| 1 | **目标只是地址。** 自建推理服务和买来的第三方 API,对 Loom 完全同等 —— 都是发请求过去的地址。哪怕那台机器你有 root,Loom 也不管它的网络配置 |
| 2 | **出口不是节点类型,是位置。** 链上最后一台服务器就是这次的出口。同一台北京云机这次是出口,下次可能只是中间一跳 |
| 3 | **服务器之间没有本质区别。** 国内云机和境外 VPS 是同一类东西,区别只有两点:在哪(出口 IP),怎么接入(能被连 / 必须它连出来) |

**推论:**

- 中继当然可以直接访问 API —— 它就是一台有 IP 的服务器。用不用境外 VPS 是
  **选路的结果**,不是架构里预先分好的类;
- `capabilities` 里的 `target` 删除,只剩 `{access, server}`;
- `target_kind`、`managed` 从节点模型移除 —— 前者不存在,后者恒为 true
  (Loom 管的机器都是你的);
- §4 的"模式 A / 模式 B"改成两个独立的轴:**地址轴**(由请求决定 / 从等价类选)
  与**出口轴**(钉死 / 任选)。四种组合都真实存在,原来的两模式只覆盖了两种;
- 中继与落地的配置渲染**合并成一套** —— 服务器就是服务器。

**为什么之前会错:** 把"应用语义"(流量到了那儿干什么)和"管理语义"(这台机器
我能不能动)混成了一维。它们是两件无关的事,而其中一件根本不适用于目标 ——
因为目标压根不在 Loom 的管理范围内。

### D13 · 隧道矩阵只覆盖 `reverse_only` 服务器

**日期** 2026-08-21 · **状态** 生效 · **相关** §6.3、§8.3

能进 mesh 的服务器(`bidirectional` / `direct_only`)由 Headscale 自动分发密钥,
**一份配置都不渲染**。只有 `reverse_only` 的才产生隧道矩阵条目。

**理由:** 文档 §8.3 早就写了 Headscale 负责密钥/peer 自动分发,§2.2 也写了只有
`reverse_only` 进不了 mesh。但这两条从没被连起来看,导致示例里所有节点都进了
矩阵,把规模夸大了三倍。

**校验器应新增一条:** `mesh_eligible = true` 的服务器出现在 `tunnels:` 里就报错,
并提示"这个是不是该交给 Headscale"。

### D14 · 快照 id 是内容哈希,时间从外部注入

**日期** 2026-08-21 · **状态** 生效 · **相关** §12、§19

快照 id = 除 `created_at` 与 `author` 外全部内容的 SHA-256 前 12 位。
时间与作者由**调用方传入**,`snapshot.Build` 自己不读时钟。

**两个理由:**

1. **打包必须和渲染一样是确定的。** §12 要求渲染是纯函数;如果打包过程
   读时钟,那"同样输入产生同样字节"就断在最后一步,而签名恰恰针对那串字节。
2. **id 相同就意味着产物没变。** 同一份 SSOT 隔天再打一次,id 一样 ——
   "这次改动有没有实际影响产物"于是变成一眼能看出的事,不必逐文件比对。

`created_at` 照常如实记录,只是不进 id。

### D15 · 签名放在旁文件,不放进 manifest

**日期** 2026-08-21 · **状态** 生效 · **相关** §14.3

产物是 `snapshot.json` + `snapshot.sig` 两个文件,而不是把签名字段塞进
manifest。

**理由:** 签名针对的必须是**确切的那串字节**。签名如果在 manifest 内部,
校验时就要先把它挖掉、再重新序列化一遍 —— 而"重新序列化出来的字节"与
"当初签的字节"是否逐字节相同,取决于序列化实现的稳定性。这是一类不必要的
风险,分成两个文件就不存在。

> §19 的 `Snapshot` 里列了 `signature` 字段,那是概念模型;落到磁盘上它是
> 旁文件。二者不冲突。

### D16 · 一台机器一把 WireGuard 私钥,放在 `/etc/wireguard/node.key`

**日期** 2026-08-22 · **状态** 生效 · **相关** §13.1、§12.1 · **上真机时才暴露的两个 bug**

原来渲染的是 `/etc/loom/secrets/%i.key` —— 按接口名展开,即**一条隧道一把私钥**。
两处都错:

**错误一:私钥应当按机器而非按隧道。** SSOT 里每个节点只有一个
`wg_public_key`。若各接口用不同私钥,对端拿到的公钥就对不上。同一把私钥用在
多个接口上是合法的 —— 对端靠公钥认身份,而身份本来就该一致。

**错误二:路径必须在 `/etc/wireguard/` 下。** Ubuntu 24.04+ 给 `wg` 上了
AppArmor profile,只允许:

```
file rw @{etc_rw}/wireguard/{,**},
```

放在别处会被拒:

```
apparmor="DENIED" profile="wg" name="/etc/loom/secrets/node.key" denied_mask="r"
```

**表现极具迷惑性:** `wg-quick up` 打印一行 `fopen: Permission denied`,
删掉刚建好的接口,**然后退出码仍是 0**。看起来像成功了。

给每台机器加 AppArmor 例外(profile 里有 `include if exists <local/wg>`)也能解,
但那是在削弱一个本该存在的防护;换个路径不花任何代价,而且 `/etc/wireguard/`
本来就是 WireGuard 密钥的惯例位置。

> **"秘密层"是个概念,不是一个目录。** 不同类型的秘密可以放在各自消费者
> 期望的位置 —— 这不违反 [D2](#d2--私钥用-wg-quick-的-postup-引用本地文件),
> 渲染层依然只写引用。

### D17 · `ClientProfile` 并入 `Node`,端口范围改 61617-61799

**日期** 2026-08-23 · **状态** 生效 · **相关** §1、§7

**合并的理由:** §1 说只有两类节点,但模型里 `ClientProfile` 是独立实体,和
`capabilities: [access]` 表达同一件事。两张表装同一个东西,还逼出一条
"档案 id 不能与节点 id 重名"的规则 —— 那条规则是为规避输出目录冲突而发明的,
本身就是重复建模的症状。

真正推动它的是把 access-a 加进拓扑:同一台机器不能既是"节点"又是另一张表里的
"档案"。合并后 `Node` 吸收 `platform` / `credentials` / `mixed_ports` /
`default_declaration`,那条规避规则删除。

**端口范围** 从 61610-61699 改为 **61617-61799**(与实际放行的一致)。
现有端口(61619/61637/61654/61682/61698)全都落在新范围内,无需改动。

### D19 · 角色字段分块,`capabilities` 由块推导

**日期** 2026-08-23 · **状态** 生效 · **相关** §1.1、§1.3 · 取代 [D18](#d18--惰性字段按能力拒绝-已被-d19-取代)

```yaml
- id: cn-a
  city: 广州
  server:                    # 这个块存在 = 持有 server 能力
    direction: bidirectional
    inbound_port: 61698

- id: access-a
  city: 北京
  access:                    # 这个块存在 = 持有 access 能力
    platform: linux-server
    credentials: [...]

```

**两个块都有也合法** —— 一台服务器自己也要走代理出去,是真实需求。渲染器
把两边合并进同一份 sing-box 配置(一台机器一个进程)。

> **曾经短暂地禁止过双角色,理由是"两类节点走两个控制面、会互相覆盖"。
> 那个论证是错的:配置源只有一个**(SSOT → 渲染器),投递也只有该机的
> Agent 一条。§18 那套一次性链接是给没有 Agent 的设备用的,而那种设备只
> 可能是纯接入节点。把"投递渠道不同"当成了"配置源不同"。

**`capabilities` 字段删除。** 它与角色块是同一个事实的两次编码 —— 写了
`capabilities: [server]` 却不给 `server` 块(或反过来)就是自相矛盾,而那
正是 [D4](#d4--推导字段不进结构体靠严格解码拒绝) 要消灭的东西。

**收益:惰性字段变成不可表达,而不是被拒绝。** 把 `direction` 写进 `access`
块,严格解码在**加载阶段**就失败,根本到不了校验器:

```
field direction not found in type model.AccessRole
```

D18 那 30 行 `checkRoleFields` 随之删除。对应的测试也从"校验器拒绝"下移到
"解码器拒绝"(`model.TestLoadRejectsDerivedFields`)。

> **判据:需要运行时校验来保证字段共现,就说明类型分错了。** 校验器该管的是
> 跨实体的一致性(隧道两端对不对得上、引用存不存在),不是同一个实体内部
> 哪些字段该一起出现 —— 后者是类型的职责。

### D20 · selector 必须配一个能切它的端点

**日期** 2026-08-23 · **状态** 生效 · **相关** §5.6、§7.3.1 · 承接 [D11](#d11--用-selector-而不是-urltest)

D11 选了 `selector` 而非 `urltest`,理由是选路的决策者必须只有一个。但当时
漏了一件事:**selector 是手动开关,得有东西去切它。** 渲染出的配置没有任何
控制端点,于是候选集永远停在 `default` 上 —— 调度层做完了也落不了地。

接入节点的配置现在带 `experimental.clash_api`,监听 `127.0.0.1:61800`,
口令走秘密层。Agent 通过它切换当前候选。

**这个洞是"检查一遍"时才发现的**,而它足以让整个 L3 白做:候选枚举、排序、
下发都对,唯独最后一步没有落点。

> **教训:一条链路上任何一环缺失,前面所有环都白做。** 而缺的那一环往往不
> 报错 —— selector 停在 default 上,配置合法、服务正常、流量也通,只是永远
> 走同一条路。

### D21 · 加字段之前先验证下游真的会用它

**日期** 2026-08-23 · **状态** 生效

一个会话里造出了三个"能写、不生效"的东西:

| # | 东西 | 怎么发现的 |
|---|---|---|
| 1 | `direction` 写在纯接入节点上 | 审查时想到 |
| 2 | selector 没有控制端点,永远停在 default | 用户追问"这句话什么意思" |
| 3 | `probe_url` —— delay 接口忽略 `url` 参数 | 读 debug 日志,发现它连的是 `www.gstatic.com` |

第三个最糟:我不但加了字段、加了必填校验、写进了文档,还**据此下过一个错误
结论** —— 对比两个探测目标发现"排序几乎一样",于是判定这个功能没必要。
而那批对比数据本身是假的:两次测的都是同一个目标。

> **判据:一个配置项从写下到生效,中间每一环都要有人验证过。**
> 尤其是最后一环 —— 下游组件真的读了它吗?
>
> 验证成本极低(传一个独特的域名,看日志解析了什么,十秒钟),而不验证的
> 代价是:基于假数据做决策,然后把错误结论写进文档。

**排查这类问题的通用手法:给参数传一个绝不会重合的值,再看下游实际用了什么。**
`neverbefore.example.org` 不出现在日志里,就说明参数被丢了。

### D22 · selector 的默认值不许是直连

**日期** 2026-08-22 · **状态** 生效

原来 selector 的 `default` 取 `tags[0]`,也就是枚举出的第一条候选。枚举零跳
优先,所以**默认永远是直连**。这不是一个决定,是枚举顺序的副产物。

代价是具体的:实测 `best-egress` 的直连候选对目标超时 10 秒,而 sing-box
每次重启都回到 default。于是每次重启后,流量都打在一条已知不通的路上,
直到有人发现。

现在默认取第一条**经过服务器**的候选;只有直连是唯一选项时才用它。一条声明
存在的意义就是绕道,直连是最不该盲选的那个。

这仍然是个静态猜测 —— 真正的选择由 Agent 按实测数据接管(§5.5.1),这里只
保证 Agent 没跑起来的那段时间里不至于停在最差的一个上。

### D23 · 停在死候选上不受阻尼保护

**日期** 2026-08-22 · **状态** 生效

`switch_threshold` 和 `min_samples` 是为了防止在两个**都能用**的候选之间反复
横跳。把它们无差别地套在所有切换上,会得到一个荒谬的结果:当前候选 100%
失败、旁边有候选 100% 可用,而 Agent 因为"样本数不够 6 个"继续等 30 分钟。

所以 Agent 的第一条规则是:**当前候选窗口内全部失败 → 立刻切,不看阈值也不
看样本数。** §5.8 说样本不足的候选"不参与排序也不被淘汰",管的是**选谁**,
不是**要不要离开一具尸体**。

同一个道理的另一半:排序键是 **(失败率分档, 目标指标)**,失败率优先。把失败
折算成"很慢"混进分位数,会让一条 50% 失败但很快的候选赢过 100% 成功但慢
一点的 —— 而用起来一半的请求是错误。失败与快慢不是同一个量纲。

### D24 · 调参字段之间的算术要校验

**日期** 2026-08-22 · **状态** 生效

主动探测一个 `tuning_period` 才出一个样本,所以 `window` 里最多装
`window / tuning_period` 个样本。小于 `min_samples` 时排序永远不会启动。

写这条规则的时候,参考矩阵和真实部署里**每一条声明**都违反它 —— 全都把
`window` 和 `tuning_period` 写成了同一个值,然后要求 20 个样本。

这是 [D21](#d21--加字段之前先验证下游真的会用它) 的延伸:没有消费者的字段
不只是"不生效",它们还会**互相矛盾而没人发现**。字段之间有算术关系时,
校验器要把关系本身钉住,不能只检查每个字段自己合法。

### D25 · "Agent"是两个角色,拆开

**日期** 2026-08-22 · **状态** 生效

被问到"是不是每个拓扑节点都该跑 agent",我原来的回答是"服务器上没有
selector 可切"。这句话是对的,但它回答的是**服务器该不该做决策**(不该,
那是 D11),而不是**服务器该不该跑 agent**。

拆开:

| 角色 | 做什么 | 装在哪 |
|---|---|---|
| **决策者** `internal/agent` | 排序、切 selector | 每个接入节点恰好一个 |
| **上报者** `internal/report` | 观测、自检、如实说 | **每个节点**,服务器也要 |

服务器上不装决策者,不等于服务器上不需要跑任何东西。DDNS 重解析、隧道断连、
有人手工改配置 —— 这些只有节点自己知道,而在此之前全程静默。

上报者上线后**第一次跑就在 5 台机器里的 3 台上找到了真实漂移**:装着的
`sing-box.service` 是 access-a 加入拓扑之前渲染的,缺 `After=wg-quick@wg-access-a`。
后果是重启时 sing-box 可能先于隧道起来。这个问题存在了多久没人知道,因为
在此之前**没有任何东西会去看**。

### D26 · 上报接口只绑隧道内地址,且这是硬错误

**日期** 2026-08-22 · **状态** 生效

上报接口没有自己的认证:能连上隧道内地址,就已经持有 WireGuard 密钥了。
再加一层口令只是多一个要分发和轮换的秘密,换不到实际的隔离。

代价是绑错地址的后果严重(拓扑和隧道健康成为公开信息)**且完全无症状** ——
接口照常工作,没有任何迹象表明它同时对着公网。所以这不是文档里的一句提醒,
而是**加载配置时的硬错误**:主机部分不是私有 IP 或回环就拒绝启动。

没有隧道的纯接入节点绑回环 —— 远端拉不到,但本机 `loom report` 的配置自检
仍然可用。**自检不该因为"拉不到"而整个消失**,那是两件事。

### D27 · 按段量,不按整条路线量

**日期** 2026-08-22 · **状态** 生效

原来的测法是:接入节点把每条完整候选链跑一遍。候选数是 `1 + N + N(N-1)`,
串行探测,而且**每个接入节点各来一遍**。

真正的问题不是慢,是**同一个事实被反复发现**。实测 `best-egress` 的 15 条
候选里有 9 条出口在境内,而境内机器根本到不了目标 —— 这是关于 cn-a 和 cn-b
两台机器的一个事实,却在 9 条不同的链上各被发现一次。

改成:**每台机器只量自己能量的那几段**(到隧道邻居的 RTT、直接访问每个目标
的结果),然后互相交换。cn-a 自己量一次,全网复用。

第一步的收益是剪枝:15 条探测降到 6 条,一轮从 13 秒降到 4 秒。更大的收益
在后面 —— 新接入的设备不必从零攒样本,拉一份现成的表就能排序。

**代价要说清楚:合成估计不等于实测。** 延迟大致能相加,但每多一跳多一次握手,
还有排队和分片。所以用估计排序,再对前几名做一次真实验证。

### D28 · 推论与亲测必须分开标记

**日期** 2026-08-22 · **状态** 生效

按别人的观测剪掉一条候选之后,要不要往度量文件里记一笔?

**要记** —— 不记的话有个洞:当前选中的候选如果正好被剪掉,它在窗口里的**旧
数据**会让排序以为它还健康,流量继续停在一条已知不通的路上,正是
[D23](#d23--停在死候选上不受阻尼保护) 要解决的那个问题。

**但必须标成 `observation_kind: derived`**,与 `active`(亲自探到的)分开。
本机并没有真的发过这个请求;混在一起,回放历史时(§16.5)分不清哪些数字
是真测的。

同一个道理的另一面:剪枝只认**已知不能到**。已知能到、已知不能到、不知道 ——
三个状态,把"不知道"当成"不能到",一台刚加进来还没被观测过的服务器会永远
不被尝试。

### D29 · §6.3 的建议是对的,给的理由过时了

**日期** 2026-08-22 · **状态** 生效(2026-08-22 修正)

§6.3 拒绝为两个 `bidirectional` 节点手工建隧道,理由写的是"该交给 Headscale
自动分发"。而 Headscale 没有部署,所以这条消息读起来像是"这里有个洞"。

**实测下来没有洞。** 两台都能被公网拨到的机器之间,链路本来就走得通:

```
access-a → cn-a>cn-b → baidu   200  272ms
配置:hysteria2 → cn-a 公网,detour 之后 hysteria2 → cn-b 公网
```

隧道只有 `reverse_only` 的服务器才需要 —— 它们拨不进去,只能自己拨出来
(§2.2)。两台 `bidirectional` 之间加隧道确实是白做工,规则的**建议是对的**。

错的是它给的**理由**:今天的替代方案不是"Headscale 会处理",而是
"这两台互相能直接拨,不需要隧道"。留着旧理由的后果是,读到这条消息的人
会去找一个不存在的组件。

> **我当初想加那条隧道的唯一动机,是让 access-a 够到 cn-a 的上报端口** ——
> 那是监控需求,不是数据平面需求,已经由转述解决(§16.1.2)。
> 判断一条规则有没有洞之前,先问清楚"到底是什么东西需要它"。

Headscale 因此仍然是**独立可选项**,不在主线上。

### D30 · apply 的五步顺序,每一条都对应一个踩过的坑

**日期** 2026-08-22 · **状态** 生效

`loom apply` 之前,部署是我一条条手打 scp 和 ssh。三个常驻进程 × 五台机器,
每次都可能漏掉一步 —— 而且**只有我能部署**。

固化下来的顺序是:暂存 → 预检 → 存 previous → 就位重启 → 验证,失败回滚
(§14.2.1)。不是想出来的,是每一条都对应一次真实的失败:

| 步骤 | 对应的坑 |
|---|---|
| 预检在覆盖之前 | 直接覆盖再重启,配置非法 → sing-box 崩溃重启循环,而我只测了新功能 |
| 只重启文件变了的服务 | 一律全重启的话,改一行 sing-box 配置也会断三条隧道 |
| unit 文件只触发 daemon-reload | 改一行 `Description` 不该断线 |
| 验证前先等几秒 | 崩溃循环的第一次崩溃在启动后一两秒,立刻查会看到 active |
| 回滚只碰动过的东西 | 实测:预检失败(什么都没装),回滚却重启了三条隧道 |

另外 **wg-quick 不能用 `systemctl restart`**:down 与 up 之间有竞态,报
`` `wg-xxx' already exists ``,而后果是 **unit 停在 failed、接口其实还在、
隧道看起来是好的** —— 最难查的那种状态。必须显式停、`ip link del`、再起。

### D31 · 备份加不加密必须显式选

**日期** 2026-08-22 · **状态** 生效

`loom backup` 不接受"默认行为"。给 `-passphrase-file` 就加密,给
`-plaintext` 就明文,两者必选其一,都不给直接报错。

两个默认值都会坏事,而且坏在不同的方向:

- **默认明文** —— 人会在不知情的情况下把全网凭据放进网盘。
- **默认加密** —— 人会在没记住口令的情况下以为自己有备份。口令丢了的
  备份和没有备份是一样的,而这件事只有在真的需要它的那天才会发现。

这是 [D3](#d3--无法完整表达的输入一律硬报错不静默降级) 的同一条道理:
两个选项各有严重后果时,不许替人选。

备份只覆盖**不可再生**的东西:秘密层与内部 CA。渲染产物不备份 ——
它们能从 SSOT 再生成,字节完全一样(§12)。

### D32 · 控制面是一棵签了名的静态树,不需要被信任

**日期** 2026-08-22 · **状态** 生效

附录 C #14"控制平面放在哪"一直未定,于是我先做了 ssh 推。被问到"我为什么
要自己部署"才想清楚:**这个问题之所以难,是因为默认假设了控制面必须可信。**

去掉那个假设,问题就没了。渲染产物里全是 `${secret:REF}` 占位符,manifest
有 Ed25519 签名,节点用**本地钉住的公钥**验。于是分发点既看不到凭据,也改
不了内容 —— 它是什么、放在哪、经过谁,都不影响安全性。**一个静态目录足矣。**

现在分发点就是 cn-a 的 nginx 上一个目录,而 cn-a 本身也是被管的节点之一。
这在"控制面必须可信"的假设下是荒唐的,在签名模型下完全正常。

三种篡改都实测过并被拒:改配置包(哈希对不上)、改 manifest(验签失败)、
`current.json` 指向别的快照(id 对不上)。

**签名私钥只在 `loom publish` 用到,不上任何服务器。**

顺带解决了一个此前没意识到的问题:ssh 推传的是**已 hydrate** 的配置,含明文
凭据;改成节点自己填之后,凭据从不离开它该在的机器。`loom secrets split`
按各节点的实际引用拆总表 —— cn-a 拿 3 项,edge-b 拿 2 项,只有 access-a 有控制
端点口令。

### D33 · 期望状态不只是文件内容

**日期** 2026-08-22 · **状态** 生效

`loom pull` 最初拿快照 id 做早退:和本机记录一样就什么都不做。

这是错的。**id 只说明配置来自哪一版,不说明机器现在是不是那个样子。**
实测 cn-b 的 `loom-pull.timer` 一度 `active` 但没 `enable`(重启就没了),
而 pull 每次都报"已是最新,无事可做"。

同一天发现的更严重的一例:**四台机器的全部 `wg-quick` 单元都是 `failed`,
而接口都在、隧道都通。** 任何一台重启,隧道都不会自己回来。这个状态存在了
多久没人知道 —— 因为在此之前,检查的是"接口在不在",而不是"单元该不该在"。

两条改动:

- pull 不再按 id 早退。安装脚本本身幂等(逐文件比哈希),跑一遍很便宜,
  顺带把 enable、服务状态这些**不在文件里**的期望状态拉回来。
- 上报者的隧道检查加上 `wg-quick@<iface>` 的单元状态,与"接口在不在"分开报。

### D34 · 装配置的东西自己也是被装的东西

**日期** 2026-08-22 · **状态** 生效

`loom pull` 的最后一步是重启服务,而它自己就是一个服务。三次踩到同一类坑:

| 触发路径 | 后果 |
|---|---|
| 重启 `loom-pull.service`(oneshot,ExecStart 就是 pull) | 内层那次把外层的回滚清单清空,外层失败时"回滚"成了空操作,机器停在装了一半的状态 |
| timer 带 `Persistent=true` + `OnBootSec` | `enable --now` 立刻触发一次 —— 而 enable 往往就发生在安装阶段里 |
| 定时器那次与手工那次重叠 | 同上 |

前两个按类堵掉:oneshot 单元永不重启、也不进"必须 active"的验证名单
(它跑完就是 inactive);timer 用 `OnActiveSec` 且不 `Persistent`。

第三个用文件锁兜住整类问题 —— **具体路径能一个个堵,但"两个 pull 同时跑"
这件事本身要有一道总闸。**

顺带修了一个相邻的错误:`NRestarts` 是 Service 的属性,Timer 没有。对 timer
查它拿到空串,而 `[ "" = 0 ]` 恒假,于是每次部署都"失败并回滚"。

### D35 · 中控只在"改变系统"时需要,不在"运行系统"时需要

**日期** 2026-08-23 · **状态** 生效

签名私钥只能在一个地方 —— 否则任何一台被拿下就能给全网签配置,签名白做。
发布器必须在私钥旁边,SSOT 必须在发布器看得见的地方。**三样东西塌到同一台
机器上,没得选。** 那台就是中控。

但它比通常说的"控制面"窄得多:

| | 中控有 | 中控**没有** |
|---|---|---|
| SSOT、私钥、发布器 | ✅ | |
| 全网视图 | 有,但每台机器也都有(靠转述,§16.1.2) | |
| 节点运行时依赖 | | ❌ 它挂了,节点照常跑、照常调参、照常上报 |
| 观测依赖 | | ❌ 随便打开哪台都能看全网 |

**它挂了不影响系统运行,只影响改变系统。** 这比典型的控制面好 —— 那种一挂,
你既瞎了也动不了。

当前中控是 access-a,**支持转移**:把 SSOT 和签名私钥搬到另一台,改一下标记。

### D36 · 发布自动化之后,界面就没有"命令台"

**日期** 2026-08-23 · **状态** 设计已定,发布器待实现

如果 SSOT 一改就自动发布,那**界面上每一个写操作都只是"改 SSOT"**。加节点是
改 SSOT,换测试地址是改 SSOT,挪窝也是改 SSOT。

于是不存在"对 cn-a 执行某某"这种通道 —— 而这正是 §12 想要的:节点上的所有
配置都是 SSOT 的渲染输出。开一条"临时改这台"的旁路,等于在系统里造一个
官方认可的漂移来源。

界面能触发的只有**收敛**(立刻拉一次、重新应用一遍),不能制造**分歧**。
真要临时动手,用 ssh —— 那条路本来就在,而且看得出是人为干预。

推论:界面按能力分两层。**读**在每个节点上都有(数据本来就在同一个端口上
无认证提供,换成 HTML 不增加任何面);**写**只在中控一台上。原本"一个运维
五道门"的顾虑,因为写操作收敛到一台而消失了。

### D37 · 节点有四个状态,加和删要对称

**日期** 2026-08-23 · **状态** 生效

原来只有"在 SSOT 里"和"不在 SSOT 里"两个状态,而这不够:

**删掉之后它自己什么都不知道。** 别人不再配到它的隧道,但它的 sing-box 继续
监听、继续用旧凭据接客 —— 而那些凭据是**跨节点共享**的。删掉 edge-a 时,
`cred/access-a-sg` 和 `cred/access-a-eg` 还明文躺在它硬盘上。一台没人管的出口。

改成四个状态(§14.4):正常 → **排空** → **下线** → 移除。

- **排空** `drain`:配置和隧道照旧,但不进候选。迁移期间新旧并存,拿实测
  数据决定何时切。隧道保留是有意的 —— 排空期间还要能观测它。
- **下线** `decommission`:进签名过的 manifest 的 `decommissioned` 名单,
  节点读到自己在里面就停服务、禁自启。

**为什么不用"不在 manifest 里"当停机信号:那是歧义的。** 可能是被删了,也
可能是渲染时漏了一个节点。对歧义信号采取不可逆动作是危险的 —— 缺席只报错并
维持现状,停机要明说。

**秘密不自动销毁。** 销毁不可逆,误签一次就全没了。它要停,不要自毁。

移除之后还有两件机器管不了的事,写进文档是因为**忘掉它们不会有任何症状**:
轮换它持有过的凭据、从内部 CA 吊销它的证书。

### D38 · 离线根密钥当前有意不做

**日期** 2026-08-23 · **状态** 生效(有意降级)

§13.3 要求离线根 CA、中间 CA 加密存储、启动时人工解锁、审计日志。

**5 台机器、一个运维的规模上,这套流程的成本远大于收益。** 当前 CA 私钥与
平台签名私钥都放在中控上,0600,靠 `loom backup` 保存(加密,口令另存)。

记在这里是为了让它是一个**明知的取舍,而不是一处遗漏** —— 两者在代码里
长得一模一样,区别只在有没有人写下来。

什么时候该改回去:出现第二个运维,或者节点数到了"某台机器被拿下的概率不再
可忽略"的量级。

### D39 · 发布器也要收敛,不能只反应文件变化

**日期** 2026-08-23 · **状态** 生效

发布器最自然的写法是"SSOT 变了就发布"。不够。

分发点会以别的方式和真相分叉:被清空、推到一半断线、有人手工动过。只盯文件
变化的发布器对这些无能为力 —— 而它们的表现是"全网停在一个旧快照上,而中控
认为一切正常"。

所以每一轮都比对**分发点当前指向的快照**与**本地算出来的**,不一致就重推。
这和 [D33](#d33--期望状态不只是文件内容)(pull 不按快照 id 早退)是同一条
道理:**期望状态要主动核对,不能等事件通知。**

同一轮里还多做一件事:推完从**节点视角**再取一次。推成功不等于取得到 ——
nginx 路径写错时推送侧完全正常。加上这条检查的第一次运行就抓到了中控自己的
DNS 问题(那台机器上有个无关的 WireGuard 接口把所有域名劫走)。

### D40 · 装文件的那一步必须产出自检清单

**日期** 2026-08-23 · **状态** 生效

配置漂移自检靠一份"绝对路径 → 内容哈希"的清单。清单原本只有
`loom hydrate` 会写 —— 而节点自取根本不经过它。

后果:**每次 pull 之后,机器上的文件更新了而清单没有,自检永远误报"被改过"。**
实测五台机器同时报 `report/config.json` 漂移,而它们装的恰恰是刚发下来的
正确版本。

判据:**产出清单的必须是"最后决定文件内容"的那一步**,不能是旁边某个恰好
也知道内容的命令。现在 `loom pull` 自己算,`loom hydrate` 也算,两条路径
各自保证自己装的东西和清单一致。

这是 [D21](#d21--加字段之前先验证下游真的会用它) 的另一面:那条说"加字段前
先确认下游会读",这条说**加一条新路径时,先确认原路径上的每个副产物都还有人产出**。
