## 一 · 实现期间的推导决定

### D1 · 每条隧道一个 WireGuard 接口,不是一个接口挂多个 peer

**日期** 2026-08-20 · **状态** 生效 · **相关** §17.2、§20.1

标准做法是一个 `wg0` 挂 N 个 peer。这里反过来:节点上每条隧道一个接口,
文件名 `wg-<对端id>.conf`。

**理由(2026-08-21 修订,原理由不成立):**

原来写的理由是"AmneziaWG 的混淆参数是接口级的"。**这条站不住** —— §17.3 明说
参数可以按隧道**或按批次**生成,一个网卡挂多个 peer 用同一批参数完全合法。

**真正的理由是路由选择原理:多台出口服务器都要承载 `AllowedIPs = 0.0.0.0/0`。**
出口流量的目的地是任意公网地址,所以每个出口 peer 都得吃下全部地址空间;而
WireGuard 按目的地址匹配 peer,**同一个网卡上不能有两个 peer 都是 0.0.0.0/0**。
必须分网卡。

**代价:** 接受方每条隧道占一个端口;接口数随隧道数线性增长。在数十节点规模
可接受。

> ⚠️ **不要为了"更简洁"合并成单接口** —— 多个出口会互相覆盖 AllowedIPs,
> 结果是只有一个出口生效,而且不报错。

### D2 · 私钥用 `wg-quick` 的 `PostUp` 引用本地文件

**日期** 2026-08-20 · **状态** 生效 · **相关** §12.1、§13.1 · **部分回答 C16**

渲染层不写 `PrivateKey`,改为:

```
PostUp = wg set %i private-key /etc/loom/secrets/%i.key
```

用 `%i` 让 wg-quick 自己展开接口名,避免文件名与接口名在两处各写一遍。

**理由:** §12 要求配置是 SSOT 的纯函数渲染,§13.1 要求私钥永不离开节点。
平台既然没有私钥,就渲染不出完整文件。这条引用是两者的调和点 —— 渲染层进
快照哈希,秘密层不进。

**仍未定(C16 的其余部分):** `secret_generation` 的记法、轮换流程、
节点首次注册时生成密钥对的具体时机。

### D3 · 无法完整表达的输入一律硬报错,不静默降级

**日期** 2026-08-20 · **状态** 生效 · **相关** §17.2

隧道设了 `obfuscation` 但渲染器尚未实现 §17 参数输出时,`Render` 返回错误
而不是输出一份不带参数的配置。

**理由:** §17.2 说参数全部置零等于标准 WireGuard 行为。静默输出无参数配置,
结果是使用者以为开了混淆而实际没开 —— 这是安全性质上的谎报,比不实现更糟。

**推广:** 未实现的协议进 `render.Result.Skipped` 并由 CLI 显式打印。
渲染少生成了东西,调用方必须看得见。

### D4 · 推导字段不进结构体,靠严格解码拒绝

**日期** 2026-08-20 · **状态** 生效 · **相关** §2.2、§19

`Node` 没有 `mesh_eligible` 字段,`Tunnel` 没有 `initiator` 字段。SSOT 用
`KnownFields(true)` 解码,写这些键直接报错。

**理由:** §19 要求"校验器应拒绝矛盾值"。比起"允许写入再校验一致性",
不给字段更彻底 —— 不存在"写了但被忽略"这个中间状态。

### D5 · 接口名为 `wg-<对端id>`,长度由校验器提前拦截

**日期** 2026-08-20 · **状态** 生效 · **相关** §20.1

Linux `IFNAMSIZ` 是 16(含结尾 NUL),可用 15 字符。校验器检查
`len("wg-"+peerID) <= 15`,超长报错并指名要缩短哪个节点 id。

**理由:** 备选方案是超长时回退到哈希名(如 `wg-a1b2c3d4`)。否决,因为
命名不统一是排障时的额外负担;把约束推给 SSOT 作者更好,而这正是校验器
该做的事。

### D6 · 校验返回全部发现,并按 (节点, 条款) 稳定排序

**日期** 2026-08-20 · **状态** 生效

**理由:** §20.1 的场景是一次维护 24 个互相对应的文件。停在第一个错误会
逼出"改一次跑一次"的循环。排序是为了 CI 输出不抖动。

### D7 · 配置包哈希只覆盖渲染层

**日期** 2026-08-20 · **状态** 生效 · **相关** §12.1、§15.3、§19

`Bundle.Hash()` 不含秘密层,也**不含 SSOT 全局哈希**。

**理由:** 把 SSOT 哈希写进每个文件,会让任何一处改动导致全部文件的 diff
变化,§12.1 要的"看到会改哪些文件的哪些行"就没了。全局哈希属于
`Snapshot.ssot_hash`,不属于文件内容。

### D8 · 技术栈

**日期** 2026-08-20 · **状态** 生效 · **相关** 附录 B

Go 1.27,唯一第三方依赖 `gopkg.in/yaml.v3`。附录 B 选 Go 的理由是渲染器与
校验器要和 Agent 共用同一份实现 —— 跨语言实现同一套规则是长期漂移来源。

### D9 · 凭据在渲染层是占位符,不是明文

**日期** 2026-08-21 · **状态** 生效 · **相关** §12.1、§18 · 扩展自 [D2](#d2--私钥用-wg-quick-的-postup-引用本地文件)

sing-box 配置里的凭据渲染成 `${secret:<secret_ref>}`,由 Agent 在写盘前用本地
秘密层替换。

**理由:** 明文写进渲染层有三个后果 —— `loom diff` 把凭据打到终端、快照哈希
覆盖了它、配置包在整条分发链路上处处是明文。D2 已经为 WireGuard 私钥确立了
"渲染层只写引用"的模式,凭据是同一个问题。

**附带的好处:** 替换失败时 sing-box 会因密码非法而拒绝启动。这正是想要的 ——
总好过拿着字面量 `${secret:...}` 去连然后认证失败。

> ⚠️ **两端必须引用同一个 `secret_ref`。** 中继侧的 user 密码与接入侧的 hop
> 密码指向不同条目时,认证会静默失败。`TestSingBoxPathCorrespondence` 断言这一点
> —— 实现时正是先写错、再被这个测试拦住的。

### D10 · ~~目标选择编码为"目标在隧道中的地址"~~ 已被 D12 推翻

**日期** 2026-08-21 · **状态** ❌ **已推翻**,当天即被 [D12](#d12--目标不是节点出口是路径上的位置) 取代

原方案:落地目标在每条隧道的本端地址上开一个 socks inbound,接入节点的下一跳
链是 `hysteria2(中继公网地址) → socks(目标隧道地址)`。

**为什么推翻:** 它建立在一个错误前提上 —— 把"目标"当成了一类节点。一旦认清
目标只是一个地址(D12),问题本身就消失了:链的最后一跳是**服务器**,它直接
向目标地址发起普通的对外连接。不需要在目标那边装任何东西。

**保留这条记录的价值:** 当模型的层次分错时,会催生出一整套看起来自洽、实际
多余的机制。D10 就是一个例子 —— 它解决的是一个不该存在的问题。

### D11 · 用 selector 而不是 urltest

**日期** 2026-08-21 · **状态** 生效 · **相关** §5.5、§5.6

接入节点每条声明生成一个 `selector` 出站,成员是它的全部 RouteCandidate。
当前选择由 Agent 设置,不用 sing-box 的 `urltest`。

**理由:** §5.6 要求选路的决策者只有一个。`urltest` 会按自己的节奏和判据独立
选路,与 Agent 的 §5.5 阻尼规则形成两个互不知情的决策者 —— 这正是 §5.6 拒绝
"让中继自主选下一跳"的同一条理由。

**附带发现的阻抗不匹配:** `switch_threshold` 在设计里是比率(如 20%),而
sing-box 的 `urltest.tolerance` 是毫秒。即使想用 urltest 也表达不了 §5.5 的
阻尼语义。

**当前状态(2026-08-23 更新):** Agent 已实现(§5.5.1),按 objective 排序并带
阻尼切 selector。Agent 没跑起来时 selector 停在 `default` 上,而 default 刻意
不取直连([D22](#d22--selector-的默认值不许是直连))。以下是原始记录:§20.2 说的
"路径静态指定"。

### D12 · 目标不是节点,出口是路径上的位置

**日期** 2026-08-21 · **状态** 生效 · **这是全项目最重要的一次模型修正** · 已重写 design.md 第一部分

**修正前的模型(错的):**

```
节点能力 = {access, relay, target}
target 分三种形态:落地型 / 端点型(自有) / 端点型(第三方)
路径 = access → relays → target_node
```

**修正后:**

```
Loom 管的:接入节点、服务器节点          ← 只有这两类
Loom 不管的:目标地址                    ← 它不是节点
路径 = 接入节点 → [服务器…] → 目标地址
```

**三条具体的认识:**

| # | 修正 |
|---|---|
| 1 | **目标只是地址。** 自建推理服务和买来的第三方 API,对 Loom 完全同等 —— 都是发请求过去的地址。哪怕那台机器你有 root,Loom 也不管它的网络配置 |
| 2 | **出口不是节点类型,是位置。** 链上最后一台服务器就是这次的出口。同一台北京云机这次是出口,下次可能只是中间一跳 |
| 3 | **服务器之间没有本质区别。** 国内云机和境外 VPS 是同一类东西,区别只有两点:在哪(出口 IP),怎么接入(能被连 / 必须它连出来) |

**推论:**

- 中继当然可以直接访问 API —— 它就是一台有 IP 的服务器。用不用境外 VPS 是
  **选路的结果**,不是架构里预先分好的类;
- `capabilities` 里的 `target` 删除,只剩 `{access, server}`;
- `target_kind`、`managed` 从节点模型移除 —— 前者不存在,后者恒为 true
  (Loom 管的机器都是你的);
- §4 的"模式 A / 模式 B"改成两个独立的轴:**地址轴**(由请求决定 / 从等价类选)
  与**出口轴**(钉死 / 任选)。四种组合都真实存在,原来的两模式只覆盖了两种;
- 中继与落地的配置渲染**合并成一套** —— 服务器就是服务器。

**为什么之前会错:** 把"应用语义"(流量到了那儿干什么)和"管理语义"(这台机器
我能不能动)混成了一维。它们是两件无关的事,而其中一件根本不适用于目标 ——
因为目标压根不在 Loom 的管理范围内。

### D13 · 隧道矩阵只覆盖 `reverse_only` 服务器

**日期** 2026-08-21 · **状态** 结论生效，理由已由 [D29](#d29--63-的建议是对的给的理由过时了) 修正 · **相关** §6.3、§8.3

两个可被公网主动拨号的服务器不需要常驻 WireGuard，当前直接走公网
Hysteria2；只有链路一端是 `reverse_only` 时才产生隧道矩阵条目。Headscale
仍是未部署的独立目标，不能拿它解释当前连通性。

**原理由已过时:** 当时假设 Headscale 负责密钥/peer 自动分发；生产并未部署
Headscale。D29 用真实数据路径说明，当前替代机制是公网 Hysteria2 直拨。

**校验器规则:** 两端都能被主动拨号时，显式 `Tunnel` 报错并提示直接公网拨号；
不要再提示一个尚未部署的 Headscale 会接管。

### D14 · 快照 id 是内容哈希,时间从外部注入

**日期** 2026-08-21 · **状态** 生效 · **相关** §12、§19

快照 id = 除 `created_at` 与 `author` 外全部内容的 SHA-256 前 12 位。
时间与作者由**调用方传入**,`snapshot.Build` 自己不读时钟。

**两个理由:**

1. **打包必须和渲染一样是确定的。** §12 要求渲染是纯函数;如果打包过程
   读时钟,那"同样输入产生同样字节"就断在最后一步,而签名恰恰针对那串字节。
2. **id 相同就意味着产物没变。** 同一份 SSOT 隔天再打一次,id 一样 ——
   "这次改动有没有实际影响产物"于是变成一眼能看出的事,不必逐文件比对。

`created_at` 照常如实记录,只是不进 id。

### D15 · 签名放在旁文件,不放进 manifest

**日期** 2026-08-21 · **状态** 生效 · **相关** §14.3

产物是 `snapshot.json` + `snapshot.sig` 两个文件,而不是把签名字段塞进
manifest。

**理由:** 签名针对的必须是**确切的那串字节**。签名如果在 manifest 内部,
校验时就要先把它挖掉、再重新序列化一遍 —— 而"重新序列化出来的字节"与
"当初签的字节"是否逐字节相同,取决于序列化实现的稳定性。这是一类不必要的
风险,分成两个文件就不存在。

> §19 的 `Snapshot` 里列了 `signature` 字段,那是概念模型;落到磁盘上它是
> 旁文件。二者不冲突。

### D16 · 一台机器一把 WireGuard 私钥,放在 `/etc/wireguard/node.key`

**日期** 2026-08-22 · **状态** 生效 · **相关** §13.1、§12.1 · **上真机时才暴露的两个 bug**

原来渲染的是 `/etc/loom/secrets/%i.key` —— 按接口名展开,即**一条隧道一把私钥**。
两处都错:

**错误一:私钥应当按机器而非按隧道。** SSOT 里每个节点只有一个
`wg_public_key`。若各接口用不同私钥,对端拿到的公钥就对不上。同一把私钥用在
多个接口上是合法的 —— 对端靠公钥认身份,而身份本来就该一致。

**错误二:路径必须在 `/etc/wireguard/` 下。** Ubuntu 24.04+ 给 `wg` 上了
AppArmor profile,只允许:

```
file rw @{etc_rw}/wireguard/{,**},
```

放在别处会被拒:

```
apparmor="DENIED" profile="wg" name="/etc/loom/secrets/node.key" denied_mask="r"
```

**表现极具迷惑性:** `wg-quick up` 打印一行 `fopen: Permission denied`,
删掉刚建好的接口,**然后退出码仍是 0**。看起来像成功了。

给每台机器加 AppArmor 例外(profile 里有 `include if exists <local/wg>`)也能解,
但那是在削弱一个本该存在的防护;换个路径不花任何代价,而且 `/etc/wireguard/`
本来就是 WireGuard 密钥的惯例位置。

> **"秘密层"是个概念,不是一个目录。** 不同类型的秘密可以放在各自消费者
> 期望的位置 —— 这不违反 [D2](#d2--私钥用-wg-quick-的-postup-引用本地文件),
> 渲染层依然只写引用。

### D17 · `ClientProfile` 并入 `Node`,端口范围改 61617-61799

**日期** 2026-08-23 · **状态** 生效 · **相关** §1、§7

**合并的理由:** §1 说只有两类节点,但模型里 `ClientProfile` 是独立实体,和
`capabilities: [access]` 表达同一件事。两张表装同一个东西,还逼出一条
"档案 id 不能与节点 id 重名"的规则 —— 那条规则是为规避输出目录冲突而发明的,
本身就是重复建模的症状。

真正推动它的是把 access-a 加进拓扑:同一台机器不能既是"节点"又是另一张表里的
"档案"。合并后 `Node` 吸收 `platform` / `credentials` / `mixed_ports` /
`default_declaration`,那条规避规则删除。

**端口范围** 从 61610-61699 改为 **61617-61799**(与实际放行的一致)。
现有端口(61619/61637/61654/61682/61698)全都落在新范围内,无需改动。

### D19 · 角色字段分块,`capabilities` 由块推导

**日期** 2026-08-23 · **状态** 生效 · **相关** §1.1、§1.3 · 取代 [D18](#d18--惰性字段按能力拒绝-已被-d19-取代)

```yaml
- id: cn-a
  city: 广州
  server:                    # 这个块存在 = 持有 server 能力
    direction: bidirectional
    inbound_port: 61698

- id: access-a
  city: 北京
  access:                    # 这个块存在 = 持有 access 能力
    platform: linux-server
    credentials: [...]

```

**两个块都有也合法** —— 一台服务器自己也要走代理出去,是真实需求。渲染器
把两边合并进同一份 sing-box 配置(一台机器一个进程)。

> **曾经短暂地禁止过双角色,理由是"两类节点走两个控制面、会互相覆盖"。
> 那个论证是错的:配置源只有一个**(SSOT → 渲染器),投递也只有该机的
> Agent 一条。§18 那套一次性链接是给没有 Agent 的设备用的,而那种设备只
> 可能是纯接入节点。把"投递渠道不同"当成了"配置源不同"。

**`capabilities` 字段删除。** 它与角色块是同一个事实的两次编码 —— 写了
`capabilities: [server]` 却不给 `server` 块(或反过来)就是自相矛盾,而那
正是 [D4](#d4--推导字段不进结构体靠严格解码拒绝) 要消灭的东西。

**收益:惰性字段变成不可表达,而不是被拒绝。** 把 `direction` 写进 `access`
块,严格解码在**加载阶段**就失败,根本到不了校验器:

```
field direction not found in type model.AccessRole
```

D18 那 30 行 `checkRoleFields` 随之删除。对应的测试也从"校验器拒绝"下移到
"解码器拒绝"(`model.TestLoadRejectsDerivedFields`)。

> **判据:需要运行时校验来保证字段共现,就说明类型分错了。** 校验器该管的是
> 跨实体的一致性(隧道两端对不对得上、引用存不存在),不是同一个实体内部
> 哪些字段该一起出现 —— 后者是类型的职责。

### D20 · selector 必须配一个能切它的端点

**日期** 2026-08-23 · **状态** 生效 · **相关** §5.6、§7.3.1 · 承接 [D11](#d11--用-selector-而不是-urltest)

D11 选了 `selector` 而非 `urltest`,理由是选路的决策者必须只有一个。但当时
漏了一件事:**selector 是手动开关,得有东西去切它。** 渲染出的配置没有任何
控制端点,于是候选集永远停在 `default` 上 —— 调度层做完了也落不了地。

接入节点的配置现在带 `experimental.clash_api`,监听 `127.0.0.1:61800`,
口令走秘密层。Agent 通过它切换当前候选。

**这个洞是"检查一遍"时才发现的**,而它足以让整个 L3 白做:候选枚举、排序、
下发都对,唯独最后一步没有落点。

> **教训:一条链路上任何一环缺失,前面所有环都白做。** 而缺的那一环往往不
> 报错 —— selector 停在 default 上,配置合法、服务正常、流量也通,只是永远
> 走同一条路。

### D21 · 加字段之前先验证下游真的会用它

**日期** 2026-08-23 · **状态** 生效

一个会话里造出了三个"能写、不生效"的东西:

| # | 东西 | 怎么发现的 |
|---|---|---|
| 1 | `direction` 写在纯接入节点上 | 审查时想到 |
| 2 | selector 没有控制端点,永远停在 default | 用户追问"这句话什么意思" |
| 3 | `probe_url` —— delay 接口忽略 `url` 参数 | 读 debug 日志,发现它连的是 `www.gstatic.com` |

第三个最糟:我不但加了字段、加了必填校验、写进了文档,还**据此下过一个错误
结论** —— 对比两个探测目标发现"排序几乎一样",于是判定这个功能没必要。
而那批对比数据本身是假的:两次测的都是同一个目标。

> **判据:一个配置项从写下到生效,中间每一环都要有人验证过。**
> 尤其是最后一环 —— 下游组件真的读了它吗?
>
> 验证成本极低(传一个独特的域名,看日志解析了什么,十秒钟),而不验证的
> 代价是:基于假数据做决策,然后把错误结论写进文档。

**排查这类问题的通用手法:给参数传一个绝不会重合的值,再看下游实际用了什么。**
`neverbefore.example.org` 不出现在日志里,就说明参数被丢了。

### D22 · selector 的默认值不许是直连

**日期** 2026-08-22 · **状态** 生效

原来 selector 的 `default` 取 `tags[0]`,也就是枚举出的第一条候选。枚举零跳
优先,所以**默认永远是直连**。这不是一个决定,是枚举顺序的副产物。

代价是具体的:实测 `best-egress` 的直连候选对目标超时 10 秒,而 sing-box
每次重启都回到 default。于是每次重启后,流量都打在一条已知不通的路上,
直到有人发现。

现在默认取第一条**经过服务器**的候选;只有直连是唯一选项时才用它。一条声明
存在的意义就是绕道,直连是最不该盲选的那个。

这仍然是个静态猜测 —— 真正的选择由 Agent 按实测数据接管(§5.5.1),这里只
保证 Agent 没跑起来的那段时间里不至于停在最差的一个上。

### D23 · 停在死候选上不受阻尼保护

**日期** 2026-08-22 · **状态** 生效

`switch_threshold` 和 `min_samples` 是为了防止在两个**都能用**的候选之间反复
横跳。把它们无差别地套在所有切换上,会得到一个荒谬的结果:当前候选 100%
失败、旁边有候选 100% 可用,而 Agent 因为"样本数不够 6 个"继续等 30 分钟。

所以 Agent 的第一条规则是:**当前候选窗口内全部失败 → 立刻切,不看阈值也不
看样本数。** §5.8 说样本不足的候选"不参与排序也不被淘汰",管的是**选谁**,
不是**要不要离开一具尸体**。

同一个道理的另一半:排序键是 **(失败率分档, 目标指标)**,失败率优先。把失败
折算成"很慢"混进分位数,会让一条 50% 失败但很快的候选赢过 100% 成功但慢
一点的 —— 而用起来一半的请求是错误。失败与快慢不是同一个量纲。

### D24 · 调参字段之间的算术要校验

**日期** 2026-08-22 · **状态** 生效

主动探测一个 `tuning_period` 才出一个样本,所以 `window` 里最多装
`window / tuning_period` 个样本。小于 `min_samples` 时排序永远不会启动。

写这条规则的时候,参考矩阵和真实部署里**每一条声明**都违反它 —— 全都把
`window` 和 `tuning_period` 写成了同一个值,然后要求 20 个样本。

这是 [D21](#d21--加字段之前先验证下游真的会用它) 的延伸:没有消费者的字段
不只是"不生效",它们还会**互相矛盾而没人发现**。字段之间有算术关系时,
校验器要把关系本身钉住,不能只检查每个字段自己合法。

### D25 · "Agent"是两个角色,拆开

**日期** 2026-08-22 · **状态** 生效

被问到"是不是每个拓扑节点都该跑 agent",我原来的回答是"服务器上没有
selector 可切"。这句话是对的,但它回答的是**服务器该不该做决策**(不该,
那是 D11),而不是**服务器该不该跑 agent**。

拆开:

| 角色 | 做什么 | 装在哪 |
|---|---|---|
| **决策者** `internal/agent` | 排序、切 selector | 每个接入节点恰好一个 |
| **上报者** `internal/report` | 观测、自检、如实说 | **每个节点**,服务器也要 |

服务器上不装决策者,不等于服务器上不需要跑任何东西。DDNS 重解析、隧道断连、
有人手工改配置 —— 这些只有节点自己知道,而在此之前全程静默。

上报者上线后**第一次跑就在 5 台机器里的 3 台上找到了真实漂移**:装着的
`sing-box.service` 是 access-a 加入拓扑之前渲染的,缺 `After=wg-quick@wg-access-a`。
后果是重启时 sing-box 可能先于隧道起来。这个问题存在了多久没人知道,因为
在此之前**没有任何东西会去看**。

### D26 · 上报接口只绑隧道内地址,且这是硬错误

**日期** 2026-08-22 · **状态** 生效

上报接口没有自己的认证:能连上隧道内地址,就已经持有 WireGuard 密钥了。
再加一层口令只是多一个要分发和轮换的秘密,换不到实际的隔离。

代价是绑错地址的后果严重(拓扑和隧道健康成为公开信息)**且完全无症状** ——
接口照常工作,没有任何迹象表明它同时对着公网。所以这不是文档里的一句提醒,
而是**加载配置时的硬错误**:主机部分不是私有 IP 或回环就拒绝启动。

没有隧道的纯接入节点绑回环 —— 远端拉不到,但本机 `loom report` 的配置自检
仍然可用。**自检不该因为"拉不到"而整个消失**,那是两件事。

### D27 · 按段量,不按整条路线量

**日期** 2026-08-22 · **状态** 生效

原来的测法是:接入节点把每条完整候选链跑一遍。候选数是 `1 + N + N(N-1)`,
串行探测,而且**每个接入节点各来一遍**。

真正的问题不是慢,是**同一个事实被反复发现**。实测 `best-egress` 的 15 条
候选里有 9 条出口在境内,而境内机器根本到不了目标 —— 这是关于 cn-a 和 cn-b
两台机器的一个事实,却在 9 条不同的链上各被发现一次。

改成:**每台机器只量自己能量的那几段**(到隧道邻居的 RTT、直接访问每个目标
的结果),然后互相交换。cn-a 自己量一次,全网复用。

第一步的收益是剪枝:15 条探测降到 6 条,一轮从 13 秒降到 4 秒。更大的收益
在后面 —— 新接入的设备不必从零攒样本,拉一份现成的表就能排序。

**代价要说清楚:合成估计不等于实测。** 延迟大致能相加,但每多一跳多一次握手,
还有排队和分片。所以用估计排序,再对前几名做一次真实验证。

### D28 · 推论与亲测必须分开标记

**日期** 2026-08-22 · **状态** 生效

按别人的观测剪掉一条候选之后,要不要往度量文件里记一笔?

**要记** —— 不记的话有个洞:当前选中的候选如果正好被剪掉,它在窗口里的**旧
数据**会让排序以为它还健康,流量继续停在一条已知不通的路上,正是
[D23](#d23--停在死候选上不受阻尼保护) 要解决的那个问题。

**但必须标成 `observation_kind: derived`**,与 `active`(亲自探到的)分开。
本机并没有真的发过这个请求;混在一起,回放历史时(§16.5)分不清哪些数字
是真测的。

同一个道理的另一面:剪枝只认**已知不能到**。已知能到、已知不能到、不知道 ——
三个状态,把"不知道"当成"不能到",一台刚加进来还没被观测过的服务器会永远
不被尝试。

### D29 · §6.3 的建议是对的,给的理由过时了

**日期** 2026-08-22 · **状态** 生效(2026-08-22 修正)

§6.3 拒绝为两个 `bidirectional` 节点手工建隧道,理由写的是"该交给 Headscale
自动分发"。而 Headscale 没有部署,所以这条消息读起来像是"这里有个洞"。

**实测下来没有洞。** 两台都能被公网拨到的机器之间,链路本来就走得通:

```
access-a → cn-a>cn-b → baidu   200  272ms
配置:hysteria2 → cn-a 公网,detour 之后 hysteria2 → cn-b 公网
```

隧道只有 `reverse_only` 的服务器才需要 —— 它们拨不进去,只能自己拨出来
(§2.2)。两台 `bidirectional` 之间加隧道确实是白做工,规则的**建议是对的**。

错的是它给的**理由**:今天的替代方案不是"Headscale 会处理",而是
"这两台互相能直接拨,不需要隧道"。留着旧理由的后果是,读到这条消息的人
会去找一个不存在的组件。

> **我当初想加那条隧道的唯一动机,是让 access-a 够到 cn-a 的上报端口** ——
> 那是监控需求,不是数据平面需求,已经由转述解决(§16.1.2)。
> 判断一条规则有没有洞之前,先问清楚"到底是什么东西需要它"。

Headscale 因此仍然是**独立可选项**,不在主线上。

### D30 · apply 的五步顺序,每一条都对应一个踩过的坑

**日期** 2026-08-22 · **状态** 生效

`loom apply` 之前,部署是我一条条手打 scp 和 ssh。三个常驻进程 × 五台机器,
每次都可能漏掉一步 —— 而且**只有我能部署**。

固化下来的顺序是:暂存 → 预检 → 存 previous → 就位重启 → 验证,失败回滚
(§14.2.1)。不是想出来的,是每一条都对应一次真实的失败:

| 步骤 | 对应的坑 |
|---|---|
| 预检在覆盖之前 | 直接覆盖再重启,配置非法 → sing-box 崩溃重启循环,而我只测了新功能 |
| 只重启文件变了的服务 | 一律全重启的话,改一行 sing-box 配置也会断三条隧道 |
| unit 文件变化重启对应常驻 service | `ExecStart` / Capability / sandbox 只有新进程才生效；只 `daemon-reload` 会被旧进程的 active 假绿骗过 |
| 验证前先等几秒 | 崩溃循环的第一次崩溃在启动后一两秒,立刻查会看到 active |
| 回滚只碰动过的东西 | 实测:预检失败(什么都没装),回滚却重启了三条隧道 |

另外 **wg-quick 不能用 `systemctl restart`**:down 与 up 之间有竞态,报
`` `wg-xxx' already exists ``,而后果是 **unit 停在 failed、接口其实还在、
隧道看起来是好的** —— 最难查的那种状态。必须显式停、`ip link del`、再起。

### D31 · 备份加不加密必须显式选

**日期** 2026-08-22 · **状态** 生效

`loom backup` 不接受"默认行为"。给 `-passphrase-file` 就加密,给
`-plaintext` 就明文,两者必选其一,都不给直接报错。

两个默认值都会坏事,而且坏在不同的方向:

- **默认明文** —— 人会在不知情的情况下把全网凭据放进网盘。
- **默认加密** —— 人会在没记住口令的情况下以为自己有备份。口令丢了的
  备份和没有备份是一样的,而这件事只有在真的需要它的那天才会发现。

这是 [D3](#d3--无法完整表达的输入一律硬报错不静默降级) 的同一条道理:
两个选项各有严重后果时,不许替人选。

备份只覆盖**不可再生**的东西:秘密层与内部 CA。渲染产物不备份 ——
它们能从 SSOT 再生成,字节完全一样(§12)。

### D32 · 控制面是一棵签了名的静态树,不需要被信任

**日期** 2026-08-22 · **状态** 生效

附录 C #14"控制平面放在哪"一直未定,于是我先做了 ssh 推。被问到"我为什么
要自己部署"才想清楚:**这个问题之所以难,是因为默认假设了控制面必须可信。**

去掉那个假设,问题就没了。渲染产物里全是 `${secret:REF}` 占位符,manifest
有 Ed25519 签名,节点用**本地钉住的公钥**验。于是分发点既看不到凭据,也改
不了内容 —— 它是什么、放在哪、经过谁,都不影响安全性。**一个静态目录足矣。**

现在分发点就是 cn-a 的 nginx 上一个目录,而 cn-a 本身也是被管的节点之一。
这在"控制面必须可信"的假设下是荒唐的,在签名模型下完全正常。

三种篡改都实测过并被拒:改配置包(哈希对不上)、改 manifest(验签失败)、
`current.json` 指向别的快照(id 对不上)。

**签名私钥只在 `loom publish` 用到,不上任何服务器。**

顺带解决了一个此前没意识到的问题:ssh 推传的是**已 hydrate** 的配置,含明文
凭据;改成节点自己填之后,凭据从不离开它该在的机器。`loom secrets split`
按各节点的实际引用拆总表 —— cn-a 拿 3 项,edge-b 拿 2 项,只有 access-a 有控制
端点口令。

### D33 · 期望状态不只是文件内容

**日期** 2026-08-22 · **状态** 生效

`loom pull` 最初拿快照 id 做早退:和本机记录一样就什么都不做。

这是错的。**id 只说明配置来自哪一版,不说明机器现在是不是那个样子。**
实测 cn-b 的 `loom-pull.timer` 一度 `active` 但没 `enable`(重启就没了),
而 pull 每次都报"已是最新,无事可做"。

同一天发现的更严重的一例:**四台机器的全部 `wg-quick` 单元都是 `failed`,
而接口都在、隧道都通。** 任何一台重启,隧道都不会自己回来。这个状态存在了
多久没人知道 —— 因为在此之前,检查的是"接口在不在",而不是"单元该不该在"。

两条改动:

- pull 不再按 id 早退。安装脚本本身幂等(逐文件比哈希),跑一遍很便宜,
  顺带把 enable、服务状态这些**不在文件里**的期望状态拉回来。
- 上报者的隧道检查加上 `wg-quick@<iface>` 的单元状态,与"接口在不在"分开报。

### D34 · 装配置的东西自己也是被装的东西

**日期** 2026-08-22 · **状态** 生效

`loom pull` 的最后一步是重启服务,而它自己就是一个服务。三次踩到同一类坑:

| 触发路径 | 后果 |
|---|---|
| 重启 `loom-pull.service`(oneshot,ExecStart 就是 pull) | 内层那次把外层的回滚清单清空,外层失败时"回滚"成了空操作,机器停在装了一半的状态 |
| timer 带 `Persistent=true` + `OnBootSec` | `enable --now` 立刻触发一次 —— 而 enable 往往就发生在安装阶段里 |
| 定时器那次与手工那次重叠 | 同上 |

前两个按类堵掉:oneshot 单元永不重启、也不进"必须 active"的验证名单
(它跑完就是 inactive);timer 用 `OnActiveSec` 且不 `Persistent`。

第三个用文件锁兜住整类问题 —— **具体路径能一个个堵,但"两个 pull 同时跑"
这件事本身要有一道总闸。**

顺带修了一个相邻的错误:`NRestarts` 是 Service 的属性,Timer 没有。对 timer
查它拿到空串,而 `[ "" = 0 ]` 恒假,于是每次部署都"失败并回滚"。

### D35 · 中控只在"改变系统"时需要,不在"运行系统"时需要

**日期** 2026-08-23 · **状态** 生效

签名私钥只能在一个地方 —— 否则任何一台被拿下就能给全网签配置,签名白做。
发布器必须在私钥旁边,SSOT 必须在发布器看得见的地方。**三样东西塌到同一台
机器上,没得选。** 那台就是中控。

但它比通常说的"控制面"窄得多:

| | 中控有 | 中控**没有** |
|---|---|---|
| SSOT、私钥、发布器 | ✅ | |
| 全网视图 | 有,但每台机器也都有(靠转述,§16.1.2) | |
| 节点运行时依赖 | | ❌ 它挂了,节点照常跑、照常调参、照常上报 |
| 观测依赖 | | ❌ 随便打开哪台都能看全网 |

**它挂了不影响系统运行,只影响改变系统。** 这比典型的控制面好 —— 那种一挂,
你既瞎了也动不了。

中控节点**支持转移**:把 SSOT 和签名私钥搬到另一台,改一下标记。

### D36 · 发布自动化之后,界面就没有"命令台"

**日期** 2026-08-23 · **状态** 设计已定,发布器待实现

如果 SSOT 一改就自动发布,那**界面上每一个写操作都只是"改 SSOT"**。加节点是
改 SSOT,换测试地址是改 SSOT,挪窝也是改 SSOT。

于是不存在"对 cn-a 执行某某"这种通道 —— 而这正是 §12 想要的:节点上的所有
配置都是 SSOT 的渲染输出。开一条"临时改这台"的旁路,等于在系统里造一个
官方认可的漂移来源。

界面能触发的只有**收敛**(立刻拉一次、重新应用一遍),不能制造**分歧**。
真要临时动手,用 ssh —— 那条路本来就在,而且看得出是人为干预。

推论:界面按能力分两层。**读**在每个节点上都有(数据本来就在同一个端口上
无认证提供,换成 HTML 不增加任何面);**写**只在中控一台上。原本"一个运维
五道门"的顾虑,因为写操作收敛到一台而消失了。

### D37 · 节点有四个状态,加和删要对称

**日期** 2026-08-23 · **状态** 生效

原来只有"在 SSOT 里"和"不在 SSOT 里"两个状态,而这不够:

**删掉之后它自己什么都不知道。** 别人不再配到它的隧道,但它的 sing-box 继续
监听、继续用旧凭据接客 —— 而那些凭据是**跨节点共享**的。删掉 edge-a 时,
`cred/access-a-sg` 和 `cred/access-a-eg` 还明文躺在它硬盘上。一台没人管的出口。

改成四个状态(§14.4):正常 → **排空** → **下线** → 移除。

- **排空** `drain`:配置和隧道照旧,但不进候选。迁移期间新旧并存,拿实测
  数据决定何时切。隧道保留是有意的 —— 排空期间还要能观测它。
- **下线** `decommission`:进签名过的 manifest 的 `decommissioned` 名单,
  节点读到自己在里面就停服务、禁自启。

**为什么不用"不在 manifest 里"当停机信号:那是歧义的。** 可能是被删了,也
可能是渲染时漏了一个节点。对歧义信号采取不可逆动作是危险的 —— 缺席只报错并
维持现状,停机要明说。

**秘密不自动销毁。** 销毁不可逆,误签一次就全没了。它要停,不要自毁。

移除之后还有两件机器管不了的事,写进文档是因为**忘掉它们不会有任何症状**:
轮换它持有过的凭据、从内部 CA 吊销它的证书。

### D38 · 离线根密钥当前有意不做

**日期** 2026-08-23 · **状态** 生效(有意降级)

§13.3 要求离线根 CA、中间 CA 加密存储、启动时人工解锁、审计日志。

**5 台机器、一个运维的规模上,这套流程的成本远大于收益。** 当前 CA 私钥与
平台签名私钥都放在中控上,0600,靠 `loom backup` 保存(加密,口令另存)。

记在这里是为了让它是一个**明知的取舍,而不是一处遗漏** —— 两者在代码里
长得一模一样,区别只在有没有人写下来。

什么时候该改回去:出现第二个运维,或者节点数到了"某台机器被拿下的概率不再
可忽略"的量级。

### D39 · 发布器也要收敛,不能只反应文件变化

**日期** 2026-08-23 · **状态** 生效

发布器最自然的写法是"SSOT 变了就发布"。不够。

分发点会以别的方式和真相分叉:被清空、推到一半断线、有人手工动过。只盯文件
变化的发布器对这些无能为力 —— 而它们的表现是"全网停在一个旧快照上,而中控
认为一切正常"。

所以每一轮都比对**分发点当前指向的快照**与**本地算出来的**,不一致就重推。
这和 [D33](#d33--期望状态不只是文件内容)(pull 不按快照 id 早退)是同一条
道理:**期望状态要主动核对,不能等事件通知。**

同一轮里还多做一件事:推完从**节点视角**再取一次。推成功不等于取得到 ——
nginx 路径写错时推送侧完全正常。加上这条检查的第一次运行就抓到了中控自己的
DNS 问题(那台机器上有个无关的 WireGuard 接口把所有域名劫走)。

### D40 · 装文件的那一步必须产出自检清单

**日期** 2026-08-23 · **状态** 生效

配置漂移自检靠一份"绝对路径 → 内容哈希"的清单。清单原本只有
`loom hydrate` 会写 —— 而节点自取根本不经过它。

后果:**每次 pull 之后,机器上的文件更新了而清单没有,自检永远误报"被改过"。**
实测五台机器同时报 `report/config.json` 漂移,而它们装的恰恰是刚发下来的
正确版本。

判据:**产出清单的必须是"最后决定文件内容"的那一步**,不能是旁边某个恰好
也知道内容的命令。现在 `loom pull` 自己算,`loom hydrate` 也算,两条路径
各自保证自己装的东西和清单一致。

这是 [D21](#d21--加字段之前先验证下游真的会用它) 的另一面:那条说"加字段前
先确认下游会读",这条说**加一条新路径时,先确认原路径上的每个副产物都还有人产出**。

### D41 · 界面上的校验按钮不是守卫

**日期** 2026-08-23 · **状态** 生效

中控界面能改 SSOT。页面上有"只校验"和"校验并保存"两个按钮 —— 而**保存路径
必须在服务端自己再校验一次**,不能信任前一个按钮点过。

理由不只是"表单可以被直接 POST"。真正的问题是**失败模式很隐蔽**:一份坏
SSOT 存进去不会有任何提示,发布器随后拒绝发布,线上停在旧快照。症状是
"我改了但没生效",而人第一反应会去查发布器、查网络、查节点,最后才想到
是自己存进去的东西根本没通过校验。

**在能挡住的地方挡住,而不是在能报错的地方报错。**

顺带两条同类的:

- 写盘用同目录临时文件加改名。发布器可能正好在读,半截 YAML 会让它报一个
  跟真实原因毫不相干的解析错误。
- 中控取不到运维口令时,写操作**全部关闭**,而不是退化成"不需要认证"。

### D42 · `<什么>/<节点 id>` 形式的引用归那个节点

**日期** 2026-08-23 · **状态** 生效

`loom secrets split` 原本只按"渲染产物里引用到了什么"来拆总表。中控界面的
运维口令 `ui/access-a` 不出现在任何渲染文件里(它由本机 bootstrap 配置读取),
于是每次重新拆分都会把它丢掉 —— 症状是"界面突然登不进去了"。

规则改成:渲染产物里引用到的,**加上**任何形如 `<什么>/<本节点 id>` 的引用。

这条规则也顺带解释了 `api/<节点>` 和 `probe/<节点>` 为什么长这样 —— 它们
本来就是节点私有的秘密,只是恰好也被渲染产物引用了。命名规范因此变成一条
可执行的约定,而不只是习惯。

### D43 · §5.6 曾经假设"地址不影响该选哪条链",这是错的

**日期** 2026-08-23 · **状态** 生效(修正 §5.6)

§5.6 原来写着:地址轴为"由请求决定"时,**"候选集里地址是常量,只在服务器
链上选"**。我照着实现了很久 —— 一条声明一个 selector,一个候选,所有目标
共用。

那句话把两件事混为一谈:**"地址不由我们选"**(对)和**"地址不影响该选哪条
链"**(错)。地址不是我们的*选择*,但它是决定该走哪条链的*输入*。

实测:

| 目标 | 经 edge-b | 经 cn-a | 直连 |
|---|---|---|---|
| `www.baidu.com` | 1.464s | 0.145s | **0.058s** |
| `www.aliyun.com` | 1.175s | 0.182s | **0.056s** |
| `api.ipify.org` | **0.401s** | 失败 | 失败 |

**没有任何一条候选对三个目标都好。** 而 `best-egress` 给整条声明选了 edge-b,
于是访问 baidu 慢了 25 倍 —— 一个我自己每天在用、而从来没测过的场景。

这条记在这里,是因为它和别的 bug 不是一类:**代码忠实地实现了文档,而文档
是错的。** 测试全绿、校验全过、部署全通,都发现不了。发现它的是"拿真实
目标测一遍"这个动作本身。

### D44 · 接入端只能选服务,不能指定地址

**日期** 2026-08-23 · **状态** 生效(2026-08-23 实现并真机验证)

修正 [D43](#d43--56-曾经假设地址不影响该选哪条链这是错的) 有两条路:让目标
集合开放、按目标学习;或者**让中控声明服务清单,接入端只能从中选**。

选后者。它一次消掉三个难题:

| | 开放目标集 | 服务清单 |
|---|---|---|
| 冷启动 | 第一个请求必然是猜 | **不存在** —— 服务上线前就能测完 |
| 分组 | 靠域名后缀 / ASN 推断,会错 | **已知**,声明的 |
| 被动观测 | **必须**(没有别的数据来源) | 回到"优先但可选" |

还有两个额外的好处:

**安全边界。** 接入端能指定任意 URL,意味着一份泄露的凭据能把服务器变成开放
代理。§8.2 的准入校验只管"允许走哪",服务清单把它扩展到"允许去哪"。

**请求带上了语义。** "我要服务 X"而不是"我要这个 URL",于是按服务的配额、
objective、归因才成立。

推论:如果服务按地址集合声明,数据平面可以**从请求的 host 反查服务** ——
接入端连"我要哪个服务"都不用说,这才是完整的"接入端不知道任何事情"。

代价是任意 URL 用不了。而这应当是一个**显式声明的服务**("我不知道里面有
什么" + 明确的兜底策略),不是默认假设 —— 区别在于显式声明时你知道自己在
放弃什么。

### D45 · 事件只记变化,而且记在中控一处

**日期** 2026-08-23 · **状态** 生效

被问到"为什么不推给中控端和其他节点"。查完发现我把一整层跳过去了:

**"推给其他节点"已经在做了** —— 转述每分钟传一轮,全网一分钟内都知道。
传输不是问题。

**真正缺的是:只有"现在",没有"曾经"。** 转述表每个观测者只留最新一份,
旧的被覆盖;度量文件里只有探测结果,没有隧道健康。所以"隧道昨晚断了 20
分钟"这件事无法回答,之前四台机器的 `wg-quick` 坏了多久也查不到。

三条判据:

**只记变化。** 两次观测不同才产生记录。一次 69 秒的断连是两条,不是 70 条。

**`From` 和 `To` 都要记。** 只记 `To` 的话,"从坏变好"和"一直是好的"
在日志里长得一样。

**记在中控一处,不是每个节点。** 每个节点视图相同,记 N 份只会让人不知道
看哪份。代价:中控停了就不记 —— 写下来,不装作没有。

分层因此是四段,而我上一次只说了第一和第四段:

```
每个节点发现问题     ✅ 自检
其他节点都知道       ✅ 转述,1 分钟传遍
中控记下来           ✅ 本条
把人拉过来           ❌ 需要外部通道
```

**第四段不能用前三段代替。** §16.3 早就写着"告警通道不能依赖被管网络",
而事件日志恰恰在被管网络里面。它是事后查的,不是叫人的。

做第四段之前值得先看一段时间事件日志 —— 那时才知道**多久发生一次值得被
吵醒的事**,而这个问题在有历史之前只能猜。

### D46 · 先装二进制,后装配置

**日期** 2026-08-23 · **状态** 生效

配对失败的方向不对称:**新版通常读得懂旧配置,旧版读不懂新配置。**

不是推测。发布器崩过一次:它跑着旧二进制,而 SSOT 里多了 `services` 字段,
于是直接拒绝发布,而症状是"改了 SSOT 但全网没动"。

所以 `loom pull` 换完二进制**就结束这一轮**,配置留给下一次(几分钟后)。
继续用当前进程里的旧代码去装新配置,正是要避免的那种配对。

二进制的 SHA256 进签名过的 manifest,而 manifest 的内容哈希就是快照 id ——
**换二进制就换快照 id**。§15.4 要的"配置与二进制绑定回滚"因此是结构性的,
不靠任何约定。

分发树里它内容寻址(`bin/<sha256>`,顶层共享):同一个二进制不重复推送,
回滚到旧快照时旧二进制还在。

### D47 · 跑不起来的二进制装上去,这台机器就再也拉不到修复了

**日期** 2026-08-23 · **状态** 生效

自升级最糟的失败模式不是"升级失败",是"升级成功但新版跑不起来" ——
那之后节点连拉取修复的能力都没了,只能 ssh 上去救。

三道防线,顺序从便宜到贵:

| 防线 | 挡住什么 |
|---|---|
| 哈希比对 | 传输截断、分发点被改 |
| **冒烟测试**(`loom selfcheck`,在临时位置跑) | 架构不对、文件损坏、**读不懂本机现有配置** |
| 保留旧版 + 服务起不来就换回去 | 冒烟测试没覆盖到的运行期问题 |

第二道里"读不懂本机现有配置"是关键:它直接检验 [D46](#d46--先装二进制后装配置)
关心的那个配对,而不只是"这个文件能不能执行"。

实测:发一个不能执行的文件过去,哈希对得上,冒烟测试 `exit status 3`,
**不安装 —— 机器上的二进制和服务全都没动**。

> **第一次升级躲不掉手工。** 节点上的旧 `loom pull` 不知道要升级二进制,
> 所以这个能力本身要先手工推一次。和信任根、本机秘密层一样属于 bootstrap。

### D48 · 发布器在跑的时候,手工 publish 是个陷阱

**日期** 2026-08-23 · **状态** 生效(记录一个反直觉的后果)

[D39](#d39--发布器也要收敛不能只反应文件变化) 让发布器每轮核对分发点、
不一致就重推。正确 —— 但它有一个反直觉的后果:

**手工 `loom publish` 会在 30 秒内被守护进程覆盖回去。**

实测踩到:我手工发了一个带二进制的快照,守护进程下一轮发现"分发点指向的
不是我算出来的",把不带二进制的版本推了回去。日志里写得清清楚楚,而我
花了几分钟才反应过来。

这不是 bug,是收敛的定义。结论是:**发布器跑着的时候,它是唯一的发布者。**
手工 publish 只在守护进程停着时才有意义(首次发布、排障),而且用完要
把该给守护进程的参数也补上 —— 否则下一轮它就把你的东西冲掉了。

### D49 · 只测首字节会挑出连得快、传得慢的路

**日期** 2026-08-23 · **状态** 生效

被问到"只考虑握手时间吗?不考连接创建后的数据传输吗"。查了一下:是的,
探测只量到首字节,吞吐完全没测。而这会**选错路**。

同一批候选,同时量:

| 候选 | 首字节 | 下载速度 | 拉 2MB | 跳数 |
|---|---|---|---|---|
| `edge-b` | 454ms | **2018 KB/s** | 0.97s | 1 |
| `edge-a` | 956ms | **860 KB/s** | 2.27s | 1 |
| `cn-a>edge-a` | 779ms | 251 KB/s | 7.78s | 2 |
| `cn-a>edge-b` | 885ms | 251 KB/s | 7.76s | 2 |
| `cn-b>edge-b` | 4545ms | 273 KB/s | 7.15s | 2 |
| `cn-b>edge-a` | 1128ms | 244 KB/s | 7.99s | 2 |

**一跳 860–2018 KB/s,两跳 244–273 KB/s。** 四条两跳的链挤在一个很窄的区间,
系统性、不是巧合。

`edge-a` 首字节排第 4、真实耗时排第 2,比排它前面那条快 3.4 倍。

改成一次探测同时量两个数,按 objective 分别用。`objective: throughput`
因此从"拒绝执行"变成可用。

**两条附带的结论:**

§3 只说了跳数上限"实践中 ≤2",没说第二跳的代价。现在有数了:**第二跳换来
可达性,代价是四分之三的吞吐。** 两跳链该是"没别的办法时才用"。

而这也部分解释了为什么"按段量、加起来"的合成估计失败(见下):丢包和吞吐
不是可加的,一条链丢包多一点,TLS 握手就要重传,首字节被非线性放大 ——
这没法从单跳时间推出来。

### D50 · 合成估计:试过,不成立

**日期** 2026-08-23 · **状态** 已否决(留记录,别再试同一条路)

用户提出用寻路算法代替枚举。方向是对的 —— 边比路少得多
(`N² + M×N` vs `M×N²`),而且边可以由 N 台机器并行量。

为此做了一个新原语:**让链条上最后那台机器去连它自己的地址**,量到的就是
纯粹那一段,不依赖任何外部目标的可达性。它有效,而且是白赚的诊断能力
(见下)。

**但"单段相加 = 整条"不成立。** 同时量单段和端到端,7 次取中位数:

| 候选 | 单段 | 端到端 | 比值 |
|---|---|---|---|
| `edge-b` | 228 | 519 | 2.28 |
| `cn-b>edge-b` | 262 | 867 | 3.31 |
| `cn-a>edge-a` | 272 | 831 | 3.06 |
| `cn-a>edge-b` | 289 | 1144 | **3.96** |

**比值 2.28–3.96,不是常数。** 加上"末跳→目标"之后排序有两处颠倒。

原因:一次 HTTPS 请求是**好几个来回**(握手、请求、响应),而**每个来回都
要走完整条链**。来回几次取决于对方网站 —— TLS 版本、会话复用、内容大小 ——
不是从"走一趟多久"能推出来的。最清楚的反例是同一个第一跳的
`cn-a>edge-b`(×3.96)和 `cn-a>edge-a`(×3.06)。

**保留:** 测量当时网络状况偏差(端到端比历史 p50 差三四成)。要真正证否需要
更长时间的秩相关分析。但那是很大的投入换不确定的收益,而"探测太贵"这个
问题有便宜得多的解法([D51](#d51--探测有界当前那条必探其余轮换))。

**白赚的:** 单段测量留下来做**诊断**。它回答了一个此前完全答不出的问题 ——
一条链慢,是慢在哪一段。不拿它做选路决定。

### D51 · 探测有界:当前那条必探,其余轮换

**日期** 2026-08-23 · **状态** 生效

候选数是 `1 + N + N(N-1)`,再乘上目标数,再乘上"要读正文才算得出吞吐" ——
全探会让探测本身变成网络上最大的一股流量(15 条 × 2 目标 × 256KB ÷ 5 分钟
≈ 90 MB/小时)。

有界之后:当前选中的**每轮必探**(它变坏了要立刻知道,D23 依赖这个信号),
其余按游标轮换。实测 792 次/小时 → 132 次/小时,而且现在测的是**对的东西**
(含吞吐)。

**少探了多少要说出来。** 静默截断会让"这一轮没试到"看起来像"试过了但不行"。

**预算引入了一条新的算术约束:**

```
每条候选的样本数 ≈ (window / tuning_period) × (budget-1) / (候选数-1)
```

小于 `min_samples` 就永远排不了序 —— 和 [D24](#d24--调参字段之间的算术要校验)
是同一类错误,原因从"窗口太短"换成"预算太小",症状一模一样。校验器现在
算这一条。`stale_after` 也要比轮换周期宽,否则候选在轮到之前就先"过期"。

### D52 · 延迟与吞吐是两个测度,用帕累托前沿而不是合成一个数

**日期** 2026-08-23 · **状态** 方向已定,待实现

我一度提出把两者合成一个"完成时间"公式,并据此说 objective 应该消失。
那是错的([见 D49 的讨论](#d49--只测首字节会挑出连得快传得慢的路)):
objective 是**在乎什么**(策略),不是**是什么**(可测量的属性),两者不能
互相推导。

正确的做法是把它们当成**两个维度**:

- 一条候选如果在延迟和吞吐上都不比另一条好,它就被支配,可以直接淘汰
- 剩下的是**帕累托前沿** —— 前沿上的候选各有所长,谁都不是无条件更优
- `objective` 决定在前沿上取哪一点

好处是把"客观淘汰"和"主观取舍"分开了:前者由数据决定,后者由声明决定。
现在的单指标排序把两件事糅在一起,于是"按延迟排"会淘汰掉吞吐好得多的候选
(实测 `edge-a` 首字节排第 4、真实耗时排第 2)。

**抖动归入吞吐这一维**,不单列第三维:波动的实际后果是有效吞吐下降
(TCP 窗口收缩、重传),而不是另一种独立的"差"。

### D53 · 共同命运:记录路由,先给人看,暂不进选路

**日期** 2026-08-23 · **状态** 方向已定,待实现

实测 mtr 证明了一件端到端测量永远看不见的事:

```
cn-a → edge-b:  192.0.2.30 → 192.0.2.31 → 198.51.100.30 → 203.0.113.30
cn-b → edge-b:  192.0.2.32 → 192.0.2.33  → 198.51.100.30 → 203.0.113.30
                                                └────── 完全相同 ──────┘
```

**cn-a 和 cn-b 到柏林,从第三跳起是同一条路。** 这解释了为什么两条候选的
实测值几乎一样(646ms / 600ms),也意味着**在它们之间切换是徒劳的** ——
共用段拥塞时两条一起坏。

还有一件事只有逐跳才看得见:代价全在出境那一跳(4ms → 203ms)。所以
**对境外目标,选哪台国内中继几乎无所谓**。

**先只做记录与展示**,不接进选路:

- 每个节点的上报者定期 mtr **自己那几段**(只有起点看得见那条路)
- 跳表转述出去,中控台可查
- IP → ASN 用**离线**数据表。不接在线服务 —— 那会把拓扑告诉第三方,
  也给系统加一个外部依赖

频率:一次 mtr 约 45 个包、30 秒,且 ICMP 常被限速。**几小时一次**,
不是几分钟一次。

### D54 · `ttft` 与 `cost` 是扩展点,不是缺口

**日期** 2026-08-23 · **状态** 生效(重新归类)

这两个 objective 一直挂在"被附录 C #8 / #13 阻塞"下面,给人一种"再写点代码
就能用"的错觉。**不是。它们要的是部署方自己的数据源,而不是平台的功能。**

平台该做的部分已经做完了:

| | 声明的位置 | 没配时会怎样 |
|---|---|---|
| `ttft` | 等价类的 `observation_point` | 校验器拒绝:"tokens/s 不是 L4 能被动观测的量;首字节只是近似,不能当它用" |
| `cost` | 等价类的 `price_source` | 校验器拒绝:"价格是声明值,不会从度量里长出来" |

外加 Agent 在渲染期第二次拒绝并说明理由。**两层守卫,而且都不静默降级。**

数据源为什么必须由部署方给:

- **`ttft`** 要 L7 观测点。四个选项(自有端点埋点 / L7 网关 / 调用方 SDK /
  主动契约请求)各有真实代价,而**哪个可行取决于你在访问谁的服务** ——
  别人的 API 埋不进去,自己的可以。这不是平台能替你选的。
  L7 网关那条尤其要谨慎:它会破坏"L4 不碰字节"这条不变量。
- **`cost`** 更进一步:**它对当前拓扑根本不适用。** 现在的候选是"同一个
  目标地址,经不同的路",走哪条路付给对方的钱一分不差。成本排序只在
  **不同供应商的等价端点**之间才有意义 —— 也就是模式 B,而模式 B 被
  附录 C #3(访问契约)卡着。

**处理方式:从缺口表移到"扩展点",排在最后。** 需要时由部署方配上数据源,
平台侧不需要再写代码。

### D55 · 不是所有变化都是问题

**日期** 2026-08-23 · **状态** 生效

事件的级别原本靠"取值在不在白名单里"判断。于是每个快照哈希都不在白名单里,
**每次发布都被记成一次故障**。

后果实测到了:界面上"还在持续的问题"列了 7 条,**7 条全是快照号和选路
结果** —— 而这个面板正是为了防止真问题被淹没才建的。它自己变成了噪声源。

改成按**类别**分级:`snapshot` / `route` 永远是 `info`,`rotation` 是
`pending`(过渡态),其余按类别各自的"正常值"判断。

顺带修了同一处的第二个 bug:**"没有后续"不等于"还在持续"。** 上报者重启时
静默播种,所以日志的最后一条可能早就不是现状 —— 一条 2.4 小时前的快照事件
被显示成"还在持续",而那台机器早换了两个版本。判断要和当前状态核对。

> 这两个 bug 合起来,让"待处理"面板既报了 7 条假的、又会漏报真的。
> **一个会说谎的告警面板比没有面板更糟**:它训练人忽略它。

顺带:没有未解决项时明确打出"✅ 没有未解决的问题"。一片空白分不出
"一切正常"和"这功能没在跑"。

### D56 · 隧道地址和端口由分配器算,不靠手填

**日期** 2026-08-23 · **状态** 生效

加一台机器要手工算的东西:每条隧道两个 `/32`、一个监听端口,而且不能跟
已有的撞。5 台机器 9 条隧道时还能对付,再加一台就是 12 条 —— 手填必错,
而**填错的表现不是报错,是那条隧道悄悄不通**。

`model.AllocateTunnel` 从现有部署里读出两条规则,继续按它们分配:

1. **每个 `reverse_only` 节点占一个 `/24`**(edge-a 是 `10.99.0.x`,
   edge-b 是 `10.99.1.x`),段内成对顺排 `.1/.2`、`.3/.4`。归属给
   reverse_only 那一端,是因为它是被拨的那头 —— 一台被拨的机器的所有
   隧道天然聚在一起。
2. **端口刻意不连号。** 端口取 `sha256(节点对)` 起步线性探测。连号本身
   是个特征 —— 61619、61620、61621 摆在一起,扫到一个就知道还有一串。

用 sha256 而不是随机数,是为了满足 §12 的纯函数要求:同样的输入永远得到
同样的分配,与调用顺序无关。

`loom addnode` 分两步,因为**私钥必须在新机器上生成**(§13.1):不带
`-pubkey` 时打出生成密钥那一步,带上收回来的公钥才吐出可以直接粘进 SSOT
的片段。粘进去能不能过校验有回归测试钉着。

### D57 · "该轮换哪几张凭据"按候选链算,不按 allowed_servers 算

**日期** 2026-08-23 · **状态** 生效

§14.4 要求删掉一台机器之后轮换它持有过的凭据 —— 那些 `cred/...` 是跨节点
共享的,它硬盘上还留着明文。**忘了轮换没有任何症状**,直到有人拿捡到的
凭据连进来。

所以 `loom status` 直接把清单列出来。第一版按声明的 `allowed_servers` 算,
**多列了两倍**:`allowed_servers` 是"允许用到",而渲染器只在**候选链真的
经过这台机器**时才给它配上 user。允许 ≠ 配了。

判据因此和渲染器对齐,并且有测试逐台交叉核对渲染出来的 sing-box 配置里
实际有哪些 user —— 这个清单少一张,那张就永远不会被轮换。

还有一个反直觉的地方:**要按"假如它还在服役"来枚举**。排空和下线的机器
已经不进候选了,而恰恰是这两个状态才需要问"该轮换什么"。问的是它硬盘上
曾经有什么,不是它现在还路由什么。

### D58 · 转述来的节点也要进快照分布表

**日期** 2026-08-23 · **状态** 生效

`loom status` 的"全网快照分布"只统计了**直接拉到**的那几台。够不到的节点

### D59 · 大块下载同时检测停顿与按签名大小计算的总时限

**日期** 2026-08-23 · **状态** 生效

二进制原来跟 manifest 共用一个 HTTP 客户端 —— 一个 **60 秒的总时长**上限。
12.3 MB 配 60 秒等于要求全程持续 205 KB/s,而本次实测二跳吞吐只有
244–273 KB/s。**贴着线跑。**

实测到了两次:edge-a 一次 60 秒超时失败,下一轮 38 秒成功。同一台机器、同一个
文件 —— 每次二进制更新都是一次掷硬币。

固定 60 秒的超时形状不对:它把"慢"和"卡住"当成一回事,而这两件事的正确
反应相反。主判据改为停顿检测:连续 45 秒没有新字节就放弃，并在错误里说清
下到多少卡住的。

但**只有停顿检测也会 fail-open**:不可信分发点每 44 秒滴一个字节，就能永久
占住 `loom-pull.service`，使后续配置乃至签名过的 decommission 永远没有机会
被读取。最终语义是两道同时成立:

- 45 秒无进展立即失败；
- 按 manifest 签名覆盖的 `size`、32 KiB/s 保守最低吞吐加一个停顿余量计算
  硬总时限，并夹在 2–20 分钟之间。

因此慢链路不再被一刀切的 60 秒误杀，持续滴流也不能无限续命。二进制网络
预取在 `deploy.lock` 外完成；硬总时限到达前也不会堵住人工 `loom apply`。

读取上限仍然保留，并绑定签名覆盖的 `size`（只给 1 MiB 余量）—— 那道防线
防的是无限流吃内存，跟两种超时是三件不同的事。

> 这个 bug 的隐蔽处在于**它平时是好的**。60 秒够 12 MB 用了很久,直到
> 二进制长大、或者链路差一点。而失败的后果不是"这次没升上":两段式升级
> (先二进制、后配置)意味着失败的机器停在半路。


### D60 · 二进制回滚靠"钉住",不靠重新编译

**日期** 2026-08-23 · **状态** 生效

回滚原来有两道防线,中间空着一档:

| 情况 | 现有措施 |
|---|---|
| 配置改坏了 | 五步安装回滚 ✅ |
| 新二进制**起不来** | `.prev` 自动换回去 ✅ |
| 新二进制**起得来但是错的** | ❌ 什么都没有 |

第三档才是最常见的 —— 今天就撞到一个(报告者跑着被替换掉的 inode,数据少
字段,任何检查里都看不出来)。当时唯一的退路是 `git checkout` + 重新编译 +
重新发布,**要求手上有源码树**。

而历史二进制在分发点上本来就都在:内容寻址 `bin/<sha256>`,26 个快照 /
21 个二进制 / 261 MB 全躺着。所以不需要新的存储,只需要让发布器改用其中
一个。

`loom pin <快照 id>` 取回来、验签、核对哈希、**真跑一遍 selfcheck** ——
钉一个跑不起来的二进制上去等于把退路也堵死。

三个设计上的取舍:

1. **钉住是状态,不是一次性命令。** 发布器是每 30 秒收敛的守护进程,
   一次性发布下一轮就被它用本机二进制覆盖回去了。
2. **必须显眼。** `-reason` 是必填的;发布器在**本机二进制变了而钉住仍
   生效**的那一刻专门说一句 —— 那正是"我重新编译了但没发出去"的时刻。
   粘性覆盖不显眼就是陷阱(同 D58)。
3. **记录在、二进制不在要报错**,不能默默回落到当前二进制 —— 那正好是
   钉住要防的事。

> 一个副作用值得知道:SSOT 没变时钉回快照 X,渲染是纯函数(§12),
> 于是重新算出来的就是 X 本身,字节相同。**钉住 + 不动 SSOT = 完整回滚。**
> SSOT 变过就不是了 —— 那会得到"旧二进制 + 新配置",正是 §15.4 要防的
> 组合。这一点目前只写在文档里,还没有让工具拦。
>
> 已由 [D62](#d62--整份回滚源头跟着成品一起回去) 补上:工具现在拦了,
> 而且 `loom rollback` 让"两半一起回去"成为默认路径。


### D61 · 源头存档在中控本地,不进分发树

**日期** 2026-08-23 · **状态** 生效

做整份回滚时发现的:**SSOT 没有任何版本历史。**

| 以为它在哪 | 实际 |
|---|---|
| git | `.gitignore` 里 `/deploy/` 被整个排除 |
| `loom backup` | 默认只收 `deploy/secrets.env` 与 `deploy/pki` |
| 中控写界面 | tmp + rename **覆盖**,不留旧版 |

三处都没有。而 `loom backup` 的注释写着"渲染产物不备份 —— 能从 SSOT 再
生成",这句话恰好暴露了那个没被检查的假设:**它默认 SSOT 一直在。**

### 第一版做错了,记在这里

最初的做法是把源头当成一个 blob 塞进分发树(`ssot/<sha256>`,与二进制
同样内容寻址)。论证是"分发点早就持有每个节点的完整渲染产物,源头里的
信息是它的子集,不增加泄露面"。

**那个论证漏了一整类东西。** 实测:

| SSOT 里的东西 | 已在渲染产物里? |
|---|---|
| 4 个真实公网 IP | ✅ 全部已在 |
| DDNS 域名 | ✅ 已在 4 个文件里 |
| **`ssh_port`(非默认值)** | ❌ **0 个文件** |

`ssh_port` 是模型里的真字段,而 SSOT 自己的注释就写着这类字段
"记在这里是为了 bootstrap 与排障,**不是为了被连**"。分发点在设计上是
当作已被攻陷来对待的([D32](#d32--控制面是一棵签了名的静态树不需要被信任)),
而签名拦不住"主动把管理平面的信息送过去"这一类风险。

> **错的是类别,不是这一个值。** 非默认 SSH 端口只是弱混淆,真正拦人的
> 是密钥。但一旦确立"源头整份上分发点",以后每加一个这类不下发的运维
> 字段都会默认外发 —— 而加字段的人不会想到这件事。

### 定下来的做法

源头存档**只在中控本地**(`deploy/ssot-history/<sha256>.yaml`),每次成功
发布写一份,内容寻址。

换个角度看这本来就是它该在的地方:**这份存档只有中控用得着** ——
只有它做渲染,节点从来不读 SSOT。它不是分发树的一部分,是中控自己的备份,
所以归 `loom backup` 管(默认清单已加上,顺带补掉"SSOT 不在备份里"这个洞)。

**完整性一点没削弱。** manifest 里的 `ssot_hash` 仍然是权威,而 manifest
是签了名的:回滚照样按它核对取回来的字节。改的只是字节从哪来 ——
本地读而不是下载。变的是耐久性,不是可信度。

耐久性的代价说清楚:中控硬盘挂了就没有源头历史。但中控挂了本来就是
"从备份恢复"事件 —— 签名私钥、秘密层、PKI 全在那台机器上,早就不可再生。
源头历史进的是同一个篮子,而那正是它该在的篮子。

> 没做的:给 SSOT 加注释扫描器。明文秘密只可能出现在注释里,而按注释形状
> 做粗筛正是本项目一贯拒绝的"会误报的检查"(见 `looksLikeSecret` 的注释)。
> 模型里根本没有能装明文秘密的字段(只有 `secret_ref` 与 `wg_public_key`),
> 加上严格解码,这个结构性保证比粗筛强 —— 由测试钉住。


### D62 · 整份回滚:源头跟着成品一起回去

**日期** 2026-08-23 · **状态** 生效

`loom pin`(D60)回滚二进制,`loom apply` 回滚"上一次"的配置。中间一直缺
"整份退回快照 X"。

**关键在于源头必须一起回去。** 只把成品退回去是无效的:发布器每 30 秒从
SSOT 重新渲染一次,收敛机制(D33、D39)会立刻把线上带回新版本。

所以 `loom rollback <id>` 动的是两样东西 —— 源头和二进制 —— 然后**什么都
不做**,让发布器自己收敛过去。

**刻意不引入"冻住分发点"这种粘性覆盖。** 那会是一个新的、必须有人记得
解除的状态,而每个这样的状态都是一个"我改了但没生效"的来源(D48 踩过)。
源头一退回去,现有的收敛机制就够了。实测:回滚后发布器下一轮自己发出了
目标快照,没敲任何发布命令。

### 自证是这条命令的核心

源头与二进制取回本地后**重算一遍快照 id,必须还是 X**。渲染是纯函数
(§12),这条等式才成立 —— 它也是纯函数性质第一次被拿来当运行期检查用。

不成立就说明这个快照里有东西不由这两样决定,而回滚会留下一个**看起来
成功、实际没回去**的系统。当场报错,不发。

### 顺带堵掉 D60 留下的洞

D60 末尾写着"钉住 + SSOT 变过 = 旧二进制 + 新配置,目前只写在文档里,
还没有让工具拦"。现在两处都拦:

- **发布器**每次发布都比对,对不上就说出那个组合,并给出两条出路
- **`loom rollback` 不带参数**报告当前状态,把源头现在算出来的 id 和钉住的
  id 摆在一起

### 实测过的失败路径

| 情况 | 结果 |
|---|---|
| 本地存档被改过 | 认出"内容与哈希对不上 —— 被改过了" |
| 存档里没有这一版 | 报出可能的两个原因,并指向 `loom backup` |
| 用错的公钥 | 验签就拒了,没取任何内容 |

两种取不到源头的情况**刻意分开说**:"被改过"和"没有这一版"该做的事不一样,
合成一条会把人带偏。

三次失败之后 SSOT 逐字节未被改动 —— 覆盖发生在全部检查通过之后。

> **回滚前那一版存在 `deploy/pinned/ssot.prev.yaml`。** 因为 D61 才刚让
> 源头有历史,而回滚本身要覆盖它:这是本次操作唯一不可再生的东西。


### D63 · 发布历史记在中控,只记变化

**日期** 2026-08-24 · **状态** 生效

`loom rollback` 要一个快照 id,而 id 是十二位十六进制 —— **没地方查**:

| 以为能查到 | 实际 |
|---|---|
| 分发点列目录 | `autoindex off`(gz02 的 nginx),列不出来 |
| 事件历史的 `snapshot` | 记的是"**某台节点装的版本变了**"。一个发出去但还没被任何节点取到的快照,那里一条记录都没有 |

所以中控自己记:`deploy/ssot-history/published.jsonl`,与源头存档同一个目录
(它们本来就是一件事 —— 中控的发布历史),因此也一起进 `loom backup`。

**只记变化,不记状态**(同 events 包)。发布器每 30 秒收敛一轮,同一个快照
被反复确认;逐轮记一行的话一天 2880 行"还是那个快照",真正的版本变化会被
淹掉。只有 id 与上一条不同才追加。

> 去重是**跟上一条比**,不是"见过的 id 就跳过"。回滚回旧版是一次真实的
> 版本变化,按"见过就跳过"的话,**回滚这件事本身会从历史里消失。**
> 有测试钉住(`TestPublishedKeepsReturnToOldSnapshot`)。

### 那一列才是重点

`loom snapshots` 的判据是"**源头存档真的在、且内容对得上哈希**",不是
"历史里有这一行" —— 存档被清理过或被改过时,历史行照样在。而回滚失败最糟的
时机就是需要它的那一刻。

```
  快照          发布时间          源头          能回滚吗
  7ca7aa7755a0  08-24 08:21       6d909ee84b7a  ❌ 源头存档没了
  45f1b5fe4f77  08-24 08:21       b0949a92998d  ❌ 存档对不上哈希
→ 39470e023ff3  08-24 08:21       5da74d247aff  ✅
```

两个显示口径上的坑,都属于"会说谎的面板比没有面板更糟"([D55](#d55--未解决问题的可见性))
那一类:

- **同一个快照出现两次时,`→` 只标最后那次。** 都标会看成有两个当前版本
- **统计对全量算,不对 `-n` 截出来的那几行算。** 否则 `-n 1` 会显示
  "1 / 2 个版本",读起来像"有一个退不了",而那纯粹是显示条数造成的


### D64 · 备份区分"必须有"与"可以还没有"

**日期** 2026-08-24 · **状态** 生效

把源头存档加进 `loom backup` 默认清单之后,**备份当场整个不干活了** ——
`deploy/ssot-history` 要发布器成功发过一次才建,而在那之前它不存在,
于是原有的"少打包了什么就硬失败"把整次备份拒了。

原来那条硬失败是**对的**,不能放松:一个"成功"但内容不全的备份,只有在
需要它的那天才会被发现。所以改成分两类:

| | 缺了怎么办 | 为什么 |
|---|---|---|
| `secrets.env`、`pki` | **硬失败** | 它们不存在意味着这台机器有别的问题 |
| `ssot-history` | 说一声,继续 | 它可以合法地还没出生 |
| 命令行显式点名的 | **硬失败** | 人写出来就是指望它在 |

**"可选"说的是它可能还没出生,不是它不重要。** 所以缺了仍然要打印出来 ——
静默省略就是在制造"你以为你备份了",与那条硬失败是同一个理由,只是不该
拦住整次备份。

> 分错边的代价不对称,这是关键:必需项当可选 → 备份看起来成功但少东西;
> 可选项当必需 → **一台刚起来的中控连备份都做不了**,而"做危险变更之前先
> 备份"恰恰是最需要它能跑的时候。


### D65 · 链路通断要变成事件

**日期** 2026-08-24 · **状态** 生效

实测发现 ber01 ↔ hz01 的隧道断了 7 小时,而**事件历史里一条记录都没有**,
未解决面板上也没有。

原因不是代码跳过了转述来的节点。是 `detect.go` 产出的六类事件里
(`reach` / `snapshot` / `tunnel` / `drift` / `rotation` / `target`)
**没有 `edge`**:

| 数据 | 转述带得过来吗 | 变成事件了吗 |
|---|---|---|
| 隧道握手年龄 | ❌ 只有直接问才有(view.go 的 `st == nil` 分支) | 只有中控自己的 |
| **节点间 RTT(`Edges`)** | ✅ 一直都在 | ❌ **从来没有** |

所以两台都不是中控的机器之间断了,除了 `loom status` 上一个 ❌,
没有任何地方会发现,"断了多久"更是答不出 —— 而那是做事件历史的全部理由。

**只记通与不通,不记 RTT。** RTT 每轮都在变,记进状态就是每轮一条事件。

**一条链路两端都报,于是产生两条事件 —— 这是刻意的。** 单向故障真实存在:
这次实测就是 ber01 → hz01 的包到得了、hz01 → ber01 的回程被丢。
合并成一条就看不出这种不对称。


### D66 · 面板问当前状态,时长才问历史

**日期** 2026-08-24 · **状态** 生效

D65 做完之后那条链路**仍然上不了面板**。

因为 detector 第一轮是**静默播种**的(否则每次重启都像全网同时变化一次 ——
这个设计是对的),而播种那一刻它已经是坏的,没有"变化",没有事件。
旧面板从事件历史筛"未解决",于是:

> **上报者启动那一刻已经坏掉的任何东西,在它恢复之前面板永远看不见。**

这跟当初"四台机器 wg-quick 全 failed、存在多久没人知道"是同一个形状的
盲区,只是换了一层。

修法是把两个问题分开问:

| 问题 | 该问谁 |
|---|---|
| **现在有什么问题** | 当前状态(`state.json`,每轮覆盖) |
| **多久了** | 起点(状态自己记)+ 事件历史 |

`events.jsonl` 只追加、只记变化;`state.json` 每轮覆盖、只记现状。
**两个文件,两个问题,不要合并。**

### 时长必须跨重启存活

第一版改完之后真机上出了个新毛病:那条断了 10 小时的链路显示成
**"至少 28 秒"** —— 因为上报者刚重启,起点归零了。技术上没说错,实际效果
是让人以为它刚坏,**比不显示更糟**。

时长是这个面板唯一真正新增的信息("链路断了"看节点表也知道,"断了两天了"
才让人动手),而上报者重启是常事 —— 就为了发这两个版本,今天重启了两次。

所以状态文件在启动时被读回来:**值没变的,起点接着用**。实测重启前后
`since` 都是 `13:26:38`,时长连续。

**停机期间变掉的不接。** 变化发生在什么时候无从得知,那就从新起点算并标成
下界 —— 把停机那段算进去等于假装知道。

### 下界必须标成下界

`已 9 小时` 和 `至少 9 小时(上报者启动时已如此)` 是不同的两句话。
把后者写成前者就是在假装知道起点 —— 而那正是面板说谎的方式(同 [D55](#d55--未解决问题的可见性))。


### D67 · 同一个测量,两种含义:target 是数据,uplink 才是告警

**日期** 2026-08-24 · **状态** 生效

面板上"gz02 到不了 api.ipify.org"挂了 14 小时。被问到"国内机器的 target
换一换,为啥非要卡在这里"。

**换不得。** 查下来这个测量有两个消费者,而我一开始只看到一个:

| 谁 | 用它干什么 | "gz02 到不了 ipify"是 |
|---|---|---|
| **Agent 剪枝**(`agent/run.go`) | 砍掉出口够不到目标的候选 | ✅ 正是要的数据 —— 15 条砍到 6 条,一轮 13 秒降到 4 秒 |
| **未解决面板** | 当成待处理问题 | ❌ 误报 |

`report/config.go` 的注释早就写着"这是链路状态测量里最值钱的一项"。
换成 baidu,Agent 就不知道 gz02 出不去,会退回挨个探 15 条。

### 错的是面板拿观测当告警

但"一刀切降级成 info"也不对:**境外机器够不到 ipify 是真故障**。

而且缺的那一半更要命:**国内机器现在没有任何一个"本该够得到"的目标**。
gz02 的直连整个坏掉,面板上不会有任何变化 —— 因为它本来就是 ❌。
两件事恰好反着:该响的不响,不该响的一直响。

### 所以是"加"不是"换"

节点上加 `probe_targets`:**这台机器本该够得到的地址**。照 `Node.DNS`
那个先例 —— 它的注释讲的是同一个道理("大陆机器用 8.8.8.8 会被污染,
境外机器用 223.5.5.5 又绕远"),目标同样要按机器所在地选。

| 来源 | 回答什么 | 事件类别 | 失败时 |
|---|---|---|---|
| 声明的 `probe_url` | 这台机器够不够得到那个目标 | `target` | **info** —— 喂剪枝的数据 |
| 节点的 `probe_targets` | 这台机器的直连还好吗 | `uplink` | **problem** —— 上面板 |

**一个测量,一条线上的记录,只多一个标记。** `Reach.Uplink` 决定失败算数据
还是算问题;转述的线格式只多一个 bool,而剪枝按 URL 匹配,完全不受影响。

境外节点的两个列表可以是同一个地址(sg02 就是),那时它既是剪枝数据又是
健康检查 —— 对一台出口来说"够不到目标"确实两者都成立。

### 实测选的目标

| 节点 | 目标 | 实测 |
|---|---|---|
| gz02 / hz01 | `www.baidu.com` | 200,40ms / 103ms |
| jm24 | `www.baidu.com` | 200,59ms(系统解析器是坏的,但 loom 自带 DNS) |
| sg02 / ber01 | `api.ipify.org` | ✅ 339ms / 110ms |

> `www.aliyun.com` 试过,返回 403(挡 curl 的 UA),不适合当自检目标 ——
> **自检目标要选一个稳定返回 2xx 的**,否则每轮都在报假故障。

### 上线当场踩到:自检本身用了系统解析器

配好之后 jm24 的 baidu 检查报 unreachable —— 而实测它 200/59ms。

`reachTarget` 用的是裸 `http.Client`,**没走 `internal/netx`**,于是用系统
解析器。而 jm24 的 systemd-resolved 上游是 8.8.8.8,大陆被污染。

讽刺的地方在于 `internal/netx` 存在的全部理由就是"不依赖机器全局设置、
自带 DNS",而**量可达性的这个函数偏偏没用它**。

症状极具误导性:它长得像"这台机器出网坏了",而真实流量一直好着 ——
sing-box 自己配了 DNS(§7.4),根本不经过系统解析器。这与
[D 系列里那个 DNS 坑](#dns两个只影响直连候选的坑)是同一个形状,
只是换了一个消费者。

修法:上报者配置带上本节点的 `dns`(来自 SSOT,渲染时填),`reachTarget`
走 `netx.Client`。国内三台拿到 `223.5.5.5`,境外两台拿到 `1.1.1.1` ——
正是 `Node.DNS` 那条注释要的"按机器所在地选"。

> **教训与 `probe_url` 那次是同一条:加东西之前先验证下游真的会用它。**
> 我实测过 jm24 用 223.5.5.5 解析后能到 baidu,然后**假设**上报者也会这么
> 解析。那个假设没验证,于是配了一个它够不到的目标 —— 亲手造了一条新的
> 永久误报,正是这次要修的东西。

### 没做的

**"能出口却没配 `probe_targets`"没有做成校验错误。** 校验发现没有分级,
每条都会拦住发布,而现有部署里四台 `egress_capable` 的机器本来都没配 ——
做成硬错误会把正常配置拦下来。代价是:漏配的节点,它的直连健康无人监控,
而且这件事本身不会被说出来。


### D68 · 换端口要记住换掉了什么:退役名单既是记忆也是盐

**日期** 2026-08-24 · **状态** 生效

`AllocateTunnel` 按 `sha256(节点对)` 分端口([D56](#d56--隧道地址和端口由分配器算不靠手填)),
确定性、刻意不连号。但它**没有"换一个"的概念** —— 重跑给出同一个端口。
hz01 ↔ ber01 那次换端口是手工挑的。

补这个能力时有两个坑,而它们互相纠缠:

### 一 · 不记住就会转回去

轮换两次会回到第一个端口 —— 而那个端口是**已知不通**的。症状是
"换了端口还是不通",人会去查网络,查不到原因。

所以要有记忆。放在哪?第一反应是加个 `port_generation`,但那正是
[CLAUDE.md 第 2 条](../CLAUDE.md)警告的形状:**它和 `listen_port` 可以
互相矛盾**,而"可写即可与推导结果矛盾"。

换成 `retired_ports []int`:**它是纯历史,不与任何字段矛盾** ——
`listen_port` 是当前事实,退役名单是曾经。而且人一眼看得懂为什么不能回去。

### 二 · 只跳过不够,还要换起点

跳过退役端口之后,线性探测会挑中它的**紧邻位**(61654 → 61655)。
如果丢弃是按范围或邻近特征做的,那等于没换。

所以退役个数进哈希输入:`sha256(pair|N)`。每退役一个就得到一个全新的、
分布均匀的起点。实测 61691 的下一轮是 61684,不是 61692。

> **`N == 0` 时哈希输入与从前完全一致**,所以既有分配不会因为这个改动而
> 变 —— `loom addnode` 对同一份 SSOT 给出的端口还是原来那个,有测试钉着。

### 工具只算不写

`loom rotate-tunnel <ssot> <A> <B> -reason <理由>` 打印出替换后的那一行,
由人粘回 SSOT —— 与 `loom addnode` 同一个道理。这避开两件麻烦:

- **自动改写会毁掉 SSOT 里的注释**(那是 YAML 往返的老问题)
- **"系统自己改 SSOT"会给它添第二个写入者**,而单一写入者是 dry-run diff、
  漂移检测、回滚三个产物的地基。Agent 至今只改运行时 selector,从不碰 SSOT

`-reason` 必填,打印的那一行带日期。因为**换端口既是修复也是诊断**:
"这条流被标记了"和"某处状态坏了"两个假设对换端口的反应完全一样,
判据是能撑多久 —— 下次翻到这一行的人需要知道这个实验在等什么答案。

### 校验器钉住的关系

`listen_port` 不能出现在 `retired_ports` 里,退役端口要在保留段内。
第一条尤其重要:两者矛盾时没有任何别的东西会发现它。

### 顺带修掉一个会误导人的注释

`deploy/ssot.yaml` 写着"从保留范围 61610-61699 里挑",而
`model.TunnelPortMin/Max` 是 **61617-61799**,防火墙放行的也是这一段 ——
jm24 那两条隧道(61711、61763)本来就在注释说的范围之外。手工挑端口的人
会被它带偏。

> 退役端口**不进渲染产物**:它是运维历史,不是配置。有验证。

### D69 · 版本坐标:commit 靠 Go 的 VCS 戳,不靠构建脚本

**日期** 2026-08-24 · **状态** 生效 · **相关** §15.4、[D62](#d62--整份回滚源头与二进制一起退回)

现场同时存在四个互不相干的标识,排障时反复绕晕:

| | 是什么 | 从哪儿看 |
|---|---|---|
| `commit` | 源码是哪一版 | `loom version` |
| `binary` | 分发的是哪一份(sha256,§15.4) | `loom version` |
| `snapshot` | 配置是哪一版 | `loom report` |
| `ssot` | 源头是哪一版 | `loom snapshots` |

以前 `selfcheck` 只印一个写死的 `buildTag = "dev"`,于是"远端跑的是哪个
commit"根本答不上来,只能报一串二进制哈希 —— 而哈希对不回 git。
**文档里把二进制 sha 写成 "HEAD",毛病就是这么来的。**

**决定:commit 由 `debug.ReadBuildInfo()` 的 VCS 戳读取,不用 `-ldflags`。**

理由是**别让正确性依赖人记得做某件事**。ldflags 方案要求每次构建都带上
一串参数,而 CLAUDE.md 里写的构建命令是 `go build ./...` —— 两者一旦不一致,
漏掉的那次构建就成了认不出自己的二进制,而且**没有任何信号**。Go 从 1.18
起对 `go build` 自动戳入 `vcs.revision`,普通构建就有。`version.Tag` 仍留着,
但它是标签不是身份。

**顺带白拿一个更要紧的东西:`vcs.modified`。** 脏工作区构建出来的二进制
对不上任何 commit,出了问题没法用 git 复现。现在 `loom version`、
`loom selfcheck`、`loom status` 都会把它报出来(D3 的"不许静默降级"在版本上的落点)。

`Binary` 是**磁盘上那个文件**的哈希,不一定等于正在跑的镜像 —— 升级会
原地换掉它,这个坑踩过(见 history/)。所以两个都要:commit 回答"现在在跑
什么",binary 回答"下次重启会变成什么"。

**为什么 `loom status` 要单独报 commit 一致性。** 快照一致不等于版本一致,
而**旧二进制配新配置**正是发布器崩掉的那类故障 —— `services` 字段一次,
`retired_ports` 字段一次(D68 加的那个)。SSOT 用 `KnownFields(true)` 严格
解码,对"控制面比数据面旧"零容忍。只看快照的表对这类故障完全是盲的。

> **推论,写在这里免得再踩第三次:改 SSOT schema 要先升级发布器,再改 SSOT。**
> 顺序反了,发布器会拒绝解析,而它的进程仍然是 `active` —— 看起来活着,
> 实际已经发不出去。

### D70 · 当前状态与历史分开:一页快照 + 一堆归档

**日期** 2026-08-24 · **状态** 生效

`docs/status.md` 长到 1361 行、88 个小节,因为它同时承担两件事:**当前是
什么样**,和**发生过什么**。后者只增不减,于是前者被埋掉了。

后果不是"文档有点长",而是**每次都要从三天的流水账里现推当前状态,
推出来还互相矛盾**。同一份文档里能同时读到 4 台机器和 5 台机器。

**决定:拆成 `docs/status/current.md`(唯一的"现在",改它不追加)
+ `docs/status/history/`(一件事一个文件,写完不再改)。**

`current.md` **必须短到能整个读完** —— 读不完的当前状态等于没有当前状态。

这个目录含真实地址,继续不进版本库。但**规矩进** —— 写法写在 CLAUDE.md 里。
只忽略内容,不忽略规矩:否则下一个会话又会把两者混回一份追加文档。

> 与本文档的区别:decisions.md 是**只追加不删改**的,因为被推翻的决定和
> 它当时的理由同样有价值。`current.md` 恰恰相反 —— 它是快照,过期内容
> 没有价值,只有干扰。两种文档,两种规矩。

### D71 · 两种"没版本"性质不同,不能都报成告警

**日期** 2026-08-24 · **状态** 生效 · **相关** [D69](#d69--版本坐标commit-靠-go-的-vcs-戳不靠构建脚本)、[D67](#d67--同一个测量两种含义target-是数据uplink-才是告警)

`loom status` 的版本表第一版只拿到"够得到的"节点名单,于是靠转述听到的
gz02 / hz01 从来没进过表 —— 既没核对,也没被列进没问到的。5 台里只覆盖
3 台,显示出来却是"都一致"。

`snapshotSpread` 踩过同一个坑并已修好,写新表时没沿用教训。

**为什么版本表不能照抄快照表的修法。** 快照表的修法是把转述来的观测折进去,
因为**快照 id 在观测里带着,转述过来仍是事实**。版本坐标不在,而且更根本的是
**身份不该听别人转述** —— B 说"C 跑的是某个 commit",这句话的可信度取决于 B,
而排障时恰恰不能假设 B 可信。所以够不到的节点,版本就是核不了。

**决定:核不了要印出来,但分成两类,只有一类算告警。**

| 情况 | 含义 | 处理 |
|---|---|---|
| 够得到却没报版本 | 它跑的是不带版本坐标的旧二进制 | ⚠️ 计入 bad |
| 够不到、只能靠转述 | 拓扑事实 | 印出来,**不计入 bad** |

第二类刻意不报警。gz02 / hz01 在这张拓扑里**永远**够不到,报成告警就是
每次都响的常驻误报 —— 正是 [D64](#d64--面板只报真问题)–D67 花力气清掉的那类噪音。
但空白也不能不说:一台跑着老二进制、又恰好够不到的机器,会被表的沉默
算成同意。

**顺带:分母要印。** "问到的 3/5 一致"和"问到的 5/5 一致"看起来必须不一样。
只写"都一致"时,n=1 和 n=5 的说服力天差地别,而显示完全相同。

### D72 · 发布器要自报死活,判据是"上次成功之后又失败"

**日期** 2026-08-25 · **状态** 生效 · **相关** [D69](#d69--版本坐标commit-靠-go-的-vcs-戳不靠构建脚本)、[D67](#d67--同一个测量两种含义target-是数据uplink-才是告警)

2026-08-24 发布器连续 **2 小时 17 分**发不出任何东西,而 `systemctl status`
全程 `active (running)`。**进程活着不等于功能活着**,而当时没有任何地方
能区分这两件事 —— 要发现它得去翻 journal,而没人会去翻一个显示正常的
服务的日志。

版本坐标也覆盖不到它:`loom report` 报的是**跑 report 那个二进制**的 commit,
发布器是另一个进程,可能还持着被换掉的旧 inode。

**决定:发布器每轮把自己写进 `/var/lib/loom/publisher.json`,`loom status` 读它。**

**判据是 `LastErrorAt > LastSuccess`,不是"距上次成功多久"。**

这条最关键。发布器只在 SSOT 变了(或分发点分叉)时才发布 —— 一周不改 SSOT
就一周不发,那完全正常。拿时长当告警会天天误报,而误报的面板等于没有面板
(D64–D67 刚清掉的就是这个)。昨天那次故障的真正形状是**19:43 成功过一次,
之后每一次都失败**,而这个形状在 SSOT 不变时不会响。

两条配套约束:

1. **LastError 成功后不清空。** 清了的话一次成功就把"刚才卡了两小时"抹掉,
   而那正是要留住的信息。恢复之后改成"曾经失败过……之后已恢复",不报警。
2. **心跳(UpdatedAt)与 LastSuccess 分开。** 昨天心跳一直正常,停住的是
   LastSuccess —— 合并成一个字段就什么都看不出来了。

状态文件写不出去不拦发布(发布是主职),但要说一次 —— 否则"状态一直是旧的"
就成了新的静默故障。

### D73 · 版本表要用"真的答上来了",不是"拓扑上够得到"(修正 [D71](#d71--两种没版本性质不同不能都报成告警))

**日期** 2026-08-25 · **状态** 生效

D71 把节点分成"够得到"和"够不到"两类,但**"够得到"取自 SSOT 拓扑,
不是取自成功拉取**。于是一台超时的机器会先被报"❌ 拉不到",再被版本表
指认成"跑的是旧二进制",而且 `bad` 加两次 —— 同一件事报两遍,还报成两回事。

**修正:分三类,判据取自真实答复集。**

| 情况 | 含义 | 处理 |
|---|---|---|
| 答上来了但没版本 | 确实是旧二进制 | ⚠️ 计入 bad |
| 根本没答上来 | 超时/断线,上面已报过 | **这里不再提** |
| 够不到、只能转述 | 拓扑事实 | 印出来,不计 bad |

**分母改取 SSOT 的节点数。** 一台彻底失联的机器(没隧道又没人转述)如果不
进分母就会从统计里整个消失,而消失的样子和一切正常一模一样。

判断逻辑拆成纯函数 `versionFindings` 并钉了 7 个测试 —— 这类坑只有喂进
"拉不到的节点"才看得出来,靠肉眼看代码看不出来(第一版就是这么漏的)。

`loom backup` 的默认清单是 `secrets.env` / `pki` / `ssot-history`,

### D75 · 追溯不回 git 的二进制,默认不许发到全网

**日期** 2026-08-25 · **状态** 生效 · **相关** [D69](#d69--版本坐标commit-靠-go-的-vcs-戳不靠构建脚本)、[D31](#d31--加不加密必须显式选)

D69 让脏构建**能被看见**,但只是打印警告 —— `selfcheck` 印完警告仍然返回
成功,发布器也照发不误。于是"看得见"和"拦得住"之间还差一步:一个对不上
任何 commit 的二进制仍然可以一次性铺满 5 台机器,而出了问题没法用 git 复现。

**决定:发布器在分发前读那个二进制文件的构建信息,认不出 commit 或构建自
脏工作区就拒发,除非显式 `-allow-dirty`。**

三个要点:

1. **读的是文件,不是本进程。** `version.OfFile` 用 `debug/buildinfo.ReadFile`,
   不执行它。钉住时发的是历史二进制,它的 commit 只有那个文件自己知道 ——
   拿发布器自己的 `Self()` 去判会判错对象。
2. **拒发也要记进 Health(D72)。** 只打日志的话,这本身就变成一个新的
   "systemd 说 active 但发不出去"的静默故障 —— 正是 D72 要根治的形状。
3. **留出口,不硬堵死。** 救火时确实可能要发一个还没提交的修复。但要
   **显式选** —— 与 [D31](#d31--加不加密必须显式选)"加不加密必须显式选"
   同一个规矩:风险选项不能默认帮人做主,也不能默认拦死。

`OfFile` 读不出构建信息时**报错,不返回空坐标** —— 空坐标会让闸门把不可
追溯的二进制当成合格的放过去,那比没有闸门更糟。

### D77 · 改代码要显式 `loom release`,改 SSOT 才自动发布

**日期** 2026-08-25 · **状态** 生效 · **相关** [D75](#d75--追溯不回-git-的二进制默认不许发到全网)、[D60](#d60--钉住的是二进制回滚的是整份)

发布器每轮重新读 `-binary` 指的那个文件,sha 一变就发。于是**任何一次
`go build` 都武装了一次全网升级** —— 改一行状态页面的措辞,5 台机器各下载
12.5 MB 并重启服务。而人在调试时会编译很多次:2026-08-24 一小时编了四次,
把分发点撑到 261 MB,D59 那个超时 bug 就是这么撞出来的。

**决定:两种改动走两条路。**

| 改了什么 | 怎么生效 | 为什么 |
|---|---|---|
| SSOT | 发布器自动发 | 它本来就是声明,改了就该生效 |
| 代码 | 必须 `loom release` | **编译只是编译,不是决定** |

优先级是 **钉住 > 放行 > 什么都不发**。钉住是救火状态,不该被一次 release
悄悄解开;而都没有时**不回落到本机二进制** —— 那正是要根治的东西。

三道检查全在**人按下回车的这一刻**做完,不留给发布器半夜静默失败:
追溯得回 git 吗(D75)、这台机器上 selfcheck 过得了吗(§15.4)、理由填了吗。

**二进制随记录一起存下来,按内容寻址放在 `bin/<sha256>`。** 只记 sha 不够 ——
记完之后 `/usr/local/bin/loom` 还会变,那样发布器拿到的就不是被批准的
那一份了。

> 副作用是本机攒下了历史二进制,而**回滚因此不用回网络取**。这正是
> "快速回滚"缺的那块,顺手就有了。

`loom release -clear` 停发二进制但配置照发,**且不删本地副本** —— 那些是
回滚缓存。

## 迁移:装上之后要手工放行一次

新发布器默认 `-release-dir deploy/released`,而那里还没有记录,所以它会
**只发配置,不发二进制**,并且每次启动说一句。

这是安全的:快照不带 `binaries` 字段时,节点的 `upgradeBinary` 走
"快照没带这个平台的二进制,不是错误"那条路,保持现有版本不动。

装上之后跑一次 `loom release -reason <理由>` 即可恢复分发。

### D78 · rollout 是显式状态机,但先只观察不接管

**日期** 2026-08-25 · **状态** 生效(观察阶段) · **相关** [D77](#d77--改代码要显式-loom-release改-ssot-才自动发布)、[D72](#d72--发布器要自报死活判据是上次成功之后又失败)

阶段本来就存在:验签 → 换二进制 → 装配置 → 验证。但它们只是 `pull` 里的
一串注释 —— **没有名字、不落盘、崩了就丢**。两个后果:

1. **崩在半路等于失忆。** 装到一半断电,下一轮从头开始,而"上一次死在
   哪一步"没人知道。
2. **"等下一个定时器"被当成了续跑机制。** 换完二进制主动 `return`,靠
   10 分钟后的下一次 pull 接着装配置。安全原则(旧程序绝不处理新 schema)
   是对的,但拿定时器当 continuation —— 于是二进制+配置一起变要 20 分钟。

新增 `internal/rollout`:`staging / activating / verifying / verified / decommissioned / failed`,
落在 `/var/lib/loom/rollout.json`,进 `report.Status`,`loom status` 汇总。

**和 `applied` 是一对**:applied 说现在装着哪个(结果),rollout 说正在往
哪走、走到哪步(过程)。一台卡在 activating 的机器 applied 仍是旧值 ——
只看快照表会以为它"还没轮到",实际上它可能已经半装着躺了半小时。

两条判据上的讲究:

- **只有 Verified 推进 LastGood。** 装上了不算,`applied` 写下来了才算 ——
  否则回退目标会指向一份装得上但跑不起来的快照。
- **Decommissioned 是成功终态但不推进 LastGood。** 它证明签名停机指令已
  完整收敛，不代表那份配置可以拿来回退。
- **卡住看的是"进入当前阶段多久",不是整次 rollout 多久。** 一次正常的
  二进制升级本来就要走好几步,总时长长不说明问题。

## 为什么先不接管

**这是全系统最关键的路径,而上一次动它的人刚把它停了 2 小时 17 分。**

所以这一版只写记录,不改任何控制流。先跑几轮真实发布,确认记下来的阶段
和现实吻合,再让它接管。**这样切换那一刻不是"新代码第一次上真机"。**

这段观察期最初把 `stuckLimit` 设为 30 分钟 —— 因为两段式升级本来就要等
下一个定时器,一台机器当时会合法地在 activating 待十几分钟。D80 换掉
"等定时器"并取得真机数据后,阈值已经降为 **10 分钟**。这里保留原始判据的
来由,不再把历史值写成当前值。

## 当时的接下来（现状见 D80）

1. 换完二进制**起子进程续跑**同一个 release,而不是 `return` 等定时器。
   子进程而不是 `exec`:exec 把唯一还知道怎么撤销的进程销毁了,而
   `loom release` 已经在本地攒下历史二进制(D77),回退不用回网络取。
2. 轮询降到 30–60 秒,同时加 **canary**:一台先行验证通过,其余的才动。
   只提速不加灰度等于优化"全网坏掉的速度"。

### D79 · 放行构建产物,不放行"正在跑的那份"

**日期** 2026-08-25 · **状态** 生效 · **相关** [D77](#d77--改代码要显式-loom-release改-ssot-才自动发布)

`loom release` 的 `-binary` 原本默认 `/usr/local/bin/loom`。那是个陷阱,
而且**实测输过一次**。

**中控同时也是一个被管理的节点。** 它自己的 `loom-pull` 每 10 分钟把
`/usr/local/bin/loom` 收敛到**已发布快照里的那份**。于是"手工装 → release"
这个流程有竞态,窗口就是一个 pull 周期:

```
11:01:22  pull:二进制要换 9b45f30b88f3 → e90d0efe56c9   ← 把手工装的退回去了
11:03     loom release                                  ← 记下的是被退回的旧版
```

慢了两分钟,放行记录就指向了上一个版本,而命令本身**报告成功**。

**决定:`-binary` 默认改成构建产物 `deploy/staging/loom`。** 那个路径不归
pull 管,不会被收敛掉。显式指向 `/usr/local/bin/loom` 时打印警告说明原因。

## 顺带简化掉一步

想通这件事之后,发布流程比原先短了:

```bash
go build -o deploy/staging/loom ./cmd/loom
loom release -reason "..."
```

**不用手工装到 `/usr/local/bin`,也不用重启发布器。** 中控自己的 pull 会
把新二进制装上去,并重启跑着旧 inode 的服务 —— 它本来就在做这件事。

原先那两步是我把中控当成"不受管的机器"想出来的,而它不是。

### D80 · 换完二进制起子进程续跑,不等下一个定时器

**日期** 2026-08-25 · **状态** 生效 · **相关** [D78](#d78--rollout-是显式状态机但先只观察不接管)、[D46](#d46--二进制在配置之前)

D78 的观察阶段拿到了要的数字:**jm24 卡在 `activating` 10 分 11 秒**,
而那 10 分钟里它是"新二进制 + 旧配置"。

原因是 `pull` 换完二进制主动 `return`,把装配置留给 10 分钟后的下一次
定时器。安全原则没错 —— 继续用**当前进程里的旧代码**去装新配置,正是
要避免的那种配对(D46)。错的是实现:**拿定时器当 continuation**。

**决定:换完二进制立刻起一个子进程,用刚装好的那个二进制跑完这一轮。**

## 为什么是子进程,不是 exec

exec 把当前进程替换掉,而当前进程是唯一还知道"旧二进制在 `.prev`、
出事了能退回去"的东西。子进程留住了这个能力,代价只是一个进程。

## fork 炸弹那道闸

子进程看到二进制哈希已经对上,不会再换,所以深度天然是 1。
**但"天然"是个假设**,而这个假设错了的代价是 fork 炸弹。所以用环境变量
`LOOM_PULL_CONTINUATION` 显式挡一道,并钉了测试 —— 包括"标记确实传给了
子进程",因为传不下去的话那道闸形同虚设。

## 顺带:轮询 10min → 45s

原来的理由是"配置变更是人发起的,太频繁只是刷日志"。那个理由**把成本
估高了、把代价估低了**:

| | |
|---|---|
| 成本 | 一次无变化的 pull 实测约 1 秒,几个小 JSON。二进制哈希对上就不下载,没有 12.5 MB 那回事。5 台 × 45 秒 ≈ 7 次/分钟 |
| 代价 | 全网收敛要等一个周期 —— 实测 10 分 11 秒 |

45 秒 + 15 秒抖动(**抖动必须小于周期**,否则它不是错峰而是让周期失去
意义)。加上发布器的 30 秒:

- 纯配置变更:端到端 90 秒以内
- 二进制 + 配置:同样一个周期,因为续跑不再等第二次定时器

后续观察已经把 `stuckLimit` 从 30 分钟降到 **10 分钟**。正常 continuation
应在同一轮完成；10 分钟仍远高于正常路径,但足以把真正停住与瞬时抖动分开。

### D81 · 身份签名之后,转述来的节点也能核对版本(收窄 [D73](#d73--版本表要用真的答上来了不是拓扑上够得到修正-d71))

**日期** 2026-08-25 · **状态** 生效 · **相关** [D71](#d71--两种没版本性质不同不能都报成告警)、§13.3

D71/D73 的结论是"版本核不了转述来的节点",理由是**身份不该听别人转述**:
"C 跑的是 commit X"如果只由 B 说,排障时恰恰不能假设 B 可信 —— 出问题的
往往就是链路上某一环。

代价是 `loom status` 长期只能报 `3/5 台核对过`,gz02 / hz01 永远空白。
而它们够不到中控是**拓扑事实**,不会自己好转。

**决定:节点给自己的身份陈述签名,转述照旧走原路。**

签了名之后转述的是密文不是信任:改一个字验不过,伪造要那台机器的私钥。
于是"够不够得到"和"能不能核对"解耦了。

## 用现成的 PKI,不引入新密钥

每台机器早就有 `/etc/loom/tls/node.key` 和 `node.crt`(CN 是
`<节点>.node.internal`,内部 CA 签发)。新密钥意味着新的分发路径和新的
轮换路径,而那是这个系统里最贵的东西 —— D74 刚因为备份漏了一把钥匙
差点变成灾难。

## 三道检查,少一道就是摆设

1. 证书链得到 CA —— 否则谁都能自签
2. **证书的名字要和 Claim.Node 对上** —— 否则 ber01 可以拿自己的合法
   私钥签一条"gz02 跑的是 commit X",而那正是转述,正是要根治的东西
3. 签名覆盖固定字节

第 2 条是整个机制的关键,单独钉了测试。签名覆盖的字节**不走 JSON**:
字段顺序、空白、转义都可能因库版本而变,而签名是针对字节的 ——
换个 Go 版本就验不过的签名不如没有。

## 验过了才算,验不过和没签名同等对待

`Attest` 为空**不等于可信**(中控只有 ca.crt,签不了)。验不过则是**故障**
要报出来 —— 要么转述内容被改过,要么证书过期了。但两种情况调用方要做的
事一样(去 ssh 那台机器),所以在版本表里同归"没核对过",不再细分。

## 用真钥匙验过

不只跑了合成 CA 的单测:拿 gz02 的**真私钥**用 openssl 签,在中控用**真
ca.crt** 验,通过;把同一份签名改说成 hz01 的,被真证书拦下:

```
证书是 "gz02.node.internal" 的,却在替 "hz01" 发言
```

### D82 · 删除收敛照 dpkg 的文件清单模型,不自己发明

**日期** 2026-08-26 · **状态** 生效 · **相关** [D33](#d33--收敛不是反应文件变化)、§14.2

`BuildPlan` 只遍历这次渲染出来的文件,**没有任何删除逻辑**。于是 SSOT 里
删掉一条隧道之后:渲染输出里没有 `wg-ber01.conf` 了,但节点上的文件和
`wg-quick@wg-ber01` 服务**都还在跑**。

以为删了、实际还连着 —— 这是安全问题,不只是洁癖。

## 这是个有名字的老问题,不该当新设计做

| 现成的 | 怎么做的 |
|---|---|
| **dpkg** | 包的文件清单存在机器上(`<pkg>.list`),卸载时按清单删 |
| **Puppet** | `resources { purge => true }`:声明之外的一律清掉 |
| **Nix** | 由构造保证:新 generation 里没有的就是没有 |

节点上早就有一份自检清单(`/etc/loom/report/manifest.json`,记着 Loom
装过哪些绝对路径)。**差集就是答案**:旧清单 ∖ 新计划 = 该删的。

照 dpkg 的模型抄,而不是发明一套,好处是边界语义有地方可查 ——
以后遇到"被人手改过的文件删不删"这类问题,知道去看 conffile 是怎么定的。

## 三条边界,都是 dpkg 已经想清楚的

1. **只删自己装过的。** 清单里没有的文件一律不碰。
2. **清单确实不存在 = 什么都不删。** 这是第一次安装的合法状态；但清单
   已存在却损坏、不可读或校验失败必须 fail closed。把“无法证明不存在”也
   当成 absent，会在权限漂移或半写文件时悄悄放弃删除边界。
3. **先停服务再删文件。** 反过来的话 `wg-quick stop` 找不到配置,接口会
   留在内核里 —— 那正是"以为删了其实还连着"的形状,只是换了个地方发生。

## 删除也是一种变更

两个推论,漏掉任何一个这个功能就是半成品:

- 只有删除、没有文件改动时,**不能走"无变化"早退** —— 否则该删的永远删不掉
- 删掉的文件要存进 `$PREV`,**回滚时放回去** —— 否则一次失败的部署会
  永久毁掉一条还在用的隧道配置

## 反推服务,不查表

要删的文件**已经不在这次的渲染输出里**,`BuildPlan` 那套
bundlePath → 服务的映射对它无能为力。所以 `UnitFor` 从绝对路径反推:
`/etc/wireguard/<x>.conf` → `wg-quick@<x>`,`/etc/systemd/system/<x>.service`
→ `<x>.service`。认不出来的返回空串,那只是普通配置文件,删掉即可。

### D83 · 拓扑分四层，候选存在与实时健康不能互相冒充

**日期** 2026-08-26 · **状态** 生效 · **相关** §16.4、[D81](#d81--身份签名之后转述来的节点也能核对版本收窄-d73)

`jm24`、`gz02`、`hz01` 都是拓扑节点。生产没有三者之间的常驻 WireGuard
三角形，但 SSOT 枚举出的业务候选明确包含 `jm24 → gz02`、`jm24 → hz01`、
`jm24 → gz02 → hz01` 与 `jm24 → hz01 → gz02`。**没有常驻 WG 直边不等于
没有路径。**

界面因此分开显示四层：SSOT 承载边、完整 `RouteCandidate`、实时观测、Agent
从 selector 实读的当前选择。承载边不能由一条陌生 Observation 发明；候选边
只能标“未核验”，不能因为存在于 SSOT 就涂绿。

反过来也一样：一条边变绿是运行时事实，必须有真实样本，而且转述来的
`Edges/Targets` 必须由观测节点自己签名绑定。D81 的 v2 只签版本、Applied、
rollout 与 selector，relay 仍能改外层测量；v3 在 Claim 中加入测量 payload 的
SHA-256，采样完成后再签。legacy/unsigned 测量仍可作为未知信息存在，但既不能
把 WG 边抬成健康，也不能进入 Agent 的不可达剪枝改变 selector。

### D84 · 部署是可恢复事务，不是按顺序跑完一串命令

**日期** 2026-08-26 · **状态** 生效 · **相关** [D80](#d80--换完二进制起子进程续跑不等下一个定时器)、[D82](#d82--删除收敛照-dpkg-的文件清单模型不自己发明)、§14.2

同一台节点上的 timer、人工 `pull/apply` 与二进制 continuation 可能同时到达。
分别给某个命令加锁仍会留下交叉写：一个进程正在替换配置，另一个正写
`applied` 或 `.prev`。**所有激活路径共用 `/var/lib/loom/deploy.lock`；网络
预取在锁外，实际文件、服务、rollout 与 applied 状态只在锁内改变。**

锁只解决并发，不解决进程被杀。激活前写入持久事务状态，记录已动文件和服务
原态；成功提交后才清除。下一轮若看到未提交事务，先完整回滚，回滚不完整则
以专用错误退出，不能在半旧半新状态上继续覆盖。状态文件和 `applied` 都采用
临时文件、`fsync`、rename 与父目录同步，不能把半截 JSON 当成“没有状态”。

验证也按事实而不是机械口令：`NRestarts` 看稳定窗口内的增量，不要求一生累计
为零；unit 变化要重启对应常驻服务；配置无变化仍修复应为 active 的服务；下载
同时有停滞超时和按字节数计算的总时限，慢速滴流不能永久占住 pull。下线时先
停并核验所有其他 Loom 单元，最后才停 pull timer；任何一步失败都保留重试入口，
不提前写“已下线”。

服务存在性是 systemd 已加载单元与 unit-file 清单的并集，不能用
“unit 文件没了”推导“旧 inode 进程没了”。下线发现也取已安装清单、
WireGuard 文件与 systemd 已加载/已安装单元的并集。任一查询不确定都
fail closed；`LoadState=not-found` 也要独立核对 active/enabled，不能跳过暗连收敛。

### D85 · 发布的原子单位包含输入时刻、放行记录与可取回字节

**日期** 2026-08-26 · **状态** 生效 · **相关** [D77](#d77--改代码要显式-loom-release改-ssot-才自动发布)、§14.2.3、§15.4

发布器过去只保证“一轮内部按顺序执行”，却没保证两轮的先后：旧轮先读取 SSOT
后阻塞，新轮先发布，旧轮再醒来就会把分发点倒回去。**所有发布入口共用发布锁，
并在取得锁后重新读取 SSOT、pin 与 release；锁前读到的内容不能参与提交。**

二进制仍必须由 `loom release` 显式批准。放行记录绑定 commit、字节哈希、大小、
自检结果、原因和时间；pin 的签名 manifest 必须与请求的 snapshot id、放行记录
声明的 snapshot 完全一致。手工 `publish` 与守护发布器使用同一套 pin/release
目录和判据，不能因入口不同悄悄丢掉已批准二进制。
写 pin/release 和 rollback 也使用同一把锁；rollback 先写新 pin 再写 SSOT，
后者失败时两者不匹配会继续拦住发布，不能失败开放地发出半份回滚。
撤销 pin/release 在删除后同步父目录，掉电不得让已撤销授权复活。

“发布成功”不再只表示本地文件写过：推送前先完成不可变归档，归档或历史记录
失败都让本轮失败；推送后从 HTTP 分发视角逐项读取 current、manifest、签名、
节点包和二进制 blob，边读边核对大小与 SHA-256。目标路径必须是规范化的非根
绝对目录，拒绝 `/`、`//` 与 `..` 等价写法；SSH 只修改本轮明确创建的条目，绝不
对整个目标树递归 `chmod`。相同 runtime tree 的语义 no-op 可以保留既有签名
快照，但目标缺文件时仍要原子修复，不能把“ID 没变”当成“分发点没坏”。

语义 no-op 只在旧 snapshot 对应的 SSOT 不可变存档仍存在时才能复用，
否则必须生成一份可回滚的新 snapshot。JSONL 历史若留下掉电造成的末尾
半行，先截至上一条完整记录再追加并读回确认。本地与 SSH 目标都拒绝
symlink 路径逃逸，采用不可预测临时名 + rename；小文件读取有大小上限，
SSH 命令还有按操作类型设定的总时限，恶意远端不能永久占住发布锁。
