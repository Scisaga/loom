# Loom · 设计文档

> **Loom 是一个基于加密隧道的链路与服务调度基础设施。**
> 它持续测量网络中所有可用路径的质量,结合成本、容量与合规约束,为每个服务选择当下最优的接入路径。
>
> CLI:`loom render` / `loom diff` / `loom apply` / `loom rollback` / `loom probe`

---

## 摘要

**问题:** 从任意接入设备到达任意目标地址,存在多条可能路径(直连、单跳、多跳)。这些路径的质量随时间变化;当同一个服务有多个可互换的地址时,还要在它们之间做选择 —— 而"最优"取决于服务性质:交互式推理看首字延迟,批量传输看吞吐,长连接看稳定性,采购决策还要看价格。

**两类应用场景:**

| 场景 | 最终地址从哪来 | 选什么 |
|---|---|---|
| **代理上网** | 由客户端的请求决定(你打开的那个网页) | 只选服务器链 |
| **服务调度** | 从一组可互换的地址里选(如各地机房的推理服务) | 选地址 **+** 选服务器链 |

两者共用同一套机制 —— 第一类只是第二类"地址退化为常量"的情形。第二类的价值更大:当同一服务在多个数据中心部署、且**价格、容量、网络质量都在变动**时,为客户持续选择成本与性能最优的接入路径。

```
        ┌──────────────┐
        │  接入节点     │  PC / Linux / Android
        │  access      │  你的设备,流量从这里进来
        └──────┬───────┘
               │
        ┌──────▼───────┐
        │  服务器节点   │  国内云机 / 境外 VPS —— 同一类东西
        │  server      │  区别只有:在哪、怎么接入
        └──────┬───────┘
               │   ← 链上最后一台服务器就是这次的「出口」
               ▼
          目标地址        网站 / API / 内网服务
                         ★ 不是节点,Loom 不管它,只是一个地址

        路径 = 接入节点 → [0..n 台服务器] → 目标地址
        零跳(直连)是一条合法候选路径,与多跳路径同台竞争
```

**核心模型:**

| 概念 | 定义 | 章节 |
|---|---|---|
| **两类节点** | 接入节点 / 服务器节点,一台机器可兼任。目标地址不是节点 | §1 |
| **出口是位置** | 链上最后一台服务器就是出口 —— 不是一种节点类型 | §1.1 |
| **方向约束** | 反连、双向、仅直连 —— 是**节点属性**,不是全局规则 | §2 |
| **路径** | 从接入到目标地址的一条具体走法,零跳到多跳 | §3 |
| **两个选择轴** | 地址轴 / 服务器轴 —— **决定度量作用在哪儿** | §4 |
| **等价类** | 只有真正可互换的地址才能进同一候选集 | §4.3 |
| **访问契约** | 输出等价还不够,请求还得能原样送过去 —— **决定换地址能否只靠 L4** | §4.4 |
| **路径候选** | `RouteCandidate = (服务器链, 目标地址)` —— 排序与归因的唯一单位 | §5.6 |
| **调度** | 策略裁剪候选集,度量在候选集内按周期选优 | §5 |

**七条不变量:**

| # | 不变量 | 出处 |
|---|---|---|
| 1 | **目标不是节点。** 自建的和买来的一视同仁,都只是地址 | §1, §9 |
| 2 | **出口是路径上的位置,不是节点类型。** 最后一跳就是出口 | §1.1 |
| 3 | 角色字段分块,能力由块推导;方向约束是**两端共同**决定的 | §1.3, §2.2 |
| 4 | **策略约束候选集,度量在候选集内选优** —— 两者不得互相污染 | §5.1 |
| 5 | **数据平面只做 L4 选路,不改写连接内容** —— 换地址只在访问契约同构时成立 | §4.4 |
| 6 | **应用层指标需要 L7 观测点** —— L4 隧道拿不到 `tokens/s` 与响应结构 | §16.2 |
| 7 | **控制平面停机,数据平面必须继续运行**;配置是 SSOT 的纯函数渲染 | §11, §12 |

# 第一部分 · 模型

---

## 1. 两类节点,加一类不是节点的东西

Loom 管两种机器,再加上一类它**根本不管**的东西:

| | 是什么 | Loom 管吗 |
|---|---|---|
| **接入节点** `access` | 你的设备。接管本机流量,按调度结果送出 | ✅ 发配置、装 Agent |
| **服务器节点** `server` | 你的机器。转发流量;排在路径最后的那台负责出公网 | ✅ 发配置、装 Agent |
| **目标地址** | 你要访问的东西:网站、API、内网服务 | ❌ **它只是一个地址** |

> ### 不变量
> **目标不是节点。** 不论那个服务是你自建的还是买别人的,对 Loom 都只是一个地址 —— 发请求过去,仅此而已。Loom 不给它发配置、不在它上面装东西、不把它算进拓扑。

### 1.1 出口不是一种节点,是路径上的一个位置

**一条路径上,最后那台服务器就是这次访问的出口。**

```
笔记本 ──→ 北京云机 ──→ api.example.com
              ↑ 这次北京云机是出口

笔记本 ──→ 广州云机 ──→ 新加坡 VPS ──→ google.com
                            ↑ 这次新加坡 VPS 是出口
```

同一台北京云机,这次是出口,下次可能只是中间一跳。**"出口"是它在某条路径上的位置,不是它的属性。**

> 因此没有"出口节点"这个类型,也没有 `target` 这个能力。写成节点类型会立刻产生一个问题:同一台机器该标成什么?

**中继当然可以直接访问 API。** 它就是一台有 IP 的服务器。如果目标地址国内直连就通,一跳足够,用不上境外 VPS。**用不用境外 VPS 是选路的结果,不是架构里预先分好的类。**

### 1.2 服务器之间只有两点区别

| 区别 | 影响什么 |
|---|---|
| **在哪** | 出口 IP 是哪个地区、能连通哪些目标、到各处的链路质量 |
| **怎么接入** | 能被主动连接,还是必须由它主动连出来(见 §2) |

境外 VPS 并不是另一个物种,它只是**接入方式复杂一些** —— 被国内主动拨号会提高被封概率,所以要反过来让它主动连出来。接上之后,它和国内云机一样,就是一台能转发流量的服务器。

### 1.3 角色分块;一台机器可以同时承担两种

节点分两块写:

```yaml
- id: cn-a
  server: {direction: bidirectional, inbound_port: 61698}

- id: access-a
  access: {platform: linux-server, credentials: [...]}

- id: sh01                      # 两个块都有:它转发流量,自己也要走代理出去
  server: {...}
  access: {...}
```

**为什么不写成 `capabilities: [server]` 这样的列表。** 两个理由:

1. 它与角色块是同一事实的两次编码,两边能对不上;
2. 字段扁平放时,把 `direction` 写在纯接入节点上不报错也不生效 ——
   而**能写入却不生效的配置比缺配置更糟**,缺配置会被发现,惰性配置会让人
   以为已经生效。分块之后它在 schema 层面就不成立(§12 的严格解码在加载
   阶段即拒绝)。

**两种角色喂的是不相干的逻辑。** `server` 块进隧道矩阵、候选枚举、准入校验;
`access` 块进本地端口与 selector。它们只在最后汇合成同一份 sing-box 配置 ——
一台机器一个进程,所以只能有一份。

> ⚠️ **合并必须发生在渲染期。** 分成两个文件会让它们抢同一个路径,后写的
> 静默覆盖先写的,而产物计数仍然对得上 —— 这个 bug 真实发生过。渲染器现在
> 对同一配置包里的重复路径直接报错。

> **为什么不担心"两个配置源打架":源只有一个。** SSOT → 渲染器是唯一的配置
> 来源,投递也只有该机的 Agent 一条。§18 那套一次性链接是给**没有 Agent 的
> 设备**用的,而那种设备只可能是纯接入节点,不存在需要合并的情况。

### 1.4 目标地址带服务类型标签

**这是"多地址选优"能够成立的前提。** 一个目标地址声明它提供什么服务:

```
- address: https://llm-hz.internal/v1
  service: llm:qwen3-32b-int8@openai-v1      # 模型+精度+接口契约(见 §4.3)
- address: https://llm-gy.internal/v1
  service: llm:qwen3-32b-int8@openai-v1      # 同一个服务,另一个地址
```

标签描述**服务类型**。同一个服务类型下的多个地址,才有"选哪个"的问题(§4)。

代理上网是这个模型的退化情形:**目标地址由你打开的网页决定**,不需要标签,也不需要选 —— 要选的只有服务器链。

## 2. 方向约束是节点属性

某些节点不能被主动连接。典型情况:跨境节点被主动拨号会显著提高被标记概率,进而导致该主机被屏蔽。

**但这是那些节点的性质,不是整个架构的性质。** 写成全局规则会丢掉三种真实场景:无约束的节点、有约束但特定场景下仍可直连的节点、以及**同时测量两种连接方式再择优**。

### 2.1 方向属性

```
direction:
  bidirectional   —— 双向可连,无限制
  reverse_only    —— 只能由该节点主动发起
  direct_only     —— 只能被主动连接
```

### 2.2 由方向属性推导出的行为

| 属性 | 该节点在隧道中的角色 | 可否加入 mesh | bootstrap 通道 |
|---|---|---|---|
| `bidirectional` | 可发起、可接受 | ✅ | SSH push 或人工 |
| `reverse_only` | **只能发起**,`PersistentKeepalive` 维持 | ❌ 会诱发主动直连,与约束冲突 | **只能人工**(§14.2) |
| `direct_only` | 只能接受 | ✅ | SSH push |

> **稳态控制通道对所有节点都是 Agent pull(§14.2)。** 上表最后一列只描述 bootstrap 阶段 —— 那是 SSH push 唯一适用的阶段。

**隧道建立方由一条边的两端共同决定,不由单端决定。** 六种组合的完整真值表:

| A 端 | B 端 | 发起方 | 说明 |
|---|---|---|---|
| `bidirectional` | `bidirectional` | 任意一方(渲染器取确定性规则:node_id 小者发起) | 需要确定性,否则渲染不是纯函数 |
| `reverse_only` | `bidirectional` | A | |
| `direct_only` | `bidirectional` | B | |
| `reverse_only` | `direct_only` | A | **合法** —— 一方只能发起、一方只能接受,恰好互补 |
| `reverse_only` | `reverse_only` | — | ❌ **非法**:双方都要发起,无人接受 |
| `direct_only` | `direct_only` | — | ❌ **非法**:双方都要被连,无人发起 |

> **mesh 成员资格、隧道发起方、可用 bootstrap 通道,三者都不是独立配置项,而是从两端的 `direction` 推导出来的。** 这消灭了一整类自相矛盾的配置 —— 校验器应直接拒绝手工指定的矛盾值,并在渲染前拒绝上表中的两种非法边。

**`reverse_only` 的服务器只能排在链的末尾。** §8.1 要求服务器接受上游连接,而 `reverse_only` 禁止被主动连接 —— 所以它接不了上游,只能由前一跳经反连隧道把流量推给它。校验器应拒绝把它排在链中间的候选。

### 2.3 `reverse_only` 可以是第一跳 —— 只要有隧道

"拨不到"说的是**公网**。一旦 `reverse_only` 节点主动连过来建起了隧道,
接入节点用隧道内地址就能直接找到它,不需要再往公网拨。

这把两跳压成一跳:

```
没有隧道:  接入 → 国内中继 → 境外出口 → 公网        两跳
有了隧道:  接入 →──────────→ 境外出口 → 公网        一跳
              (境外出口先反连过来)
```

**约束是"谁发起",不是"发起到谁"。** 让境外节点也反连接入节点,与它反连
国内中继在风险上是同一件事。

> **实测收益(2026-08-23,access-a):** 到柏林 550ms → 333ms(省 40%);
> 到新加坡 521ms → 465ms(省 11%)。差距因链路而异,**必须实测**。

**代价是它不扩展。** N 个客户端 × M 个出口的隧道数无界,而 §6.3 的扇出
(中继 × 出口)是有界的。这条只适用于**常开、有稳定入口的接入节点** ——
一台会睡眠的笔记本不值得让境外机为它长期维持隧道。

#### 对端走 DDNS 时必须重解析

WireGuard 的 `Endpoint` 只在接口启动时解析一次。对端是固定 IP 时无所谓;
走 DDNS 时 IP 一变隧道就断,**而且不报错**。

渲染器给"对端 endpoint 是域名"的发起方生成一个定时器,调用 wireguard-tools
自带的 `reresolve-dns.sh`:它检查每个 peer 最近有没有握手,没有就重新解析
并重设 endpoint。约一分钟自愈。

> ⚠️ **不要把 DDNS 解析出的 IP 写进 SSOT。** 它自己会变,与你改没改配置
> 无关 —— 塞进配置会让每次运营商换 IP 都产生一次配置变更、一个新快照、
> 一轮部署,快照历史里全是噪声,§15.2 的自动回滚还会被反复触发。
> **配置里放稳定的域名,解析交给运行时。**(§12.1:运行时状态不进 SSOT)
>
> 代价是重解析是**静默**的 —— 修好了也没人知道。这个洞由度量补:Agent
> 上报每条隧道的握手时长(§16.1 的"握手成功率"),超阈值告警(§16.3)。
> **修复靠运行时自愈,知情靠度量,两件事分开。**

### 2.4 双模测量

对某些节点,反连与直连可能都能工作,只是风险与质量不同:

```
direction: reverse_only
direct_probe: enabled          # 允许低频探测直连可行性与质量
direct_use: disabled           # 但不允许实际承载流量
```

这样可以**积累两种方式的质量与稳定性数据**再决定是否放开。探测必须低频、可关闭,且**探测行为本身就是风险**,需显式开启而非默认。

## 3. 路径

```
Path = 接入节点 → [服务器₁ → 服务器₂ → …] → 目标地址
```

服务器数量可以为 **0**(直连),实践中 ≤2。**链上最后一台服务器就是这次的出口**(§1.1)。

### 3.1 直连是一等公民

零跳路径与多跳路径**在候选集里地位平等**,由度量决定胜负。

这取代了"国内域名走直连"这类硬编码规则 —— 那种规则本质是**对质量的先验猜测**。直连通常自然胜出,不需要维护规则表;而当直连劣化时系统会自动改走中继,硬编码规则做不到。

> ⚠️ 但这**不取消策略**。见 §5.1:是否允许某条路径是策略问题,在允许的路径中选哪条才是度量问题。

### 3.2 组合爆炸必须裁剪

候选路径数 = 接入节点 × 服务器排列 × 候选地址。必须限制:最大跳数(建议 2);每个 (接入节点, 服务) 对预先裁剪候选集;**不对全排列探测,只探测候选集内的路径**。

**探测成本是系统的主要持续开销,必须显式管理。** 在推理场景下这个成本是真金白银(见 §16.2)。

## 4. 两个选择轴

**这是全文最关键的区分:它决定度量作用在哪儿。**

每次访问都要回答两个**互不相干**的问题:

| 轴 | 问题 | 取值 |
|---|---|---|
| **地址轴** | 最终去哪个地址 | `由请求决定` / `从等价类里选` |
| **服务器轴** | 经哪几台服务器到达 | `出口钉死` / `全程可选` |

两个轴自由组合,四种情形都真实存在:

| 地址轴 | 服务器轴 | 场景 | 要度量什么 |
|---|---|---|---|
| 由请求决定 | 全程可选 | 普通代理上网 | 只有服务器链 |
| 由请求决定 | **出口钉死** | 固定出口 IP(§4.1) | 除出口外的服务器链 |
| **从等价类里选** | 全程可选 | 服务调度(§4.2) | 地址 + 服务器链,**合起来** |
| 从等价类里选 | 出口钉死 | 有合规要求的服务调度 | 地址 + 除出口外的链 |

```
地址由请求决定 · 出口钉死
   客户端说:"我要走 SG 出口"
   [接入] --度量选前面几跳--> [SG 服务器](钉死) --> 你打开的那个网页

地址从等价类里选
   客户端说:"我要一个 qwen3-32b 推理端点"
                                ┌--> https://llm-hz.internal/v1
   [接入] --选服务器链--> [出口] --┼--> https://llm-gy.internal/v1
                                └--> https://llm-wlcb.internal/v1
```

> **服务器轴始终需要度量;地址轴只在"从等价类里选"时才需要。** 代理上网是地址轴退化为常量的情形 —— 地址是客户端给的,没得选。

> ⚠️ **"两个轴"说的是决策自由度,不是指标可分离。**
> 钉死出口不限制前面几跳怎么选(§4.1),这是"互不相干"的确切含义。但**质量必须按完整路径度量** —— 经广州到杭州地址的 TTFT,推不出经北京到杭州地址的 TTFT。评分与排序的单位是 `(服务器链, 地址)` 组合,**不是两个轴各自打分再相加**(§5.6)。

### 4.1 为什么要钉死出口

固定出口 IP。原因通常与性能无关:

- 目标站风控会因 IP 频繁变化触发验证或封禁;
- 账号与地域绑定,换出口可能命中不同区域配额、不同可用模型、不同合规策略;
- 某些 API 鉴权与来源 IP 绑定。

> **链路质量最优与出口 IP 稳定是冲突的两个目标。** 钉死出口就是明确选择了后者 —— 但**只放弃了最后一跳的优化,前面几跳仍然全程动态选优**。不必为了稳定出口 IP 牺牲国内段的链路质量。

### 4.2 为什么要在多个地址间选

在一组可互换的服务地址间调度。这是 Loom 价值最大的场景,也是 §5.3 成本维度存在的原因。

**注意这些地址与 Loom 的拓扑无关。** 它们可能是你自建的推理服务,也可能是买的第三方 API —— Loom 一视同仁,都只是地址(§1)。区别只在能不能验证它们真的可互换(§4.3)、以及请求能不能原样换过去(§4.4)。

### 4.3 等价类:标签不足以保证可替代性

**电网类比在这里会破。** 电子完全同质,服务地址不是。同样标着"推理服务"的两个地址,背后可能跑不同模型、不同量化精度、不同上下文长度、不同 API 兼容层。

> **只有真正可互换的地址才能进同一个候选集。**

因此标签必须落到**等价类**粒度:

```
❌ llm-inference                        # 太宽,不保证可替代
✅ llm:qwen3-32b-int8@openai-v1         # 模型 + 精度 + 接口契约
```

而且等价性应当是**可验证的**,不是配置里声明一下就算:

| 校验 | 做法 |
|---|---|
| 接口兼容 | 定期发送同一组契约测试请求,校验响应结构 |
| 能力一致 | 校验上下文长度、支持的参数、流式行为 |
| 输出可比 | 用固定 prompt + 固定 seed 比对输出差异度 |

**校验失败的地址自动移出候选集并告警。**

> 没有这层,你会做出一个"帮客户自动切到更便宜的机房、结果输出质量悄悄劣化"的系统 —— 这比不优化更糟。

### 4.4 访问契约:换地址能不能只靠 L4 完成

§4.3 保证的是**输出等价** —— 两个地址算出来的东西一样。但要让流量真的能被换过去,还需要第二个条件:**客户端已经发出的那一个请求,原样送到新地址也能被接受。**

这是两件不同的事。缺了后者,选优结果无法落地。

| 契约项 | 不同构时会发生什么 |
|---|---|
| 域名与证书 | TLS SNI 与证书校验失败,连接直接断 |
| 鉴权凭据 | 换供应商后 API Key 无效,401 |
| 请求路径与格式 | 路由不到,或参数不被识别 |
| 协议版本 | HTTP/2 与 HTTP/1.1 的连接复用行为不同 |

> ### 不变量
> **Loom 的数据平面是 L4 的:它决定连接送到哪里,不改写连接内部的任何字节。**
> 因此"从等价类里选地址"只在**访问契约同构**的地址之间成立。契约不同构时,换地址必须由 L4 之外的组件完成。

**三种承载方式,按契约是否同构选择:**

| 方式 | 前提 | Loom 的角色 | 适用 |
|---|---|---|---|
| **L4 直选**(默认) | 成员共用同一域名、同一 CA 签发的证书、同一套凭据与接口 | 出口服务器解析域名时**解析到选中的地址**,其余不动 | 自建服务的多机房部署(§4.2) |
| **L7 网关** | 无 | 网关改写 Host、换鉴权、做协议转换;Loom 选的是**到网关的服务器链**,地址由网关选 | 第三方 API,契约不同构 |
| **调用方 SDK** | 调用方代码可改 | Loom 只回答"用哪个地址",调用方自己带对应凭据去调 | 自研应用,且不愿引入网关 |

**出口侧解析是 L4 直选的落地机制。** §7.4 要求默认用 `socks5h://`,即由代理端而非客户端解析 DNS。这条规则在代理场景下是为了避免调度判断失真;在服务调度场景下它**直接成为地址选择的载体** —— 客户端始终请求 `llm.internal`,解析成哪个地址由 Loom 在出口服务器上决定,客户端无感知。

> **等价类的成员准入必须同时校验输出等价与契约同构。** 只满足前者的地址不能进 L4 直选的候选集。它需要 L7 网关承载,而网关是一个**独立组件**,与 L0–L3 正交(见 §20 独立可选项)。

## 5. 调度

### 5.1 策略裁剪候选集,度量在候选集内选优

> ### 不变量
> **度量不能取代策略。** 是否允许一个候选,是策略问题;在允许的候选中选哪个,才是度量问题。

```
所有可能 (路径 × 目标) 组合
     │  ← 策略过滤:方向约束、max_hops、等价类、
     │              合规约束(数据不出省 / 机房资质 / 备案状态)
     ▼
候选集
     │  ← 周期性评分:度量指标 + 声明属性(价格、配额)
     ▼
当前选中
```

**合规与安全是约束,不是评分项。** 数据驻留、机房资质、备案状态属于"允许/不允许",绝不能被高分挤掉。它们在过滤层生效,不进目标函数。

**先验网络知识同理。** ASN / 运营商归属可用于**裁剪候选集**(如"该接入点是电信,优先只探测电信出口的中继",减少探测组合数)和**排障标注**(标出某路径跨了哪些运营商),但**不进评分函数**。

> 理由:拓扑先验只能说明理论上该怎么走,实测直接说明实际上哪条更快。**两者冲突时永远信实测。** 一旦先验进入评分,它就会在某些场景下压过实测数据,违反本节不变量。
>
> 此外,真正决定国内跨网质量的是互联带宽与结算策略,这些没有公开数据源;公开可得的 BGP / AS 关系数据其更新尺度也与链路质量的变化尺度不匹配。**几十节点规模下,端到端实测的成本低于维护拓扑数据库,准确度还更高。**

### 5.2 评分输入分两类

| 类别 | 来源 | 特性 | 例子 |
|---|---|---|---|
| **度量值** | 探测与被动观测 | 高频变化、有噪声、需平滑 | RTT、丢包、抖动、TTFT、tokens/s |
| **声明值** | 合同、价格源、配置 | 低频变化、精确、有生效时间 | 单价、阶梯定价、配额、容量上限 |

> **两类输入性质不同,必须分开存储与处理。** 价格有版本、有生效时间、可能是阶梯的,不能塞进时序度量表。

### 5.3 目标函数:约束式优于加权求和

**"最优"不存在,只有"按什么最优"。**

| 目标 | 主导指标 | 适用 |
|---|---|---|
| `latency` | RTT p50 | 交互式请求、DNS |
| `ttft` | 建连开销 + 首包时间 | **流式推理** |
| `throughput` | 有效带宽、丢包率 | 大文件传输、备份 |
| `stability` | 抖动、断连率、握手成功率 | SSH、长连接 |
| `cost` | 单价 × 预估用量 | 成本敏感的批量任务 |

`ttft` 值得单列:流式推理体验由首字延迟主导,它对 RTT 和建连开销敏感、对带宽几乎不敏感。用 `throughput` 或 `latency` 去优化它都会选错。

> ⚠️ **但 `ttft` 与 `cost` 都不是 L4 能自己测出来的。** 选这两个目标,等于要求该等价类存在 L7 观测点或价格数据源(§16.2、§5.2)。校验器应拒绝"目标函数要的量根本没人产出"的声明。

**对外表达用约束 + 单一优化目标,不用加权求和:**

```
✅  在 华东 且 p95延迟 < 200ms 的端点中,选成本最低的
❌  score = 0.4×成本 + 0.6×延迟
```

客户能说清前者,给不出后者的权重。内部实现可以用加权启发式,但**暴露给用户的接口应该是约束式的**。

### 5.4 当前用启发式,后续引入求解器

**当前阶段:启发式。** 按约束过滤 → 按单一目标排序 → 取最优。

理由不是"先凑合",而是**现阶段的调度不是组合优化问题**:每个访问声明**独立地**从候选集里取最优,候选数在几十到几百量级,可枚举。对可枚举集合求 argmin,不需要搜索。

**后续引入求解器的触发条件是:决策之间产生耦合。** 典型来源是地址侧容量配额(§5.7)、服务器带宽约束、阶梯定价、多租户全局最优 —— 任一出现,问题就从 N 个独立 argmin 变成带约束的全局分配,启发式不再够用。

> 求解器届时作为**独立服务**接入,只服务于排序计算,**不进入每连接决策路径**(§5.6 的本地决策不因此松动)。具体选型等触发时再定。

> **在没有度量数据之前写优化器,权重只能靠猜,且无法验证是否有效。** 这也是 §20 中 L2 必须早于 L3 的原因。

### 5.5 调整周期与阻尼

> **"实时"应理解为"持续测量、周期决策",而不是"立即切换"。**

**主机制:固定调整周期。** 每个周期(如 10 分钟)重新评估一次,周期内不切换。这让系统行为可预测、可观察,并把切换频率的上界锁死。

**但周期只约束频率,不消除振荡** —— A/B 两条路径每 10 分钟交替仍是每天 144 次切换。因此最小组合是两件:

| 机制 | 作用 |
|---|---|
| **调整周期** | 锁死切换频率上界,周期内稳定 |
| **切换阈值** | 新候选须优于当前一个幅度(如 20%)才切,消除来回 |

后续可加:平滑窗口(移动中位数而非瞬时值)、切换代价项、熔断(单位时间切换超限则锁定并告警)。

**两个周期,对应 §5.6 的两个决策者:**

| 周期 | 谁执行 | 建议值 | 理由 |
|---|---|---|---|
| **排序周期** `ranking_period` | 控制平面重算并下发 ranked list | 30 分钟~小时级 | 换端点有结算、缓存、连接池代价;价格与配额本身就是低频量 |
| **微调周期** `tuning_period` | 接入节点在 top-N 内本地重选 | 5~10 分钟 | 链路质量变化尺度 |

> **两个周期必须分别配置**(§19 的 `AccessDeclaration` 各有一个字段)。合成一个值会强迫你在"端点切太频"和"链路反应太慢"之间二选一。**地址由请求决定时排序周期无意义**(地址轴是常量),只用微调周期。

### 5.6 决策位置由信息可得性决定

**这不是折中,是模式边界的自然结果。**

**排序的单位是完整路径候选,不是目标:**

```
RouteCandidate = (服务器链, 目标地址)
```

下发的 ranked list 是 **RouteCandidate 的有序表**,不是地址的有序表。理由见 §4:同一个地址经不同服务器链的质量互不相干。只下发全局地址排名,客户端会把"经广州最优的地址"错用在北京链路上。

| 地址轴 | 决策在哪 | 依据 |
|---|---|---|
| **由请求决定** | **接入节点本地** | 候选集里地址是常量,只在服务器链上选;本地测量足够 |
| **从等价类里选** | **控制平面算 RouteCandidate 排序 → 下发 ranked list;接入节点在 top-N 内按本地实测微调** | 价格、配额、容量、跨客户观测客户端拿不到;此刻链路的实际表现控制平面来不及感知 |

> **分工依据是信息可得性:控制平面掌握客户端无法观测的东西(价格、配额、他人观测),客户端掌握控制平面无法及时感知的东西(此刻这条链路的实际表现)。各自决定自己有信息优势的那部分。**

**接入节点选定整条 RouteCandidate,服务器不再做选择。**

服务器上的规则是 `凭据 → 访问声明 → 允许的下一跳集合`(§8.2),它做的是**准入校验**而非选路。

> **为什么不让服务器选:** 服务器不知道这条连接属于哪个 RouteCandidate,也拿不到接入侧的实测数据。让它自主选下一跳,就有了两个互不知情的决策者,排序结果无法落地也无法归因。**选路的决策者必须只有一个。**

**机制就是普通的链式代理,没有额外发明。**

```
接入节点  --连接-->  服务器₁  --转发-->  服务器₂  --出去-->  目标地址
             ↑                  ↑                   ↑
        用凭据认证        下一跳是服务器₂        最后一跳直接出公网
```

接入节点建连时按顺序指明每一跳。每台服务器只做两件事:**校验这张凭据是否允许转发到请求的下一跳**,然后转发。

| 这一跳的下一跳是什么 | 服务器怎么处理 |
|---|---|
| 另一台服务器 | 走隧道转给它 |
| 目标地址(说明本机是出口) | 直接出公网 |

**因为目标不是节点(§1),最后一跳就是普通的对外连接** —— 不需要在目标那边装任何东西,也不需要为它维护配置。这正是"目标只是一个地址"这条不变量在数据平面上的体现。

`ranking_period` 正是控制平面重算排序并下发的周期(§5.5)。**控制平面离线 → 客户端沿用上次 ranked list 继续在 top-N 内本地选择 → 降级的是排序新鲜度,不是选路能力**,§11 铁律保住。

### 5.7 跨客户聚合是网络效应

服务调度场景下,来自不同接入点的测量数据聚合后,每条链路与每个地址的质量画像会显著更准。**客户越多,推荐越准,这是会随规模自我强化的部分。**

架构上要为它留位置:测量数据脱敏后跨租户聚合,聚合结果回流到排序。同时必须处理:

- 单个客户的测量不能被他人反推(脱敏与聚合阈值);
- 避免"羊群效应" —— 所有客户被导向同一个当前最优地址,反而把它压垮。**容量感知与分散策略是服务调度成熟后的必需项。**

### 5.8 数据不足与候选集为空

评分默认候选有数据。**三种情况下它没有,行为必须是确定的,不能留给实现随手决定。**

| 情况 | 定义 | 行为 |
|---|---|---|
| **冷启动** | 新端点或新路径,样本数 < `min_samples` | **不参与排序,也不被淘汰。** 以受限速率主动探测积累样本,达标后才进入排序 |
| **数据过期** | 最新样本早于 `stale_after` | 视同无数据,退回冷启动状态。**过期数据绝不参与评分** —— 拿陈旧数据排序比不排序更糟 |
| **候选集为空** | 策略过滤或契约校验后无可用成员 | 见下 |

**度量窗口与样本数必须显式声明**,而不是"取最近的值":

| 参数 | 作用 | 建议 |
|---|---|---|
| `window` | 聚合窗口长度 | 与 `tuning_period` 同量级 |
| `min_samples` | 进入排序所需的最小样本数 | 不足则冷启动 |
| `stale_after` | 超过则视同无数据 | 约 3 个 `tuning_period` |

**候选集为空时,`fallback` 是访问声明上的显式字段,只有三个取值:**

| 取值 | 行为 | 适用 |
|---|---|---|
| **`fail_closed`(默认)** | 拒绝新连接并告警 | 有合规约束的声明 |
| `direct` | 回退到零跳直连 | 目标本身公网可达,且直连不违反策略 |
| `last_known_good` | 沿用最后一个可用候选,标记为降级并告警 | 目标轴稳定性优先于质量的场景 |

> **为什么默认 `fail_closed`:** §5.1 规定合规是约束不是评分项。若候选集因合规过滤而变空,任何"退而求其次"的自动回退都等于绕过约束。**空候选集是需要人介入的事件,不是需要自动兜底的事件。**

## 6. 隧道与协议

**协议按跳选择,不做全局统一。**

### 6.1 跨受限链路

**默认 WireGuard。** `PersistentKeepalive` 天生就是"由一侧维持隧道、建立后即双向",与 `reverse_only` 原生契合;长连接稳定。这类链路上**稳定 > 速度**。

Hysteria2 的 Brutal 拥塞控制在高丢包链路收益最大,但它是 client-dials-server 模型:满足 `reverse_only` 需再套一层反向承载,抵消部分速度优势且增加活动部件;QUIC 复位加激进拥塞控制的组合稳定性更差。

> **默认 WG(需抗 DPI 时换 AmneziaWG,见 §17)。仅当某条具体链路 WG 吞吐实测太差,才单独换成反向承载的 Hy2。不做全局切换。**

### 6.2 无约束链路

**Hysteria2。** 与标记风险无关,速度优势白拿,尤其移动网络丢包时。

### 6.2.1 接入侧协议可按节点配置

前两节讲的是"哪个更好"。接入这一跳还有一个更硬的前置问题:**上游的网络让
什么出去。**

有的网络会整体封禁 UDP(封 QUIC,把流量逼回可审计的 TCP 代理)。那种链路上:

| | 能用吗 |
|---|---|
| Hysteria2(QUIC/UDP) | ❌ |
| **WireGuard(UDP)** | ❌ **它也是 UDP** |
| Trojan / VLESS(TCP + TLS) | ✅ |

> ⚠️ §6.1 说跨受限链路默认 WireGuard,那是针对服务器之间。**接入节点所在的
> 网络你往往控制不了**,而 UDP 被整体封禁时,WireGuard 和 Hysteria2 会一起
> 失效 —— 这时唯一的出路是 TCP。

因此 `inbound_protocol` 按节点配置:面向受限客户端的服务器说 TCP,其余说 QUIC。
这是 §6 开头"协议按跳选择"的第二个理由 —— 第一个是快慢与隐蔽,第二个是
**能不能通**。

**默认仍是 Hysteria2。** 只在确认 UDP 不通之后才改 —— 见下面的排查方法,
以及那个很容易掉进去的坑。

#### 怎么判断 UDP 到底通不通

| 现象 | 含义 | 修法 |
|---|---|---|
| `connection refused` | 包到了,没人监听 | 起服务 |
| `i/o timeout` | 包被丢 | 防火墙 —— 但**先确认是哪一侧** |

判断被谁丢掉,要在服务器上抓包:

```bash
tcpdump -nn -i any "udp and host <客户端出口IP>"
```

> ⚠️ **这里有个坑,我们真掉进去过。**
>
> 抓包过滤器里的"客户端出口 IP"必须是**该客户端直连时的出口**。如果那台机器
> 同时配了 HTTP 代理,`curl https://api.ipify.org` 报出的是**代理的**出口 IP,
> 不是它自己的。拿那个 IP 去做过滤器,抓不到任何包 —— 而"抓不到包"看起来和
> "UDP 被封"一模一样。
>
> **正确做法:先不加 host 过滤器抓一次**,直接看源 IP 是什么。多花十秒,
> 省掉一次完全错误的归因。
>
> 同理,测试端口必须落在防火墙实际放行的范围内。拿范围外的端口去测,
> 测到的是防火墙规则,不是网络能力。

### 6.3 隧道矩阵只在 `reverse_only` 服务器上才需要

**先说清楚适用范围,否则会把矩阵想得比实际大得多。**

| 服务器的 `direction` | 怎么建立互联 | 需要渲染配置吗 |
|---|---|---|
| `bidirectional` / `direct_only` | 加入 mesh(§8.3),Headscale **自动分发密钥与 peer** | ❌ 不需要 |
| `reverse_only` | 进不了 mesh(§2.2),必须手工建点对点隧道 | ✅ **需要** |

也就是说:**只有 `reverse_only` 的服务器才产生隧道矩阵。** 典型就是境外 VPS —— 它被主动拨号会提高被封概率,所以进不了会自动尝试直连的 mesh。

**这类服务器必须向所有需要到达它的服务器扇出反连:**

```
接入(北京) ──选中──→ 北京云机 ──[反连隧道]──→ 境外 VPS
接入(贵州) ──选中──→ 广州云机 ──[反连隧道]──→ 境外 VPS
                            ↑ 每台各自直连,无单点汇聚
```

强制汇聚会产生 `贵州 → 广州 → 北京 → 境外` 的绕行。扇出的代价只是 N×M 条空闲隧道的 keepalive 心跳,可忽略。

**一条隧道一个网卡,不是一个网卡挂多个 peer。**

这不是风格选择。**多台境外 VPS 都要承载 `AllowedIPs = 0.0.0.0/0`**(出口流量的目的地是任意公网地址),而 WireGuard 按目的地址匹配 peer —— 同一个网卡上不能有两个 peer 都吃下全部地址空间。**必须分网卡。**

> ⚠️ **这个 N×M 矩阵是全系统最容易手工出错的地方** —— 两端密钥、AllowedIPs、端口、方向必须严格对应。必须由渲染生成(见 §12、§20.1)。

## 7. 接入节点

### 7.1 两种接管方式

| 方式 | 机制 | 需要 root | 粒度 |
|---|---|---|---|
| **TUN** | 虚拟网卡无条件接管全部流量,再按规则分流 | 是 | 按规则匹配 |
| **mixed(HTTP+SOCKS5)** | 监听本地端口,程序显式指向 | 否 | 按端口 / 按程序 |

### 7.2 平台差异

| 平台 | 程序能否单独设代理 | 该用什么 |
|---|---|---|
| **Android** | ❌ 绝大多数 App 不能 | **必须 TUN** |
| **Linux 服务器** | ✅ 能 | **只用 mixed**,不开 TUN |
| **桌面** | ✅ 能 | TUN 兜底 + mixed 精确控制 |

> **Android 必须 TUN 是因为程序不能设代理;Linux 应该优先用代理,恰恰因为它能设。**

Linux 服务器开 TUN 需 root、要改路由表,**配错一次可能把自己的 SSH 锁在外面**。mixed 是纯用户态监听,配崩了最多代理不通。

### 7.3 端口即访问声明

每个 mixed 端口绑定一个访问声明,**端口号本身就编码了模式与参数**:

```
127.0.0.1:1080  →  地址=由请求决定 · 出口=钉死 sg-vps
127.0.0.1:1081  →  地址=由请求决定 · 出口=钉死 jp-vps
127.0.0.1:1082  →  地址=由请求决定 · 出口=任选最快
127.0.0.1:1083  →  地址=从等价类选 llm:qwen3-32b-int8@openai-v1
                   出口=任选
                   carrier    = l4_direct        # 成员共用 llm.internal
                   objective  = ttft
                   constraint = 华东 且 p95<200ms
                   fallback   = fail_closed
127.0.0.1:1084  →  仅直连(对照与调试)
```

> **1083 能成立,依赖 `carrier: l4_direct`** —— 该等价类的所有成员地址共用 `llm.internal` 这个域名、同一 CA 的证书、同一套凭据(§4.4)。客户端始终请求 `llm.internal`,Loom 在出口服务器解析这一步把它指向选中的地址。**若成员契约不同构,这个端口指向的应当是 L7 网关。**
>
> **1080 与 1082 的区别只在出口轴。** 前者钉死了出口服务器(要固定 IP),后者让调度挑最快的 —— 两者的最终地址都是你打开的那个网页。这正是 §4 说两个轴互不相干的意思。

```bash
export all_proxy=socks5h://127.0.0.1:1082    # 本 shell 走推理调度
https_proxy=http://127.0.0.1:1080 curl ...   # 仅这条命令走 SG
```

优于全局切换的四点:**并发**(不同程序同时用不同路径)、**无状态**(端口即答案,不用记切到哪了)、**天然程序化**(环境变量、systemd、Docker、CI 直接支持)、**无需特权**。

### 7.3.1 selector 需要一个能切它的端点

渲染出的每条访问声明对应一个 sing-box `selector` 出站,成员是它的全部
RouteCandidate(§5.6)。

**`selector` 是手动开关:它自己不测速、也不切换。** 这是刻意的 —— sing-box
另有 `urltest` 会自动选最快的,但那会成为第二个互不知情的决策者,与 §5.6
"选路的决策者必须只有一个"冲突。

所以接入节点的配置里必须带一个本地控制端点:

```json
"experimental": { "clash_api": {
  "external_controller": "127.0.0.1:61800",
  "secret": "<秘密层引用>"
}}
```

Agent 通过它切换当前候选。**没有这个端点,渲染出的候选集永远停在 default
上 —— §5 的整套调度做完了也落不了地。**

只监听回环,并且带口令:同机的其他进程不该能改你的选路。

### 7.4 环境变量代理的已知坑

- **是约定不是标准。** `curl`/`wget`/`git`/`pip`/`npm`/Go 的 `net/http` 认;**`ping`/`ssh`/`dig`/`nc` 完全不认**;Java 要 `-Dhttp.proxyHost`。
- **`socks5://` vs `socks5h://`** —— 前者本地解析 DNS,后者代理端解析。本地解析会拿到就近 CDN 的 IP,**同时让调度判断失真**。默认用 `socks5h://`。
- **大小写都要设。** 部分程序只读 `http_proxy`,部分只读 `HTTP_PROXY`。
- **`no_proxy` 语义各实现不一致** —— 别用它做精细分流,交给 Loom 的服务匹配。
- **不认代理的程序**:用 `proxychains-ng` 或 `graftcp`。但 proxychains 靠 `LD_PRELOAD`,**对静态链接二进制无效** —— 很多 Go 程序正是如此,只能靠 TUN 兜底。

### 7.5 Android 的调度承载

Android 没有 Agent(§15.4),但 §5.6 要求接入节点承担四件事:接收 ranked list、本地测量、执行切换阈值、离线沿用上次排序。**这些能力必须由 Android 客户端自身内嵌**,否则 Android 只能退化成静态选路。

| 能力 | 承载方式 |
|---|---|
| 接收 ranked list | 客户端内嵌**最小 pull 客户端**:mTLS 拉取、校验平台签名、落地为本地文件(复用 §14.3 的端点与签名校验) |
| 本地测量与切换 | sing-box 的 `urltest` / `selector` outbound,候选集与阈值由渲染产物填充 |
| 离线沿用 | ranked list 已落地为本地文件,与 §11 的推论一致 |
| 观测上报 | 走同一条 pull 通道回传;**指标限于 L4 可得的那几项**(§16.2) |

> **这不等于把 Agent 装进 Android。** 它不做配置收敛、不做二进制自更新、不做漂移纠正 —— 那些走应用分发渠道(§17.5)。它只做"拉排名 + 报观测"这一条窄通道。

## 8. 服务器节点

**所有服务器跑同一套配置形状。** 国内云机和境外 VPS 不是两种东西,区别只在接入方式(§1.2)与它在某条路径上排第几。

### 8.1 职责

1. 接受上游连接(Hysteria2 inbound,多凭据)—— 上游可能是接入节点,也可能是另一台服务器;
2. 按连接所属的访问声明,把流量送往下一跳;
3. **当它是链上最后一跳时,直接连向目标地址**(出公网)。这需要 `ip_forward` + MASQUERADE;
4. 维持到各 `reverse_only` 服务器的反连隧道(§6.3);
5. **作为探测发起点**,上报链路与地址的质量 —— 这是 §5 调度的数据来源;
6. 可选:作为 Agent → 控制平面的反向代理端点(见 §14.3)。

> 第 3 条不是某类"落地节点"的专属职责,而是**每台服务器都具备的能力**。它这次用不用得上,取决于它在这条路径上是不是最后一跳(§1.1)。

### 8.2 凭据即访问声明

服务器上的规则是 `凭据 → 访问声明 → **允许的下一跳集合**`。接入节点通过**使用哪张凭据**表达它要什么,通过**建连时指明的下一跳**表达它选中了哪条 RouteCandidate。

**服务器做准入校验,不做选路**(§5.6):校验请求的下一跳是否在该凭据允许的集合内,是则转发,否则拒绝并计入异常。下一跳可能是另一台服务器,也可能是目标地址。

| 接入节点 | 持有凭据 | 效果 |
|---|---|---|
| Android / 需固定 IP 的账号 | 一把 | 单一访问声明 |
| PC / Linux | 多把 | 按服务选择不同声明 |

**服务器侧零改动,差别只在发几把钥匙。**

> **凭据同时是授权边界。** 允许的下一跳集合是访问声明的渲染产物(§19)—— **拿到一张凭据不等于能经这台服务器访问任意地方。**

### 8.3 mesh 互联

持有 `bidirectional` 或 `direct_only` 的服务器通过 **Headscale + 自建 DERP** 组网,获得:**密钥/peer 自动分发**、ACL 策略、MagicDNS、Subnet router、NAT 穿透。

> **这一条决定了隧道矩阵有多大。** 能进 mesh 的服务器一份配置都不用渲染;只有 `reverse_only` 的才需要(§6.3)。

**两个必须知道的限制:**

- **DERP 必须自建,且它不是"备用"。** 跨运营商对称 NAT 很常见,回退中继是常态而非例外。derper 要放在出口质量好的节点上,**带宽按"实际转发节点"规划**。
- **Android 只允许一个 VpnService。** sing-box 与 Tailscale 无法在 Android 上同时作为 VPN 运行。**Android 只跑 sing-box,不入 mesh**;需访问 mesh 内网时由中继代为转发(多一跳,需 ACL 授权)。

> Headscale 可回退:嫌重可塌缩为"纯渲染 + 静态配置",代价是丢掉自动密钥分发、ACL 和 NAT 穿透。**它与调度正交,不在主线上。**

## 9. 目标地址

> ### 不变量
> **目标不是节点。** 它不进拓扑、不参与配置渲染、没有 Agent、不上报状态。Loom 对它做的唯一事情是:**从某台服务器连过去,并测量这次连接的质量。**

自建的推理服务和买来的第三方 API,在这里**完全同等对待**。你可能在自建服务的机器上有 root,但那与 Loom 无关 —— Loom 不管它的网络配置,只把它当成一个要访问的地址。

### 9.1 一个目标地址声明什么

```
- address: https://llm-hz.internal/v1
  service: llm:qwen3-32b-int8@openai-v1     # 服务类型标签(§1.4)
  access_contract: {...}                    # 换地址的前提(§4.4)
  credential_ref: vault:llm/hz              # 若需鉴权
```

没有 `server` 块、没有 `direction`、没有隧道 —— 那些都是节点才有的东西。

### 9.2 由此产生的三个后果

- **它不参与配置渲染**,只作为候选集中的一个条目存在;
- 质量数据只能来自外部观测,且受 §16.2 的观测点可得性限制 —— 没有 L7 观测点时,拿不到 `tokens/s` 与响应结构;
- **不同来源的地址通常不满足 §4.4 的访问契约同构**:不同域名、不同凭据、不同接口细节。

> ⚠️ **因此不能默认几个地址可以被 L4 直接互换。** 前提是二者之一:它们共用访问契约,或由 L7 网关承载改写。**把这一点当成默认可行,是服务调度最容易犯的设计错误。**

### 9.3 出口鉴权凭据

若目标地址需要鉴权(API Key 等),**出口服务器需要持有它**。这与 §8.2 的接入凭据是**两类不同的东西**:

| 凭据类型 | 谁持有 | 用途 |
|---|---|---|
| **接入凭据** | 接入节点 | 向服务器证明"我是谁、我要哪条访问声明" |
| **出口凭据** | 出口服务器 | 向目标地址证明身份 |

两者都由控制平面签发下发,但**作用域完全不同,不可混用**。出口凭据同样只以引用形式进渲染层(§12.1)。

# 第三部分 · 控制平面

---

## 10. 职责

拓扑与服务定义、配置渲染、候选集裁剪与排序、探测调度、价格与配额管理、密钥签发、部署编排、可视化。

**它不在数据路径上,不转发任何用户流量。**

---

## 11. 铁律:控制平面与数据平面分离

> **控制平面停机,数据平面必须继续正常运行。**

推论:

- 节点配置必须**落地为本地文件** + systemd 管理,不得在运行时向控制平面查询;
- 节点必须能**自治运行**;
- **排序结果也必须落地。** 控制平面离线时,节点沿用最后一次下发的 ranked list 继续本地选服务器链(见 §5.6)。

### 11.1 因此不需要分布式控制平面

对数十节点规模,分布式控制平面意味着共识协议、脑裂处理、状态同步、多写冲突、成员变更 —— 一个独立且困难的工程项目,**而且它自己就是新的故障源**。

真正的目标是**控制平面挂掉不会造成损失**,即**故障域隔离**:

| 手段 | 说明 |
|---|---|
| 状态全部可序列化 | 拓扑 + 服务定义 + 密钥材料 → 定期导出、异地备份 |
| 控制平面无状态化 | 状态在数据库/Git,进程可随时重建 |
| Warm standby | 另一台机器有同步备份,**手工**切换,不做自动选主 |
| 节点自治 | 离线时按现有配置与最后排序继续运行 |

> 只有规模到数百节点或多租户并发时才重新评估。

---

## 12. SSOT 与纯函数渲染

> **拓扑与服务定义是唯一事实来源。所有节点上的配置文件,都是它的渲染输出。**

```
SSOT(拓扑 + 服务定义 + 策略)
      │  render()   ← 纯函数:同样输入必然产生同样输出
      ▼
每节点配置包(sing-box.json / wg*.conf / systemd unit / 候选集 / ...)
```

**手工登录任何机器改配置,都是错误操作。** 正确做法是改 SSOT 再重新渲染。

理由是一致性约束:§6.3 的 N×M 矩阵两端必须严格对应;凭据到访问声明的映射必须在所有服务器上一致;候选集必须与实际存活的节点集合一致;混淆参数双端必须逐位相同。**这些人工维护必然出错。**

### 12.1 纯函数的三个产物

1. **dry-run diff** —— 部署前看到会改哪些文件的哪些行;
2. **漂移检测** —— Agent 比对本地文件哈希与期望值,不一致即纠正;
3. **回滚** —— 用旧快照重新渲染,不需保存旧配置文件。

渲染函数里**不能有**随机数、当前时间戳、外部查询。**平台生成的随机性**(混淆参数、客户端凭据)必须**先固化进 SSOT** 再参与渲染。

**节点私钥是显式例外。** §13.1 要求 WG 私钥只在节点本地生成、永不离开节点 —— 平台既然没有它,就渲染不出含 `PrivateKey = ...` 的完整文件。两条规则用**渲染配置 + 本地秘密覆盖层**调和:

| 层 | 内容 | 谁产生 | 进快照吗 |
|---|---|---|---|
| **渲染层** | 配置文件全文;私钥位置写成对本地文件的引用(wg-quick `PostUp` 读 `/etc/loom/secrets/node.key`) | 平台渲染 | ✅ 全文哈希 |
| **秘密层** | 私钥文件本身,**一台机器一把**(SSOT 里每节点只有一个公钥) | 节点本地生成 | ❌ 只记 `secret_generation` 与**公钥** |

纯函数性质因此保住:同一份 SSOT 在任何时候渲染出的字节完全相同,私钥不参与渲染,§15.3 的哈希比对也只比对渲染层。

> **回滚不回滚秘密层。** 节点保留当前 generation 的私钥。私钥轮换必须是**独立的一次操作**,不能搭在配置回滚上 —— 否则回滚会把对端 SSOT 里已更新的公钥变成过期值,两边对不上,隧道反而起不来。

> **运行时状态不进 SSOT。** 当前选中哪条路径、各候选的实时评分,是度量的产物,变化频繁,不应污染配置版本历史。价格属于**声明值**,有版本和生效时间,进 SSOT。

## 13. 密钥与信任

### 13.1 私钥不集中生成

| 密钥类型 | 在哪生成 | 控制平面持有 |
|---|---|---|
| **节点 WG 私钥** | **节点本地** | 仅公钥 |
| **节点 SSH 主机密钥** | 节点本地 | 仅公钥 |
| **SSH 用户证书** | 控制平面(CA 签发) | CA 私钥 |
| **客户端凭据** | 控制平面 | 是(必须下发,无法避免) |
| **混淆参数** | 控制平面 | 是(非密钥,是双端须一致的公共参数) |

> **核心安全属性:控制平面沦陷 ≠ 隧道历史流量可解密。** 攻击者能篡改拓扑(会被审计和监控发现),但拿不到节点私钥。

Agent 首次注册时在本地生成 WG 密钥对,只上报公钥。**私钥永不离开节点。**

### 13.2 SSH 证书 CA 替代 authorized_keys

手工步骤(每台主机**一次性**):放 CA 公钥 → `sshd_config` 设 `TrustedUserCAKeys` → 重载 sshd。

此后:签发**短期用户证书**(如 TTL 1 小时);主机只信任 CA 签名;**密钥轮换、新增运维、临时授权 = 签一张新证书,零接触主机**;证书自带过期;用 `principals` 做细粒度授权。

反向也建议用 **Host CA** 签发主机证书,免去 `known_hosts` 分发和 TOFU 风险。

### 13.3 CA 私钥是最高价值目标

泄露 = 可签发任意主机的登录证书。按投入排序:离线保管根 CA、签发中间 CA 日常使用;中间 CA 私钥加密存储、启动时人工解锁;所有签发写审计日志;有条件上硬件。

## 14. 控制通道

### 14.1 可达性是图,不是列表

控制平面不一定能直连所有节点。BFS 求最短路径 → 生成 `ProxyJump` 链:`ssh -J bj-cloud,cd-local target`。

**这个图只在 bootstrap 阶段需要。** 节点装上 Agent 后走 pull 通道。

### 14.2 双通道由方向属性决定

| 通道 | 用途 | 方向 | 适用 |
|---|---|---|---|
| **SSH push** | **仅 bootstrap** | 平台 → 节点(经 ProxyJump) | `bidirectional` / `direct_only` |
| **Agent pull** | **稳态**:配置下发、状态与度量上报、排序下发 | **节点 → 平台**(主动轮询) | 所有节点,`reverse_only` **只能**用这个 |

Agent pull 解决四件事:方向合规、NAT 穿透、控制平面可离线、漂移自动收敛。

> `reverse_only` 节点的 bootstrap 是唯一躲不掉的人工步骤,每台一次。

### 14.3 拉取通道的保护

- 平台**不直接暴露**公网;在服务器节点上开反向代理端点;
- Agent 用 mTLS 客户端证书认证(平台 CA 签发,可吊销);
- 拉取端点只提供**只读**配置获取与上报,不提供管理 API;
- **配置包由平台签名**,Agent 校验签名后才应用。

最后一条关键:**它让"传输通道"与"配置真实性"解耦** —— 即使中继被攻破也无法注入恶意配置。

## 15. 部署与回滚

### 15.1 流程

```
1. 修改拓扑 / 服务定义 / 策略
2. 校验(端口冲突、矩阵完整性、两端 direction 组合合法性、
        角色块完整性(server 缺 direction / access 缺 platform)、
        等价类的输出契约与访问契约、
        carrier 与成员契约一致性、目标函数所需观测点存在性、
        fallback 与合规约束相容性、凭据引用、混淆参数合法性)
   —— 完整清单见 §19
3. 渲染 → 新版本配置包 + diff
4. dry-run diff,人工确认
5. 打不可变快照,签名
6. Agent 下次轮询拉取 → 应用 → 上报
7. 汇总:全部成功 / 部分失败 / 超时
```

### 15.2 自动回滚

> **改网络配置最常见的事故是把自己锁在外面。** 一条错误路由、一个防火墙规则、一个写错的 AllowedIPs,节点就再也连不上 —— 而它恰恰在另一个城市或国家。

```
Agent 应用新配置
   ↓  启动看门狗(如 300 秒)
Agent 依次自检四级,全部通过才上报成功
   ├── 全部通过 → 平台下发确认,取消定时器,新配置转正
   └── 任一失败或超时未确认 → Agent 自动回滚上一版本并重启服务
```

**没有这个机制,你迟早会失去一台远端节点的控制权,只能开工单重装。**

**确认条件必须包含数据平面。**

> **控制通道活着不等于配置是好的。** §14.3 的 Agent 拉取通道走中继反代,§15.4 明确指出**该通道不依赖数据平面隧道健康** —— 这正是它适合下发制品的原因,但也意味着:**一个打挂了全部用户隧道的配置,照样能让 Agent 回连成功并被确认转正。**

因此确认条件是四级,逐级递进,只验最后一级等于没验:

| 级 | 检查 | 失败含义 |
|---|---|---|
| 1 | 配置语法与本地校验(`sing-box check`、wg 配置解析) | 配置写坏了,服务起不来 |
| 2 | 本节点相关隧道握手成功(WG handshake、Hy2 连通) | 隧道断了 |
| 3 | **代表性端到端探测**:每个访问声明至少一条候选路径可达 | 隧道活着但选路不通 |
| 4 | 回连控制平面上报 | Agent 自己还活着 |

**部分失败按访问声明粒度判定,不按路径粒度。** 一条候选路径不通不回滚 —— 候选集本来就允许成员劣化,那是调度该处理的事;**某个访问声明的候选路径全部不通才回滚**,那意味着这个声明彻底不可用。

补充:高风险变更**强制**走此流程;节点本地保留最近 N 个版本,回滚不依赖网络;分批部署,先 1 台再全量。

### 15.3 幂等收敛

Agent 做**声明式收敛**:每次轮询对比期望态哈希与实际文件哈希,一致则什么都不做,不一致则重写并 reload。

Agent 崩溃、机器重启、有人手工改了文件,下次轮询自动纠正。**不需要"部署成功"这个状态,只有"当前是否收敛"。**

### 15.4 制品与版本管理

节点上运行的二进制(sing-box、WireGuard/AmneziaWG、Tailscale、Agent 自身)也有版本,需要下发与更新。

**原则:版本是期望态的一部分,并入同一条收敛回路,不建独立的 updater 子系统。** 收敛时除比对配置文件哈希外,同时比对组件版本。

| 要求 | 说明 |
|---|---|
| **版本显式钉住** | SSOT 中声明具体版本号,**永不使用 `latest`**。自动的是下载,不是升级决策 —— 上游一次不兼容发布可在一个轮询周期内打挂全部节点 |
| **配置与二进制绑定回滚** | 新版可能不认旧配置,旧版也可能不认新配置。**只回滚其一会得到起不来的节点**。快照必须同时钉住两者,§15.2 的回滚一起回 |
| **本地保留旧版本** | 回滚不能依赖网络下载。节点本地保留最近 N 个版本的二进制 |
| **制品镜像** | 节点不直连上游。控制平面镜像制品,经 §14.3 的中继反代通道下发 —— **该通道不依赖数据平面隧道健康**,正好适用 |
| **双重签名** | 镜像入库时校验上游校验和/签名;分发时用平台密钥重新签名,Agent 校验后才安装 |
| **分批推进** | 二进制变更的爆炸半径大于配置变更,强制先小批量再全量 |

**Agent 自更新需单独设计。** 其他进程崩了 Agent 可以回滚,Agent 自己崩了则无人接管。要求:

- **A/B 双槽 + 软链切换**,不做原地覆盖;
- 看门狗放在 **Agent 之外**(systemd 或极小的守护进程),超时未确认则切回旧槽;
- 自更新与其他组件更新分开进行,不在同一批次。

> **Android 不适用本机制** —— 无 Agent,更新走应用分发渠道(见 §17.5)。这是模型中的一处明确空洞。
>
> 目标地址不是节点,自然也不涉及制品下发(§9)。

## 16. 度量与可观测

**这是 Loom 的核心能力,不是配套设施** —— §5 的整个调度机制建立在它之上。

### 16.1 采集什么

| 层次 | 指标 | 观测点 | 用途 |
|---|---|---|---|
| **网络层** | RTT、丢包、抖动、握手成功率 | 隧道两端(Agent) | 服务器轴选优 |
| **应用层** | TTFT、tokens/s、错误率、响应结构 | **只能在 L7**:地址侧埋点 / L7 网关 / 调用方 SDK(§16.2) | 地址轴选优 |
| **调度层** | 切换事件与原因、各候选实时评分 | 接入节点 + 控制平面 | 判断阻尼参数是否合适、是否振荡 |
| **运行层** | 流量、连接数、凭据用量、Agent 签到 | 服务器 + 控制平面 | 容量规划、异常与失联发现 |

### 16.2 被动观测优先,但被动能看到什么由观测点决定

**两个约束同时成立,方向相反。**

**约束一 · 主动探测要花真金白银。** 在推理场景下,TTFT 和 tokens/s 只能靠发真实推理请求测出来 —— 这与 ICMP 的成本结构完全不同。所以真实流量的被动观测应当是主数据源:零额外成本、零额外暴露、且比合成探测更准确。

**约束二 · L4 隧道看不到应用层。** Loom 的数据平面是加密隧道 + L4 代理(§4.4),**流量对它是不透明的**:TLS 之后没有请求边界,HTTP/2 多路复用后连"这是第几个请求"都不知道,QUIC 连包边界都在加密里。

于是被动观测能拿到什么,完全取决于**观测点在哪一层**:

| 观测点 | 能拿到 | 拿不到 | 前提 |
|---|---|---|---|
| **L4 隧道 / 代理**(总是可得) | 建连耗时、**首字节返回时间**、字节数、连接时长、RST 与超时、并发连接数 | tokens/s、响应结构、错误码、请求边界 | 无 |
| **自有端点埋点** | 全部应用层指标,且最准 | — | 端点是自己的(`managed: true`) |
| **L7 网关**(§4.4) | 全部应用层指标 | — | 引入网关组件 |
| **调用方 SDK / OpenTelemetry** | 全部应用层指标 + 端到端体感 | — | 调用方代码可改 |
| **主动契约请求**(§4.3) | 全部应用层指标 | — | 花钱,须限频限额 |

> ### 不变量
> **`tokens/s` 与响应结构不是 L4 能被动观测的量。**
> 声明用它们做目标函数,就等于声明必须存在一个 L7 观测点。**没有 L7 观测点的候选只能用 L4 指标排序** —— 首字节返回时间是 TTFT 的可用近似,但不等于 TTFT(它含建连与排队,不含 token 解码速率)。

**因此:**

- 有 L7 观测点的候选,被动观测是主数据源;
- 只有 L4 观测点的候选,**主动契约请求是拿到应用层指标的唯一途径**,必须限频、限额;
- 主动探测只覆盖**没有真实流量的候选**;
- **探测预算本身要计入成本核算**,并在评分中体现;
- `Measurement` 必须记录 `observation_point`(§19)—— **不同观测点的数据不可直接比较**,拿 L4 近似值和 L7 真值一起排序会得出错误结论。

### 16.3 告警

隧道断连超阈值、Agent 失联、**等价类契约校验失败**(输出契约或访问契约)、路径或端点质量劣化、**切换熔断触发**、价格数据过期、证书/凭据将过期、部署失败或回滚发生。

**§5.8 引入的三类新告警:**

| 告警 | 含义 |
|---|---|
| **候选集为空** | `fail_closed` 已生效,该访问声明正在拒绝新连接 —— **这是最高优先级,需要人介入** |
| **候选长期冷启动** | 某候选样本数迟迟不达标,说明它既没有真实流量、也没被探测覆盖 |
| **度量数据过期** | 排序正在退化 —— 若多数候选同时过期,说明观测通道本身出了问题,而不是候选出了问题 |

> **告警通道不能依赖被管网络** —— 否则网络挂了收不到告警。

### 16.4 可视化

要叠加实时状态:当前选中哪条路径与哪个端点、各候选的实时评分与成本、哪条隧道是活的、哪个节点失联。**静态拓扑图价值有限,带评分的候选集视图才是排障与决策入口。**

### 16.5 回放与回测

> **§5.5 的阻尼参数无法在线调优。** 你不能拿生产流量试"阈值 20% 与 15% 哪个更好" —— 一次实验要跑很多天,而且期间的网络状况不可复现,两组结果不可比。

因此度量数据必须**可回放**:

```
历史度量序列(某时段全部候选的指标时序)
        │  ← 输入
   [调度引擎,离线模式]
        │  ← 换一组参数重跑
   决策序列(何时切到哪个候选)
        │
   评估:切换次数 / 是否振荡 / 累计延迟 / 累计成本
```

这让下列问题变成可回答的:

- 阈值设 15% 而不是 20%,上周会多切几次?
- 调整周期改成 5 分钟,会不会出现振荡?
- 换一个目标函数,累计成本会降多少?
- **上线一个新端点后,它会抢走多少流量?** —— 在真正接入前就能估算

**实现要求:**

| 要求 | 说明 |
|---|---|
| 度量数据带完整时间戳并长期留存 | 回测的输入 |
| 调度引擎可脱离实时环境运行 | 纯函数式:(度量序列, 参数) → 决策序列 |
| 决策与参数一并记录 | 否则无法解释"当时为什么这么选" |

> 这个能力**在启发式阶段就用得上**,不必等求解器。

## 17. 指纹重建

### 17.1 不自己改协议

fork WireGuard 改包格式的风险:密码学改动极易引入漏洞且**漏洞通常不可见**(隧道照常工作但已不安全);双端须严格一致;需长期跟进上游安全更新。

### 17.2 AmneziaWG 参数化

AmneziaWG 是 WireGuard-Go 的 fork,**只改传输层,密码学核心(Curve25519 / ChaCha20-Poly1305 / Noise IK)完全不动**。

| 参数 | 作用 |
|---|---|
| **Jc / Jmin / Jmax** | 会话前发送随机大小垃圾包,打破基于序列的特征 |
| **S1–S4** | 给 Handshake Init / Response / Cookie / Transport 加随机填充,破坏固定长度特征(标准 WG 的 148 / 92 字节是最明显的指纹) |
| **H1–H4** | 用随机 uint32 替换标准消息类型标识(1–4)。**必须 ≥5**,否则退化为标准 WG |
| **I1–I5** | 2.0 引入,握手前发送伪装成常见 UDP 协议(QUIC / DNS 等)的包 |

**全部置零 = 标准 WireGuard 行为**,便于平滑迁移和对照排障。

### 17.3 参数必须每次部署重新生成

> **在所有部署里取值相同的参数,本身就是一个新的特征 —— 那等于用一个新指纹换掉旧指纹。**

平台必须内建**参数生成器**:按合法范围随机抽取 → 校验约束(H1–H4 ≥ 5 且互不相同;S1 + 56 ≠ S2;…)→ **固化进 SSOT 快照** → 支持按隧道或按批次生成 → 记录版本以支持整网原子切换。

**约束校验必须实现。** 参数非法时隧道**静默不通**(不报错、只是连不上),排障极其痛苦。

### 17.4 轮换是高危操作

双端必须同时切换,否则隧道立即中断。必须走 §15.2 自动回滚;客户端需提前推送新参数或强制升级;先在非关键链路验证再整网切换。

> **动手前需核对 AmneziaWG 当前版本文档** —— 参数含义与约束在 1.x → 2.0 之间有变化(S3/S4、I1–I5 是 2.0 新增,H1–H4 从固定值改为范围)。

### 17.5 性能代价与客户端耦合

userspace 实现(基于 wireguard-go)**有明显 CPU 开销**,服务器规格需按 userspace 转发规划。

**更重要的是它与客户端强耦合:** 一旦启用自定义参数,现成客户端不认,你被迫自建客户端 —— 随之而来的是 Android 签名密钥管理(**丢失 = 无法发布升级**)、CI 构建流水线、分发渠道、版本兼容矩阵、强制升级机制。

> **默认用现成客户端 + 标准参数。自建构建是一个独立的重决策,不要顺手启用。**

## 18. 凭据与分发

**绝不通过邮件/IM 发明文配置。**

| 机制 | 说明 |
|---|---|
| **一次性链接** | 短 TTL(如 15 分钟)、访问一次即失效 |
| **设备绑定** | 首次访问记录设备指纹,后续只对此设备有效 |
| **二维码** | 移动端扫码导入 |
| **可吊销** | 独立吊销,所有服务器下一轮询周期移除该 user |
| **有效期** | 自带过期时间 |

**配置模板化**:Android 是 TUN + 单凭据;桌面是 TUN + 多 mixed 端口 + 多凭据;Linux 服务器是仅 mixed + 多凭据。平台应提供**下发前预览**。

```
  eligible                     # 策略过滤结果(§5.1),false 则不进排序
  score, rank                  # 排序产物 —— 运行时状态,不进 SSOT(§12.1)
  sample_count, last_sample_at # 冷启动与过期判定(§5.8)

AccessDeclaration              # §4 —— 访问声明,选路的单位
  id, name

  # 两个轴分别声明,不合成一个 mode(§4)
  address_axis                 # from_request | class:<equivalence_class_id>
  egress_axis                  # any | pinned:<node_id>

  matcher                      # 域名 / IP / 端口 / 进程 / 本地代理端口
  objective                    # latency | ttft | throughput | stability | cost
  constraints[]                # 合规、地域、SLA —— 过滤而非评分(§5.1)
  allowed_servers[], max_hops  # 渲染成服务器侧"允许的下一跳集合"(§8.2)
  ranking_period?              # 控制平面重算 ranked list 的周期(§5.5)
                               # address_axis = from_request 时无意义
  tuning_period                # 接入节点 top-N 内微调的周期(§5.5)
  switch_threshold             # §5.5
  top_n                        # 下发给接入节点的候选数(§5.6)
  window, min_samples, stale_after            # §5.8
  fallback                     # fail_closed | direct | last_known_good(§5.8)

PriceRecord                    # 声明值,与度量值分开(§5.2)
  address, equivalence_class
  unit_price, tiers[], currency
  effective_from, effective_to, source

Measurement                    # 运行时状态,不进 SSOT(§12.1)
  candidate_id, declaration_id, ts   # 按完整路径归因(§5.6)
  rtt_p50, rtt_p95, loss, jitter                    # 网络层
  first_byte_ms, bytes_in, bytes_out, conn_ms       # L4 可得(§16.2)
  ttft, tokens_per_sec, error_rate                  # 应用层,需 L7 观测点(§16.2)
  observation_point            # l4_tunnel | l7_gateway | sdk | endpoint
                               # 不同观测点的数据不可直接比较(§16.2)
  observation_kind             # passive | active(active 计入探测预算)
  score

Credential                     # §8.2 —— 接入凭据
  id, secret_ref, owner
  declaration_id
  issued_at, expires_at, revoked_at
                               # 出口凭据是另一类东西,见 ServiceAddress(§9.3)

Snapshot                       # 不可变版本
  id, created_at, author, ssot_hash, signature
  rendered_bundles{owner: bundle_hash}          # 只含渲染层,不含秘密层
                               # owner 是节点 id 或客户端档案 id
  component_versions{node_id: {sing-box, wireguard, tailscale, agent}}
                               # 与配置同快照,绑定回滚(§15.4)
  secret_generations{node_id: gen}
                               # 只记代次与公钥,不含私钥;
                               # 回滚不回滚秘密层(§12.1)
```

**七处关键关系:**

- **`Node` 与 `ServiceAddress` 是两张表,不是一张。** 前者是 Loom 管的机器,后者只是地址 —— 这条区分是全模型的地基(§1、§9);
- **没有 `target` 角色** —— 出口是路径上的位置,由 `RouteCandidate.server_chain` 的最后一项决定(§1.1);
- `Tunnel` 只在 `mesh_eligible = false`(即 `reverse_only`)的服务器上产生 —— 其余由 Headscale 自动分发(§6.3、§8.3);
- `Tunnel.initiator` 由**两端** `direction` 共同推导 —— 见 §2.2 的六格真值表,其中两种组合非法;
- `EquivalenceClass.carrier` 由成员 `access_contract` 是否同构决定 —— **`l4_direct` 是有前提的,不是默认可行**(§4.4);
- `RouteCandidate` 是排序、下发与归因的**唯一单位** —— 地址与服务器链不分开排序(§5.6);
- `PriceRecord` 与 `Measurement` 分表 —— **声明值与度量值性质不同**(§5.2)。

**校验器必须拒绝的矛盾配置:**

| 矛盾 | 出处 |
|---|---|
| 两端 `direction` 组合非法(rev↔rev、dir↔dir) | §2.2 |
| 节点同时持有 `server` 能力与 `reverse_only` 却被要求接受接入连接 | §2.2、§8.1 |
| 手工指定 `mesh_eligible` / `Tunnel.initiator` / `uses_tun` / `capabilities` | §2.2、§7.2、§1.3 |
| 把角色字段写进错误的块(如 `access: {direction: …}`) | §1.3,严格解码在加载阶段即拒绝 |
| **`mesh_eligible = true` 的服务器出现在 `Tunnel` 里** | §6.3,该交给 Headscale |
| **把目标地址写成 `Node`** | §1,目标不是节点 |
| `carrier: l4_direct` 但成员 `access_contract` 不同构 | §4.4 |
| `objective: ttft` 但等价类缺少 L7 观测点 | §16.2 |
| 有合规 `constraints` 但 `fallback ≠ fail_closed` | §5.8 |
| `address_axis = from_request` 却配置了 `ranking_period` | §5.5 |
| `egress_axis = pinned:<x>` 但 `x` 不在 `allowed_servers` 里 | §5.1 |

# 第四部分 · 构建顺序

---

## 20. 依赖驱动的构建顺序

**不是时间表,是依赖拓扑。** 每一层只依赖它下面的层。

```
L0  模型与渲染
    ↓
L1  数据平面连通
    ↓
L2  度量采集
    ↓
L3  调度引擎
    ↓
L4  部署自动化
    ↓
L5  运维界面      L6  凭据分发
```

**独立可选项**(不在主线上,任何时候可插入):

- **mesh 组网**(Headscale + derper)—— 与调度正交;
- **L7 API 网关**(§4.4)—— **只有需要把访问契约不同构的地址纳入同一等价类时才需要**。它同时是 §16.2 应用层指标的观测点,因此若目标函数含 `ttft` / `tokens/s` 而地址侧没有埋点,它就从"可选"变成"必需";
- **指纹参数化**(AmneziaWG)—— 依赖 L4 的自动回滚,且触发客户端自建的重决策;
- **回放/回测**(§16.5)—— 依赖 L2 的度量留存,**在 L3 期间就应具备**,否则阻尼参数只能拍脑袋;
- **求解器**—— 依赖 L2 与 L3,**由 §5.4 的耦合条件触发,不按时间排期**。

### 20.1 L0 · 模型与渲染

**做什么:** 把"网络长什么样、有哪些服务、什么策略"写成结构化数据,再写一个把它变成配置文件的函数。**这一层不含任何自动部署** —— 生成完文件,人工 scp 过去。

**为什么它必须最先做 —— 一个具体例子。** SSOT 里你写一行:

```yaml
tunnel: { from: cn-bj, to: sg-vps, protocol: wg }
```

渲染器要输出**两个必须严格对应的文件**:

| `cn-bj` 侧(国内云机) | `sg-vps` 侧(境外 VPS,`reverse_only`) |
|---|---|
| sg-vps 的公钥 | cn-bj 的公钥 |
| **不写 Endpoint**(对方是 `reverse_only`) | `Endpoint = <cn-bj 公网IP>:51820` |
| `ListenPort = 51820` | `PersistentKeepalive = 25` |
| `AllowedIPs = 10.99.0.2/32` | `AllowedIPs = 10.99.0.1/32` |

密钥要配对、IP 不能撞、端口要一致、**方向由 `direction` 属性推导**。

**4 台国内云机 × 3 台境外 VPS = 12 条隧道 = 24 个文件,每一对都必须逐字段吻合。** 手工写错一个字符的后果是隧道**静默不通** —— 不报错,只是连不上,而你要在两地之间来回比对才能找到。

> **注意矩阵只覆盖 `reverse_only` 的服务器**(§6.3)。能进 mesh 的那些由 Headscale 自动分发密钥,一份配置都不用渲染。把这一点搞错,会把矩阵想得比实际大好几倍。

L0 就是消灭这件事。它排在最前,是因为 L1 要建的隧道矩阵、L3 要用的候选集,全都是这份数据的渲染产物。

**产出:** 一套可校验、可 diff、可重放的配置生成能力。

### 20.2 L1 · 数据平面连通

隧道矩阵、接入节点接管、服务器转发、末跳出公网。**此时路径是静态指定的** —— 还没有选优,只是能通。

**产出:** 每条候选路径都真实可用。没有连通的路径,无从测量。

### 20.3 L2 · 度量采集

被动观测、主动探测、网络层与应用层指标采集与上报、探测预算控制。

> **开工前必须先定观测点(§16.2)。** L4 隧道只能产出连接级指标;`ttft` / `tokens/s` / 响应结构需要自有端点埋点、L7 网关或调用方 SDK。**观测点没定,这一层就只能做出网络层的一半。**

**产出:** 每条 RouteCandidate 有真实质量数据,且每条数据标明了观测点。

### 20.4 L3 · 调度引擎

策略过滤、等价类校验(输出等价 + 契约同构)、目标函数打分、两级周期与切换阈值、RouteCandidate 排序下发、两个轴的决策分工(§5.6)、冷启动与空候选集处理(§5.8)。

**产出:** Loom 的核心能力成立。

### 20.5 两条容易搞反的依赖

**L0 必须早于 L1。** 隧道矩阵是全系统最易出错的手工工作。先手工建矩阵再补渲染,等于先制造错误再补工具。

**L2 必须早于 L3。** 没有真实质量数据就写调度引擎,权重只能靠猜,而且**无法验证阻尼参数是否合适** —— 振荡是否发生,只有靠数据才看得出来。

**访问契约与观测点必须早于 L2。** 这两个决定(§4.4、§16.2)看起来像实现细节,实际决定了 L2 能采到什么、L3 能优化什么。**先建观测再定观测点,等于先采一堆用不上的数据。** 具体地:目标函数选了 `ttft`,却发现所有候选都只有 L4 观测点 —— 那 L3 从第一天起就在拿首字节时间冒充 TTFT,而且没人会发现。

# 附录

## A · 明确不做的事

| 不做 | 理由 |
|---|---|
| 分布式共识控制平面 | §11.1,规模不匹配 |
| 控制平面参与数据转发 | 违反 §11,且成为瓶颈与单点 |
| fork 修改密码学协议 | §17.1,风险不可控 |
| 纯度量驱动、无策略约束的调度 | §5.1,策略必须在度量之前生效 |
| 仅凭标签判定端点可互换 | §4.3,必须有可验证的等价类契约 |
| 连接建立后的路径迁移 | TCP 语义不允许;切换只影响新建连接 |
| 对外暴露加权求和式目标函数 | §5.3,客户给不出权重 |
| 把主干网拓扑先验写进评分函数 | §5.1,先验只能进过滤层与排障标注,实测优先 |
| **在数据平面改写请求内容**(Host、鉴权、协议转换) | §4.4,那是 L7 网关的职责;数据平面只做 L4 选路 |
| **默认几个地址可被 L4 直接互换** | §4.4、§9.2,访问契约通常不同构 |
| **把目标地址建模成节点** | §1、§9,它不进拓扑、不参与渲染 |
| **给能进 mesh 的服务器手工建隧道** | §6.3,Headscale 自动分发密钥 |
| **用 L4 观测推断 `tokens/s` 或响应结构** | §16.2,加密隧道里没有请求边界 |
| **地址与服务器链分开排序后相加** | §5.6,质量取决于 `(服务器链, 地址)` 组合 |
| **候选集为空时自动绕过合规约束回退** | §5.8,空候选集需要人介入,不需要兜底 |
| **只用控制通道回连作为部署确认条件** | §15.2,该通道不依赖数据平面健康 |
| 把节点私钥纳入 SSOT 以求"纯渲染" | §12.1、§13.1,秘密层与渲染层分离 |

## B · 技术选型建议(非强制)

| 组件 | 建议 | 理由 |
|---|---|---|
| SSOT 存储 | Git 仓库 + 结构化文件(YAML/TOML) | 天然版本化、diff、blame、回滚、审计 |
| **控制平面** | **Go** | 与 Agent 同语言,**渲染器与校验器共用同一份实现** —— 跨语言实现同一套规则是长期漂移来源,会产生"两侧对同一份配置的合法性判断不一致" |
| **Agent** | **Go**,单个静态二进制 | 交叉编译、零运行时依赖、单文件分发、A/B 双槽自更新简单(§15.4) |
| 渲染 | 任意模板引擎,但**必须纯函数** | 可测试、可 dry-run |
| Agent ↔ 平台 | mTLS + 配置包独立签名 | 传输安全与内容真实性解耦 |
| 度量存储 | 轻量时序;价格与配额用关系表 | **声明值与度量值分开**(§5.2) |
| 数据平面 | sing-box(接入 / 服务器)+ WireGuard(隧道) | 成熟、可编程、覆盖所需全部形态 |
| **L7 网关**(若需要,§4.4) | 现成反代 + 少量鉴权/改写逻辑 | **不要自己写 L7 代理。** 它同时承担 §16.2 的应用层埋点,埋点比转发更值得投入 |
| UI | 服务端渲染 | 内部工具,不需要复杂前端 |

> **求解器(§5.4)作为独立服务经 API 接入,其语言选择与控制平面无关** —— 因此"与求解器同栈"不构成控制平面的选型理由。

**命名约定**:项目名为 Loom,但**不向下渗透**。内部一律用通用词:`node` / `path` / `declaration` / `snapshot` / `agent` / `tunnel` / `credential` / `render` / `apply` / `rollback`。

## C · 开工前需要确定的问题

> 加粗的两条是**阻塞项** —— 它们决定 L2 能采什么、L3 能优化什么,必须在 L2 之前有答案(§20.5)。其余可以边做边定。

**模型侧**

1. **节点清单**:各节点位置、能力集合、方向属性、是否 managed
2. **服务标签体系**:初期定义哪些等价类,粒度如何划分
3. **⚠️ 访问契约与承载方式(§4.4)** —— 每个等价类的成员地址是否共用域名、证书、凭据与接口?`carrier` 取 `l4_direct` / `l7_gateway` / `sdk` 中的哪个?**这条不定,服务调度无法落地**
4. **第三方端点**:哪些不可部署的端点需纳入候选;它们的契约是否同构,不同构时是否值得为它引入网关
5. **访问声明**:初期定义哪几个,各自模式、objective、约束、`fallback`
6. **最大跳数**:2 是否够用
7. **双模测量**:哪些 `reverse_only` 节点允许开启直连探测

**调度侧**

8. **⚠️ 观测点(§16.2)** —— `ttft` / `tokens/s` 从哪来:自有端点埋点、L7 网关、调用方 SDK,还是只能主动契约请求?**没有答案就不要选这两个目标函数**
9. **两级周期**:`ranking_period` 与 `tuning_period` 分别设多少
10. **度量窗口**:`window` / `min_samples` / `stale_after` 取值(§5.8)
11. **等价类校验**:多久校验一次、失败后自动移出还是仅告警
12. **探测预算**:主动探测的频率上限与成本上限
13. **价格数据来源**:人工录入、合同导入,还是供应商 API

**平台侧**

14. **控制平面放在哪** —— 需稳定、能被各 Agent 经中继反代访问
15. **CA 私钥怎么保管** —— 整个系统的信任根
16. **秘密层怎么放** —— 私钥文件路径约定、generation 记法、轮换流程(§12.1)
17. **Android 客户端做到什么程度** —— 是否内嵌 §7.5 的最小 pull 客户端,还是接受 Android 退化为静态选路
18. **是否面向多租户** —— 决定 §5.7 跨客户聚合的脱敏设计是否现在就要做
19. **是否启用指纹参数化** —— 触发自建客户端的重决策(§17.5)
