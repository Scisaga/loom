## 两类节点,加一类不是节点的东西

Loom 管两种机器,再加上一类它**根本不管**的东西:

> **术语边界：** 产品生命周期只有一种受管实体 `Device`；本节的“接入节点/服务器节点”
> 是同一 Device 的数据平面投影，不是两套身份或 Enrollment。v1 Go/YAML 仍使用 `Node`
> 作为兼容存储名，迁移规则见[Device 生命周期设计](device-lifecycle.md)。

| | 是什么 | Loom 管吗 |
|---|---|---|
| **接入节点** `access` | 你的设备。接管本机流量,按调度结果送出 | ✅ 发配置、装 Agent |
| **服务器节点** `server` | 你的机器。转发流量;排在路径最后的那台负责出公网 | ✅ 发配置、装 Agent |
| **目标地址** | 你要访问的东西:网站、API、内网服务 | ❌ **它只是一个地址** |

> ### 不变量
> **目标不是节点。** 不论那个服务是你自建的还是买别人的,对 Loom 都只是一个地址 —— 发请求过去,仅此而已。Loom 不给它发配置、不在它上面装东西、不把它算进拓扑。

### 出口不是一种节点,是路径上的一个位置

**一条路径上,最后那台服务器就是这次访问的出口。**

```
笔记本 ──→ 北京云机 ──→ api.example.com
              ↑ 这次北京云机是出口

笔记本 ──→ 广州云机 ──→ 新加坡 VPS ──→ google.com
                            ↑ 这次新加坡 VPS 是出口
```

同一台北京云机,这次是出口,下次可能只是中间一跳。**"出口"是它在某条路径上的位置,不是它的属性。**

> 因此没有"出口节点"这个类型,也没有 `target` 这个能力。写成节点类型会立刻产生一个问题:同一台机器该标成什么?

**中继当然可以直接访问 API。** 它就是一台有 IP 的服务器。如果目标地址国内直连就通,一跳足够,用不上境外 VPS。**用不用境外 VPS 是选路的结果,不是架构里预先分好的类。**

### 服务器之间只有职责和可达性差异

目标态用正向职责 `forward` 表示能承载数据转发；`internet_egress` 必然蕴含
`forward`。不要用“非 `use_loom` 节点”定义服务器，因为同一 Device 可以既使用 Loom，
又为其他 Device 转发。

| 差异 | 影响什么 |
|---|---|
| **位置与能力** | 出口 IP 所在地区、可达目标、容量和链路质量 |
| **公网接入 profile** | 直连 443、替代 HTTPS 端口，或经 NAT 映射的公开 listener（[职责](servers.md#职责)、[拉取通道的保护](public-endpoints.md#拉取通道的保护)） |
| **每条边的发起与 transport** | 这条边由哪端拨号，以及使用 WG、HY2 或经批准的 TCP transport（[发起方向、可达性与 transport 是每条边的契约](#发起方向可达性与-transport-是每条边的契约)、[隧道与协议](transports.md#隧道与协议)） |

境外 VPS 并不是另一种节点，国内/境外、直连/NAT、仅能主动发起某条 WG 边都只是
Device 或 link intent 上的事实。它们不能被提升成全网节点分类。某条“境外服务器向境内
服务器反连 WG”的现有链路只是一个具体实现；相同逻辑转发边在满足发起和可达约束时也
可使用 HY2，但这不自动让 HY2 成为控制面的 L3 overlay。

### 数据平面职责分块；`control` 是正交只读投影

v1 数据平面期望态按 `server` / `access` 两块写；目标态迁移为正向 Responsibilities：
`forward`、`use_loom` 与蕴含 `forward` 的 `internet_egress`，一台 Device 可同时承担多个职责。
与它们正交的
`control` 块只由 certified `FinalControlSet` authority 与同一 head/QC 承诺、hash 匹配的 private
`ControlPeerDirectory` 联合物化，不能在普通 SSOT proposal 或 Enrollment Responsibilities 中直接
写入。公开 ControlSet 只有 opaque member ID 和用途隔离公钥；Device 映射、peer URL 与 fault
domain 只在私有目录。下例是授权 operator 的 materialized view，不是允许自授权的输入：

```yaml
- id: cn-a
  server: {direction: bidirectional, inbound_port: 61698}

- id: access-a
  access: {platform: linux-server, credentials: [...]}

- id: sh01                      # 两个块都有:它转发流量,自己也要走代理出去
  server: {...}
  access: {...}

- id: control-a                # 只读投影：control 与两个数据平面角色正交
  server: {...}
  control: {...}               # 仅由 FinalControlSet materializer 生成
```

**为什么数据平面不写成 `capabilities: [server]` 这样的列表。** 两个理由:

1. 它与角色块是同一事实的两次编码,两边能对不上;
2. 字段扁平放时,把 `direction` 写在纯接入节点上不报错也不生效 ——
   而**能写入却不生效的配置比缺配置更糟**,缺配置会被发现,惰性配置会让人
   以为已经生效。分块之后它在 schema 层面就不成立([逻辑 SSOT 与纯函数渲染](control-rendering.md#逻辑-ssot-与纯函数渲染) 的严格解码在加载
   阶段即拒绝)。

**三个投影喂的是不相干的逻辑。** v1 `server` / 目标 `forward` 进入 LinkIntent、候选枚举和
准入校验；v1 `access` / 目标 `use_loom` 进入本地接管与 selector；`control` 块是 certified `FinalControlSet` 与其 matching private
peer directory 的只读物化投影，只供
SSOT/UI/endpoint materialization，Raft 选举与投票只读取 committed Joint/Final config ledger，
不因机器同时是 server/access 而改变数据路径。前两个角色只在最后汇合成同一份 sing-box 配置 ——
一台机器一个进程,所以只能有一份。

> ⚠️ **合并必须发生在渲染期。** 分成两个文件会让它们抢同一个路径,后写的
> 静默覆盖先写的,而产物计数仍然对得上。稳定契约要求渲染器
> 对同一配置包里的重复路径直接报错；实现覆盖情况只见[实现对照](../development/implementation.md)。

> **为什么不担心“多个配置源打架”：逻辑源只有一个。** certified SSOT → 渲染器是唯一的配置
> 来源。[凭据与分发](credentials-model.md#凭据与分发) 的加入输入只负责把中控已创建的 Device 与本机生成的身份绑定，并引导
> 首次签名配置；它适用于包括服务器在内的所有新 Device，不是第二个配置源。完成绑定后，
> 各运行宿主仍用同一 Device 身份走 signed pull/Agent 投递，兼具 `server` 与 `access`
> 职责的配置继续在同一次渲染中合并。多个 control 副本也不产生多份 SSOT：只有
> 经 Raft commit、state-machine 复算并取得 replication QC 的唯一 certified head 能对外
> 生效；candidate render 只用于提交前校验，详见 [铁律:控制平面与数据平面分离](control-rendering.md#铁律控制平面与数据平面分离)与[逻辑 SSOT 与纯函数渲染](control-rendering.md#逻辑-ssot-与纯函数渲染)。

### 目标地址带服务类型标签

**这是"多地址选优"能够成立的前提。** 一个目标地址声明它提供什么服务:

```
- address: https://llm-b.internal/v1
  service: llm:qwen3-32b-int8@openai-v1      # 模型+精度+接口契约(见 等价类:标签不足以保证可替代性)
- address: https://llm-a.internal/v1
  service: llm:qwen3-32b-int8@openai-v1      # 同一个服务,另一个地址
```

标签描述**服务类型**。同一个服务类型下的多个地址,才有"选哪个"的问题([两个选择轴](#两个选择轴))。

代理上网是这个模型的退化情形:**目标地址由你打开的网页决定**,不需要标签,也不需要选 —— 要选的只有服务器链。

## 发起方向、可达性与 transport 是每条边的契约

“谁能主动拨谁”首先来自两端的网络事实，但目标态必须把结果固化为每条
`LinkIntent`，不能拿一个节点级标签推导该 Device 的所有公网、控制和数据连接。
同一台服务器完全可以同时：接受公网 HY2 数据入口、主动建立一条 WG 反连，并只在
overlay 上接受 control RPC。三件事的暴露面和凭据各自独立。

### 目标态的 LinkIntent

每条受管边至少固定：

```text
from/to                  精确 Device 或逻辑 service endpoint
allowed_transports       wireguard | hysteria2 | trojan_tls 中的有序允许集合
initiator                from | to；由可达性验证后固化，不在运行时猜
listen/profile refs      对应 listener、映射、身份和凭据的 exact refs
purpose                  control_overlay | data_forward | bootstrap
```

发起方向不授予访问权限；transport 可用也不等于允许把这条边用于另一 purpose。公网客户端
入口必须由对应的 signed EndpointSet 授权，管理 SSH 是独立运维事实，控制服务只在 overlay
地址监听。

### v1 `direction` 只是迁移输入

v1 严格 schema 仍保留节点级 `direction`，只用于确定现有 WG 边的发起方：

```text
bidirectional  可发起也可接受
reverse_only   该 Device 在这条兼容 WG 边上只能发起
direct_only    该 Device 在这条兼容 WG 边上只能接受
```

两端组合继续按下表确定迁移得到的 WG `LinkIntent.initiator`；非法组合必须在迁移时失败，
不能静默挑一端：

| A 端 | B 端 | 兼容 WG 发起方 |
|---|---|---|
| `bidirectional` | `bidirectional` | `node_id` 较小者（保证纯函数） |
| `reverse_only` | `bidirectional` | A |
| `direct_only` | `bidirectional` | B |
| `reverse_only` | `direct_only` | A |
| `reverse_only` | `reverse_only` | 非法 |
| `direct_only` | `direct_only` | 非法 |

迁移完成后，渲染和调度读取 `LinkIntent`，不再把 `direction` 当作 mesh 成员资格、公开
listener 授权或节点分类。`reverse_only` 尤其不表示该服务器不能提供认证的公网 HY2/Trojan
入口，也不表示它不能被 SSH 管理。

### 反连只是某条链路的实现

现有“境外服务器主动向境内服务器建立 WG”的关系可继续作为一条
`purpose=data_forward, transport=wireguard, initiator=境外端` 的 link。若两端 reachability、认证和
性能验证允许，同一逻辑数据边可以改用 HY2；它仍必须拥有独立 listener/credential 与
明确发起端，不能从“HY2 更快”推导全网切换。

WG 提供稳定双向 L3，因此首版 control overlay 继续使用 WG。HY2 默认承载公网数据入口和
首版 bootstrap tunnel；除非单独设计并验收 L3-over-HY2，否则它不能替代 Raft/control 的
overlay。默认也不把 WG 再套进 HY2。

#### 对端走 DDNS 时必须重解析

WireGuard 的 `Endpoint` 只在接口启动时解析一次。对端是固定 IP 时无所谓;
走 DDNS 时 IP 一变隧道就断,**而且不报错**。

渲染器给"对端 endpoint 是域名"的发起方生成一个定时器,调用 wireguard-tools
自带的 `reresolve-dns.sh`:它检查每个 peer 最近有没有握手,没有就重新解析
并重设 endpoint。约一分钟自愈。

> ⚠️ **不要把 DDNS 解析出的 IP 写进 SSOT。** 它自己会变,与你改没改配置
> 无关 —— 塞进配置会让每次运营商换 IP 都产生一次配置变更、一个新快照、
> 一轮部署,快照历史里全是噪声,[自动回滚（仅 Linux/server 发布 canary 的跨节点目标态）](deployment.md#自动回滚仅-linuxserver-发布-canary-的跨节点目标态) 的自动回滚还会被反复触发。
> **配置里放稳定的域名,解析交给运行时。**([纯函数的三个产物](control-rendering.md#纯函数的三个产物):运行时状态不进 SSOT)
>
> 代价是重解析是**静默**的 —— 修好了也没人知道。这个洞由度量补:Agent
> 上报每条隧道的握手时长([采集什么](reporting.md#采集什么) 的"握手成功率"),超阈值告警([告警](events-topology.md#告警))。
> **修复靠运行时自愈,知情靠度量,两件事分开。**

### 双模测量

对某些 link，两个发起方向或两种 transport 可能都能工作，只是风险与质量不同：

```
link: demo-a--demo-b
probe_transport: hy2
probe_enabled: true            # 允许低频验证候选 transport
data_use: false                # 尚未进入已授权 LinkIntent，不承载业务
```

这样可以积累证据后再通过 certified operation 改 LinkIntent。探测必须低频、可关闭，且
**探测行为本身就是风险**，需显式开启而非默认；观测本身不能改变允许 transport。

## 路径

```
Path = 接入节点 → [服务器₁ → 服务器₂ → …] → 目标地址
```

服务器数量可以为 **0**(直连),实践中 ≤2。**链上最后一台服务器就是这次的出口**([出口不是一种节点,是路径上的一个位置](#出口不是一种节点是路径上的一个位置))。

### 直连是一等公民

零跳路径与多跳路径**在候选集里地位平等**,由度量决定胜负。

零跳时，**接入节点本身就是出口位置**。`RouteCandidate.ServerChain` 仍保持
空数组，而不是写成 `[access]`；后者会被数据平面解释为一次真实代理跳，导致
节点连接自己。兼任 access/server 的节点可以把自身列进 `allowed_servers` 并
声明 `egress_capable`，这表示空链候选的本地出口归属，不要求为自连配置
`inbound_port`。若另一接入节点也要经它出网，才需要真实 inbound。

这取代了"国内域名走直连"这类硬编码规则 —— 那种规则本质是**对质量的先验猜测**。直连通常自然胜出,不需要维护规则表;而当直连劣化时系统会自动改走中继,硬编码规则做不到。

> ⚠️ 但这**不取消策略**。见 [策略裁剪候选集,度量在候选集内选优](scheduling.md#策略裁剪候选集度量在候选集内选优):是否允许某条路径是策略问题,在允许的路径中选哪条才是度量问题。

### 组合爆炸必须裁剪

候选路径数 = 接入节点 × 服务器排列 × 候选地址。必须限制:最大跳数(建议 2);每个 (接入节点, 服务) 对预先裁剪候选集;**不对全排列探测,只探测候选集内的路径**。

**探测成本是系统的主要持续开销,必须显式管理。** 在推理场景下这个成本是真金白银(见 [被动观测优先,但被动能看到什么由观测点决定](measurement.md#被动观测优先但被动能看到什么由观测点决定))。

## 两个选择轴

**这是全文最关键的区分:它决定度量作用在哪儿。**

每次访问都要回答两个**互不相干**的问题:

| 轴 | 问题 | 取值 |
|---|---|---|
| **地址轴** | 最终去哪个地址 | `由请求决定` / `从等价类里选` |
| **服务器轴** | 经哪几台服务器到达 | `出口钉死` / `全程可选` |

两个轴自由组合,四种情形都真实存在:

| 地址轴 | 服务器轴 | 场景 | 要度量什么 |
|---|---|---|---|
| 由请求决定 | 全程可选 | 普通代理上网 | 只有服务器链 |
| 由请求决定 | **出口钉死** | 固定出口 IP([为什么要钉死出口](#为什么要钉死出口)) | 除出口外的服务器链 |
| **从等价类里选** | 全程可选 | 服务调度([为什么要在多个地址间选](#为什么要在多个地址间选)) | 地址 + 服务器链,**合起来** |
| 从等价类里选 | 出口钉死 | 有合规要求的服务调度 | 地址 + 除出口外的链 |

```
地址由请求决定 · 出口钉死
   客户端说:"我要走 SG 出口"
   [接入] --度量选前面几跳--> [SG 服务器（钉死）] --> 你打开的那个网页

地址从等价类里选
   客户端说:"我要一个 qwen3-32b 推理端点"
                                ┌--> https://llm-b.internal/v1
   [接入] --选服务器链--> [出口] --┼--> https://llm-a.internal/v1
                                └--> https://llm-c.internal/v1
```

> **服务器轴始终需要可归因的质量证据；地址轴只在"从等价类里选"时才需要。** 证据缺失时
> 保持 unknown，不为填空追加探测。代理上网是地址轴退化为常量的情形 —— 地址是客户端给的,没得选。

> ⚠️ **"两个轴"说的是决策自由度,不是指标可分离。**
> 钉死出口不限制前面几跳怎么选([为什么要钉死出口](#为什么要钉死出口)),这是"互不相干"的确切含义。评分与排序的单位仍是
> `(服务器链, 地址)` 组合，证据可以来自该完整路径的明确观测点，或来自标明为估算的入口与
> 服务器分段；经广州到杭州地址实测的 TTFT 不能推成经北京到杭州的 TTFT。未覆盖维度保持
> unknown，不能把两个轴独立打分后相加，也不能为补齐每个组合强制客户端扫描完整路径([决策位置由信息可得性决定](scheduling.md#决策位置由信息可得性决定))。

### 为什么要钉死出口

固定出口 IP。原因通常与性能无关:

- 目标站风控会因 IP 频繁变化触发验证或封禁;
- 账号与地域绑定,换出口可能命中不同区域配额、不同可用模型、不同合规策略;
- 某些 API 鉴权与来源 IP 绑定。

> **链路质量最优与出口 IP 稳定是冲突的两个目标。** 钉死出口就是明确选择了后者 —— 但**只放弃了最后一跳的优化,前面几跳仍然全程动态选优**。不必为了稳定出口 IP 牺牲国内段的链路质量。

### 为什么要在多个地址间选

在一组可互换的服务地址间调度。这是 Loom 价值最大的场景,也是 [目标函数:约束式优于加权求和](scheduling.md#目标函数约束式优于加权求和) 成本维度存在的原因。

**注意这些地址与 Loom 的拓扑无关。** 它们可能是你自建的推理服务,也可能是买的第三方 API —— Loom 一视同仁,都只是地址([两类节点,加一类不是节点的东西](#两类节点加一类不是节点的东西))。区别只在能不能验证它们真的可互换([等价类:标签不足以保证可替代性](#等价类标签不足以保证可替代性))、以及请求能不能原样换过去([访问契约:换地址能不能只靠 L4 完成](#访问契约换地址能不能只靠-l4-完成))。

### 等价类:标签不足以保证可替代性

**电网类比在这里会破。** 电子完全同质,服务地址不是。同样标着"推理服务"的两个地址,背后可能跑不同模型、不同量化精度、不同上下文长度、不同 API 兼容层。

> **只有真正可互换的地址才能进同一个候选集。**

因此标签必须落到**等价类**粒度:

```
❌ llm-inference                        # 太宽,不保证可替代
✅ llm:qwen3-32b-int8@openai-v1         # 模型 + 精度 + 接口契约
```

而且等价性应当是**可验证的**,不是配置里声明一下就算:

| 校验 | 做法 |
|---|---|
| 接口兼容 | 定期发送同一组契约测试请求,校验响应结构 |
| 能力一致 | 校验上下文长度、支持的参数、流式行为 |
| 输出可比 | 用固定 prompt + 固定 seed 比对输出差异度 |

**校验失败的地址自动移出候选集并告警。**

> 没有这层,你会做出一个"帮客户自动切到更便宜的机房、结果输出质量悄悄劣化"的系统 —— 这比不优化更糟。

### 访问契约:换地址能不能只靠 L4 完成

[等价类:标签不足以保证可替代性](#等价类标签不足以保证可替代性) 保证的是**输出等价** —— 两个地址算出来的东西一样。但要让流量真的能被换过去,还需要第二个条件:**客户端已经发出的那一个请求,原样送到新地址也能被接受。**

这是两件不同的事。缺了后者,选优结果无法落地。

| 契约项 | 不同构时会发生什么 |
|---|---|
| 域名与证书 | TLS SNI 与证书校验失败,连接直接断 |
| 鉴权凭据 | 换供应商后 API Key 无效,401 |
| 请求路径与格式 | 路由不到,或参数不被识别 |
| 协议版本 | HTTP/2 与 HTTP/1.1 的连接复用行为不同 |

> ### 不变量
> **Loom 的数据平面是 L4 的:它决定连接送到哪里,不改写连接内部的任何字节。**
> 因此"从等价类里选地址"只在**访问契约同构**的地址之间成立。契约不同构时,换地址必须由 L4 之外的组件完成。

**三种承载方式,按契约是否同构选择:**

| 方式 | 前提 | Loom 的角色 | 适用 |
|---|---|---|---|
| **L4 直选**(默认) | 成员共用同一域名、同一 CA 签发的证书、同一套凭据与接口 | 出口服务器解析域名时**解析到选中的地址**,其余不动 | 自建服务的多机房部署([为什么要在多个地址间选](#为什么要在多个地址间选)) |
| **L7 网关** | 无 | 网关改写 Host、换鉴权、做协议转换;Loom 选的是**到网关的服务器链**,地址由网关选 | 第三方 API,契约不同构 |
| **调用方 SDK** | 调用方代码可改 | Loom 只回答"用哪个地址",调用方自己带对应凭据去调 | 自研应用,且不愿引入网关 |

**出口侧解析是 L4 直选的落地机制。** [环境变量代理的已知坑](agent-runtime.md#环境变量代理的已知坑) 要求默认用 `socks5h://`,即由代理端而非客户端解析 DNS。这条规则在代理场景下是为了避免调度判断失真;在服务调度场景下它**直接成为地址选择的载体** —— 客户端始终请求 `llm.internal`,解析成哪个地址由 Loom 在出口服务器上决定,客户端无感知。

> **等价类的成员准入必须同时校验输出等价与契约同构。** 只满足前者的地址不能进 L4 直选的候选集。它需要 L7 网关承载,而网关是一个**独立组件**,与 模型与渲染–L3 正交(见 [依赖驱动的构建顺序](../development/dependencies.md#依赖驱动的构建顺序) 独立可选项)。

### 服务:中控分流与度量的单位

> 显式访问具名局域网时，请求以 `LocalNetwork + IP + 协议端口` 分类，再复用本节
> 之后的 Declaration、Agent 与 ServerChain；它不是第二套 Service 或选路器。该
> 目标态及未实现边界见 [Local Network 专题](../proposals/local-network.md)。

> **v1 兼容边界:** host → Service → selector 与 `default_declaration` 只表达 Auto 中
> 未命中 Service 的 catch-all；它们不能表达客户端顶层 Direct / Auto / 指定出口。
> 三模式是客户端在 signed plan 授权范围内的本地偏好，不新增 SSOT 写 API。哪些宿主
> 源码支持范围见[实现对照](../development/implementation.md)，实机结论另核对对应[原始验收证据](../operations/local-deployment.md#证据保留与清理)。

#### 应用照常请求 URL，Loom UI 不重复选择每个请求的目标

应用本来就会正常请求 URL。问题在于让用户再到 Loom UI 填一遍任意目标 URL，
或通过本地端口为每次请求另选一套策略；这样会混淆请求与配置职责。Auto 中未命中服务的流量由中控 `default_declaration`
承接；客户端顶层 Direct / Auto / 指定出口另按[路由模式](../clients/routing.md)作用于全部接管流量。
不按每次请求另选 URL 或端口：

**它把策略推给了接入端。** "连 1080 还是 1082"就是在选策略 —— 而接入端
恰恰是最不该知道拓扑的地方。

**它让目标集合开放。** 开放意味着你不可能事先测完,于是被动观测从"优先"
变成"必须",分组只能靠域名后缀这类**推断**,而且每个没见过的目标都要经历
一次"猜错再纠正"。三个难题全是开放集合带来的。

**它让凭据变成开放代理。** 一份泄露的接入凭据,能把你的服务器变成任何人
都能用的出口。[凭据即访问声明](servers.md#凭据即访问声明) 说服务器上的规则是准入校验 —— 只校验"允许走哪"而不
校验"允许去哪",这个准入是漏的。

#### 每个请求不需要额外携带选择

所以:**中控声明服务,服务声明它的地址集合;数据平面按请求的 host 反查服务。**

```
中控声明     服务 → 一组地址 → 访问声明(objective、约束、允许的出口)
数据平面     请求的 host → 匹配到服务 → 走该服务当前选中的候选
接入端       一个端口(或 TUN),正常发请求,不知道任何事情
没匹配上     Auto 按中控 default_declaration；没有就 fail_closed(数据不足与候选集为空)
```

Auto 模式下接入端连"我要哪个服务"都不用说 —— host 本身就是答案。这里的
`default_declaration` 是中控规则的 catch-all，不是客户端顶层模式。

#### 两种地址集合,别混

| | 语义 | 数据平面做什么 | 度量单位 |
|---|---|---|---|
| **等价类**([等价类:标签不足以保证可替代性](#等价类标签不足以保证可替代性)) | N 个地址**可互换**,挑一个 | **选地址** | (链, 地址) |
| **服务地址清单** | N 个地址**都要用** | 不选,只归组 | (链, 服务) |

等价类回答"用哪个",服务地址清单回答"这些走同一条路"。一个服务可以引用
一个等价类 —— 那时两者叠加:先按服务归组,再在组内选地址。

#### 服务清单会不全,而这是可观测的

声明 `openai = api.openai.com`,而客户端还会去 `cdn.oaistatic.com`。这些
请求落到兜底,路由就不一致。

解法是让它**看得见**:上报者记录"被请求过、但没匹配上任何服务"的 host,
界面上列出来让人决定归到哪个服务。

注意这里观测的用途变小了:它**不是路由决策的依据**,只是补全清单的辅助。
决策仍然只依赖声明出来的东西 —— 于是"推断错了导致路由错"这类故障不存在。

#### 任意 URL 默认放行也必须显式声明

catch-all 不该是隐含假设。若 Auto 模式确实需要“其余请求都能走”，必须由中控
显式配置 `default_declaration`；它是中控授权、审计和签名发布的 catch-all 策略，
不是客户端 Direct 模式。区别在于:**显式声明的时候,你知道自己在放弃什么。**
